# 검증 계획 (spike)

기간은 1~2주다. 목적은 **조율 층 스킬과 기존 실행 층(unit loop + `step2step`)을 연결했을 때 원칙 1~5가 실제로 지켜지는지**를 실제 과제로 확인하는 것이다. mock이나 fixture가 아니라 실제 CLI 세션과 실제 모델을 쓴다.

<a id="hypotheses"></a>
## 확인할 가설

| ID | 가설 | 측정 |
| --- | --- | --- |
| H1 | 개발 요청을 하면 조율 세션에서 스킬이 자동으로 켜진다 | Claude Code는 `claude plugin eval`로 플러그인 유무를 비교한다. Codex는 같은 프롬프트를 반복해 스킬 사용을 센다 |
| H2 | 작업 전에 확정 항목이 거의 다 나온다 | 분할·실행 중 새로 나온 확정 항목의 수와 누락 원인 |
| H3 | 새 세션이 계약만으로 작업을 끝낸다 | 작업별 done / blocked / 게이트 실패, 컨텍스트 압축 발생 여부 |
| H4 | Claude 작업 세션의 계획 본문을 승인 전에 항상 얻는다 | 훅이 저장한 ExitPlanMode 입력의 확보율 |
| H5 | 의도 대조가 계획의 어긋남을 잡는다 | `reject_plan` 횟수와 사유, 승인된 계획의 결과 검토 |
| H6 | 추측하지 않는다 | 작업 세션 질문이 모두 사용자에게 전달됐는가(자동 응답 0건) |
| H7 | 강제가 작동한다 | 조율 세션의 제품 코드 수정 시도와 `write_set` 밖 쓰기가 모두 거부 또는 검출됐는가, 잘못 거부한 수 |
| H8 | 결과가 의도와 맞는다 | 사용자 평가(일치/부분/불일치)와 그 사유 |
| H9 | 부담이 감당할 만하다 | 질문 수, 응답 시간, 전체 소요 시간, 토큰. 플러그인 없는 기준 실행과 비교 |

<a id="setup"></a>
## 준비

**조율 층 (새로 만듦)**
- 스킬: `barrel-start`, `barrel-clarify`, `barrel-decompose`, `barrel-run`
- 훅:
  - SessionStart: 조율 세션과 작업 세션을 구분해 주입
  - PreToolUse: 조율 세션의 코드 수정 거부, 작업 세션의 `write_set` 검사
  - 사용자 입력 이벤트: 승인 기록

**실행 층 (기존 unit loop + `step2step` 보완, [보완 목록](plugin-architecture.md#gaps))**
1. 작업 세션을 plan 모드로 시작한다. Claude 훅 스크립트가 ExitPlanMode 입력을 저장하게 한다.
2. 별도 세션에서 의도를 대조한 뒤 `approve_plan` 또는 `reject_plan`을 호출한다.
3. 질문이 오면 `menu_default_answer` 대신 `blocked`로 멈추고 조율 세션에 전달한다.
4. `write_set` 필드를 추가하고 커밋 전에 검사한다.
5. `provider: codex`용 세션 팩토리를 `step2step.codex`로 만든다.
6. 작업별 결과 보고를 남긴다.

**시작 전 확인**
- 보완한 코드에 기존 가짜 세션 테스트(`barrel/tests/test_unitloop.py`)를 통과시킨다.
- `unit_loop.py --dry-run`으로 설정·preflight·fail-first 게이트를 확인한다.
- `python -m step2step.claude.calibrate_dialogs <dir> --answer`로 현재 Claude Code 버전의 화면 표시를 다시 확인한다.

<a id="tasks"></a>
## 과제

1. **신규 (전체 트랙):** 새 저장소에 작은 웹 기능 하나를 만든다.
2. **유지보수 (확장 트랙):** 사용자가 고른 기존 저장소에서 실제 변경 요청 하나를 처리한다.
3. **국소:** 한두 파일을 고치는 요청 하나. 트랙이 실제로 가벼워지는지 본다.

조율은 [OD-2](open-decisions.md#od-2)에서 정한 CLI로 먼저 하고, 같은 과제를 다른 CLI로 반복한다. 작업 세션은 구현을 Claude, 의도 대조를 Codex로 섞어 쓴다. 비교 기준으로 같은 요청을 플러그인 없이도 한 번씩 실행한다.

<a id="metrics"></a>
## 통과 기준 (제안값)

| 지표 | 기준 |
| --- | --- |
| 자동 발동 (H1) | 개발 요청 프롬프트의 90% 이상 |
| 계획 본문 확보 (H4) | Claude 작업 세션의 100% |
| 추측 응답 (H6) | 0건 |
| 조율 세션의 제품 코드 수정 (H7) | 반영 0건 |
| `write_set` 밖 변경의 커밋 (H7) | 0건 |
| 게이트를 거치지 않은 완료 | 0건 |
| 실행 중 새로 나온 확정 항목 (H2) | 과제마다 기록하고, 원인별로 체크리스트를 고친다 |
| 의도 일치 (H8) | 세 과제 모두 "일치". 아니면 확정 누락으로 사유가 설명됨 |
| 부담 (H9) | 기준 실행 대비 증가분을 기록하고, 받아들일지 사용자가 판단 |

수치는 제안값이며 검증 전에 조정할 수 있다.

<a id="after"></a>
## 끝난 뒤

- **통과:** [정본 반영 순서](migration.md#sot-update)대로 전환을 확정한다.
- **부분 통과:** Codex 쪽 조율이나 팩토리만 실패했다면 Claude Code 조율을 우선 운영할지 정한다.
- **불통과:** 원인을 기록하고, 실행 기반([OD-1](open-decisions.md#od-1))을 다시 판단한다.
