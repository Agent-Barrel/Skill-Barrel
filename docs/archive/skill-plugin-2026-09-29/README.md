## 한 문장 요약

시킨 일에서 **확정이 필요한 것을 실제 작업 전에 모두 사용자에게 확정받아** 정확한 의도를 고정한다. 그 결과를 **작은 코드 작업**으로 나누고, **작업마다 새 코딩 에이전트 세션 하나가 맡는다.**

<a id="non-goals"></a>
## 하지 않는 것

- **끝날 때까지 에이전트를 계속 돌리지 않는다.** 목표를 이룰 때까지 에이전트를 반복 구동하는 구조가 아니다. 확정된 작업 목록을 순서대로 새 세션에 맡길 뿐이며, 막히면 멈추고 사용자 확정으로 돌아간다.
- 무인 상시 실행, 재부팅 후 자동 재개, 다중 프로젝트 스케줄러를 만들지 않는다.
- 여러 구독 계정을 번갈아 써서 사용 한도를 넓히지 않는다.
- 자체 Slack 중계 서버, 원격 콘솔, 대시보드를 만들지 않는다. 설치 파일·자동 업데이트·관리자 helper도 만들지 않는다. 필요하면 벤더 기능(Claude Desktop 병렬 세션, Claude in Slack, Codex app 등)을 쓴다([OD-7](open-decisions.md#od-7)).

## 왜 바꾸는가

- **작업마다 새 세션을 띄우는 실행 기반은 이미 이 레포에 있다**([기존 구현](research.md#existing)).
  - `step2step`은 실제 Claude Code 대화형 세션을 `-p` 없이 새로 띄우고, Codex는 app-server로 구동한다.
  - unit loop는 작업 목록을 세션 하나씩 맡기고 게이트로 판정한다.
  - 따라서 전환의 핵심은 확정 도출과 분할을 사용자가 쓰는 CLI 안의 스킬로 옮기고, 이 실행 기반에 연결하는 것이다.
- **설치형 앱 방식은 실제 실행으로 이어지지 않았다.** 8/11 이후 120커밋, Rust 약 29만 줄을 썼지만 실제 모델이 요청부터 완료까지 돈 기록이 없다. 막힌 곳 대부분은 앱이 CLI를 바깥에서 구동하는 비용이다([현재 상태](research.md#current)).
- **헤드리스 경로는 정책이 불안정하다.** 앱이 CLI를 헤드리스(`-p`)로 구동하는 경로는 [과금 정책이 흔들리는](research.md#policy) 영역이다. `step2step`의 대화형 구동은 이 영역을 피한다.

## 기존 정본과의 관계

- **그대로 가져오는 것:** 방법론 규칙.
  - 사전 평가·근거 기반 인터뷰·세 묶음 승인: [workflow](../app-plan/specs/workflow.md)
  - 작은 작업·의도 확인·검증·독립 리뷰·기존 실패 판단·실패 대응: [orchestration](../app-plan/specs/orchestration.md)
  - 결정 P-001·Q-004·Q-005·Q-006·D-032·D-040·D-041·D-068
- **바뀌는 것:** 확정과 분할을 하는 곳.
  - 설치형 앱 화면 대신 사용자가 연 CLI 안의 스킬에서 한다.
  - 작업 실행은 기존 실행 층(unit loop + `step2step`)이 작업마다 새 세션으로 맡는다.
  - P-001 2의 "작업 방식의 주체는 이 시스템"은 스킬·정본 파일·실행 층이 맡는다. 방법론은 특정 공급자의 기억이나 세션에 의존하지 않는다.
- **기존 구현의 쓰임:** [OD-3](open-decisions.md#od-3)
  - Python 실행 층은 보완해서 쓴다.
  - Rust 엔진은 계약·흐름 설계의 참고로 둔다. 조사·인터뷰·세 묶음 승인·작업별 의도 확인 세션이 구현돼 있지만, 실제 모델로 돈 기록은 없다.
- 이 폴더의 내용은 확정 전까지 `requirements/features/decisions.csv`에 반영하지 않는다.
