# 확정 항목 도출

목표: 결과가 **사용자 의도에 따라 달라지는 선택을 작업 전에 빠짐없이** 찾아 확정한다. 그래야 작업 세션이 판단의 빈칸을 추측으로 채우지 않는다(P-001 5).

<a id="definition"></a>
## 확정 항목이란

| 종류 | 예 | 처리 |
| --- | --- | --- |
| 사용자 확정 | 소셜 로그인 포함 여부, 삭제된 데이터 보존 기간 | 질문하고 답을 기록한다 |
| 기존 결정으로 해결 | 이미 승인된 스택, 프로젝트 Git 정책 | 근거(문서·행·revision)를 연결하고 묻지 않는다 |
| 사용자가 위임한 판단 | "세부 배치는 알아서 해" | 위임 범위를 적어 기록한다. 범위 밖 판단은 다시 확정 대상이다 |
| 기술 구현 판단 | 내부 함수 구조, 라이브러리 내부 설정 | 에이전트가 정하고 근거를 남긴다. 사용자 질문으로 바꾸지 않는다 |

판정 기준은 하나다. **"이 선택에 따라 결과물이 사용자가 기대한 것과 달라질 수 있는가."** 달라질 수 있는데 정본에 답이 없으면 확정 항목이다. 요구·범위·스택·권한·비용을 바꾸는 판단은 항상 사용자 확정이다(D-041).

<a id="discovery"></a>
## 빠짐없이 찾는 방법

한 가지 방법만 쓰면 누락이 생긴다. 다섯 가지를 겹쳐 쓴다.

1. **요청 분해.** 요청 문장에서 목적, 사용자, 핵심 흐름, 입력·출력, 경계·예외, 범위 밖을 뽑는다.
2. **차원 체크리스트.** 트랙에 맞는 차원을 하나씩 확인한다.
   - 사용자·권한, 핵심 흐름과 화면, 입력 검증과 오류·빈 상태
   - 데이터 모델, 보존·삭제·이전, 기존 데이터 호환
   - API 계약과 소비자, 외부 서비스·계정·비용
   - 기술 스택·의존성·라이선스, 성능·규모, 보안·개인정보, 플랫폼 호환
   - 배포·운영 환경, Git 반영 정책(커밋/PR/병합), 검수 기준과 검증 환경
3. **유사 서비스·경쟁 제품 조사.** 같은 도메인과 다른 도메인의 사례에서 사용자가 생각하지 못한 결정을 찾는다. 조사 결과는 질문의 맥락과 선택지가 된다([원래 구상](../../plan/00-original-flow.md) 5, [근거 기반 인터뷰](../app-plan/specs/workflow.md#research)).
4. **유지보수 대조.** 기존 코드·정본과 요청의 차이를 확인한다. 유지할 동작과 불변 조건, 재사용할 기존 결정도 함께 본다.
5. **독립 공백 검토.** 새 세션이 확정 목록과 정본 초안을 읽고 "구현자가 추측해야 하는 곳"을 찾는다. 가능하면 다른 공급자 모델을 쓴다. 찾은 곳은 새 항목이 된다. 확장·전체 트랙에서는 필수, 국소 트랙에서는 선택이다.

작업 분할(S4)은 마지막 검사 역할도 한다. 작업 계약의 필수 칸을 정본만으로 채울 수 없으면, 그 칸이 누락된 확정 항목이다.

### 예: "회원가입에 소셜 로그인을 추가해줘"

| ID | 항목 | 종류 |
| --- | --- | --- |
| C-001 | 어떤 제공자를 붙이는가 (Google·Apple·Kakao 등) | 사용자 확정 |
| C-002 | 같은 이메일의 기존 계정이 있으면 합치는가, 막는가 | 사용자 확정 |
| C-003 | 소셜 가입자에게 추가 정보를 요구하는가 | 사용자 확정 |
| C-004 | 연결 해제·탈퇴 시 계정과 데이터를 어떻게 처리하는가 | 사용자 확정 |
| C-005 | 인증 라이브러리 | 기존 결정으로 해결 (승인된 스택) |
| C-006 | 로그인 버튼 배치 | 위임 (기존 디자인 체계 안에서) |

C-002와 C-004는 요청 문장에 없다. 차원 체크리스트(데이터 보존·이전)와 유사 서비스 조사에서 나온다.

<a id="questions"></a>
## 질문 형식

- 한 번에 하나의 결정 주제를 묻는다. 같은 주제 안의 서로 독립적인 작은 항목은 묶을 수 있다. Claude Code의 질문 UI는 한 번에 최대 4개까지 받는다.
- 질문마다 다음을 제시한다.
  - 지금 왜 묻는지
  - 무엇을 정해야 하는지
  - 함께 고려할 것
  - 선택지별 결과
  - 추천과 그 이유
- 사용자가 원하면 조사 원문을 보여준다. 다른 서비스가 이 문제를 어떻게 풀었는지 볼 수 있다.
- 이미 확정된 정책은 다시 묻지 않는다. 일반 구현 판단을 사용자 질문으로 바꾸지 않는다.
- 답을 받으면 바로 확정 목록과 관련 정본에 반영한 뒤 다음 주제로 간다.

<a id="closure"></a>
## 닫힘 조건

작업 분할(S4)로 넘어가려면 아래를 모두 충족해야 한다. 게이트가 확정 목록을 읽어 1~5를 검사하고, 6은 승인 원장으로 확인한다.

1. `open` 상태인 항목이 없다.
2. `answered` 항목에는 반영된 정본 revision이 있다.
3. `delegated` 항목에는 위임 범위가 적혀 있다.
4. `out-of-scope` 항목은 이번 요청에서 빠지는 결과가 의도 요약에 적혀 있다.
5. 확장·전체 트랙은 독립 공백 검토를 마쳤다.
6. 사용자가 **의도 요약**을 승인했다.

<a id="late"></a>
## 작업 중 발견된 확정 항목

작업 세션이 새 판단을 요구하는 질문을 내면, 실행 층은 추측한 답을 넣지 않고 그 작업을 `blocked`로 멈춘다. 현재 unit loop는 질문 메뉴에 기본 답("Use your best judgement and continue")을 넣는데, 이를 바꾼다([작업 세션의 질문](task-sessions.md#questions)). 답이 작업 세션의 대화에만 남지 않고 확정 목록에 기록되게 하려는 규칙이다.

1. 조율 세션이 그 항목을 확정 목록에 `open`으로 추가하고 사용자에게 묻는다.
2. 답을 정본에 반영하고, 영향받는 작업 계약의 revision을 올린다.
3. 영향받은 작업은 **새 세션**에서 다시 실행한다. 막힌 세션을 이어 쓰지 않는다.
4. 어느 도출 방법에서 놓쳤는지 누락 원인을 기록하고 체크리스트를 고친다. 이 기록이 [검증 지표](validation.md#metrics) H2다.
