0. PC에 있는 Codex CLI, Claude Code 를 주력으로 작동(Codex 를 기본으로 작동하고, 난이도 있는 질문에 대해 Claude Fable 에게 조언 구하기 + 실제 구현 작업 시 Opus5 사용하기, 리서치는 Codex 와 Claude 의 조사 결과를 종합해서 결론 내리기...  등으로 섞어서 사용)
1. 이 제품을 처음 실행하면 PC 에 사용할 수 있는 Claude Code 와 Codex CLI 를 찾고, 없으면 유저에게 입력을 받는게 필요함. claude 의 경우 confdir 을 통해, codex 의 경우 CODEX_HOME를 통해 유저가 가지고 있는 구독을 최대한 활용할 수 있는 방안으로 진행해줘.(유저에게 구독의 계정명을 입력받고 그 정보로 폴더 구분해서 사용할 것)
1-1. 서로 다른 구독으로 작동하더라도, 이 앱의 메인 작동 방식이 구독에 따라 왔다갔다하거나 특정 구독 계정만 알고 있는 context 는 없이, claude code 나 codex cli 같은 앱의 메모리에 의존하지 않고 상호 공유되며 세션 작동마다 참조하는 공통 메모리 관리가 필요함.
2. 시작업은 (1) 제품 컨셉 입력, (2) 유지보수할 프로젝트와 유지보수 내용 입력. 그 시작점부터 요구사항 도출을 시작하는 것.
3. 요구사항 도출 단계와 함께 요구사항 명세서 작성 (유저 인터뷰)
4. 요구사항 도출이 끝나면 요구사항 구현을 위한 기능명세서 작성 (유저 인터뷰)
5. 기능 명세서와 요구사항 명세서 작성 간에 유저에게 질문하는 경우, 실제 질문을 하기 전에 유사 서비스(같은 도메인, 다른 도메인), 경쟁 제품은 어떤게 있으며 거기에선 어떤식으로⠁요구사항을 구현(문제를⠁해결)했는지에 대해 리서치한 뒤에, 현재 결정해야할 사항이 무엇이며, 어떤 맥락에서 이 질문을 하고, 어떤 것들을 함께 고려해야하는지와 함께 질문을 던짐. 이 질문에서 유저가 원하면 리서치 결과 다른 서비스에서는 어떤 식으로 문제를 해결했는지에 대한 리서치 결과를 얻을 수 있도록 함.
6. 기능명세서까지 작성이 완료되면 구현 준비 단계로 진입.
7. 구현 준비의 가장 첫 단계는 기술 리서치. 즉, "어떤 요구사항을 만족하기 위한 기능을 어떻게 구현할 것인지"가 첫번째 고려사항. 기술 리서치 시 기능이나 요구사항에 대한 요건을 만족하는 오픈소스나 서비스를 리서치해서 사용할 수 있거나 거기에서 적용한 방식을 동일하게 적용할 수 있는지 리서치하는거야. 해당 기술을 도입할 때의 장점, 단점, 제약사항(pyQT같이 유료 소스라던지... 등)을 전부 정확히 조사해야함. 또, 모든 리서치는 최신 정보를 활용해서 이뤄져야 함.
8. 리서치 결과 기반으로 기술 스택을 확정하는 과정을 거침. (유저 인터뷰, 승인) 동일하게 유저가 원하면 리서치 결과⡀다른⠐서비스에서는 어떤⠈식으로 문제를 해결했는지에 대한 리서치 결과를 얻을⠂수 있도록 함
9. 확정된 정보들 기반으로 실제 구현 작업 시작
10. 구현 및 테스트 과정에서 필요한 것들이 있다면 요청, 다만, Computer Use 나 Playwright MCP 등을 활용해서, 유저가 필요한 정보만 주면 직접 세팅까지 마치는 것을 지향. (AWS 접근이 필요하면 AWS에 로그인해달라고 하거나 AWS 계정정보를 받고, 필요한 권한에 맞춰서 aws cli 에 넣을 iam 계정 키 발급해서 입력한 뒤 aws 사용... 등)
11. 슬랙 연동. 질문 및 요청 사항은 사용자와 slack 으로 소통
12. 데스크탑에서 현재 작업 상태 및 추가 소통이 가능한 대시보드형 UI 필요
