# 작업 분할·의도 확인·실행·검증

근거: P-001, Q-004/Q-005/Q-006/Q-016, D-022/D-024/D-032/D-040/D-041/D-068/D-069. [모델 역할](../model-routing.csv)과 [기능별 검수](../features.csv)를 함께 적용한다. 이 문서의 DTO 필드는 구현 계약이며 새로운 사용자 승인 요구가 아니다.

## 역할과 책임

| 역할 | 맡는 판단 | 산출물 |
| --- | --- | --- |
| 사전 평가 RTE-011 | 요청·맥락·영향·환경·독립 리뷰 필요성 | Assessment |
| 주 조율 RTE-001 / SOT 관리 RTE-012 | 정본·의존성·작은 작업·구체 지시·결과 채택 | 문서 revision, TaskContract, ContextBundle |
| 실행 전 의도 확인 RTE-013 | 작성된 계획이 최초 의도와 현재 승인에 맞는지 | IntentCheck |
| 구현 RTE-003 | 검토된 계획과 세부 명세 구현 | 변경·산출물·진행/검증 자료 |
| 독립 리뷰 RTE-014 | 위험도상 필요한 구현 후 결함 검토 | ReviewEvidence |
| 설계/이미지 RTE-015/016 | 흐름·API·디자인·자산을 구체화 | 설계 revision·검증한 자산 |
| 명확한 효율 실행 RTE-017 | 작은 범위의 세부 동작·예외·검수가 확정된 실행에 Sonnet 5 등 효율 모델을 배정 | 명확성·위험 근거, 실제 산출물·검수, 배정/재평가 기록 |

고성능·높은 effort로 SOT를 관리한다. 정본을 한 장기 CLI 세션에만 두거나 무제한 비용을 허용하는 뜻은 아니다. 실제 모델/강도·설계 기본값·사용자 확정의 차이는 라우팅 CSV가 소유한다.

D-067의 고품질 대응 Astra max ↔ Fable 5.1 max와 조율·조사·SOT/리뷰/설계의 Astra max 기본값은 유지한다. D-068은 가벼운 작업의 Astra medium 고정 우선만 대체하여, 작은 단위의 세부 지시가 명확하면 Sonnet 5 등 효율 모델을 허용한다. 사전 평가·의도 확인의 medium은 유지한다. [모델 정책](accounts-and-budget.md#model-policy)의 분류·대체 조건을 적용하고, 작업을 작게 나눴다는 이유만으로 SOT나 복잡한 판단을 경량 배정하지 않는다.

<a id="task-input"></a>
## 작은 작업과 실행 전 의도 확인

앱이 직접 배정하는 구현·조사·계획 작업을 한 세션에서 의도대로 끝낼 수 있게 나눈다. 필요한 입력 크기·예상 작업·검증량·새로 탐색할 범위를 고려하고, 과부하가 예상되면 선행 조사나 하위 작업으로 분리한다. 고정 토큰 수/비율은 합의하지 않았다. 잠금이 저장소 전체여도 작업량은 작은 세션으로 순차 분할할 수 있다.

| 작업 입력 | 필수 내용 |
| --- | --- |
| 의도·범위 | 최초 요청, 달성할 결과, 유지할 동작, 명시한 제약, 범위 밖 작업 |
| 정본 참조 | REQ/FEAT ID, 관련 저장소 ID, 문서 path·행/절·revision/hash, 필요한 승인 묶음 |
| 구체 동작 | 관련 UI/흐름/API/디자인, 입력·출력·오류·예외·데이터 조건, 필요한 구현 세부사항 |
| 실행 계약 | 선행 작업, read/write·외부 효과, 기억·위임·예산 revision, attempt/lease, 자원 수명 |
| 완료 계약 | 실제 검수 방법/환경·필수 증거, 리뷰 필요성, Git 목표, 결과 보존/복구 |
| 반환 경로 | 누락·모순·새 의존성 보고, 정본 변경 요청, 부분 결과·실패·미검증 표시 |

전체 대화나 기능 카드 하나로 이 전달을 대신하지 않는다. 필요한 범위의 짧은 설명과 정확한 참조로 구성하고, 참조를 열면 생략된 필수 정보를 찾을 수 있어야 한다. 구현 담당자는 요구의 빈칸을 주관으로 채우지 않는다. SOT 변경은 관리 역할에 반환하고 관련 revision·의존성·승인을 갱신한 뒤 종속 작업을 진행한다. 권한은 작업의 실제 쓰기 범위와 연결한다.

효율 배정에는 입력 revision, 구체적인 변경 절차·입출력·오류 처리·검수, 미해결 판단·영향 범위를 근거로 남긴다. 빈칸이 있는 작업은 먼저 구체화하며 인증·권한·데이터 변경 등 위험이 크면 해당 고품질 역할을 유지한다. 선택적 Jev 분류는 최소 구조화 요약에 대한 보조 의견만 제공한다. 미설정·오류·불확실 결과는 기존 정책 판단으로 돌아가며 유효한 IntentCheck·권한·예산을 대체하지 않는다. [분류 API와 비용·전송 계약](accounts-and-budget.md#routing-classifier)은 후속 구현·검증 항목이다.

Plan 모드 또는 동등한 계획을 만든 뒤 RTE-013이 최초 의도·현재 승인·검수와 대조한다. `IntentCheck`는 task ID·plan hash·입력/승인 revision·검토 역할/시각·일치/누락/수정 필요·근거를 기록한다. 불일치/필수 누락이 남으면 실행 조건을 충족하지 못한다. CLI의 `approve_plan()` 호출 자체는 검토 증거가 아니다.

같은 입력과 계획의 유효한 검토는 재개 때 재사용한다. 계획·의도·명세·의존성이 바뀌면 영향 범위만 다시 확인한다. 사전 평가·구현 후 코드 리뷰와 서로 대체하지 않으며 작은 작업마다 사람 승인 관문을 추가하지 않는다.

상용 CLI의 내부 서브에이전트 생성과 수행 방식은 자율이다. 내부 작업마다 계약·계획·맥락·토큰 원장·AI 검토를 요구하거나 읽기 전용으로 제한하는 안은 채택하지 않았다. 앱이 배정한 작업의 권한·예산·의존성과 실제 결과는 그대로 검사한다. 예상 밖 압축만으로 별도 검토·강제 정본 재주입·세션 교체 관문을 만들지 않는다. 실제 실패에는 아래 실패/복구 계약을 적용한다.

<a id="scheduler"></a>
## 의존성과 실행 스케줄러

각 작업에 읽기 집합 `R`, 쓰기 집합 `W`, 외부 효과 대상 `S`를 선언한다. 두 작업 A/B는 `W_A ∩ (R_B ∪ W_B) = ∅` 및 `W_B ∩ (R_A ∪ W_A) = ∅`이며 외부 자원·권한·예산·실행 환경에도 충돌이 없을 때만 병렬 후보가 된다. 읽기끼리는 가능하지만, 파일 목록이 달라도 공통 스키마나 생성 산출물·배포 환경을 통해 연결될 수 있다.

| 사례 | 기대 동작 |
| --- | --- |
| A가 요구 문서를 수정하고 B가 그 문서를 읽어 구현 | A의 변경·필요한 승인·새 버전 확정 후 B 시작. 이전 문서로 동시에 구현하지 않는다. |
| A/B가 서로 독립된 파일을 수정하고 같은 고정 명세를 읽음 | 읽기·쓰기 및 외부 자원 독립성이 확인되면 병렬 가능. 결과 통합 시 입력 hash와 검증 결과 재확인. |
| 다른 프로젝트가 같은 실제 저장소·DB·포트·배포 대상을 사용 | 프로젝트 이름이 달라도 같은 자원으로 잠금·순서를 관리. |
| CLI가 필요한 범위를 미리 한정할 수 없음 | 저장소 전체 또는 해당 외부 환경을 보수적으로 범위에 넣고 직렬 실행. 프롬프트 약속만으로 독립성을 보장하지 않는다. |
| 실행 중 새 참조·쓰기 필요가 발견됨 | 범위를 넓혀 계속하기 전에 관련 작업을 보류하고 의존성·승인·입력 버전을 재평가. 확인된 손상·오염 결과는 유효한 결과로 합치지 않는다. |

worktree는 작업 디렉터리 분리 수단이다. 같은 논리 문서를 다른 사본에서 읽었다고 의존성이 사라지지는 않는다. 새 문서 revision이 필요한 작업은 선행 변경 이후 시작한다. 실제 접근 제한·관찰의 구현 가능성은 V-04로 검증하며 실패하면 독립성이 입증된 단위 외에는 직렬 실행한다.

작업 상태는 `planned → ready → running → verifying → completed`를 기본으로 하며 `waiting_user`, `blocked`, `interrupting`, `interrupted`, `failed`, `recovery_required`, `cancelled`를 명시한다. 전이는 DB 트랜잭션 안에서 기록하고 이벤트 outbox를 함께 쓴다. UI 연결이나 프로세스 메모리가 상태 전이의 유일한 근거가 되어서는 안 된다.

제품 구현 실행 전에는 선행 작업·세 승인·ContextBundle·위임·예산·계정 능력·자원 lease를 검사한다. 실제 저장소 경로를 정규화하고 동일 저장소·symlink·공통 DB·포트·배포 대상 등 논리 자원을 같은 ID로 취급한다. read/write 충돌식은 D-032를 따른다. 문서·설정·스키마·생성 파일·기억의 적용 revision도 입력으로 추적한다.

가능한 한 격리된 작업 디렉터리에서 작업하고 변경 묶음을 검증한 뒤 적용한다. 그러나 격리된 worktree가 의미적 의존성을 지우지는 않는다. CLI가 저장소 전체를 자유롭게 읽는 경우 `read_set`을 일부 파일이라고 축소해서 신고하지 않는다. 실제 접근을 제한하거나 관찰·중단할 수 없는 구간은 해당 저장소 전체에 보수적인 잠금을 잡는다. 병렬성보다 D-032의 일관성 요구가 우선이다.

잠금·예산·계정 슬롯은 일관된 순서 또는 한 예약 트랜잭션으로 획득해 교착을 피한다. 준비된 독립 작업은 기본적으로 오래 기다린 순서로 실행하고 사용자가 우선순위를 조정할 수 있게 하는 안을 사용한다. 자원 한도는 설정 가능하게 하며 초기 슬롯 1개에서 검증한다. foreground 작업은 별도 독점 예약과 합의된 시간 범위를 요구한다.

초기 슬롯 1·오래 기다린 순서·사용자 우선순위 조정은 변경 가능한 설계 기본값이다. 실행 조건에는 해당 작업의 유효한 IntentCheck와 프로젝트 active 상태도 포함한다. 다른 저장소라도 API·공통 명세·DB·배포 대상이 같으면 의존성이 있다.

<a id="execution"></a>
## 구현과 결과 통합

승인된 작은 기능 단위로 구현·실제 검증을 반복한다. 필요한 실제 설치·배포·사용 검증까지 연결하고 해당 환경이 없으면 미검증 이유를 남긴다. 통합 전 HEAD·입력 hash·명세/API/디자인 revision과 사용자 외부 편집을 재확인한다. 사용자/다른 작업 변경은 덮어쓰거나 전체 스테이징하지 않는다. 저장소별 반영과 부분 실패는 [Git 계약](repositories.md#delivery)을 따른다.

일반 구현 RTE-003과 Opus 계열 RTE-007은 실제 확인한 Opus 5.5 max/xhigh·기존 Opus 5·Sol 6 후보를 [설계 기본 순서](accounts-and-budget.md#model-policy)로 선택한다. 명확성·위험 조건을 충족한 작은 구현·정리는 RTE-017의 Sonnet 5 medium 등 효율 후보로 배정한다. 신규 실행에서 프로필별 정확한 ID/effort·인증·유효기간을 확인하며 진행 중 작업의 고정 정책과 실제 선택 이력을 소급 변경하지 않는다. 복잡도/위험이 커지면 해당 역할로 재배정하고 계획·의도 확인·필수 검수와 승인 범위를 유지한다.

외부 전송은 D-069에 따라 MCP 또는 호출된 에이전트에 맡길 수 있다. host가 승인 범위·연결 주체·도구/schema revision·task/run/attempt·외부 operation ID와 receipt를 검사하고, 결과 불명 상태에서는 재전송이나 다른 adapter 전환을 하지 않는다. 내부 서브에이전트 전수 감시를 추가하는 요구가 아니며 앱이 허용한 외부 효과의 경계다. [공통 adapter 계약](accounts-and-budget.md#external-adapters)의 구현과 실제 Slack MCP 왕복은 후속 항목이다.

<a id="verification"></a>
## 실제 검증·독립 리뷰·기존 실패

`VerificationEvidence`는 FEAT/검수 ID·대상 코드/산출물 hash·명세 revision·환경/의존성·실제 명령·시각·출력·결과·한계를 연결한다. 에이전트 자기 보고·테스트 명령 작성·mock만으로 실제 수행을 대신하지 않는다. 새/악화된 실패와 필수 검수는 해결해야 하며 미실행을 통과로 기록하지 않는다.

사전 평가에서 핵심 로직·인증·데이터 등 영향 큰 작업은 구현과 별도 새 세션의 코드 리뷰를 계획한다. 한 공급자여도 가능하며 같은 모델 사용을 금지하지 않는다. 검토 범위/단위는 에이전트가 관리한다. 단순 수정은 기존 검수로 완료할 수 있고 모든 작은 변경에 독립 리뷰를 강제하지 않는다.

리뷰에는 승인 정본·실제 diff·기준/대상 hash·테스트 결과를 전달한다. 승인 요구 위반·실제 결함 등 필수 수정과 선택 개선을 구분하는 것은 구현 계약이다. 필수 지적은 수정·재검증 후 관련 범위를 다시 검토한다. 구현자와 검토자 판단이 다르면 주 조율/SOT가 원문·실제 증거로 해결하며 요구·범위를 바꿔야 할 때만 사용자 판단으로 연결한다. 코드·명세·기준 branch 변경은 영향받는 리뷰/검수를 무효화한다. 내부 AI 리뷰는 원격의 필수 사람 리뷰나 CI를 대신하지 않는다.

유지보수에서 요청과 무관한 기존 실패를 발견하면 **매번 원인·영향을 설명하고 분리할지 수정 범위를 넓힐지 사용자에게 판단받는다(Q-005)**. 그 답변에 의존하는 완료는 기다린다. 독립 작업은 진행할 수 있다.

| 비교 대상 | 기록·판정 |
| --- | --- |
| 기준 상태 | D-039/Q-018의 선택된 시작점과 보존할 사용자 변경. dirty 입력을 HEAD와 같다고 가정하지 않음. |
| 전후 증거 | 코드/명세 revision, 테스트 목록/명령, 환경·의존성, 실패 원인·출력, 이번 수정 영향. 실패 수나 이름만 같다는 것은 불충분. |
| 불확실한 실패 | 미실행·환경 준비 실패·간헐적 실패·원인 미상은 입증된 기존 실패와 구분. 임의 제외 금지. |
| 사용자 판단 | 분리/확장 선택·대상·근거를 연결. 분리해도 원시 실패를 성공으로 바꾸거나 필수 검수/원격 조건을 제거하지 않음. |

완료는 유효한 필수 검수·필요 독립 리뷰·기존 실패 판단·목표 Git 반영·필수 정리를 확인한 뒤 자동 발생한다. 최종 사용자 승인 관문은 없다. 필요한 병합/배포·실기기·정리가 남으면 결과를 이용할 수 있어도 해당 대기 상태를 표시한다. 완료 후 수정 요청은 새 작업에 연결한다.

<a id="failure"></a>
## 실패·방법 변경·복구

오류 유형·원인 가설·이전 시도와 다른 점·결과를 남기고 유효한 대안을 먼저 검토한다. 같은 증거의 같은 시도를 무한 반복하거나 경로/숫자를 모두 제거한 fingerprint로 다른 실패를 합치지 않는다. 합의하지 않은 ‘2회면 질문’ 같은 숫자를 고정하지 않는다. 설정 가능한 turn/time/cost 상한은 보존·대기의 근거이며 성공 판정이 아니다.

승인 요구·스택·권한·비용 안의 방법 변경은 근거 설명 후 진행한다. 명시적 필수 방법이나 위임 범위를 바꾸면 먼저 판단받는다. 유효 대안이 소진되면 시도·근거·남은 선택을 구체적으로 설명한다. 인증·정책 거절은 quota/전송 실패와 구분하며 계정 순환으로 우회하지 않는다.

실제 세션 실패·멈춤·검증 실패에는 [체크포인트·재개 계약](memory-and-lifecycle.md#recovery)을 적용한다. 압축 자체가 실패를 뜻하지 않으며, 실패 복구를 위한 세션 교체를 금지하는 것도 아니다.
