# 내장·원격 콘솔과 Slack 전달

근거: D-014/D-018/D-023/D-027~029/D-035/D-038/D-043~045/D-057/D-061~063/D-069. 수신·전달 구조의 검증은 V-05, 외부 adapter는 V-06, 실제 EC2 납품은 FEAT-061이다.

<a id="transport"></a>
## 연결·권한·전달

Mac은 중앙으로 outbound TLS 연결을 시작한다. 사용자 라우터의 inbound 포트 개방을 요구하지 않는다. 장치 키와 연결 권한은 로컬에서 생성·보관하고 중앙에는 검증에 필요한 공개 정보만 등록하는 안을 사용한다. 브라우저는 짧게 유효한 일회용 코드/QR을 제시하고 Mac에서 연결 대상·조회/제어 범위를 확인받는다. 코드 추측 방지, 재사용 차단, 연결별 폐기·만료를 구현한다.

제품 계정이 없다는 이유로 인증을 생략하지 않는다. 브라우저 세션은 TLS·보안 쿠키·Origin/CSRF 검증과 장치/프로젝트 권한을 사용한다. Tauri IPC는 번들된 UI에 필요한 명령만 노출한다. 원격 페이지가 로컬 CLI 실행·파일 접근 API를 직접 호출하도록 광범위한 capability를 열지 않는다(RES-011).

일반 콘솔 명령도 안정적인 ID·기대 revision을 사용한다. Mac 연결이 없을 때 새 변경 명령은 오프라인 오류로 응답한다. 연결 중 전송하다가 끊긴 명령은 결과 불명 상태로 표시하고 동일 ID로 수락 여부를 조회한다. 브라우저가 ‘실패’라는 이유로 새로운 ID를 만들어 중복 승인·실행을 일으키지 않는다. 일반 콘솔을 장기 오프라인 작업 접수함으로 확장하지 않는다.

실시간 이벤트는 로컬의 증가하는 순번과 snapshot revision을 가진다. 재연결 시 마지막 수신 순번 이후 이벤트를 요청하고, 보존 범위를 벗어나면 최신 snapshot을 받는다. 서버는 내용을 영구 이벤트 이력으로 축적하지 않는다. 브라우저가 명령 결과를 받지 못해도 로컬 내장 콘솔에서 현재 상태를 확인할 수 있다.

인터넷 HTTPS·등록한 브라우저만 접근하며 VPN은 필수가 아니다. app/protocol/schema capability 협상으로 구버전 명령 호환을 확인한다.

정본·실행은 Mac 하나의 workspace에 있고 제품 계정은 없다. 독립 설치의 상태·예산을 자동 합산하지 않는다. 동일 React 화면을 내장 IPC/원격 HTTPS 어댑터로 제공하며 중앙 장애에도 내장 콘솔은 전 과정을 사용할 수 있다. Mac 오프라인에는 일반 콘솔 수정/승인을 접수하지 않는다.

중앙의 영구 저장 범위는 연결/권한·Slack OAuth/라우팅·최소 전달 메타데이터다. 프로젝트 본문은 연결된 화면 요청에 일시 중계하며 로그/분석/HTTP/Service Worker 캐시에 이력을 쌓지 않는다. `no-store`와 연결 해제 시 상세 상태 정리를 적용한다. 정적 UI 파일 캐시는 별개다. TLS·저장 암호화는 적용하지만 중앙이 본문을 처리하므로 E2EE라고 표현하지 않는다.

protocol/schema·지원 명령·app/helper/DB 호환을 handshake한다. 구버전 명령은 묵시 해석하지 않고 명시 거부한다. 권한 해제는 이후 조회/명령을 막고 기존 연결을 닫는다. 연결 코드/세션 TTL은 변경 가능한 운영값이며 고정 사용자 정책으로 기록하지 않는다.

## Slack 7일 큐

사내 배포의 중앙 Events API + OAuth를 기본안으로 삼는다. 공개 Marketplace 등록을 제품 범위로 요구하지 않는다(RES-014/D-051). 본인 Slack 계정만 Mac에서 연결 확인하며 DM을 기본으로 프로젝트별 지정 채널을 선택할 수 있다(D-043/D-061). Slack 설치는 임의 workspace와 로컬 Mac이 뒤섞이지 않도록 일회용 연결 state와 로컬 확인으로 묶는다. 메시지·thread를 읽고 답하는 데 필요한 최소 scopes를 실제 동작으로 검증한 후 확정한다.

| 단계 | 처리 계약 |
| --- | --- |
| 1. 수신 | Slack 서명·시각·연결 권한을 확인하고 `event_id` 등을 고유 키로 정규화한다. 이벤트/API 종류별 고유 키를 구분한다. |
| 2. 영속 수락 | `command_id`, 최초 수신 시각, 대상, 암호화 본문, `expires_at = 최초 수신 + 7일`을 트랜잭션으로 저장한 뒤 Slack에 신속히 ACK한다. 중복 수신으로 만료 시각을 연장하지 않는다. |
| 3. 대기 안내 | Mac이 오프라인이면 요청 스레드에 전달 대기와 만료 시점을 알린다. 안내 전송 자체도 outbox로 기록하고 중복 안내를 방지한다. |
| 4. 전달 | Mac 연결 중에는 즉시 시도한다. 실패하면 지수 backoff·jitter·최대 간격과 Slack의 Retry-After를 반영한다. 재연결 때 만료되지 않은 항목을 다시 시도한다. |
| 5. 로컬 수락 | 장치/프로젝트 권한·대상 revision·명령 ID를 확인한다. inbox와 명령 수락 결과를 영속 기록한 뒤 중앙에 receipt를 돌려준다. 같은 ID 재전달에는 저장된 결과를 반환한다. |
| 6. 적용·결과 | 로컬 트랜잭션에서 첫 유효 명령만 적용하고 이벤트/outbox를 함께 기록한다. 중앙 수신·로컬 수락·실제 적용·작업 완료를 구분해 콘솔과 Slack에 반영한다. |
| 7. 삭제·만료 | 로컬 영속 수락 receipt를 중앙이 기록하면 본문을 삭제한다. 전달 기한이 지나면 본문을 삭제하고 최소 만료 메타데이터·만료 통지 outbox만 남긴다. 만료 통지에도 원문을 복제하지 않는다. |

Slack Events API의 재시도 자체는 이 7일 보관·재전달을 제공하지 않는다. 앱이 내구성 있게 저장하지 못하면 성공 ACK를 보내지 않는다. Slack의 한정된 재시도 기간보다 중앙 장애가 길면 이벤트를 받을 수 없는 구간이 생길 수 있으므로 **Mac 오프라인 7일 보관과 중앙 서버 장애 중 무손실 수신을 같은 보장으로 표현하지 않는다.** 서버 장애 감지·복구 운영값은 EC2 배포 단계에 검증한다. 큐 본문은 장기 DB snapshot/PITR로 보존 제한을 우회하지 않게 분리한다.

ACK 손실이면 같은 ID로 다시 보내므로 로컬 중복 기록은 전달 창보다 길게 유지한다. 서버·Mac 재시작 후에도 수신 시각·만료·시도 횟수·receipt가 복구되어야 한다. 만료 경계에서 이미 Mac이 수락한 사실이 늦게 확인되면 로컬 정본 receipt로 상태를 정정하고 모순된 알림을 설명한다. 만료는 미전달 명령을 더 시도하지 않는 규칙이며 이미 수락된 작업의 취소가 아니다.

질문·승인 답변은 해당 질문 ID·종류·명세 revision이 아직 유효할 때만 적용한다. 같은 버전에 두 채널이 다르게 답하면 로컬에서 첫 유효 적용을 확정하고 나머지에는 현재 결과·변경 방법을 안내한다. 이미 지난 revision에 대한 답은 새 revision 승인으로 바꾸지 않는다. 이전 답을 바꾸려는 사용자 의도는 별도 변경 명령으로 받아 영향 검토로 연결한다.

Slack 편집·삭제 경합은 source revision과 Mac 영속 receipt로 판정한다. 수락 전 대체/취소, 수락 후 변경 요청/명시적 취소 안내를 구분한다. 첨부 필수 입력 확보 또는 명시적 누락 상태를 수락 receipt에 포함하고, 마지막 필요한 사용 후 앱 사본을 정리한다. 상세 actor·만료·삭제 계약은 아래 원본 변경 표를 따른다.

## 원본 편집·삭제와 수락 경합

| 항목 | 구현 계약 |
| --- | --- |
| 발신자 확인 | OAuth 설치와 별도로 Mac이 승인한 `team_id + user_id`를 저장한다. 모든 사용자 명령·버튼은 이 주체와 Mac 연결을 검사한다. 다른 사람·봇의 메시지로 작업을 만들지 않는다. |
| 대화 대상 | DM 기본, 프로젝트별 지정 채널 선택. 채널의 새 요청은 멘션으로 시작하고 알려진 요청 thread 답변은 멘션 없이 받는다. 프로젝트가 불명확하면 선택 요청이며 임의의 최근 프로젝트를 변경하지 않는다. |
| 전달 원장 | `source_key=(team, channel, message_ts)`, source revision, 불변 `command_id`, 대상 revision, 생성·만료·superseded 상태를 저장한다. 동일 이벤트 retry는 같은 ID, 본문이 실제 바뀐 편집은 새 불변 ID로 관리한다. 같은 command ID 아래 내용을 바꾸지 않는다. |
| 수신 확인 | Slack 서명·재전송 검증 후 영속 큐에 저장하고 빠르게 ACK한다. 메모리에만 저장하고 성공 ACK하지 않는다. Slack의 제한된 재시도보다 긴 중앙 장애에서 ‘절대 유실 없음’을 약속하지 않는다. |
| 수락 전 편집 | 최신 source revision이 이전 pending 세대를 대체한다. Mac 수락 명령과 supersede/cancel 판정은 로컬 inbox의 조건부 트랜잭션으로 순서를 정한다. 중앙의 전송 시작/ACK 미수신만으로 미수락이라 단정하지 않는다. |
| 수락 후 편집 | Mac receipt가 accepted/applied이면 새 변경 요청으로 연결한다. 이전 실행 기록을 덮어쓰지 않고 영향·재승인을 검토한다. 역순·중복 metadata 편집은 실제 내용·revision 비교로 제거한다. |
| 삭제 이벤트 | `message_deleted`의 삭제 행위자가 항상 주어지는 것으로 가정하지 않는다. 서명 검증된 이벤트의 정확한 기존 source mapping으로 전달 원본 철회를 처리한다. wrapper 사용자를 명령자로 추정하지 않는다. 미매핑 삭제는 작업 명령이 될 수 없다. |
| 수락 후 삭제 | 메시지 삭제만으로 작업을 중단하지 않는다. 기존 요청을 보존하고 가능한 채널/콘솔에 명시적 중단 방법을 안내한다. 삭제 안내 전송 실패를 작업 취소로 처리하지 않는다. |
| 승인 | 버튼에 approval 종류·question ID·target revision·command ID를 연결하고 서버/코어가 발신자·기대 버전·현재 상태를 검증한다. 버튼 라벨의 자연어만 신뢰하지 않는다. |
| 7일 만료 | 최초 전달 대기의 서버 수신 시각을 기준으로 최대 7일. pending 세대 편집으로 무기한 보관 시간을 갱신하지 않는 초기 설계다. 이미 수락된 작업은 7일 후 자동 취소되지 않는다. |
| 본문 정리 | Mac 영속 수락 또는 만료·취소가 확인되면 중앙 본문과 큐 전용 첨부 사본을 제거한다. receipt·삭제 사실은 본문 없이 유지한다. 큐 body 저장 영역을 장기 snapshot/PITR 보존에 넣어 만료를 우회하지 않는다. 필요시 본문별 키 폐기와 실제 복원 불가 검증을 병행한다. |

대기 메시지는 `received → queued → accepted → applied`를 작업의 running/completed와 구분해 표시한다. 큐 전송 보장과 외부 시스템의 정확히 한 번 실행은 별개다. 외부 효과는 idempotency/receipt/상태 조회로 재개하며 결과 불명이면 `recovery_required`로 남긴다.

세 묶음 승인 버튼에는 묶음의 모든 대상 revision/hash를 연결한다. 앱 재실행·보관/삭제 프로젝트·만료된 질문·취소한 작업도 현재 로컬 수명과 대기 조건을 재검사한다. 과거 Slack 이벤트만으로 이를 되살리지 않는다. 첨부의 durable 확보/누락 receipt·마지막 소비자 수명은 [자원 계약](resources.md#attachments)을 따른다.

## 외부 전송 수단과 사용자 명령 수신의 경계

D-069에 따라 작업 결과의 Slack 전송은 선택한 Slack MCP나 호출된 에이전트에 위임할 수 있다. 특정 공급자의 전송 구현을 에이전트 자체 기능으로 고정하지 않고 [공통 외부 adapter 계약](accounts-and-budget.md#external-adapters)에 연결한다. 승인 범위·연결 주체·도구/schema revision·외부 operation ID·receipt를 host에서 검증한다. 전송 후 응답 손실은 결과 불명으로 보존하며 상태 조회로 확인하기 전에 재전송하거나 다른 adapter로 같은 메시지를 보내지 않는다.

이 변경은 들어오는 본인 명령의 인증, Mac 승인 연결, 7일 내구 큐, revision이 고정된 승인 버튼, 첨부 확보/정리를 대체하지 않는다. MCP나 다른 에이전트의 자연어 출력은 사용자 승인 증거가 아니며 host의 승인 토큰 검증을 통과해야 한다. 고정 상태 안내를 보내기 위해 매번 모델을 호출하도록 요구하지 않는다.

일반 외부 adapter·에이전트 위임 실행과 실제 Slack MCP 왕복은 후속 구현·실환경 검증 항목이다. 기존 Slack 수신·publication 구현이나 모의 테스트만으로 이 연동이 완료됐다고 표시하지 않는다. 기존 FEAT-035/FEAT-036/FEAT-052와 REQ-031/REQ-032/REQ-045 범위에서 추적한다.
