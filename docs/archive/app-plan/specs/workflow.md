# 요청·명세·화면 설계와 승인

적용 기준: 2026-09-19 통합, 2026-09-23 D-068 후속 반영. 행동·검수의 정본은 [features.csv](../features.csv), 결정은 [decisions.csv](../decisions.csv)다. 아래 계약은 D-010/D-020/D-034/D-045/D-068 및 Q-010/Q-011/Q-019/P-002를 함께 적용한다.

<a id="assessment"></a>
## 시작과 사전 평가

신규 컨셉 또는 유지보수 요청에서 시작한다. 평가 역할은 RTE-011의 Astra medium이며 주 조율·계획의 Astra max와 구분한다. D-068에 따라 작은 단위의 세부 지시·검수가 명확한 실행에는 RTE-017의 Sonnet 5 등 효율 모델을 허용한다. 고강도 SOT·복잡한 판단과 사전 평가·의도 확인의 역할은 유지한다. 최신 모델의 실제 지원과 작업 분류는 [모델·계정 계약](accounts-and-budget.md#model-policy)을 확인한다.

코드 없는 컨셉은 예상 범위·환경·불확실성을, 유지보수는 전역 목적·불변 조건·이전 결정·저장소 집합·사용자 변경·명세와 코드 차이·검증 환경·자료 최신성/누락을 평가한다. 파일/줄 수만으로 범위를 정하지 않는다.

| 검토 범위 | 선택 근거 |
| --- | --- |
| 국소 | 영향이 고립됨을 입증하고 필요한 상위 목적·불변 조건을 확인했다. |
| 확장 | 관련 모듈·데이터 흐름·API 소비자에 영향이 있다. |
| 전체 구조 | 핵심 규칙·공유 데이터·권한 또는 맥락 공백으로 영향을 한정할 수 없다. |

이 세 범주는 기존 요구를 적용하는 설계 분류다. 작은 인증 변경은 넓게, 큰 저장소의 문구 수정은 근거가 있으면 좁게 검토할 수 있다. 읽은 자료·검토 이유·미확인 영역·영향 REQ/FEAT·재사용 승인·추가 질문/리서치·read/write·환경·독립 리뷰 필요성을 기록한다. 새 의존성이나 정보가 드러나면 평가와 관련 계획을 갱신한다.

효율 모델 배정은 복잡도·영향·필요 맥락·검수 난도와 지시의 명확성을 함께 판단한다. 입력 revision·구체 절차·입출력·예외·검수가 정해졌는지, 미해결 판단이나 권한·데이터 위험이 없는지 확인한다. 작은 작업으로 나눴다는 사실만으로 medium에 배정하지 않는다. 선택적 Jev 분류가 없거나 불확실하면 기존 정책 판단을 사용하며 API confidence를 의미 정확성 보장으로 취급하지 않는다. 새로운 위험이 드러나면 역할·강도·계획을 재평가하고 실제 선택과 이유를 기록한다.

시작 브랜치·기존 변경 보존은 [저장소 계약](repositories.md#start), 기존 테스트 실패는 [검증 계약](orchestration.md#verification)을 따른다. 전체 구조 검토가 전체 재승인을 뜻하지 않는다.

<a id="research"></a>
## 근거를 갖춘 인터뷰

의사결정 주제마다 동일/타 도메인 사례와 기술 후보를 조사하고 출처·날짜·확인 사실·해석·대안·장단점·비용·라이선스·제약·미확인점을 구분한다. 유효한 같은 주제 근거는 재사용하며 모델·요금·지원 버전 등 시점 의존 정보는 결정할 때 다시 확인한다. 두 공급자가 가능하면 조사 결과를 비교하고, 한 공급자 결과는 양사 교차 확인으로 표시하지 않는다.

한 번에 필요한 판단을 하나씩 설명하고 추천·대안을 제시한다. 답변마다 결정과 관련 요구·기능·설계를 저장한 뒤 다음 주제로 넘어간다. 확정한 제품 정책을 다시 묻거나 일반적인 구현 판단을 모두 사용자 질문으로 바꾸지 않는다. 상세 조사 근거는 별도로 열람할 수 있다. 과거 조사 기록은 [research.csv](../research.csv)이며 실제 호환 실험을 대신하지 않는다.

## 세 묶음 승인과 구현 진입

| 순서 | 준비할 산출물 | 사용자 승인 대상 |
| --- | --- | --- |
| 1 | 요구 인터뷰와 요구사항 CSV | 요구사항 revision |
| 2 | 기능 CSV 초안 → 기능 기반 와이어프레임 → 발견한 누락의 정본 반영 | 기능명세 + 와이어프레임의 각 revision/hash |
| 3 | 기술 조사·필요 API 규칙 설계·주요 화면 상세 디자인 | 기술 스택 + 주요 상세 디자인의 각 revision/hash |
| 실행 준비 | 작은 작업 분할·세부 지시·검증/복구 계획·최초 의도 대조 | 에이전트 내부 검토. 새로운 사람 승인 단계 없음 |
| 실행·완료 | 작은 기능 단위 구현·실제 검증·필요 독립 리뷰·Git 반영·필수 정리 | 필수 조건 충족 시 자동 완료. 최종 사람 승인 없음 |

승인은 대상과 범위가 보이는 revision 버튼으로 받는다. 일반 자연어 답변·산출물 생성·Git 커밋·CLI Plan 승인 입력은 제품의 묶음 승인을 대신하지 않는다. `ApprovalBundle`은 묶음 안의 모든 문서 revision/hash와 적용 전제를 고정한다. 스택만 승인한 기록으로 나중 디자인을 승인하거나 와이어프레임 승인으로 상세 디자인 확인을 생략하지 않는다.

UI 또는 API가 없는 프로젝트는 불필요한 자료를 생략하고 비해당 이유를 기록한다. 이는 요구·기능·스택 승인 자체를 없애는 예외가 아니다. 작은 유지보수는 변경 없는 유효 승인·기존 흐름·디자인을 재사용한다. 영향 있는 부분만 새 revision/승인/검수로 연결한다. 미래 기능 전체를 현재 작업 전에 설계할 필요는 없다.

실제 제품 코드는 필요한 세 묶음 승인과 [실행 전 의도 확인](orchestration.md#task-input) 후 시작한다. 사용자 요구/범위/스택/권한/비용을 바꾸는 판단은 먼저 받되, 승인 안의 기술 방법 변경은 근거 설명 후 진행한다. 답변에 의존하는 작업은 대기하고 독립 작업은 진행할 수 있다.

<a id="design"></a>
## 와이어프레임·API·상세 디자인

와이어프레임은 기능 ID와 주요 화면/흐름 ID를 연결하고 정보 배치·이동·입력·분기·필요한 오류/빈 상태를 나타낸다. 낮은 시각 완성도로 흐름을 먼저 확인해 상세 디자인을 반복해서 갈아엎지 않게 한다. 특정 제작 도구·표현 형식은 구현 검증으로 정한다.

API가 필요하면 흐름 확인 뒤 요청/응답·권한·오류·관련 저장소·검증 조건을 명세한다. HTTP API에는 OpenAPI 등을 검토할 수 있지만 내부 호출·정적 사이트에 HTTP 서버나 특정 도구를 강제하지 않는다. API와 상세 디자인은 공통 입력이 안정적이고 읽기/쓰기 의존성이 없을 때 병행한다. 실제 코드는 필요한 승인 후 구현한다.

상세 디자인은 프로젝트의 목적·사용자·콘텐츠에 맞는 모던 레퍼런스를 폭넓게 살피고 실제 적용할 기법과 이유를 기록한다. 구성·정보 위계·타이포그래피·여백·이미지 배경/본문 배치·반응형 등은 프로젝트별 적용 예시다. 레퍼런스 수집에서 끝내지 않고 시안과 구현 지시에 연결하며, 이미지 추가만으로 AI Slop을 피했다고 판정하지 않는다. 특정 스타일·조사 개수·모든 화면의 미디어를 전역 강제하지 않는다.

각 작업에는 기능/화면/흐름/API/디자인과 정확한 revision·검수 조건을 전달한다. 작은 기능의 UI→서버→저장→검증을 연결해 반복하며, 기반 작업이 선행해야 하면 의존성을 지킨다. 모든 API를 먼저 완성한 후 UI를 붙이는 순서나 각 작은 작업의 별도 사람 승인은 고정하지 않는다. mock·시안 통과와 실제 통합 검증을 구분한다.

<a id="assets"></a>
## 이미지와 최종 자산

이미지 생성 공급자는 고정하지 않는다(Q-019). GPT를 먼저 시도하거나 실패해야 전환하는 조건도 없다. Gemini nanobanana·grok·qwen 등은 허용 예시이며 전부 필수 연동할 대상이 아니다. 무료 스톡 대체 선택지를 사용자가 채택했다고 기록하지 않는다.

디자인에 필요한 위치·목적·비율·스타일을 정하고, 사용 가능한 계정·기능·품질·기존 예산/위임에 맞는 생성 경로를 선택한다. 생성 지시·출처·확보 파일/hash·시안·최종 위치를 연결한다. 웹의 기능 지원과 실제 생성 완료 감지→다운로드→파일 확인→프로젝트 반영 자동화 성공은 별도로 검증한다. CLI 구독 인증만으로 웹 로그인/생성 준비를 판정하지 않는다.

로그인·MFA·전경 사용은 [위임 계약](accounts-and-budget.md#delegation)을 따른다. 막힌 경우 원인·허용 대안을 검토하고 해당 자산에 의존하지 않는 작업은 진행한다. 유료 API·소재 구매·신규 구독을 조용히 추가하지 않는다. 필요한 이미지를 빼거나 임시 자료만 둔 상태로 완료하지 않는다. 영상은 예시였으며 실제 요구하는 프로젝트에서 공급자·소재·비용·검수를 정한다.

실제 화면에서 레퍼런스로 정리한 의도, 이미지 표시·잘림·모바일 배치·텍스트 가독성·로딩 영향을 확인한다. 최종 투입 자산은 프로젝트 Git 자료로 승격하고 버려진 후보·다운로드 임시 사본은 [자원 수명](resources.md#lifetime)으로 정리한다.

## 직접 편집·revision·변경 영향

CSV는 편집 가능한 작업본이며 승인 내용은 불변 snapshot/hash다. 둘은 같은 문서 ID/revision으로 연결한다. 실행 상태는 DB에서 관리하고 CSV의 `확정/초안/기술검증필요`와 분리한다. 열 계약은 [README](../README.md#csv-schema)를 따른다. 현재 Python의 18열 런타임 CSV를 새 스키마로 묵시 수용하지 않는다.

파일/대화 편집은 같은 변경 명령으로 처리한다. 파일 안정화 후 마지막 적용 revision과 비교하고 파싱·참조 누락·동시 변경·정책 충돌·영향을 검사한다. 부분 저장/파싱 실패 동안 이전 유효 snapshot을 보존한다. 직접 편집으로 생긴 충돌 해결은 기존 계획으로 추론 가능해도 구체 diff·맥락·근거·영향을 설명하고 사용자 적용 확인을 받는다(D-020). 침묵을 동의로 취급하지 않는다.

명령에는 대상/기대 revision을 넣고 첫 유효 적용만 인정한다. 오래된 승인·두 채널의 상충 답변은 최신 내용 승인을 대신하지 않는다. 변경된 기능/흐름/API/디자인·관련 저장소와 종속 계획/리뷰/검수 증거를 재평가하며, 기존 `tested` 표식으로 새 결과를 완료하지 않는다. 변경 없는 범위의 유효 승인은 유지한다.

<a id="experiments"></a>
## 승인 전 최소 실험

선택에 필요한 최소 실험은 `ExperimentContract`에 목적·질문·성공/실패 기준·입력/출력/쓰기 경계·소비 자원·기존 예산/권한·정리 조건을 먼저 기록하고 별도 공간에서 수행한다. 원본 저장소·운영 환경은 바꾸지 않는다. 필요한 권한/비용이 없으면 해당 실험을 대기한다. 실험 결과를 실제 제품에 반영하는 것은 필요한 승인을 거친 별도 작업이다.
