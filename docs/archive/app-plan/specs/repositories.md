## 사용자 정책과 시작 상태

개발자와 비개발자 모두 지원한다. 개발자에게는 프로젝트별 `파일 수정만 / 로컬 커밋까지 / push·PR까지 / 병합까지` 범위·대상을 정하고 이후 유효한 설정을 재사용한다. 비개발자는 복잡한 범위 메뉴를 생략하고 자동 병합까지 관리하는 기본 방향을 유지하되, **Git 지식과 기존 프로젝트 관리 정책을 먼저 확인한다(Q-018)**.

모름·정책 없음 답변을 받으면 기술 선택을 에이전트가 관리하고 필요한 사용자 의도만 쉬운 말로 질문한다. 비개발자라는 분류나 미응답을 정책 없음으로 간주하지 않는다. 알고 있는 지식과 프로젝트 정책은 별도 항목이며, 확인된 정책이 있으면 존중한다. 이미 받은 유효 정보는 재사용하고 다른 프로젝트 정책은 임의 적용하지 않는다.

| 시작 상황 | 필수 처리 |
| --- | --- |
| 개발자 dirty 저장소 | branch/HEAD와 staged·unstaged·untracked 변경을 설명하고 보존 방식·시작점을 선택받는다. snapshot/별도 commit/stash 등 선택안의 복구 방법을 설명한다. |
| 비개발자, 정책 없음/모름 확인 | 기존 수정의 포함 여부 등 필요한 의도만 질문하고 기술 보존·시작점은 앱이 관리한다. 명시한 시작점·유효 선택을 존중한다. |
| 기존 정책 있음 | 정책과 실제 상태를 연결하고 충돌·누락된 의도만 확인한다. 지식이 있다고 모든 기술 메뉴를 반복하지 않는다. |
| 비Git 폴더 | 분석 후 초기화/복사/대상을 판단받는다. Q-018의 브랜치 질문 간소화를 비Git 초기화의 포괄 승인으로 확대하지 않는다. |
| 원격 clone | 필요한 인증·호스트·권한·대상/시작 revision을 확인한다. 실패한 임시 사본만 정리하며 정식 프로젝트 폴더로 채택한 clone은 결과물이다. |
| 선택 대기 | 독립 읽기 전용 조사·계획은 가능하다. 해당 선택을 가정하는 원본 변경·자동 commit/stash/reset·통합은 먼저 하지 않는다. |

staging·untracked·binary·submodule을 포함해 실제 사용자 변경을 보존한다. 별도 브랜치 생성만으로 dirty snapshot이 생겼다고 판단하지 않는다. 보존과 이번 결과의 커밋/업로드 포함 동의는 별개다. 기술적 시작점을 앱이 정하더라도 원격 기본/현재 브랜치를 무조건 고정하지 않고 요청·상태·정책에 근거한다.

실행 전·통합 전 HEAD/입력 hash를 재검사한다. 다른 도구에서 생긴 수정·다른 작업 staging은 덮어쓰지 않는다. 기술 충돌은 위임 범위 안에서 해결하고 사용자 의도/명세 충돌·범위 확장은 근거와 구체안을 제시해 판단받는다. 전체 `git clean -fdx`나 전체 작업트리 reset을 보존/정리 방식으로 사용하지 않는다.

## 도구 준비와 설치

Git은 로컬 이력 도구, gh는 GitHub 기능/인증 도구이며 준비 상태를 구분한다. 호환 기존 설치를 우선 재사용하고 없으면 앱이 준비한다. 앱 전용 설치는 필수가 아니며 Git/gh 전역 설치를 허용한다. Homebrew·GitHub Desktop을 Git/gh 준비의 필수 전제나 일괄 설치 대상으로 정하지 않는다.

프로젝트에 npm·Homebrew 등 추가 도구가 필요하면 사용자 승인 범위 안에서 PC에 설치·설정한다. 이미 승인한 구체 단계마다 반복 확인하지 않는다. 실제 관리자 인증이 필요한 단계는 공식 절차와 제한된 helper operation을 적용한다. 전역 설치가 항상 root 실행을 뜻하지 않는다.

경로·버전·설치 수단은 호환성·공식 출처·무결성·라이선스·서명/배포 조건을 확인해 정한다. 기존 개인 설치·config·인증과 다른 프로젝트 환경을 무조건 덮어쓰지 않는다. 버전 충돌은 보존 가능한 방법을 검토하고 위임 범위를 넓혀야 하는 변경만 판단받는다. 취소·다운로드 실패·오프라인·공간 부족 시 실제 준비 상태와 다음 행동을 표시한다.

Git이 없으면 필수 Git 작업을 완료할 수 없지만 독립 인터뷰·조사는 가능하다. GitHub 미연결은 로컬 개발·커밋·병합을 막지 않는다. 필요한 worktree/submodule/LFS/서명·credential 지원은 실제 조합에서 검증한다. 도구 설치는 인증이나 원격 저장 동의를 대신하지 않는다.

## GitHub 연결과 작성자

GitHub 연결은 온보딩에서 권장하되 건너뛰기를 제공하고 원격이 필요한 작업 진입 시 안내한다. 가입·이메일 확인·로그인/MFA는 공식 절차를 사용하며 Playwright·브라우저·Computer Use로 사용자 로그인까지 안내한 후 설정을 자동 처리할 수 있다. 특정 도구/경로 우선순위는 고정하지 않는다.

`웹 로그인 / gh 또는 API 인증 / Git 원격 접근 / Git 작성자 설정 / 업로드 위임`은 각각 확인한다. 공식 브라우저 인증·credential helper·기존 SSO/SSH를 연결하는 방식은 실제 환경에서 검증한다. 웹 로그인만으로 모두 준비됐다고 표시하지 않는다. 자격 증명 저장 위치를 확인하고 Keychain 실패를 정상 격리/보관 성공으로 숨기지 않는다. 비밀번호나 토큰을 일반 대화/정본에 수집하는 흐름을 기본으로 두지 않는다.

| 작성자 상태 | 적용 |
| --- | --- |
| 유효한 기존 사용자/회사 설정 | 재사용. GitHub 로그인만으로 변경하지 않음. |
| 기존 설정 없음·GitHub 연결 | 실제 연결 계정 이름과 확인된 GitHub noreply 주소를 프로젝트에 적용. 이메일 공개 설정 자체는 변경하지 않음. |
| 기존 설정 없음·미연결 | 앱 명의로 기록. 개인 실명/이메일을 추측하지 않음. 구체 앱 이메일은 구현값. |
| 앱 임시 명의 이후 GitHub 연결 | 이후 새 커밋부터 계정 정보 사용. 과거 이력 재작성/강제 push 없음. |
| 부분 설정·무효·충돌 | 완전한 기존 설정으로 오인하지 않고 출처·영향을 설명해 필요한 판단을 받음. |

새 설정은 프로젝트 범위이며 전역 작성자 설정·과거 기록을 자동 변경하지 않는다. 사용자는 나중에 변경할 수 있다. `noreply`는 계정과 연결된 주소이며 익명화를 보장하지 않는다. 회사의 작성자/서명/보호 규칙을 앱 명의로 우회하지 않는다. CLI와 오케스트레이터가 만든 커밋도 선택한 정책에 맞는지 결과에서 확인하며 앱의 요청/작업 기록은 별도로 연결한다.

초기 서비스 전용 자동화는 GitHub 계정 연결·저장소 생성·PR·원격 병합이다. GitLab 등은 로컬 개발·기존 인증으로 가능한 clone/push를 제공하고 서비스별 설정/MR은 사용자가 맡는다. 필요한 미지원 단계는 시작 시 안내하고 미완료로 추적한다. GitHub Enterprise 등 구체 서버·인증 조합은 검증한 범위만 표시한다. `glab`이나 다른 서비스 전용 자동화를 초기 필수로 도입하지 않으며 GitHub로 강제 이전하지 않는다.

## Git 전달과 새 프로젝트 자동 저장

`GitDeliveryPolicy`는 프로젝트/저장소·범위·대상 branch/remote·설정 출처·유효 revision·간접 외부 효과 위임을 기록한다. 작업 단위는 에이전트가 관리한다. 허용 범위는 재사용하고 범위 확장만 판단받는다. 로컬 브랜치 merge와 원격 PR/MR merge는 별도 결과다.

작업이 소유한 변경 목록을 식별해 반영한다. 전체 `git add -A`로 사용자/다른 작업 변경을 함께 커밋하는 경로를 그대로 이식하지 않는다. 사용자 변경을 보존했다는 사실은 이를 업로드할 권한을 뜻하지 않는다. 명세·최종 자산도 명시한 게시 대상에 포함한다.

검수·필요 독립 리뷰가 통과한 결과와 실제 commit/대상 HEAD가 일치하는지 확인한다. 보호 브랜치·CI·필수 리뷰·서명·권한·충돌을 무시하거나 직접 push/관리자 옵션으로 우회하지 않는다. push/merge의 자동 배포 효과는 기존 외부 위임도 검사한다. 병합 예약/요청 수락과 실제 병합 완료를 구분하며, 목표 병합이 남으면 해당 요청은 미완료다.

GitHub 연결 때 비개발자에게 **앞으로 만드는 새 프로젝트의 개인 비공개 저장 여부**를 한 번 선택받는다. 켜면 필요한 코드·공통 문서 저장소 생성/업로드/병합을 관리하고 프로젝트별 끄기를 제공한다. 로그인만으로 동의하지 않는다. 기존 remote·소유자·공개 범위는 유지하며 조직/공개 대상은 별도 선택이다. 연결 전에 이미 만들던 프로젝트의 업로드는 실제 요청·위임을 확인한다.

설정 끄기/연결 해제는 이후 적용 정책 revision을 갱신하며 원격 저장소 삭제·공개 전환·기존 이력 제거가 아니다. 이름 충돌·쓰기 권한 부족·생성 성공 후 응답 유실·업로드 단절은 외부 receipt/재조회로 처리한다. 여러 저장소 반영은 원자적이지 않으며 저장소별 성공/실패/불명 결과와 전체 통합 검수를 분리한다.

## 저장소 구성과 문서 정본

초기부터 프로젝트 하나에 여러 독립 저장소를 연결한다. 관련 저장소를 일반 로컬 상위 폴더에 모으고 기능·배포·CI 경계에 맞게 분리하되 과분할하지 않는다. 명시적 사용자 지시 없이 모노레포를 추천/생성하지 않는다. 기존 모노레포 유지보수는 지원하며 이를 자동 분리할 권한은 없다.

```text
프로젝트/           일반 폴더, 자동 git init 없음
  project-docs/     새 다중 저장소의 공통 기획·설계 Git 저장소 하나
  frontend/         독립 코드 저장소
  backend/          독립 코드 저장소, 그 API 명세의 원본
```

이름은 예시다. 저장소 하나로 충분한 작은 프로젝트에 추가 문서 저장소를 강제하지 않는다. 기존 문서/저장소를 임의 이동·복제·삭제하지 않고 현재 구조를 연결한다. 상위 폴더를 다시 저장소/submodule로 묶는 요구가 아니다. 작은 작업마다 저장소를 새로 만들지 않는다.

공통 요구·기능·결정·화면 흐름·저장소 관계는 공통 문서 저장소, 저장소별 API/구현 설명은 해당 코드 저장소가 원본을 소유한다. 참조는 `repository_id + path + 문서/행/절 ID + revision/hash`로 연결하며 API 정의를 여러 곳의 독립 정본으로 복제하지 않는다. 생성/검증용 사본은 원본과 버전을 표시한다. 문서 선행 변경·필요 승인 뒤 종속 구현을 시작한다.

| Git/허용 원격에 포함 | 자동 저장에서 제외 |
| --- | --- |
| 정리된 요구·기능 CSV, 프로젝트 결정, 와이어프레임, API 명세, 디자인, 실제 제품 이미지·코드·필요한 설정 예시 | 전체 대화/CLI transcript, 공통 기억·다른 프로젝트 정보, 로그인 token/비밀값, 기기별 앱 DB/실행 상태 |

프로젝트 결정 정리는 전체 대화 원문과 다르다. 버려진 이미지 후보·작업 다운로드·일시 trace까지 모두 영구 보관하지 않는다. 명세 작업본은 편집 가능하고 승인 snapshot은 앱에서 불변 hash로 연결한다. Git 저장·사용자 승인·구현 완료는 별개며 clone만으로 계정/외부 위임/예산/승인 상태가 복원되지 않는다.

저장소별 path·remote·시작 revision·변경·commit/PR·검증과 프로젝트 전체 요청을 연결한다. 저장소가 달라도 공유 API/DB/배포 대상 의존성을 검사한다. 모든 코드를 한 CLI 세션에 넣지 않고 해당 작업 문서만 전달한다. 문서/자산은 정식 산출물로 보호하며 프로젝트 앱 기록 삭제에도 Git 결과물은 유지한다.
