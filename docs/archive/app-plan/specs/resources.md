# 첨부·산출물과 모든 작업의 자원 수명

근거: D-046/D-055/D-062/D-063, Q-009/Q-013/Q-020/Q-021. `file-cleanup-warn.md`의 참고 아이디어는 아래 계약으로 통합한다. Nix/Bazel 설치, 일괄 읽기 전용, TTL 단독 삭제, 고정 N일 보관 정책을 채택한 것이 아니다.

<a id="attachments"></a>
## 첨부 확보와 소비자

`Attachment`에는 출처(console/Slack file ID), 파일명·MIME·실제 크기·hash, 업로드 상태, 프로젝트/요청, named consumer, 보존 이유와 파생 요약·근거를 저장한다. Slack 비공개 파일은 정식 권한으로 내려받고 링크만 있다고 입력 확보 완료로 표시하지 않는다. 콘솔 업로드도 완료·hash 검증 이후에 분석한다. 지원 형식은 이미지·PDF·CSV·텍스트이며 지원하지 않는 형식·크기 초과·암호화/손상 파일은 구체적인 이유와 가능한 대안을 제시한다. 크기·개수·보관 공간 한도는 설정으로 구현하고 실측해 기본값을 정한다.

파일명은 표시 정보이며 저장 경로는 앱이 생성한 resource ID를 사용한다. 경로 탈출·symlink·압축 폭탄·부분 업로드·용량 부족을 처리하고 자료 속 지시를 사용자 승인·권한으로 취급하지 않는다. 원본을 해석하지 못한 경우 임의 요약으로 증거를 채우지 않는다.

Mac이 수락할 때 필수 입력도 durable하게 확보했는지 확인한다. 필수 파일이 삭제/만료돼 확보되지 않았으면 ‘입력 누락으로 대기’라는 명시적 receipt를 남기고 사용자에게 복구 입력을 요청한다. 분석 가능한 요청으로 수락했다는 허위 상태를 만들지 않는다. 중앙의 일시 사본은 전달 큐와 함께 제한하고, 로컬 사본은 D-063의 마지막 소비자 종료 후 정리한다. Slack 자체 파일·사용자 원본은 앱 사본 정리 대상이 아니다.

## 생성·보존·정리

정리는 에이전트가 기억을 보고 임의 경로를 지우는 방식이 아니라 **생성 시 등록한 소유권과 마지막 소비자 참조에 따른 수명 관리**로 구현한다. AI는 보존 이유·다음 소비자를 제안할 수 있지만 파일 삭제 권한이나 완료 판정의 정본은 아니다.

`ManagedResource` 필수 필드: resource ID, 종류, 앱 소유 root/상대경로, 생성 task/attempt, hash·크기, consumer ID 집합, retain reason, lease/process 참조, 승격된 사용자 산출물 여부, 상태(`allocated/active/released/cleanup_pending/deleted/cleanup_failed`), 마지막 오류·재시도 시각. 소비자는 ‘나중에 쓸 수도 있음’이 아니라 구체 작업/검수 ID로 연결한다. 생성 전에 자원 등록을 영속화하고 파일 생성과 DB 반영 사이 crash의 orphan을 복구 스캔으로 조정한다.

| 자원 | 보존·정리 시점 |
| --- | --- |
| 첨부 앱 사본·추출 텍스트·변환 이미지 | 분석만으로 곧바로 지우지 않는다. 이름 있는 후속 구현/검증 소비자가 끝난 뒤 필요한 요약·출처·증거를 보존하고 사본·불필요한 파생 파일 제거. |
| 실험·빌드·테스트 임시 공간 | 작업별 격리 디렉터리에 생성. 채택한 결과·필수 검증 증거를 정식 산출물로 승격하고 나머지 제거. 실패 재현에 필요한 파일은 이유와 다음 소비자를 기록. |
| 임시 clone·worktree | 앱의 임시 작업 사본만 관리. 변경 통합·필요 결과 보존·취소 보관/폐기 선택·프로세스 종료 후 해제. 앱이 생성한 정식 프로젝트 저장소와 사용자 원본은 제외. |
| CLI transcript·PTY 로그·화면/브라우저 trace | 필요한 진단·검수 근거만 보존하고 불필요한 원시 로그는 요약·삭제. 오류·삭제 실패를 일반 로그에 묻어 두지 않음. 실제 CLI가 만드는 앱 관리 프로필 내 파일도 관찰·수명 관리. |
| 캐시·앱 관리 CLI 버전 | 용량 한도와 사용 lease에 따라 정리. 실행 중 버전·공유 사용자 캐시를 삭제하지 않음. 재다운로드 비용·네트워크 사용은 구분해 표시. |
| updater download·migration 임시 파일 | 취소·실패·새 버전 건강 확인 시 수명 검사. 복구에 아직 필요한 파일은 이유를 남기고 유지. 영구 업데이트 임시 디렉터리 누적 금지. |
| 승인 snapshot·완성 결과·필수 검수 증거 | 정본/사용자 산출물이므로 일반 임시 정리로 삭제하지 않음. 기억 영구삭제 요구가 포함된 파생 본문은 삭제 전파 계약에 따름. |

정리 트리거는 완료·취소·실패·소비자 해제·재시작 복구·앱 업데이트·용량 부족이다. 삭제 전에 실제 소유 root, symlink·경로 탈출, 최신 참조/lease, 파일 handle·실행 프로세스, 결과 승격을 확인한다. 검사와 삭제 사이 재참조 경합은 동일 자원 잠금/트랜잭션 상태로 차단한다. root 정리가 필요해도 등록된 앱 소유 경로·operation만 허용한다.

삭제 결과를 확인한 뒤 `deleted`로 바꾼다. 권한 오류·열린 파일·디스크 오류는 `cleanup_failed`로 남겨 재시도하고 UI에 남은 용량·이유를 표시한다. 삭제 실패를 무시하고 ‘정리 완료’ 또는 전체 작업 완료로 표시하지 않는다. 필수 정리가 남으면 결과는 이용 가능하더라도 작업은 정리 대기 상태임을 구분한다. 디스크 부족 시 쓰기 작업을 보류하고 안전하게 회수 가능한 자원부터 정리한다. 참조가 있는 자료나 사용자 원본을 지워 공간을 만드는 정책은 사용하지 않는다.

기억 영구삭제는 본문·파생 요약·검색 색인·앱 관리 맥락 사본의 연결을 따라 전파하고 tombstone에 삭제 사실과 ID만 남긴다. 진행 세션에 이미 들어간 내용은 회수됐다고 주장하지 않으며 이후 재구성 때 재주입하지 않는다. SQLite `secure_delete`만으로 WAL·FTS·공급자 기록·OS 백업까지 물리적으로 완전 삭제했다고 표현하지 않는다. 앱 관리 저장소의 삭제 결과와 앱 밖 한계를 구분한다.

## 정리 구현 시 확인할 경계

재생성 불가능한 사용자 입력·원시 관측·필수 진단 근거를 자동으로 재생 가능한 캐시로 분류하지 않는다. 보존할 산출물 승격과 consumer/root 등록은 하나의 회복 가능한 전이로 관리하고, 생성 전 임시 root를 등록해 등록·생성·GC 경합을 막는다. 단순 파일 문자열 스캔만으로 압축/인코딩된 참조를 모두 찾았다고 보지 않는다.

출력 이동은 같은 filesystem의 원자적 rename을 우선 검토한다. 다른 filesystem이면 임시 이름 복사·완전성 확인·최종 게시 후 원본 해제를 기록하며 crash에 대비한다. 구체 방식은 구현 검증으로 정하고 검증 없이 원자성을 주장하지 않는다.

정리 대상 root·실제 경로·symlink·mount 경계를 검사한다. 빈 경로/상위 경로 삭제를 막고 연결된 사용자 원본을 따라가 삭제하지 않는다. 작업 자식 프로세스·열린 handle·lease를 함께 확인하며 PID 파일/TTL 하나만으로 고아라고 단정하지 않는다. 시작 시 orphan을 조정하되 살아 있는 작업은 보호한다.

TTL·용량 상한은 재평가/정리 후보 선정에 사용할 수 있으나 유효 참조·활성 프로세스·보존 선택을 무시하는 삭제 허가가 아니다. dry-run으로 후보/이유를 검증하는 것은 구현 방법이며 며칠 관찰·N일 뒤 삭제는 확정 정책이 아니다. 필요시 trash/격리 이름으로 먼저 이동할 수 있지만 실제 삭제 전에는 `cleanup_pending`이며 `deleted`가 아니다. I/O·배치 크기·재시도 간격은 실측 설정으로 둔다.

검수는 V-09/V-14에서 삭제 실패·재참조 경합·crash orphan·디스크 부족·취소 보관·정식 clone 보호를 확인한다. updater 내부 temp도 앱 attempt와 연결해야 하며 플러그인 오류 무시를 제품의 정리 완료로 받아들이지 않는다.
