# 구현 순서와 남은 검증·입력

아래 단계는 제품 구현 계획이며 완료 보고가 아니다. D-068의 최신 모델·효율 배정과 D-069의 유연한 외부 연동도 같은 단계·검증에 연결한다. 기능별 단계는 [features.csv](features.csv)의 `구현단계`, 실제 실험 조건/실패 처리는 [verification.csv](verification.csv)의 `V-01`~`V-14`를 따른다. 공통 의미 계약은 [데이터 계약](specs/data-contracts.md)에 있다.

각 단계는 소유 기능을 처음 구현/통합하는 시점이며 공통 M0 계약·M5 회귀는 전 기능에 적용한다. 여러 단계가 적힌 기능은 기반과 종단 통합을 함께 요구한다. M3를 확인할 최소 내장 화면은 M2부터 만들 수 있고 M4는 채널 기능 동등성 완료 시점이다. Python은 참조로 보존하고 계약·재현 사례·실패 복구를 선택해 이식한다. 자동 승인처럼 새 정책에 어긋난 기대값을 그대로 옮기지 않는다.

D-068의 최신 정확한 모델 ID 발견·선택 UI·저장 이력은 M1, 작업 명확성/위험에 따른 효율 배정은 M3에서 연결한다. 선택적 Jev API의 키·요약 전송·비용 원장·fallback 검증과 D-069의 공통 MCP/에이전트 위임 adapter는 후속 구현 범위다. V-02/V-06/V-12의 모의 계약과 실제 계정·청구·Slack 전송 검증을 구분하고, Slack 수신·7일 큐·승인·첨부의 M4 계약은 유지한다.

## 설치·업데이트·실제 서버 배포

최초 설치는 DMG, macOS 업데이트는 Tauri archive와 별도 signature·CDN 정적 JSON이다. 동의가 특정 version/배포물에 대응해야 하며 서명 확인→작업 drain→복구 자원 확보→helper/앱 교체→migration/건강 확인→재개를 core가 조정한다. JSON 자체를 서명된 manifest라 부르거나 다운로드 완료 알림만으로 서명 통과를 가정하지 않는다. 상세는 [설치 계약](specs/install-and-update.md)이다.

서명 입력이 없으면 모의 계약/로컬 구현과 실제 서명 검증을 구분한다. M1 왕복을 M5로 미루지 않는다. CDN에는 불변 artifact를 먼저 올려 접근/서명/무결성을 검증하고 마지막에 JSON을 게시한다. 실패 교체와 updater 내부 temp까지 수명·복구를 확인한다.

중앙은 M4 로컬 통합 후 사용자가 제공한 EC2 VM에 실제 배포한다. 구체 배포/복구안·비밀 저장/회전·HTTPS·Slack 이벤트/설치·영속 큐·재시작·도메인/비용 범위를 먼저 준비하고 그 단계에서 필요한 값을 받는다. 컨테이너/설명서 전달만으로 완료하지 않는다. 설치 파일 배포는 사용자가 맡는다.

7일 만료와 revision 경합은 주입 가능한 시계/fixture로 확인한 뒤 실제 재연결·서버 재시작을 검증한다. 모의 테스트만으로 공급자 로그인·과금·화면 권한·서명·실제 배포 통과를 선언하지 않는다. 최종 추적에는 FEAT별 코드 위치·명세 revision·실제 증거·제한을 남긴다.
