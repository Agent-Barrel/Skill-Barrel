# 파일 정리 방식 적용 시 주의사항

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


Nix식 참조 기반 자동 삭제 + Bazel식 작업별 임시 공간 정리

## 배경

적용하려는 원리는 두 가지다.

- **Nix 방식**: 사용 중인 대상(GC root)에서 참조를 따라가 도달할 수 없는 파일만 정리한다.
- **Bazel 방식**: 작업마다 별도 임시 공간(sandbox)에서 실행하고, 필요한 출력만 밖으로 옮긴 뒤 임시 공간을 통째로 삭제한다.

두 방식 모두 **"지워도 다시 만들 수 있다"**는 전제 위에서 동작한다. 이 전제가 깨지는 파일이 섞여 있는 지점에서 사고가 난다.

---

## 0. 전제 조건

### 재생성 불가능한 파일은 GC 대상에서 분리
실측 로그, 사용자 입력, 손으로 고친 파일처럼 다시 만들 수 없는 파일은 GC 대상 영역 밖에 둔다. Nix/Bazel이 과감하게 지울 수 있는 이유는 전부 입력에서 다시 뽑아낼 수 있기 때문이다.

### 완성된 출력은 immutable로 취급
참조 기반 삭제는 파일 내용이 바뀌지 않는다는 가정에서만 정확하다. 생성 후 수정이 가능하면 참조 그래프가 실제 상태와 어긋난다.

- 대응: 완성된 출력은 읽기 전용으로 잠근다.

---

## 1. 참조 기반 삭제 (Nix 방식)

### 1-1. 참조를 어떻게 알아낼 것인가
가장 큰 설계 포인트. Nix는 출력 파일 안에서 store 경로의 해시 문자열을 스캔해서 참조를 찾는데, 이건 경로에 해시가 들어가 있는 구조라서 가능한 방식이다.

- 대응: 같은 구조가 아니라면 작업이 끝날 때 "무엇을 참조했는지"를 매니페스트나 DB에 명시적으로 기록한다.
- 주의: 스캔 방식은 압축되거나 인코딩된 참조를 놓친다.

### 1-2. root 등록 누락
root로 잡히지 않은 파일은 멀쩡히 쓰는 중이어도 지워진다.

- 대응: 실행 중인 프로세스가 열어둔 파일도 root로 취급한다. (Nix는 /proc을 뒤져서 runtime root를 잡는다.)

### 1-3. 생성과 GC 사이의 레이스
파일은 만들었는데 아직 root 등록 전인 틈에 GC가 돌면 방금 만든 파일이 삭제된다.

- 대응: 작업 시작 시점에 temp root를 먼저 등록한다. 순서는 항상 **등록 먼저, 생성 나중**.
- 대응: GC 실행 중에는 global lock으로 새 등록/생성과 겹치지 않게 막는다.

### 1-4. stale root로 인한 디스크 누수
반대 방향의 사고. 아무도 안 쓰는 root가 남아 있으면 그 밑의 파일은 영원히 안 지워진다. Nix에서 `result` 심링크가 남아서 디스크가 안 비는 게 대표적인 사례다.

- 대응: root마다 생성 주체 / 시각 / 사유를 기록한다.
- 대응: 필요하면 TTL을 걸어서 자동 만료시킨다.

### 1-5. 삭제 자체의 안전성
지우는 도중에 프로세스가 죽으면 "반쯤 지워졌는데 유효하다고 표시된 항목"이 생길 수 있다.

- 대응: 바로 rm 하지 말고 trash 디렉토리로 rename한 뒤 실제 삭제한다.
- 대응: DB의 유효 표시를 먼저 내리고, 그 다음 디스크에서 지운다.

### 1-6. GC 실행 시점
작업 도중에 GC가 돌면 I/O 경합이 생긴다.

- 대응: 디스크 여유 공간 임계치 기반으로 트리거하고(Nix의 min-free / max-free 방식), 한 번에 지울 양의 상한을 둔다.

## 2. 작업별 임시 공간 (Bazel 방식)

### 2-1. 선언하지 않은 출력은 사라진다
출력으로 선언하지 않은 파일은 sandbox와 함께 삭제된다. 실패 시의 로그, 코어덤프, 중간 산출물이 특히 그렇다.

- 대응: 실패 시 sandbox를 보존하는 옵션을 만든다. (Bazel의 `--sandbox_debug`에 해당)

### 2-2. 출력 옮기기의 atomic 보장
임시 공간과 최종 위치가 같은 파일시스템이면 rename 한 번으로 atomic하게 옮겨진다. 파일시스템이 다르면 copy + delete가 되어, 중간에 죽으면 반쪽짜리 출력이 남는다.

- 대응: 임시 공간을 최종 위치와 같은 파일시스템에 둔다.
- 대응: 불가능하면 임시 이름으로 복사한 뒤, 복사가 끝나면 rename한다.

### 2-3. 삭제 경로 안전장치 (가장 위험한 부분)

- 지울 경로가 sandbox base 아래인지 realpath로 검증한다. 변수가 비어서 상위 디렉토리를 날리는 고전적인 사고를 막는다.
- 심링크는 따라가지 않고 링크 자체만 삭제한다.
- sandbox 안에 bind mount를 걸었다면 **umount를 먼저** 한다. 안 그러면 원본이 지워진다.

### 2-4. 남아 있는 자식 프로세스
작업이 남긴 자식 프로세스가 삭제 도중에도 파일을 쓰면, 삭제가 실패하거나 찌꺼기가 남는다.

- 대응: 삭제 전에 작업의 프로세스 그룹 전체를 종료한다.

### 2-5. 크래시 후 고아 sandbox
프로세스가 비정상 종료되면 sandbox가 정리되지 않고 남는다.

- 대응: 시작 시 이전 잔여물을 청소하는 루틴을 둔다.
- 대응: 살아 있는 작업의 sandbox인지 구분할 수 있도록 lock 파일이나 PID 파일을 남긴다.

### 2-6. 삭제 비용
파일 수가 많은 sandbox는 삭제 자체가 느려서 다음 작업이 밀린다.

- 대응: rename으로 먼저 치워 놓고 백그라운드에서 삭제한다. (Bazel도 비동기 삭제를 쓴다.)

### 2-7. Windows 환경
열린 핸들(백신, 인덱서 포함) 때문에 삭제가 간헐적으로 실패한다.

- 대응: 재시도 로직을 넣고, 그래도 실패한 항목은 다음 청소 때 다시 시도한다.

---

## 3. 두 방식을 결합할 때

"sandbox에서 출력 꺼내기"와 "참조/root 등록"은 **하나의 트랜잭션**이어야 한다. 이 둘 사이에 틈이 있으면 방금 꺼낸 출력이 곧바로 GC 대상이 된다.

- 대응: 1-3의 temp root를 sandbox 작업 시작 시점에 걸어 두고, 출력 등록이 끝난 뒤에 해제한다.

---

## 4. 도입 순서

1. **dry-run**: 삭제 대상 목록만 뽑는다. 실제로는 아무것도 지우지 않는다.
2. **검증**: 며칠 돌려 보고 오탐(지우면 안 되는데 대상에 오른 것)이 없는지 확인한다.
3. **trash 단계**: trash로 옮기기만 하고, 실제 삭제는 N일 뒤에 한다.
4. **실삭제 전환**: 문제가 없으면 실제 삭제로 넘어간다.

전 단계에서 삭제 로그(무엇을, 왜 지웠는지 = 어떤 root에서도 도달 불가)를 남긴다. 나중에 "이거 왜 없어졌냐"를 추적할 때 필요하다.

---

## 5. 적용 전 체크리스트

- [ ] 재생성 불가능한 파일이 GC 대상 영역에서 분리되어 있는가
- [ ] 완성된 출력이 읽기 전용으로 잠기는가
- [ ] 참조 관계를 기록하는 방식(매니페스트/DB)이 정해졌는가
- [ ] temp root 등록이 파일 생성보다 먼저 일어나는가
- [ ] GC와 작업 생성이 lock으로 분리되는가
- [ ] root에 생성 주체 / 시각 / 사유가 기록되는가
- [ ] 삭제가 trash rename → 실삭제 순서로 동작하는가
- [ ] 실패 시 sandbox를 보존하는 옵션이 있는가
- [ ] 임시 공간과 최종 위치가 같은 파일시스템인가
- [ ] 삭제 경로 검증(realpath, 심링크, bind mount)이 들어가 있는가
- [ ] 삭제 전에 프로세스 그룹 전체를 종료하는가
- [ ] 시작 시 고아 sandbox 청소 루틴이 있는가
- [ ] 출력 꺼내기와 root 등록이 하나의 트랜잭션인가
- [ ] dry-run 모드와 삭제 로그가 준비되어 있는가
