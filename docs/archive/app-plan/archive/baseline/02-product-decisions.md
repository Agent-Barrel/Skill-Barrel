## 작업 전 평가와 승인

사전 평가는 새로운 조율 역할이다. [model-routing.csv](../../model-routing.csv)의 **주 조율·계획·종합 Astra xhigh**, **어려운 판단·Claude 조사 Fable 5.1 max**, **구현 Opus5 max 및 xhigh 선택**은 유지한다. 평가 역할을 Astra medium으로 추가하는 것이며 기존 모든 역할을 medium으로 낮추지 않는다. 실제 모델 식별자·계정 권한·강도는 FEAT-011에서 확인한다. 설정 모델이 없으면 허용된 대체안을 적용하고 실제 선택을 표시한다.

평가는 신규 요청과 유지보수 요청 모두에서 시작한다. 코드가 없는 신규 컨셉은 예상 범위·필요 환경·불확실성을 평가한다. 기존 프로젝트에서는 저장소 구조, 사용자 변경, 승인 명세, 이전 결정·실행 결과, 코드·문서 간 차이, 외부 연동, 테스트·배포 환경, 맥락의 최신성·누락을 입력으로 삼는다.

출력은 검토 범위와 이유, 읽을 자료, 영향받는 요구·기능·스택, 재사용 가능한 승인, 추가 질문·리서치, 작업 읽기/쓰기 범위, 실행·검증 환경의 부족분이다. 중요한 공백이 남으면 읽기 전용 조사를 확장한다. 새 의존성이나 넓은 영향이 드러나면 평가 revision을 갱신하고 관련 작업 계획을 다시 만든다.

**전체 검토가 전체 재승인을 뜻하지는 않는다.** 요구·기능·스택의 내용과 적용 조건이 그대로면 해당 승인 근거를 재사용한다. 변경되거나 새 판단이 필요한 범위의 revision만 사용자에게 제시한다. 반대로 작은 수정이라고 미승인 요구·기능·스택을 건너뛰지 않는다. 명세 충돌의 해결안 적용 확인(D-020)은 별도 의사결정이며 일반 자동 QA로 대체하지 않는다.

## 기억의 범위·수정·삭제

| 종류 | 저장·참조 규칙 |
| --- | --- |
| 프로젝트 정본 | 해당 프로젝트의 요구·기능·스택·결정·작업 증거. 버전과 출처를 보존하고 다른 프로젝트로 자동 복사하지 않는다. |
| 명시한 공통 선호 | 사용자가 공통으로 적용하겠다고 표현한 선호. 범위·출처·유효 버전을 기록하고 자동 축적한다. 특정 프로젝트 요청을 전체 선호로 승격하지 않는다. |
| 추론한 선호 후보 | 추론 근거와 확신 수준을 표시한다. 확인 전에는 확정 선호나 승인 근거로 사용하지 않는다. |
| 검증된 성공 경험 | 당시 환경·문제·시도·결과·검증 증거·적용 조건을 함께 저장한다. 성공했다는 에이전트의 자기 보고만으로 검증 완료 처리하지 않는다. |

새 맥락 묶음은 현재 요청·프로젝트의 명시적 결정, 적용 가능한 공통 선호, 조건이 맞는 경험 순으로 근거를 구성한다. 이 순서는 누락이나 모순을 숨기는 우선순위가 아니다. 승인된 프로젝트 결정과 새 공통 원칙이 충돌하면 영향을 설명하고 판단받는다. 요약은 원문·검증 증거를 가리키며 불확실성과 생략된 범위를 포함한다.

직접 수정·삭제 때는 영향받는 작업과 다음 중 하나를 기록한다. 초기 추천 설정은 `매번 묻기`이며 사용자가 기본 동작을 바꿀 수 있다.

| 선택 | 실행 의미 |
| --- | --- |
| 다음 작업부터 | 이미 실행에 들어간 TaskContract는 고정된 기억·정책 revision을 유지한다. 아직 시작하지 않은 작업은 새 revision으로 재평가한다. 기존 작업의 재시작·계정 전환도 같은 작업이면 기존 유효 정책을 재구성한다. |
| 관련 작업을 중지하고 지금 적용 | 영향을 받는 작업에 중단 요청을 보내고 중단 확인·현재 외부 효과 확인 후 새 revision으로 재계획한다. 중단 요청 성공을 확인하기 전에는 ‘적용 완료’로 표시하지 않는다. 완료된 외부 동작은 소급 취소되지 않는다. |
| AI 자동 갱신 | 이미 열린 CLI 세션에는 중간 주입하지 않는다. 새 CLI 세션 시작 시 적용 가능한 최신 기억을 선택한다. 다만 기존 작업의 승인·위임 범위를 자동으로 확대하거나 사용자에게 고정된 정책 revision을 덮어쓰지 않는다. |

권한·비용·승인 범위라는 이유만으로 제품이 무조건 기존 작업을 즉시 중지하는 예외를 넣지 않는다. 예를 들어 예산 변경을 다음 작업부터 적용하면 기존 예약과 정책을 분리해 보여준다. 외부에서 실제 자격 증명이 철회되거나 공급자가 실행을 거부한 경우는 기억 적용 선택과 다른 실행 실패이며, 불가능한 작업을 계속 시도하지 않는다.

사용중지는 새 맥락 검색·추천에서 제외하고 과거 근거를 유지한다. 영구삭제는 앱 관리 본문·파생 요약·색인·맥락 사본을 제거하고 삭제 사실만 남긴다(D-046). 기존 작업 유지 선택도 이미 주입된 맥락을 회수했다는 뜻은 아니며, 삭제된 본문을 재시작 때 다시 주입하지 않는다. 앱 자체 백업/내보내기/복원은 제공하지 않고 OS 백업에 맡긴다(D-055). 앱 밖의 백업·공급자 세션에 남은 과거 본문까지 제거를 보장하지 않는다. [삭제·정리 계약](04-resolved-details.md)을 따른다.

## 병렬 실행 계약

각 작업에 읽기 집합 `R`, 쓰기 집합 `W`, 외부 효과 대상 `S`를 선언한다. 두 작업 A/B는 `W_A ∩ (R_B ∪ W_B) = ∅` 및 `W_B ∩ (R_A ∪ W_A) = ∅`이며 외부 자원·권한·예산·실행 환경에도 충돌이 없을 때만 병렬 후보가 된다. 읽기끼리는 가능하지만, 파일 목록이 달라도 공통 스키마나 생성 산출물·배포 환경을 통해 연결될 수 있다.

| 사례 | 기대 동작 |
| --- | --- |
| A가 요구 문서를 수정하고 B가 그 문서를 읽어 구현 | A의 변경·필요한 승인·새 버전 확정 후 B 시작. 이전 문서로 동시에 구현하지 않는다. |
| A/B가 서로 독립된 파일을 수정하고 같은 고정 명세를 읽음 | 읽기·쓰기 및 외부 자원 독립성이 확인되면 병렬 가능. 결과 통합 시 입력 hash와 검증 결과 재확인. |
| 다른 프로젝트가 같은 실제 저장소·DB·포트·배포 대상을 사용 | 프로젝트 이름이 달라도 같은 자원으로 잠금·순서를 관리. |
| CLI가 필요한 범위를 미리 한정할 수 없음 | 저장소 전체 또는 해당 외부 환경을 보수적으로 범위에 넣고 직렬 실행. 프롬프트 약속만으로 독립성을 보장하지 않는다. |
| 실행 중 새 참조·쓰기 필요가 발견됨 | 범위를 넓혀 계속하기 전에 관련 작업을 보류하고 의존성·승인·입력 버전을 재평가. 확인된 손상·오염 결과는 유효한 결과로 합치지 않는다. |

worktree는 작업 디렉터리 분리 수단이다. 같은 논리 문서를 다른 사본에서 읽었다고 의존성이 사라지지는 않는다. 새 문서 revision이 필요한 작업은 선행 변경 이후 시작한다. 실제 접근 제한·관찰의 구현 가능성은 V-04로 검증하며 실패하면 독립성이 입증된 단위 외에는 직렬 실행한다.

## 예산·계정·위임

한 작업공간의 전체 프로젝트가 월간 추가 AI 지출 원장을 공유한다. `구독 포함 사용량`, `API 가격 환산액`, `실제 추가 청구액`, `아직 확정되지 않은 추정액`을 다른 필드로 표시한다. 선충전 크레딧도 소비한 달에 계상하고 구매·충전은 별도 표시해 이중 차감하지 않는다(D-050). 두 작업이 같은 잔여 예산을 동시에 예약하지 않도록 실행 전 예약과 정산을 트랜잭션으로 처리한다. 월 변경으로 미확정 예약을 소멸시키지 않는다.

| 모드 | 실행 조건과 한계 |
| --- | --- |
| 엄격 | 명시적 추가 과금 허용·월예산이 있고, 경로별 강제 상한 또는 보수적인 최대 비용을 확인할 수 있어야 한다. 청구 지연·미확정 최대 비용 때문에 한도를 보장할 수 없는 유료 경로는 사용하지 않고 이유를 표시한다. 토큰 카운터만으로 실제 청구액의 절대 상한을 보장하지 않는다. |
| 추정 | 동일한 허용·월예산 아래 추정 비용을 예약하며 실행할 수 있다. 추정 근거·오차·청구 지연·초과 가능성을 보여주고, 잔여 예산을 초과할 것으로 예상되는 새 작업은 대기시킨다. 무제한 지출 허용 모드가 아니다. |

로컬 예산은 이 제품이 시작한 사용을 통제한다. 같은 AI 계정을 다른 앱에서도 쓰는 경우 공급자의 신뢰할 수 있는 전체 사용량·상한이 없으면 계정 전체 청구를 보장할 수 없다. 프로필 별칭이나 ChatGPT 로그인 확인만으로 추가 사용료가 전혀 없다고 판정하지 않는다.

외부 서비스 작업은 프로젝트별 `환경·대상·행동·비용·기간/유효 조건` 위임을 사용한다. 이미 위임한 범위는 반복 확인하지 않는다. 범위를 넓혀야 하면 실제 변경 대상·영향·비용을 제시한다. 로그인·MFA·OS 권한과 전경 화면 사용 시간 합의는 별도 조건이다. 제품의 회원가입·과금 기능 제외가 AI 공급자·Slack·인프라 서비스의 인증이나 요금까지 없애는 것은 아니다.

## 로컬·중앙·Slack의 사용자 경험

로컬 내장 콘솔과 중앙 콘솔은 같은 프로젝트·요청·질문·승인 상태를 표시한다. 정본은 Mac이며 중앙은 표시용 데이터를 중계한다. 중앙에서 UI를 제공해도 React의 상호작용은 접속한 브라우저에서 실행된다. 서버 호스팅의 이점은 로컬 UI 서버·배포 의존성을 없애고 다른 장치에서 접속할 수 있다는 데 있다. Mac에서 브라우저를 열면 그 브라우저의 메모리·CPU 사용은 남는다.

인터넷 HTTPS 원격 접속을 허용하며 VPN은 필수가 아니다(D-057). 제품 계정 없이도 원격 접근 권한은 필요하다. 짧게 유효한 연결 코드/QR, 로컬에서 확인하는 연결 승인, 브라우저별 취소 가능한 권한을 사용한다. Slack은 OAuth와 로컬 연결 확인을 거친 본인 계정만 조작 가능하며 DM 기본·프로젝트별 채널 선택을 지원한다(D-043/D-061). 공개 링크나 다른 채널 구성원 자격만으로 프로젝트를 조작할 수 없다. 수락 전/후 편집·삭제, revision 승인 버튼, 첨부 수명은 [세부 계약](04-resolved-details.md)을 따른다.

Mac 연결이 끊기면 중앙은 연결 상태와 재연결 안내를 표시한다. 상세 자료를 오프라인 이력 서비스로 보관하지 않는다. 일반 중앙 콘솔의 오프라인 수정·승인은 받지 않는 설계 기본값을 사용하며, 화면에서 전달되지 않은 상태를 명확히 표시한다. Slack에서 받은 요청·답변은 D-038에 따라 서버가 보관·재시도한다.

‘Slack 수신’, ‘Mac 전달’, ‘로컬 적용’, ‘작업 완료’를 다른 상태로 표시한다. 7일은 **Mac에 넘길 전달 대기 유효기간**이며 이미 Mac이 수락한 장기 작업을 7일 후 취소하는 규칙이 아니다. 재전달은 같은 명령 ID를 사용하고 첫 유효 적용만 인정한다. 늦은 승인·답변은 현재 대상 버전과 맞는지 확인하고 맞지 않으면 이유와 현재 필요한 판단을 안내한다. Slack 자체에 남은 메시지의 보존 기간까지 이 제품이 보장하지 않는다.
