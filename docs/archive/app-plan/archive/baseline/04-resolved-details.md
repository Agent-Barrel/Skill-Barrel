# 확정된 세부 결정과 구현 계약

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


인터뷰 기준일: 2026-09-17. 최종 반영일: 2026-09-18. 이 문서는 후속 인터뷰 답변을 그때마다 기록하는 최신 결정 원장이다. **이번 세션의 작업은 `docs/plan` 문서 수정·검증뿐이다. 제품 코드 작성, 설치, 인증 변경, 배포를 수행하지 않는다.** 다음 세션은 이 디렉터리에서 결정·설계·검증 조건을 읽고, 그 세션에서 요청받은 범위에 따라 작업한다. ‘Implement the plan.’만으로 이번 문서 작업을 제품 구현 승인으로 확대하지 않는다(D-065).

원문 `00-original-flow.md`는 보존한다. 결정 우선순위는 최신 사용자 답변 → 최신 결정 ID → 기존 기준선이다. 업데이트 기획은 Tauri updater의 현행 결정·계약만 유지하며 이전 도구 선택과 교체 이력은 남기지 않는다(D-066). **사용자 결정**, 이를 충족하기 위한 **구현 계약**, 변경 가능한 **초기 설정**, 아직 실행하지 않은 **검증 조건**을 구분한다. 문서 반영은 제품 구현 완료·실험 통과·기능명세 전체 승인과 다르다.

## 2. 이후 인터뷰의 저장 절차

1. 한 주제의 근거·추천·대안을 제시하고 필요한 판단 하나를 질문한다. 이미 확정된 정책은 다시 묻지 않는다.
2. 답변을 받으면 다음 질문보다 먼저 해당 결정 ID, 사용자 결정과 설계 해석, 대체한 이전 결정, 남은 기술 검증을 이 원장에 기록한다.
3. 같은 작업 구간에서 관련 요구사항·기능·라우팅·아키텍처의 내용을 갱신하고 참조를 검증한다. 동기화가 아직 끝나지 않았다면 해당 파일과 남은 반영을 명시한다.
4. 사용자가 답하지 않은 추천을 확정으로 승격하지 않는다. 답변 대기 중에는 그 결정에 의존하지 않는 조사·문서 보완을 수행한다.
5. 세션 종료 전 현재 범위·마지막 결정 ID·미확정 항목·다음 행동을 README에 남긴다. 별도 대화나 임시 요약을 읽어야만 의도를 복원할 수 있는 상태로 끝내지 않는다.

## 3. 작업 시작·판단·실패 계약

아래는 확정 정책을 실행할 수 있도록 구체화한 구현 계약이다. 프로젝트마다 달라지는 사용자 의도를 앱의 전역 자동값으로 고정하지 않는다.

| 상황 | 필수 동작·경계 | 검수 사례 |
| --- | --- | --- |
| dirty 저장소 | 현재 branch/HEAD, staged·unstaged·untracked 변경을 구분해 설명한다. 사용자에게 보존할 내용과 시작 브랜치를 받는다. snapshot/별도 commit/stash 등 선택안의 복구 방법을 설명하고 선택한 방법만 수행한다. | unrelated staging 보존, untracked·binary·submodule 상태 누락 없음, 별도 브랜치 생성만으로 보존 성공 처리하지 않음. |
| 브랜치 선택 대기 | 읽기 전용 분석·설계처럼 대기 판단과 독립인 작업은 가능하다. 선택 전 원본 변경·자동 commit/stash/reset·충돌 통합은 하지 않는다. | 브랜치 답변을 기다리며 관련 없는 조사 수행, 종속 구현은 시작하지 않음. |
| 비Git·원격 저장소 | 비Git 폴더는 자동 폐기·거절하지 않고 분석 후 Git 초기화/복사/대상 선택을 질문한다. clone은 앱 소유 공간에 만들고 선택한 시작점을 기록한다. | 접근 실패·부분 clone은 앱 소유 사본만 정리. 사용자 원본을 clone 실패 정리 대상으로 삼지 않음. |
| 외부 편집·통합 충돌 | 실행 전과 결과 통합 전에 HEAD·입력 hash·기준 revision을 재검사한다. 충돌 범위를 격리하고 이미 위임된 통합 범위를 넘는 해결이나 명세 충돌 적용은 설명 후 판단받는다. | 사용자가 중간에 고친 파일·다른 작업의 staging을 덮어쓰지 않음. 전체 `git clean -fdx`를 정리 수단으로 사용하지 않음. |
| 진전 없는 오류 | 오류 분류, 원인 가설, 이전 방법과 다른 점, 실행 결과를 시도 이력으로 남긴다. 증거가 바뀌지 않은 같은 시도만 무한 반복하지 않는다. | 경로·숫자를 전부 지운 fingerprint로 다른 실패를 합치지 않음. 설정 가능한 turn/time/cost 상한에 닿으면 보존·대기하며 실패를 완료로 바꾸지 않음. |
| 접근법 변경 | 승인 범위 안의 기술적 대안은 이유를 설명하고 수행한다. 명시적 필수 방법·스택·위임·비용 범위를 바꾸는 안은 먼저 사용자에게 판단받는다. | 인증 만료·정책 거절을 quota 소진과 구분. 공급자 정책 거절을 계정 순환으로 우회하지 않음. |
| 승인 전 실험 | `ExperimentContract`에 목적, 판단할 질문, 성공/실패 기준, 입력·출력·쓰기 경계, 예산·권한·정리 조건을 둔다. 별도 작업 공간에서 수행하고 결과를 조사 근거로 연결한다. | 원본 저장소·운영 인프라 쓰기 없음. 실험 결과가 있어도 미승인 제품 구현은 시작하지 않음. |
| 답변·승인 경합 | 일반 답변과 revision 승인 버튼을 서로 다른 command 종류로 처리한다. 첫 유효 답변만 조건부 적용한다. 상충하는 늦은 답변은 변경 검토 대상으로 제시한다. | Slack과 콘솔의 동시 승인·중복 클릭·오래된 질문 답변으로 이중 적용이나 무조건 덮어쓰기가 없음. |

세 승인 이후에도 승인된 문서·정책을 참조한 작업 계획이 선행한다. 답변을 기다린다고 모든 작업을 멈추지는 않지만, 해당 답변을 가정해야만 진행할 수 있는 작업은 시작하지 않는다. 필수 검수기준과 필요한 실제 설치·배포·사용 확인이 모두 충족되어야 자동 완료한다.

## 4. 드라이버·설정·금액 계약

### 드라이버 선택과 세션 수명

Codex는 공식 app-server stdio, Claude는 공식 stream-json을 기본 어댑터로 한다. Claude PTY는 JSON 경로에서 지원하지 못하는 대화형 기능을 보완한다. 시작 전에 `DriverCapabilities`로 CLI 버전, 인증 유형, 실제 모델·effort, 질문·permission·cancel·resume 지원을 확인한다. JSON 경로가 불명확한 실행 중 실패했다고 즉시 PTY로 같은 작업을 다시 실행하지 않는다. 먼저 기존 프로세스 중단과 외부 효과를 확인한 뒤 새 attempt에서 앱 ContextBundle을 재구성한다.

Claude `-p`는 구독 인증 동작을 실제로 검증한다. `--bare`는 OAuth/Keychain 구독 로그인 경로를 읽지 않으므로 이 제품의 구독 격리 기본값으로 쓰지 않는다. 구조화 권한 요청과 사용자 질문의 왕복을 검증하며 `--permission-prompts none`, `bypassPermissions` 등으로 대화를 없애서 검증 성공으로 처리하지 않는다. Codex도 설치 버전의 protocol/schema와 승인 정책을 확인하며 기존 Python의 `never`·`danger-full-access` 기본값을 그대로 이식하지 않는다.

설정은 앱 관리 기본 환경 → 사용자가 선택 도입한 항목 → 평가한 프로젝트 지침과 적용 가능한 관리 정책의 실제 우선순위를 기록한다. 이 순서는 공식 CLI의 관리 정책 우선순위를 바꾼다는 뜻이 아니다. 개인 디렉터리·자동 훅·MCP·메모리를 통째로 복사하지 않는다. `setting-sources`·명시적 settings·strict MCP 등 사용 가능한 공식 옵션을 검증하고 차단할 수 없는 묵시 로딩은 숨기지 않는다. 설정 도입 확인과 계정 로그인은 별도 UI다.

실행파일은 알려진 설치 위치와 명시적 경로 입력을 통해 찾는다. GUI 앱에서 셸 dotfile을 실행해 PATH를 얻는 방식을 필수로 하지 않는다. 기존 CLI가 호환되면 재사용하며 앱 관리 버전이 필요할 때만 공식 출처·무결성·라이선스를 확인해 별도 경로에 둔다. 활성 세션이 사용하는 버전은 정리·교체하지 않는다. 인증 비밀을 앱 메모리 원장·로그·중앙에 복제하지 않는다. `CODEX_HOME`/`CLAUDE_CONFIG_DIR` 분리와 실제 Keychain/계정 격리는 각각 검증한다.

### 월간 금액과 정책 고정

`BudgetReservation`은 workspace·정책 revision·통화·시간대·소비 기간·예약액·근거·정산 상태를 가진다. 충전 구매와 실제 소비를 다른 ledger 종류로 기록한다. 공급자 사용 증거가 기간별 분리를 제공하면 그 기간에 귀속하고, 월 경계를 넘은 사용의 정확한 분리가 불가능하면 미확정으로 표시해 보수적으로 예약한다. 월 변경으로 기존 미확정 예약을 소멸시키거나 다음 달 잔여액을 이중 사용하지 않는다. 통화·시간대는 유료 기능 첫 설정에서 선택하고 월별 기준을 고정한다. 실패한 작업도 실제 유료 소비를 계상하며 취소·실패만으로 미확정 예약을 무료 정산하지 않는다.

사용자가 ‘다음 작업부터’를 선택한 변경은 실행 중 TaskContract의 기억·위임·예산 revision을 바꾸지 않는다. 같은 작업의 앱 재시작·계정 전환도 이를 유지한다. 다만 영구삭제한 기억 본문은 다시 주입할 수 없으므로 삭제 표식과 재구성 제한을 표시한다. 자동 기억 갱신은 새 CLI 세션에만 적용하며 권한·비용 범위를 확대하지 않는다. 공급자가 실제 권한을 철회한 경우는 정책 적용 유예와 달리 실행 불가 상태다.

## 5. 원격·Slack·첨부 계약

### 인터넷 연결과 중앙 보존

Mac이 중앙으로 outbound TLS 연결을 만든다. 등록한 브라우저는 HTTPS로 같은 React UI를 사용한다. `protocol_version`, 지원 명령·schema, 앱/helper/DB 호환 범위를 handshake하며 호환되지 않는 명령은 명시적으로 거부한다. 업데이트를 미룬 앱을 최신 명령으로 조용히 구동하지 않는다. 코드/QR은 짧은 수명의 1회 연결 수단이고 Mac에서 브라우저 연결을 확인한다. 권한 취소는 이후 조회·명령을 막고 기존 연결을 닫는다. 세션/코드 TTL은 변경 가능한 운영값으로 구현하고 실제 보안·사용성 검증 후 고정한다.

중앙은 실행·프로젝트 정본을 보관하지 않는다. Mac 오프라인이면 일반 콘솔의 새 수정·승인을 받지 않는다. 이미 보낸 명령의 결과가 불명확할 때는 같은 ID로 상태를 조회하며 새 명령으로 중복 실행하지 않는다. 연결 끊김 후 상세 화면 상태·캐시를 제거하고 로컬 콘솔은 계속 사용할 수 있다.

### Slack 수신·편집·삭제의 경합

| 항목 | 구현 계약 |
| --- | --- |
| 발신자 확인 | OAuth 설치와 별도로 Mac이 승인한 `team_id + user_id`를 저장한다. 모든 사용자 명령·버튼은 이 주체와 Mac 연결을 검사한다. 다른 사람·봇의 메시지로 작업을 만들지 않는다. |
| 대화 대상 | DM 기본, 프로젝트별 지정 채널 선택. 채널의 새 요청은 멘션으로 시작하고 알려진 요청 thread 답변은 멘션 없이 받는다. 프로젝트가 불명확하면 선택 요청이며 임의의 최근 프로젝트를 변경하지 않는다. |
| 전달 원장 | `source_key=(team, channel, message_ts)`, source revision, 불변 `command_id`, 대상 revision, 생성·만료·superseded 상태를 저장한다. 동일 이벤트 retry는 같은 ID, 본문이 실제 바뀐 편집은 새 불변 ID로 관리한다. 같은 command ID 아래 내용을 바꾸지 않는다. |
| 수신 확인 | Slack 서명·재전송 검증 후 영속 큐에 저장하고 빠르게 ACK한다. 메모리에만 저장하고 성공 ACK하지 않는다. Slack의 제한된 재시도보다 긴 중앙 장애에서 ‘절대 유실 없음’을 약속하지 않는다. |
| 수락 전 편집 | 최신 source revision이 이전 pending 세대를 대체한다. Mac 수락 명령과 supersede/cancel 판정은 로컬 inbox의 조건부 트랜잭션으로 순서를 정한다. 중앙의 전송 시작/ACK 미수신만으로 미수락이라 단정하지 않는다. |
| 수락 후 편집 | Mac receipt가 accepted/applied이면 새 변경 요청으로 연결한다. 이전 실행 기록을 덮어쓰지 않고 영향·재승인을 검토한다. 역순·중복 metadata 편집은 실제 내용·revision 비교로 제거한다. |
| 삭제 이벤트 | `message_deleted`의 삭제 행위자가 항상 주어지는 것으로 가정하지 않는다. 서명 검증된 이벤트의 정확한 기존 source mapping으로 전달 원본 철회를 처리한다. wrapper 사용자를 명령자로 추정하지 않는다. 미매핑 삭제는 작업 명령이 될 수 없다. |
| 수락 후 삭제 | 메시지 삭제만으로 작업을 중단하지 않는다. 기존 요청을 보존하고 가능한 채널/콘솔에 명시적 중단 방법을 안내한다. 삭제 안내 전송 실패를 작업 취소로 처리하지 않는다. |
| 승인 | 버튼에 approval 종류·question ID·target revision·command ID를 연결하고 서버/코어가 발신자·기대 버전·현재 상태를 검증한다. 버튼 라벨의 자연어만 신뢰하지 않는다. |
| 7일 만료 | 최초 전달 대기의 서버 수신 시각을 기준으로 최대 7일. pending 세대 편집으로 무기한 보관 시간을 갱신하지 않는 초기 설계다. 이미 수락된 작업은 7일 후 자동 취소되지 않는다. |
| 본문 정리 | Mac 영속 수락 또는 만료·취소가 확인되면 중앙 본문과 큐 전용 첨부 사본을 제거한다. receipt·삭제 사실은 본문 없이 유지한다. 큐 body 저장 영역을 장기 snapshot/PITR 보존에 넣어 만료를 우회하지 않는다. 필요시 본문별 키 폐기와 실제 복원 불가 검증을 병행한다. |

대기 메시지는 `received → queued → accepted → applied`를 작업의 running/completed와 구분해 표시한다. 큐 전송 보장과 외부 시스템의 정확히 한 번 실행은 별개다. 외부 효과는 idempotency/receipt/상태 조회로 재개하며 결과 불명이면 `recovery_required`로 남긴다.

### 첨부 입력

`Attachment`에는 출처(console/Slack file ID), 파일명·MIME·실제 크기·hash, 업로드 상태, 프로젝트/요청, named consumer, 보존 이유와 파생 요약·근거를 저장한다. Slack 비공개 파일은 정식 권한으로 내려받고 링크만 있다고 입력 확보 완료로 표시하지 않는다. 콘솔 업로드도 완료·hash 검증 이후에 분석한다. 지원 형식은 이미지·PDF·CSV·텍스트이며 지원하지 않는 형식·크기 초과·암호화/손상 파일은 구체적인 이유와 가능한 대안을 제시한다. 크기·개수·보관 공간 한도는 설정으로 구현하고 실측해 기본값을 정한다.

파일명은 표시 정보이며 저장 경로는 앱이 생성한 resource ID를 사용한다. 경로 탈출·symlink·압축 폭탄·부분 업로드·용량 부족을 처리하고 자료 속 지시를 사용자 승인·권한으로 취급하지 않는다. 원본을 해석하지 못한 경우 임의 요약으로 증거를 채우지 않는다.

Mac이 수락할 때 필수 입력도 durable하게 확보했는지 확인한다. 필수 파일이 삭제/만료돼 확보되지 않았으면 ‘입력 누락으로 대기’라는 명시적 receipt를 남기고 사용자에게 복구 입력을 요청한다. 분석 가능한 요청으로 수락했다는 허위 상태를 만들지 않는다. 중앙의 일시 사본은 전달 큐와 함께 제한하고, 로컬 사본은 D-063의 마지막 소비자 종료 후 정리한다. Slack 자체 파일·사용자 원본은 앱 사본 정리 대상이 아니다.

## 6. 관리자 보조 서비스와 절전

일반 UI·Rust core·CLI는 로그인한 일반 사용자 권한으로 실행한다. 화면 조작은 해당 GUI 세션의 사용자 프로세스가 담당한다. root helper는 앱 번들에 포함하고 `SMAppService` LaunchDaemon으로 등록한다. 작은 Objective-C/Swift bridge는 ServiceManagement·XPC·전원/권한 상태 같은 필요한 macOS API에 한정한다.

`PrivilegedOperation`은 operation ID, 요청한 로컬 task/attempt, 대상 사용자·허용 행동·실제 경로/자원, 유효시간, delegation revision, 기대 사전 상태, 결과 receipt·복구 방법을 가진다. helper는 연결자의 코드 서명·지정 requirement/Team ID·audit identity와 요청 범위를 자체 검사한다. 보조 서비스 접근 소켓·XPC를 열어 둔 사실이나 UID만으로 임의 root 실행을 허용하지 않는다. 원격 payload나 AI가 만든 검증되지 않은 shell 문자열을 그대로 root shell에 전달하는 API는 두지 않는다. 필요한 작업 종류는 좁은 operation으로 추가하고 승인된 대상·인자·작업 소유권을 검증한다.

최초 실행은 `/Applications`의 설치 위치·서명·helper 등록 상태를 확인하고 필요한 관리자 승인·System Settings 안내를 제공한다. 권한 거절/철회·로그아웃·helper 프로토콜 불일치 시 관련 작업만 보류한다. helper가 존재해도 SIP/TCC·보안 정책을 우회할 수 없으며 화면 권한·접근성·파일 접근 등의 상태는 각각 확인한다. 권한이 없는 테스트를 통과로 표시하지 않는다.

절전은 `follow_os`, `prevent_idle_sleep_on_ac_while_active`, `prevent_idle_sleep_while_active`의 초기 설정안을 사용한다. Slack/콘솔에서 같은 설정 revision을 변경한다. 필요한 작업이 끝나거나 중단되면 power assertion을 해제하고 crash·배터리/AC 변경·절전/깨우기 이후 상태를 재평가한다. 강제 잠자기를 막는 루프나 잠금 해제 자동화는 만들지 않는다.

## 7. Tauri updater·릴리스 계약

### 배포물과 사용자 동의

최초 설치용은 Developer ID 서명·공증된 DMG다. 자동 업데이트는 **Tauri v2 updater의 `.app.tar.gz` 및 `.app.tar.gz.sig`**를 사용한다. `createUpdaterArtifacts=true`, 고정 public key, HTTPS endpoint를 설정한다. 업데이트 artifact의 서명과 Apple 코드 서명·공증은 별개의 검증이다. 출처: [Tauri updater](https://v2.tauri.app/plugin/updater/), [macOS 서명](https://v2.tauri.app/distribute/sign/macos/).

2026-09-18 조사에서는 공식 최신 안정 `tauri-plugin-updater 2.10.1`을 출발 후보로 확인했다. 제품 dependency를 이미 설치·확정한 뜻은 아니며 M1에서 core/API·OS와 함께 검증 후 lockfile로 고정한다. 현재 스택과의 적합성·구체 소스 제약은 [RES-024](research.md#res-024--tauri-updater로-확정한-자동-업데이트)에 기록했다. 효과는 Rust core·React·CDN 흐름의 통합 단순화이며 성능이나 장애 복구가 자동으로 보장된다는 뜻은 아니다.

정적 CDN JSON에는 `version`, `notes`, `pub_date`, `platforms.darwin-aarch64.url`, `platforms.darwin-aarch64.signature`를 둔다. signature는 `.sig`의 **내용**이며 파일 URL이 아니다. 이 JSON은 Tauri가 artifact에 하는 서명 검증과 동일한 ‘서명된 manifest’로 주장하지 않는다. HTTPS·배포 권한·불변 artifact 경로를 통제하고 서명된 번들 안의 앱/helper/DB 호환 정보도 확인한다. 초기 지원 외 플랫폼 항목을 가짜 URL로 채우지 않는다.

자동 확인 후 새 버전과 변경·중단 영향을 표시하고 사용자가 해당 릴리스의 설치에 동의해야 진행한다. 동의는 버전+artifact 식별자에 묶고 다른 배포물로 바뀌면 다시 받는다. 나중에 선택하면 강제 설치하지 않는다. 자동 확인 주기·다운로드 보관 한도는 조정 가능한 설정이며 정책으로 미리 합의된 숫자는 없다.

### 업데이트 상태와 복구

`UpdateState`는 `available → awaiting_consent → downloading → verified → draining → installing → restarting → health_check → completed`와 `deferred/failed/recovery_required`를 저장한다. 다운로드/설치를 분리하고 Rust core의 coordinator가 수행한다. 내장 UI에서 updater의 저수준 설치 API를 직접 호출해 동의·drain을 우회하지 않도록 capability를 좁힌다. 원격 UI는 허용된 제품 명령만 전송하며 네이티브 updater 권한을 받지 않는다.

`download()`의 성공 반환을 확인한 뒤에만 `verified`로 전이한다. v2.10.1의 download 완료 callback/Finished 이벤트는 서명 검증 전에 발생한다. `install(bytes)`는 별도 검증을 하지 않으므로 검증된 동일 bytes만 전달한다. 초기 경로는 같은 실행에서 검증한 bytes를 사용하고, crash·앱 재시작으로 이를 잃으면 다시 다운로드·검증한다. 장기 캐시 재사용을 추가한다면 다시 읽은 최종 bytes의 서명·릴리스 일치를 설치 직전에 검증하는 계약부터 추가한다.

기본 다운로드는 전체 archive를 RAM에 보유한다. updater bytes를 UI로 복사하지 않고 크기·메모리·디스크 여유를 검사한다. 크기 상한 초과·긴 drain 대기·취소에서는 다운로드 future/bytes를 해제하고 대기 상태를 보존한다. 실제 전송량에 따른 취소·timeout·큰 번들 peak RAM을 검증한다. 설치는 blocking 작업에서 실행하되 Tauri main event loop는 관리자 인증을 처리할 수 있게 유지한다. UI/main thread에서 동기 install로 대기하지 않는다.

drain은 새 작업을 받되 실행을 시작하지 않도록 대기시키고 실행 중 작업·CLI·외부 효과·helper 작업을 안전한 체크포인트까지 정리하는 단계다. DB/outbox/예약·자원 참조를 저장하고 기존 실행자가 실제로 멈췄는지 확인한다. 비중단 구간이 끝나지 않거나 외부 결과가 불명확하면 설치를 미루며 임의 timeout으로 강제 종료하지 않는다. 사용자 승인 없이 ‘종료할 때 설치’로 바꾸지 않는다.

번들 교체 전 helper 작업을 drain하고 등록·실행 상태를 기록한다. 새 앱은 app/helper/protocol/schema 호환성을 검사하고 SMAppService 등록·재연결 상태를 확인한 후 스케줄러를 다시 연다. 옛 helper가 새 파일로 자동 교체·재시작됐다고 가정하지 않는다. 구체 unregister/register/재시작 순서는 서명된 최소 앱 왕복 실험에서 확정하고 실패 시 기존 정상 버전으로 실행을 유지하거나 명시적 복구 상태로 남긴다.

**설치 중 오류의 자동 rollback을 플러그인 보장으로 두지 않는다.** v2.10.1에는 기존 번들 이동/제거 후 새 번들 이동이 실패할 수 있는 경계가 있고 완전한 복원 전이가 없다. `installing` 진입 전에 번들 밖의 앱 소유 공간에 재시작 가능한 update journal, 현재/목표 버전·서명/hash·DB 호환 범위, 복구할 수 있는 서명된 배포물과 공간을 확보한다. 플러그인의 내부 임시 backup만을 복구 근거로 삼지 않는다. 이는 이번 업데이트 동안 필요한 제한적 복구 자원이며 사용자 백업 제품 기능이 아니다.

기존 앱이 남아 있는 실패와 번들 경로가 없어지거나 불완전한 실패를 구분한다. 후자의 경우 앱 내부 UI만으로 복구가 가능하다고 하지 않는다. 자동 복구 경로의 실행 주체·고정 대상·서명 검증·권한·DB 호환을 M1에서 검증하고, 불가능한 경우 서명 DMG로 앱 실행 파일을 재설치하는 복구 절차를 준비한다. 이 절차에서 workspace 데이터를 초기화하지 않는다. 정상 업데이트는 동의 기반 자동 설치를 유지한다. 필요한 복구 자원을 확보하지 못한 상태에서는 설치를 시작하지 않는다.

DB migration은 적용 전 무결성·호환 범위를 확인하고 트랜잭션 가능한 단위를 사용한다. 필요한 제한적 migration 복구 파일은 작업 자원이며 건강 확인 후 정리한다. 이는 D-055에서 제외한 사용자 백업/내보내기 기능이 아니다. migration 후 구버전이 읽지 못하는 DB에 실행 파일만 자동 롤백하지 않는다. 자동 복구가 안전하지 않으면 복구 안내·진단 근거를 보존하고 실행을 보류한다.

Tauri macOS updater 소스에는 쓰기 권한이 부족할 때 관리자 권한을 요청하는 경로가 있다. 이것만으로 앱 번들 helper의 등록·승인·재연결이 해결되는 것은 아니다. root helper를 updater를 대신하는 무제한 설치기로 만들지 않고 실제 선택 버전의 권한·실패 경로를 검증한다. [공식 updater 소스](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs).

인터넷 HTTPS 배포에서 `dangerousInsecureTransportProtocol`, `dangerousAcceptInvalidCerts`, `dangerousAcceptInvalidHostnames`는 비활성으로 유지한다. 자동 downgrade를 켜서 복구를 구현하지 않는다. 초기 지원 설치 위치는 `/Applications`의 정상 앱 번들이며 DMG에서 직접 실행·translocation·쓰기 불가·다른 volume/특수문자 경로는 설치 전 진단한다. 표준 위치로 이동/재실행이 필요하면 설명하고 사용자 파일을 임의로 이동하지 않는다.

플러그인이 내부에 만드는 temp 경로는 앱 원장에 저절로 등록되지 않는다. M1에서 선택한 버전의 생성·삭제 경계를 관찰해 앱 소유 update attempt와 연결하고 crash 후 소유권을 확인할 수 있는 정리 어댑터를 마련한다. 별도 설치 호스트가 필요하면 그 자식 시작 때 전용 temp root를 부여하는 안을 검증한다. 멀티스레드 core의 전역 `TMPDIR`를 설치 직전에 바꾸거나 시스템 temp 전체를 이름 prefix로 지우지 않는다. 소유권·오류를 관찰할 수 없는 부분은 upstream 개선 또는 좁은 어댑터 변경 대상으로 명시하고 V-09 통과 전 ‘모든 잔여물 정리’ 완료로 표시하지 않는다.

### CDN 게시와 배포 입력

릴리스는 변경 불가능한 버전 디렉터리에 앱/DMG/updater archive/signature/호환 정보/검증 결과를 모은다. 중첩 helper까지 서명·공증하고 최종 바이트 기준 서명·hash를 확인한다. **artifact 업로드 → CDN 다운로드·무결성 확인 → static JSON 갱신** 순서로 게시한다. 아직 다운로드할 수 없는 버전을 manifest로 먼저 알리지 않는다. 설치 동의 후 내려받는 artifact가 바뀌지 않도록 동일 버전 경로를 덮어쓰지 않는다. updater signing key는 앱·저장소·공개 버킷에 넣지 않는다.

초기부터 서명된 최소 앱 vA/vB로 DMG 설치→최초 권한→helper 허용 작업→Tauri update→새 helper 재연결→작업 재개를 검증한다. 서명 자격·CDN·EC2가 없으면 코드/로컬 실험과 외부 검증 상태를 분리하며 통과를 만들어내지 않는다. 필요한 값은 해당 단계에서 구체 산출물을 준비한 뒤 요청한다. 실제 EC2 배포와 공개 HTTPS/Slack 왕복은 향후 제품 납품 범위다.

## 8. 모든 작업의 디스크 정리

정리는 에이전트가 기억을 보고 임의 경로를 지우는 방식이 아니라 **생성 시 등록한 소유권과 마지막 소비자 참조에 따른 수명 관리**로 구현한다. AI는 보존 이유·다음 소비자를 제안할 수 있지만 파일 삭제 권한이나 완료 판정의 정본은 아니다.

`ManagedResource` 필수 필드: resource ID, 종류, 앱 소유 root/상대경로, 생성 task/attempt, hash·크기, consumer ID 집합, retain reason, lease/process 참조, 승격된 사용자 산출물 여부, 상태(`allocated/active/released/cleanup_pending/deleted/cleanup_failed`), 마지막 오류·재시도 시각. 소비자는 ‘나중에 쓸 수도 있음’이 아니라 구체 작업/검수 ID로 연결한다. 생성 전에 자원 등록을 영속화하고 파일 생성과 DB 반영 사이 crash의 orphan을 복구 스캔으로 조정한다.

| 자원 | 보존·정리 시점 |
| --- | --- |
| 첨부 앱 사본·추출 텍스트·변환 이미지 | 분석만으로 곧바로 지우지 않는다. 이름 있는 후속 구현/검증 소비자가 끝난 뒤 필요한 요약·출처·증거를 보존하고 사본·불필요한 파생 파일 제거. |
| 실험·빌드·테스트 임시 공간 | 작업별 격리 디렉터리에 생성. 채택한 결과·필수 검증 증거를 정식 산출물로 승격하고 나머지 제거. 실패 재현에 필요한 파일은 이유와 다음 소비자를 기록. |
| clone·worktree | 앱이 만든 것만 관리. 검증된 변경 통합·필요 결과 보존·사용 프로세스 종료를 확인한 뒤 해제. 사용자가 제공한 저장소는 정리 대상이 아님. |
| CLI transcript·PTY 로그·화면/브라우저 trace | 필요한 진단·검수 근거만 보존하고 불필요한 원시 로그는 요약·삭제. 오류·삭제 실패를 일반 로그에 묻어 두지 않음. 실제 CLI가 만드는 앱 관리 프로필 내 파일도 관찰·수명 관리. |
| 캐시·앱 관리 CLI 버전 | 용량 한도와 사용 lease에 따라 정리. 실행 중 버전·공유 사용자 캐시를 삭제하지 않음. 재다운로드 비용·네트워크 사용은 구분해 표시. |
| updater download·migration 임시 파일 | 취소·실패·새 버전 건강 확인 시 수명 검사. 복구에 아직 필요한 파일은 이유를 남기고 유지. 영구 업데이트 임시 디렉터리 누적 금지. |
| 승인 snapshot·완성 결과·필수 검수 증거 | 정본/사용자 산출물이므로 일반 임시 정리로 삭제하지 않음. 기억 영구삭제 요구가 포함된 파생 본문은 삭제 전파 계약에 따름. |

정리 트리거는 완료·취소·실패·소비자 해제·재시작 복구·앱 업데이트·용량 부족이다. 삭제 전에 실제 소유 root, symlink·경로 탈출, 최신 참조/lease, 파일 handle·실행 프로세스, 결과 승격을 확인한다. 검사와 삭제 사이 재참조 경합은 동일 자원 잠금/트랜잭션 상태로 차단한다. root 정리가 필요해도 등록된 앱 소유 경로·operation만 허용한다.

삭제 결과를 확인한 뒤 `deleted`로 바꾼다. 권한 오류·열린 파일·디스크 오류는 `cleanup_failed`로 남겨 재시도하고 UI에 남은 용량·이유를 표시한다. 삭제 실패를 무시하고 ‘정리 완료’ 또는 전체 작업 완료로 표시하지 않는다. 필수 정리가 남으면 결과는 이용 가능하더라도 작업은 정리 대기 상태임을 구분한다. 디스크 부족 시 쓰기 작업을 보류하고 안전하게 회수 가능한 자원부터 정리한다. 참조가 있는 자료나 사용자 원본을 지워 공간을 만드는 정책은 사용하지 않는다.

기억 영구삭제는 본문·파생 요약·검색 색인·앱 관리 맥락 사본의 연결을 따라 전파하고 tombstone에 삭제 사실과 ID만 남긴다. 진행 세션에 이미 들어간 내용은 회수됐다고 주장하지 않으며 이후 재구성 때 재주입하지 않는다. SQLite `secure_delete`만으로 WAL·FTS·공급자 기록·OS 백업까지 물리적으로 완전 삭제했다고 표현하지 않는다. 앱 관리 저장소의 삭제 결과와 앱 밖 한계를 구분한다.
