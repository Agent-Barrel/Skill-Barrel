# Q-017. 초기 원격 저장소 자동화의 서비스 지원 범위

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


- 질문일·조사일: 2026-09-18
- 상태: **답변 저장 완료 — 1안 확정**
- 대상: GitHub 외 GitLab의 계정 연결·저장소 생성·PR/MR·원격 병합 자동화
- 범위: 초기 제품이 제공하는 원격 서비스 연동 범위. 내부 에이전트 수행 방식이나 어떤 CLI를 반드시 쓸지를 정하는 질문이 아니다.

## 질문 당시 기존 계획과 답변에서 남은 범위

- [Q-001](001-git-delivery.md)은 개발자와 비개발자 모두를 대상으로 하며, 비개발자의 Git 작업은 에이전트가 자동 병합까지 관리하도록 했다.
- [Q-002](002-git-github-onboarding.md)·[Q-003](003-github-project-storage.md)·[Q-008](008-git-tool-provisioning.md)·[Q-012](012-git-author-identity.md)은 GitHub 연결·새 프로젝트 저장·도구 준비·작성자 설정을 구체화했다. GitLab 계정 연결과 원격 서비스 자동화를 같은 수준으로 제공할지는 답변받지 않았다.
- [Q-014](014-project-repository-scope.md)·[Q-015](015-shared-project-documentation.md)는 기존에 나뉜 여러 저장소와 공통 문서를 하나의 프로젝트에서 다룬다. 여러 저장소가 연결될 수 있다는 결정과 모든 Git 호스팅 서비스를 자동화한다는 결정은 다르다.
- 로컬 Git 저장소를 분석·개발·검증하는 기능, 기존 인증으로 clone·push하는 기능, 서비스 계정을 연결하고 원격 저장소·PR/MR·보호 규칙을 다루는 기능을 구분해야 한다. 이 범위가 불명확하면 사용자가 GitLab 저장소를 연결했을 때 자동으로 어디까지 완료할 수 있는지 안내하기 어렵다.

## 현재 코드 확인

- [현재 구현 격차표](../baseline/01-implementation-gap.md)의 E-04/FEAT-003은 로컬·공개 GitHub HTTPS 입력을 설명한다. 그러나 [실제 URL 검사](../../../../barrel/core/service.py)의 `validate_clone_url()`은 공개 HTTPS 주소를 허용하며 GitHub 호스트로 제한하지 않는다고 명시한다. 표의 ‘공개 GitHub’ 표현을 현재 코드의 호스트 제한으로 읽지 않는다.
- [Git 작업 코드](../../../../barrel/core/gitops.py)는 일반 `git clone`·`git push`를 사용한다. 현재 clone은 인증 프롬프트와 credential helper 사용을 제한하므로, 모든 비공개 저장소의 계정 연결·인증 준비가 구현된 상태로 볼 수 없다.
- 일반 Git 명령이 존재한다는 사실은 GitLab 서비스의 로그인·원격 저장소 생성·MR 생성/병합이 모두 구현됐다는 근거가 아니다. 두 지원 계층을 다음 세션의 기능명세에서 구분해야 한다.

## 공식 자료와 추천

- [GitHub CLI 공식 문서](https://cli.github.com/manual/)는 `gh`를 GitHub용 도구로 설명하고 GitHub Enterprise 호스트 인증도 다룬다. 앞서 선택한 GitHub 온보딩 도구가 GitLab 연동까지 자동으로 제공하는 것은 아니다.
- [GitLab 공식 인증 문서](https://docs.gitlab.com/cli/authentication/)는 `glab`의 GitLab.com 및 자체 운영 인스턴스 인증을 설명한다. GitLab.com의 웹 인증과 달리 자체 운영 환경의 OAuth에는 별도 애플리케이션 등록·설정 등이 필요할 수 있다.
- [GitLab MR 병합 문서](https://docs.gitlab.com/cli/mr/merge/)는 별도의 MR 병합 명령과 파이프라인 연계를 제공한다. GitLab도 자동화 수단이 있으나 앱의 연결·권한·상태·실패 처리를 실제로 통합하고 검증해야 한다.

질문 당시 **1안을 추천했고 사용자가 1안을 선택했다.** 지금까지 구체화한 GitHub 온보딩과 자동 저장을 초기 기준으로 완성하고, 다른 서비스의 기존 로컬 코드 작업은 유지하는 범위다. GitLab 사용자는 서비스별 설정과 MR 처리를 직접 해야 한다는 제한이 있다. GitLab의 서비스 자동화까지 초기부터 제공하는 2안은 선택하지 않았다.

## 사용자에게 제시한 질문

**Q-017. 초기 버전에서 GitLab도 GitHub처럼 자동으로 관리할 수 있어야 할까요?**

1. **GitHub 자동화부터 지원 — 추천:** 계정 연결·저장소 생성·PR·원격 병합 자동화는 GitHub부터 제공합니다. GitLab 등 다른 서비스의 저장소도 로컬 개발과, 이미 설정된 인증으로 가능한 clone·push에는 사용할 수 있지만 서비스별 설정과 MR 처리는 사용자가 맡습니다.
2. **GitLab까지 함께 지원:** GitHub와 GitLab 모두 계정 연결·저장소 생성·PR/MR·원격 병합을 자동 처리합니다. 회사에서 자체 운영하는 GitLab도 지원 대상에 포함하되 실제 연결 환경을 검증합니다. 초기 구현·검증 범위가 늘어납니다.

두 안 모두 기존 저장소를 GitHub로 강제 이전하지 않으며, 원격 저장소 없이 로컬에서 개발하는 기능은 유지합니다.

## 답변으로 확정된 내용

사용자는 **1안, GitHub 자동화부터 지원**을 선택했다. 당시 질문·선택지·공통 조건은 위에 보존한다.

1. 초기 제품의 계정 연결·저장소 생성·PR·원격 병합 자동화는 GitHub부터 제공한다.
2. GitLab 등 다른 서비스의 저장소도 로컬 개발과 이미 설정된 인증으로 가능한 clone·push에 사용할 수 있다. 해당 서비스의 계정·서비스별 설정과 MR 처리는 사용자가 맡는다.
3. GitLab.com과 회사에서 자체 운영하는 GitLab의 서비스 자동화를 초기 범위에 포함하는 2안은 채택하지 않았다. 이 결정을 영구적인 GitLab 지원 금지로 확대하지 않는다.
4. 기존 저장소를 GitHub로 강제 이전하지 않으며 원격 저장소 없이 로컬에서 개발하는 기능을 유지한다.

## 선택한 정책을 적용할 때의 경계

아래는 기존 결정과 연결한 해석·설계 항목이다. 답변 원문과 선택 범위를 넘어 새로운 사용자 확정 사항으로 취급하지 않는다.

- 두 안 모두 사용자 로컬 코드의 개발·검증을 GitHub 연결 여부만으로 막지 않는다. 일반 Git 동작은 현재 인증·권한·저장소 규칙이 허용하는 범위에서 수행한다. 지원하지 않는 원격 서비스 작업을 수행 완료로 표시하지 않는다.
- 1안에서 다른 서비스의 원격 PR/MR 처리가 필요하면 지원 범위를 시작 단계에 알려야 한다. 실제 필요한 병합이 남아 있는데 개발·테스트 성공만으로 요청 전체가 완료됐다고 표시하지 않는다. 기존 저장소를 임의로 GitHub에 복사해 우회하지 않는다.
- 로컬 브랜치 병합·push와 호스팅 서비스의 PR/MR 병합을 같은 기능으로 취급하지 않는다. 기존 브랜치 보호·CI·필수 리뷰를 직접 push나 관리자 옵션으로 우회하는 권한을 이 답변에서 얻지 않는다.
- [Q-003](003-github-project-storage.md)의 GitHub 개인 비공개 저장소 자동 저장 위임을 유지한다. 이 위임이 다른 호스트나 조직에 대한 위임으로 자동 확대되지는 않는다.
- GitHub Enterprise·자체 운영 GitLab의 실제 지원은 선택한 서비스 범위와 검증한 서버·인증 환경을 구분한다. 공식 CLI가 특정 환경을 지원한다는 사실만으로 모든 서버 버전·사내 네트워크 조합을 앱에서 검증했다고 표시하지 않는다.
- GitHub의 `gh`·API·허용된 브라우저 자동화 중 구체적인 수단은 구현 판단이다. `glab` 조사 결과를 초기 필수 설치나 GitLab 자동화 요구로 가져오지 않는다. 필요한 도구 설치는 [Q-008](008-git-tool-provisioning.md)의 사용자 승인 후 설치 원칙을 따르며, 이번 문서 작업에서 도구를 설치하거나 로그인하지 않는다.
- 기존 서비스의 원격 URL·소유자·공개 범위를 보존한다. GitHub와 GitLab이 함께 있는 프로젝트도 저장소별 대상을 구분하며 [Q-014](014-project-repository-scope.md)의 프로젝트 단위 조정과 작은 작업 분할을 유지한다.
- Bitbucket·Azure DevOps 등 다른 서비스의 전용 자동화를 초기 범위에 포함한 결정도 아니다. 일반 Git 사용 가능 범위와 서비스별 자동화 지원 여부를 구분해 안내한다.
