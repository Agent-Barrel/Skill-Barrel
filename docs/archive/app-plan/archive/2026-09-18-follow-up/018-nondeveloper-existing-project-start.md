# Q-018. 비개발자의 기존 프로젝트 시작과 Git 선택

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


- 질문일·조사일: 2026-09-18
- 상태: **답변 저장 완료 — 1안 선택 및 Git 지식·기존 정책 확인 조건 추가**
- 대상: 비개발자가 기존 Git 프로젝트를 맡길 때의 시작점·기존 수정 보존 안내
- 범위: D-039의 기술적 선택 질문을 비개발자에게 그대로 적용할지, 사용자 의도에 대한 질문으로 줄일지. 개발자의 기존 선택 정책이나 사용자 변경 보존 원칙을 없애는 질문은 아니다.

## 기존 결정 사이에 필요한 정렬

- [기존 D-039](../baseline/04-resolved-details.md)는 프로젝트 선택 시 현재 브랜치·미커밋 변경을 설명하고 시작 브랜치와 보존 방식을 질문하도록 정했다. [REQ-041](../../requirements.csv)·[FEAT-048](../../features.csv)도 이 정책을 구현 대상으로 삼는다.
- [Q-001](001-git-delivery.md)에서는 비개발자에게 Git 허용 범위를 묻는 것도 어려울 수 있으므로 자동 병합까지 진행하고 작업 단위는 에이전트가 관리하도록 했다.
- Q-001의 당시 질문은 D-039의 기존 변경 보존·시작 브랜치 정책을 유지한다고 명시했다. 따라서 Q-001 답변만으로 비개발자에게 모든 시작점 질문을 생략하라고 확정한 것으로 볼 수는 없다.
- 하지만 D-039를 기술 용어와 함께 그대로 적용하면, 비개발자는 Git 반영 범위 질문을 건너뛰어도 곧바로 브랜치·stash·commit 등의 선택을 해야 할 수 있다. 이 사용자 경험을 어느 수준으로 자동화할지 정렬할 필요가 있다.

예를 들어 사용자가 첫 화면을 직접 고쳐둔 프로젝트에 ‘로그인을 추가해줘’라고 요청할 수 있다. 이때 첫 화면 수정도 이번 결과에 포함할지의 의도와, 그 수정 내용을 보존하는 Git 명령·작업 공간의 선택은 구분할 수 있다.

## 조사와 현재 코드

- [GitHub Desktop 공식 가이드](https://docs.github.com/en/desktop/making-changes-in-a-branch/managing-branches-in-github-desktop#switching-between-branches)는 브랜치 전환 때 미커밋 변경을 현재 브랜치에 남길지 새 브랜치로 가져갈지 선택하도록 한다. 원래 수정 내용의 취급 의도를 사용자에게 확인하는 사례다. 이 앱도 같은 UI나 stash 방식을 그대로 따라야 한다는 근거는 아니다.
- 현재 [환경 검사](../../../../barrel/core/preflight.py)는 clean tree가 필요한 상태에서 미커밋 변경이 있으면 커밋 또는 stash 후 다시 시작하라고 안내한다. [유지보수 분석](../../../../barrel/core/analyze.py)도 미커밋 변경을 발견하면 같은 취지의 오류로 중단한다.
- 현재 코드는 비개발자에게 수정 내용을 쉬운 말로 설명하고 의도를 받은 뒤 준비를 대신하는 UX를 구현한 상태가 아니다. 새 앱에서 현재 오류 문구를 그대로 재사용하면 Q-001의 비개발자 방향과 어긋날 수 있다.

## 질문 당시 추천과 사용자 보완

질문 당시에는 1안을 추천했다. 사용자는 **1안을 선택하되, 비개발자에게도 Git 관련 지식과 기존에 관리하던 정책이 있는지 먼저 질문하고, 잘 모르거나 정책이 없다고 답하면 에이전트가 관리하도록 보완했다.** 아래 질문 원문에서 비개발자의 기술 선택을 곧바로 생략한다고 읽힐 수 있는 부분보다 이 보완 조건을 우선한다.

이 선택은 사용자 변경을 자동 삭제하거나 무조건 포함하는 정책이 아니다. 에이전트가 관리하는 경우에도 결과에 영향을 주는 사용자 의도가 불명확하면 내용을 설명하고 질문한다. 2안의 일률적인 직접 선택 절차는 채택하지 않았다.

## 사용자에게 제시한 질문

**Q-018. 비개발자가 기존 프로젝트를 맡길 때도 시작 브랜치·변경 보존 방식을 직접 고르게 할까요?**

1. **기술적인 선택은 에이전트가 관리 — 추천:** 비개발자에게 브랜치·stash 같은 선택을 요구하지 않습니다. 기존 수정 내용을 이번 결과에 포함할지처럼 사용자 의도가 필요한 경우에만, 바뀌는 내용을 쉬운 말로 보여주고 질문합니다. 의도가 명확하면 자동으로 준비하고 진행합니다.
2. **기존 규칙 유지:** 비개발자도 현재 상태를 설명받고, 어떤 브랜치에서 시작할지와 기존 변경을 어떻게 보존할지 선택한 뒤 진행합니다.

두 안 모두 사용자가 원래 작업한 내용은 보존하고, 명시한 시작점과 유효한 기존 선택을 존중합니다. 개발자에게는 기존 D-039의 선택 방식을 유지합니다.

## 사용자 답변 원문

```text
1로 하되, 비개발자에게도 git 관련 지식 있고 관리하던 정책이 있는지 물어봐. 잘 모르겠다거나 없다고 하면 그때 에이전트가 관리하는걸로 해줘
```

## 답변으로 확정된 내용

1. **1안, 기술적인 선택은 에이전트가 관리**를 선택하되 적용 전에 확인할 조건을 추가했다.
2. **비개발자에게도 Git 관련 지식이 있는지, 기존에 관리하던 Git 정책이 있는지 질문한다.** 비개발자라는 분류만으로 Git 지식이나 정책이 없다고 가정하지 않는다.
3. **잘 모르겠다고 하거나 기존 정책이 없다고 하면 에이전트가 관리한다.** 그런 경우 브랜치·stash 같은 기술적 선택을 직접 요구하지 않고, 필요한 사용자 의도만 쉬운 말로 확인한다.
4. 사용자가 기존 관리 정책을 가지고 있으면 해당 정책을 확인해 적용한다. 비개발자용 자동 관리 기본값으로 기존 정책을 덮어쓰지 않는다.
5. 당시 질문의 공통 조건인 사용자 원래 작업 보존, 명시한 시작점·유효한 기존 선택 존중, 개발자에 대한 D-039 선택 방식 유지를 따른다.

## 선택한 정책을 적용할 때의 경계

아래는 기존 결정과 연결한 해석·설계 항목이다. 답변 원문과 선택한 범위를 넘어 새로운 사용자 확정 사항으로 취급하지 않는다.

- D-039 중 비개발자에게 Git의 기술적 시작점·보존 방법을 직접 선택시키는 부분은 이번 답변의 사전 확인 조건과 함께 조정한다. Git 지식이 있다는 이유만으로 매번 모든 기술 메뉴를 고르게 하거나, 지식이 없다는 이유로 확인된 프로젝트 정책을 무시하지 않는다. 개발자에게도 동일한 생략 정책을 적용한 것으로 확대하지 않는다.
- Git 지식과 프로젝트별 관리 정책을 구분해 기록한다. 온보딩·이전 대화에서 이미 받은 유효한 정보를 재사용하되, 다른 프로젝트의 정책을 임의로 가져오지 않는다. 개발자 여부를 다시 분류하거나 Git 지식을 시험하는 절차를 추가한 답변은 아니다. 질문에 아직 답하지 않은 상태를 ‘모름·정책 없음’으로 간주하지 않는다.
- 정책이 있다고 하면 그 내용을 확인하고 정본에 연결한다. 이미 명시된 브랜치·반영·보존 규칙은 작업 계획에 적용하며, 충돌이나 실제로 빠진 의도만 질문한다. 이 확인을 Q-001의 복잡한 Git 허용 범위 메뉴를 모든 비개발자에게 다시 보여주는 절차로 확대하지 않는다.
- 시작점을 에이전트가 고르는 경우에도 사용자의 요청, 현재 작업 상태, 프로젝트 규칙·유효한 설정에 근거한다. 무조건 원격 기본 브랜치나 현재 브랜치 하나로 고정하지 않는다. 어느 결과·버전을 기준으로 해야 할지 불명확하면 비개발자가 이해할 수 있는 내용으로 확인한다.
- 사용자 수정이 있다는 사실과 해당 수정을 이번 결과의 커밋·원격 반영에 포함할 권한을 구분한다. 이미 유효한 요청·선택이 있으면 재사용하고, 포함 여부를 임의로 추정해 함께 업로드하지 않는다.
- 보존 방법은 구현자가 결정하되 사용자 파일·staging·untracked·binary·submodule 상태를 빠뜨리지 않는다. 별도 브랜치 생성만으로 기존 미커밋 내용이 보존됐다고 판단하지 않는다. 원본을 보존할 수 없으면 원본 변경 전에 필요한 조건을 해결한다.
- 선택이 필요한 부분은 대기하되 독립적인 읽기 전용 조사·계획은 기존 정책대로 진행한다. 답변 대기 중 종속 변경을 먼저 적용하지 않는다.
- 작업 도중 사용자가 다른 도구로 바꾼 내용과 통합 충돌은 기존 D-039/D-032의 재확인·충돌 처리 계약을 유지한다. 단순 코드 충돌의 기술적 해결과 사용자 의도·승인 명세의 변경을 구분한다.
- 비Git 폴더 초기화, 작업 취소 시 보관·폐기([Q-009](009-cancelled-work-artifacts.md)), 외부 위임 범위, 브랜치 보호 우회 여부를 새로 선택하는 질문은 아니다.
- Git 작업 단위·격리 방법·명령 순서를 비개발자가 세세히 관리하게 만들지 않는다. 이는 [Q-006](006-native-subagent-boundary.md)·[Q-016](016-unexpected-context-compaction.md)의 내부 작업 관리 최소화와도 연결하되, 실제 결과와 사용자 원래 작업의 보존은 검증한다.
