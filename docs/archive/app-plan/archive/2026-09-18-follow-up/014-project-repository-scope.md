# Q-014. 한 프로젝트에 여러 Git 저장소 연결

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


- 질문일·조사일: 2026-09-18
- 상태: **답변 원문 저장 완료 — 1안 선택 및 기본 저장소 구성 보완**
- 대상: 화면·서버·모바일·공유 라이브러리 등이 별도 Git 저장소에 있는 하나의 서비스 또는 제품
- 범위: 초기 버전의 프로젝트 단위와 연결할 저장소 수. 여러 독립 프로젝트를 동시에 실행하는 기능은 이미 확정됐으며 재질문하지 않는다.

## 기존 계획과 코드에서 확인한 빈틈

- [D-003/D-006](../baseline/decisions.md)은 일반 소프트웨어 개발과 여러 프로젝트의 동시 진행을 지원한다. [REQ-020](../../requirements.csv)·[FEAT-020](../../features.csv) 및 [D-032](../baseline/02-product-decisions.md)는 프로젝트 간 읽기·쓰기·자원 의존성에 따라 실행을 조정한다.
- 이 결정들은 **하나의 프로젝트가 여러 저장소에 걸친 기능을 하나의 요구·명세·진행 상태로 관리하는지**를 명시하지 않는다. 여러 프로젝트를 따로 실행하는 것과 여러 저장소를 한 프로젝트에 연결하는 것은 다른 제품 기능이다.
- [아키텍처의 Project / WorkRequest](../baseline/03-architecture-and-roadmap.md)는 프로젝트·실제 저장소 식별·작업 요청을 연결하지만 저장소 집합의 범위와 관계는 명시하지 않는다.
- 현재 [Project 모델](../../../../barrel/core/models.py)은 `repo_path` 하나를 가진다. [서비스](../../../../barrel/core/service.py)의 구현·Git 처리도 `project.repo_path`를 사용한다. 현재 구조를 그대로 이식하면 한 프로젝트의 여러 저장소를 표현하는 계약을 놓칠 수 있다.
- [Q-011](011-wireframe-design-approval-flow.md)의 API·UI 작업과 [Q-013](013-project-specs-in-git.md)의 코드·명세 동시 관리는 저장소가 하나여도 가능하다. 이 답변들만으로 여러 저장소 지원까지 이미 승인받았다고 해석하지 않는다.

예를 들어 쇼핑몰 화면과 주문 서버가 다른 저장소에 있는데 ‘배송지 수정 기능’을 한 번 요청하면, 두 저장소의 API·화면·검증을 하나의 작업으로 조정할지 아니면 각각 별도 프로젝트로 처리할지 결정해야 한다. 이 범위는 새 Rust 코어의 프로젝트 구조·명세 참조·위임·진행 상태에 영향을 준다.

## 유사 서비스 조사

- [Kiro Web 공식 설명](https://kiro.dev/web/)은 하나의 세션에 여러 저장소를 선택하고, 공통 변경을 조정해 각 저장소에 PR/MR을 만드는 방식을 지원한다고 설명한다. 여러 저장소에 걸친 서비스 변경을 하나의 요청으로 다루는 비교 사례다. 공급자가 말하는 ‘한 세션’을 이 앱의 단일 CLI 세션에 모든 맥락을 넣는 요구로 가져오지 않는다.
- [GitHub Copilot Agents 공식 설명](https://docs.github.com/en/copilot/responsible-use/agents)의 Copilot cloud agent 항목은 PR을 만드는 해당 저장소에 접근 범위를 제한한다고 설명한다. 저장소 하나를 실행 단위로 삼는 비교 사례이며, Copilot의 다른 모든 실행 환경도 동일하다고 일반화하지 않는다.

질문 당시에는 1안을 추천하면서 ‘새 프로젝트의 기본은 저장소 하나’로 제안했다. **사용자는 여러 관련 저장소를 한 로컬 폴더에 모으는 구성을 명확히 했으며, 명시적으로 지시하지 않은 모노레포는 추천하지 않는다고 보완했다.** 아래 질문의 원문은 당시 제안의 기록이며, 저장소 구성은 뒤의 답변과 확정 내용을 우선한다. 여러 저장소 지원에는 저장소 집합·각 저장소의 상태·통합 검증을 초기 구조부터 다루는 구현 범위가 포함된다.

## 사용자에게 제시한 질문

**Q-014. 하나의 프로젝트에 여러 Git 저장소를 연결하는 기능을 초기 버전부터 지원할까요?**

1. **지원 — 추천:** 화면·서버·모바일 코드가 서로 다른 저장소에 있어도 하나의 프로젝트로 묶고, 한 요청에 필요한 변경과 검증을 에이전트가 조정합니다. 새 프로젝트는 기본적으로 저장소 하나로 시작하고, 필요한 경우 추가합니다.
2. **초기는 저장소 하나로 제한:** 한 프로젝트에는 저장소 하나만 연결합니다. 그 안에 화면·서버 코드를 함께 두는 것은 가능하지만, 이미 저장소가 나뉜 서비스는 별도 프로젝트로 다룹니다.

작업은 기존 원칙대로 작은 단위로 나누고, 저장소별 권한·검증 조건을 적용합니다. 기존 저장소 구조를 자동으로 합치거나 옮기지는 않습니다.

## 사용자 답변 원문

```text
1안으로 가자. 이렇게 하려고 했어. 사실 지금 내가 진행하는 프로젝트들도 그렇게 진행하고 있거든. 프론트엔드와 백엔드 레포를 한 폴더에 몰아 놓으면 API 명세 관련해서 직접 확인하기 편하고, 관련있는 레포끼리 모여있으니 관리도 편해.
마이크로 서비스 이거나 세부 모듈이 많은 프로젝트도 동일하게 이런 구조가 관리와 참조에 이점이 있다고 생각해.
다만, 사용자가 명시적으로 모노레포를 지시한 상황이 아니면 모노레포로 만드는건 추천하지 않아. 로컬 폴더에 서로 관련있는 여러 레포를 clone 해두고 작업한다는 개념에 더 가까워. 기능적 구분으로 레포를 나눠두고 레포 별로 배포나 CI 작업 등을 하기 편하게 하려고 하는거야.
그렇다고 너무 단위를 쪼갤 필요는 없어.
```

## 답변에서 확정된 내용

1. **초기 버전부터 하나의 프로젝트에 여러 Git 저장소를 연결한다.** 관련 저장소의 변경·명세 참조·검증을 하나의 프로젝트와 요청에서 조정한다.
2. **관련 있는 독립 저장소들을 하나의 로컬 상위 폴더 아래에 clone해 작업하는 구성을 지원한다.** 프론트엔드·백엔드 저장소의 API 명세를 서로 확인하기 쉽고, 관련 저장소를 함께 관리하기 위한 구조다. 마이크로서비스나 여러 세부 모듈이 있는 프로젝트에도 같은 원칙을 적용한다.
3. **사용자가 명시적으로 모노레포를 지시하지 않으면 모노레포 구성을 추천하거나 기본으로 만들지 않는다.** 질문 당시의 ‘새 프로젝트는 기본적으로 저장소 하나’라는 제안은, 화면·서버 등 기능적으로 나뉜 구성까지 하나의 저장소에 모으는 기본 정책으로 채택하지 않는다.
4. **기능적인 구분을 기준으로 저장소를 나누어 저장소별 배포·CI를 관리하기 편하게 한다.** 단, 필요 이상으로 단위를 잘게 쪼개지 않는다.
5. 사용자가 현재 진행하는 프로젝트도 이러한 폴더·저장소 구성을 사용하고 있다는 배경을 기록한다. 이 답변은 현재 검토 중인 레포의 폴더나 Git 구조를 바로 변경하라는 요청은 아니다.

## 선택한 정책을 적용할 때의 경계

아래는 기존 결정과 연결한 설계 해석·검토 항목이다. 새 사용자 확정 사항으로 취급하지 않는다.

- 사용자에게 보이는 프로젝트·로컬 상위 폴더와 실제 Git 저장소를 별도 개념으로 표현한다. 요청·요구·명세는 프로젝트에서 연결하고, 실제 경로·원격·시작 revision·변경·커밋/PR·검증 결과는 대상 저장소를 식별할 수 있어야 한다. 상위 폴더 자체를 자동으로 Git 저장소로 초기화해 중첩 저장소나 모노레포를 만드는 것으로 해석하지 않는다.
- 여러 저장소 지원이 모든 저장소·계정·조직의 임의 접근 권한을 주지는 않는다. 저장소 추가와 작업 대상 확대는 기존 범위·위임 정책을 따른다. 원격 서비스의 초기 자동화 범위는 후속 [Q-017](017-git-hosting-support.md)에서 GitHub부터 제공하도록 확정했다. GitLab 등 다른 서비스의 기존 로컬 코드 개발·인증된 일반 Git 작업은 유지한다.
- [Q-003](003-github-project-storage.md)의 비개발자 신규 프로젝트 자동 저장은 개인 비공개 저장소 기본값과 연결 시 선택을 유지한다. 기능·배포·CI 경계에 따라 필요한 저장소를 구성하되, 모든 프로젝트에 반드시 둘 이상의 저장소를 만들거나 모든 모듈을 별도 저장소로 만들라는 뜻은 아니다. 기존 원격·소유자·공개 범위를 유지한다.
- 저장소를 나누는 단위와 에이전트에게 맡기는 작업 단위는 다르다. 작은 작업마다 새 저장소를 만드는 정책으로 확장하지 않는다. 구체적인 저장소 이름·필수 개수·기술별 고정 분리 규칙은 이번 답변에서 확정하지 않았다.
- 기존 프로젝트를 연결할 때 현재 구조를 임의로 합치거나 나누거나 옮기지 않는다. 이미 모노레포인 프로젝트를 유지보수하는 것과 새로 모노레포를 추천·생성하는 것은 구분한다. 이번 기본값 변경만으로 기존 모노레포를 자동 분리할 권한이 생기지는 않는다.
- [P-001](p001-context-and-intent.md)의 문서·세션 분할을 유지한다. 프로젝트에 여러 저장소가 연결돼도 한 상용 에이전트 세션에 모든 코드를 넣지 않는다. [Q-006](006-native-subagent-boundary.md)에 따라 공급자 내부 서브에이전트까지 관리하지 않는다.
- [D-032](../baseline/02-product-decisions.md)는 같은 프로젝트 안에서도 적용한다. 저장소가 달라도 API 명세·공유 라이브러리·DB·배포 대상에 의존성이 있으면 필요한 선행 작업을 마친 뒤 진행한다. 파일 위치가 다르다는 이유만으로 병렬 실행하지 않는다.
- Q-013에 따라 관련 문서와 코드를 연결한다. 여러 저장소에서 공유하는 요구·API·결정은 기준 문서와 정확한 revision을 참조하고, 서로 모순되는 독립 정본으로 복제하지 않는다. [Q-015](015-shared-project-documentation.md)에서 새 다중 저장소 프로젝트는 공통 문서용 독립 저장소 하나를 두고, 저장소별 기술 문서는 해당 코드 저장소에서 관리·참조하도록 확정했다. 기존 문서 구조와 작은 프로젝트는 존중하며 구체적인 폴더 이름·참조 표현은 확정된 범위 안에서 설계한다.
- 저장소별 일부 구현·병합 성공과 전체 요청 완료는 구분한다. 여러 저장소의 Git 반영을 하나의 원자적 동작처럼 표시하지 않으며, 부분 실패는 기존 외부 효과 receipt·재조회·복구 계약과 연결한다. 필수 통합 검증을 마치지 않은 요청을 완료로 표시하지 않는다.
- Git submodule 같은 저장소 내부 구성과 여러 독립 저장소를 앱에서 한 프로젝트로 연결하는 기능을 같다고 취급하지 않는다. 초기화·접근·revision 검증의 구체 지원은 실제 구현에서 확인한다.
