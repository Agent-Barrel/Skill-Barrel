# Q-007. 앱·Mac 재실행 후 작업 재개 시점

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


- 질문일·조사일: 2026-09-18
- 상태: **답변 저장 완료 — 2안 확정**
- 범위: 앱 또는 Mac 종료로 중단된 기존 작업을 앱 재실행 후 언제 이어갈지
- 별개 항목: 로그인 시 앱 자동 실행 여부, 창 닫기와 앱 종료의 UI, 사용자에게 이미 확정받은 단계 승인·위임 범위

## 기존 기획에서 정해진 것과 남은 것

- [REQ-039](../../requirements.csv), [FEAT-044/045](../../features.csv)는 체크포인트를 보존하고, 이전 프로세스·파일·외부 작업 결과를 확인한 뒤 중복 실행 없이 이어가도록 한다.
- [아키텍처의 영속 기억·재개](../baseline/03-architecture-and-roadmap.md)는 기존 승인·정책·맥락을 재구성하며, 외부 결과가 불명확하면 복구 대기로 남기도록 한다. [D-031](../baseline/02-product-decisions.md)의 정책 적용 시점과 [D-047 및 절전·업데이트 계약](../baseline/04-resolved-details.md)도 유지한다.
- [제품 결정의 시작·종료 추천값](../baseline/02-product-decisions.md)은 로그인 시 자동 시작을 사용자 선택으로 두고, 앱 종료 시 상태를 저장한다고 설명한다. 하지만 앱이 다시 실행됐을 때 복구 가능한 작업을 자동으로 시작할지, 사용자 재개 입력을 기다릴지는 명확하지 않다.
- 현재 [웹 작업 실행기](../../../../barrel/web/jobs.py)는 실행 중 작업을 메모리의 스레드 목록으로 관리한다. [기능 격차 문서](../baseline/01-implementation-gap.md)도 FEAT-045의 앱 재시작·영속 복구를 남은 작업으로 표시한다. 현재 코드의 동작을 이 제품의 재개 정책으로 그대로 확정하지 않는다.

이번 질문은 **복구 가능성 판단 후 실제 실행을 시작할 시점**에 관한 것이다. 복구 방법이나 개별 CLI 내부 수행 방식을 사용자에게 설계하도록 묻는 질문이 아니다. [Q-006](006-native-subagent-boundary.md)의 내부 자율성과 과도한 세부 관리 방지 원칙을 유지한다.

## 조사·비교 근거

- [Temporal 공식 문서](https://docs.temporal.io/)는 장애·네트워크 문제·인프라 중단 이후 저장된 실행 상태로 작업을 이어가는 방식을 설명한다. 자동화 작업의 연속성을 중시하는 비교 사례다. Temporal 도입이나 이 앱에서 동일한 실행 보장이 이미 검증됐다는 뜻은 아니다.
- [GitHub Actions 공식 문서](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)는 실행 내역에서 전체·실패 작업·특정 작업을 사용자가 선택해 재실행하는 UI·CLI를 제공한다. 사용자가 다시 실행할 시점을 선택하는 비교 사례다. GitHub Actions의 재실행과 이 앱의 체크포인트 재개가 같은 기술이라는 뜻은 아니다.

위 사례를 바탕으로, 질문 당시 작성자는 조건 확인 후 자동 재개를 추천했다. 사용자가 앱을 다시 연 목적이 상태 확인뿐일 수도 있어, 수동 종료나 모든 재실행에 확인을 두는 대안도 제시했다. **사용자는 추천 1안 대신 아래 2안을 선택했다.**

## 사용자에게 제시한 질문

**Q-007. 앱이나 Mac이 꺼졌다 다시 실행되면, 진행 중이던 작업은 어떻게 이어갈까요?**

1. **자동으로 이어가기 — 추천:** 앱이 다시 실행되면 마지막 상태를 확인하고, 이어갈 수 있는 작업은 자동으로 재개합니다. 사용자가 앱을 종료했다가 다시 연 경우도 포함하며, 재개 내역을 알려줍니다.
2. **직접 앱을 종료했을 때만 재개 확인:** 장애·Mac 재시작·업데이트 뒤에는 자동으로 이어가고, 사용자가 앱의 ‘종료’를 선택했다면 다시 열어도 ‘계속하기’를 눌러야 합니다.
3. **항상 ‘계속하기’를 눌러 재개:** 복구한 상태와 남은 작업을 보여주고, 사용자가 재개할 때까지 기다립니다.

어느 안이든 사용자가 작업을 명시적으로 일시중지·취소했다면 자동 재개하지 않습니다. 답변·승인 대기나 권한·예산 부족, 외부 작업 결과 불명확 등 기존 대기 사유가 남아 있으면 해당 작업은 계속 대기합니다.

## 답변으로 확정된 내용

사용자는 **2안, 직접 앱을 종료했을 때만 재개 확인**을 선택했다. 선택지와 당시 공통 조건은 위 질문에 보존한다.

1. 장애·Mac 재시작·업데이트 뒤에는 앱이 마지막 상태와 복구 가능성을 확인한 후 이어갈 수 있는 작업을 자동으로 재개한다.
2. 사용자가 앱의 ‘종료’를 직접 선택했다면, 앱을 다시 열어도 사용자가 ‘계속하기’를 누를 때까지 작업을 재개하지 않는다.
3. 사용자가 작업을 명시적으로 일시중지·취소한 상태는 자동 재개하지 않는다.
4. 답변·승인 대기, 권한·예산 부족, 외부 작업 결과 불명확 등 기존 대기 사유가 남아 있는 작업은 계속 대기한다.

앱 재실행 정책을 정한 답변이다. 로그인 시 자동 시작을 켜거나, 앱을 종료한 동안 로컬 작업을 계속 실행하도록 정한 답변이 아니다.

## 적용 경계와 다음 세션 확인 사항

- 앱 재실행과 작업 재개를 구분한다. 자동 재개를 선택해도 앱이 종료된 동안 로컬 작업을 계속 실행하거나 로그인 시 자동 실행을 강제로 켜는 의미는 아니다.
- 앱을 다시 여는 행동, 작업의 명시적 일시중지·취소, 기존 질문·승인 대기, 장애로 인한 중단을 구분해 저장한다. 재시작으로 사용자 중지 의도나 대기 조건을 지우지 않는다.
- 기존 상태·입력·위임·예산·외부 결과를 확인한 뒤 유효한 작업만 재개한다. 이미 성공한 배포·병합 등을 무조건 다시 실행하지 않는다. 필요한 새 판단이 있으면 기존 D-039~041·명세 변경 계약에 따라 해당 작업만 기다린다.
- 기존 승인과 유효한 작업 계획을 재사용한다. 재실행 자체를 이유로 전체 인터뷰·전체 리서치·모든 계획 검토를 처음부터 반복하지 않는다. 변경·누락이 발견된 범위를 확인하는 방식으로 P-001과 Q-006을 함께 적용한다.
- 선택한 2안에 맞춰 앱 시작·종료 사유, 복구 판정, 재개 상태 표시를 구현 계약에 연결한다. 이 질문에서 고정 시간 간격·재시도 횟수·추가 모델 호출 수를 정하지 않는다.
- Mac이 켜진 상태에서의 짧은 네트워크 단절이나 CLI의 일시적 오류 처리 전체를 매번 사용자 재개 확인으로 바꾸는 질문이 아니다. 기존 허용된 대체 경로·원인 재검토·유효 대안 시도 원칙을 유지한다.
