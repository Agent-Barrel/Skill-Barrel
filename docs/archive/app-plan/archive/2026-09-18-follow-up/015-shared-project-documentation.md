# Q-015. 여러 저장소를 연결하는 프로젝트의 공통 문서 위치

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


- 질문일·조사일: 2026-09-18
- 상태: **답변 저장 완료 — 1안 확정**
- 대상: 여러 독립 Git 저장소로 구성하는 새 프로젝트의 공통 요구·기능·의도·설계 문서
- 범위: 공통 문서를 별도 저장소에 둘지 대표 코드 저장소에 둘지의 기본 정책. 구체적인 폴더 이름이나 문서 도구를 고르는 질문은 아니다.

## 기존 답변과 연결해 확인한 판단 지점

- [Q-013](013-project-specs-in-git.md)에서 프로젝트 기획·설계 자료를 코드와 함께 Git으로 관리하고, 원격 저장을 허용하면 함께 업로드하기로 했다. 앱의 로컬 DB만 문서의 보관 장소로 사용하는 안은 선택하지 않았다.
- [Q-014](014-project-repository-scope.md)에서는 관련 독립 저장소들을 하나의 로컬 상위 폴더에 모으고, 명시적 사용자 지시가 없으면 모노레포로 만들지 않는다고 확정했다. 따라서 공통 기획 문서를 상위 일반 폴더에 파일로만 두면, 각 코드 저장소를 커밋·업로드해도 해당 문서는 어느 저장소에도 포함되지 않을 수 있다.
- 프로젝트 전체 요구·기능·화면 흐름은 프론트엔드나 백엔드 어느 한쪽만의 문서가 아니다. 같은 내용을 여러 저장소에 복사해 각각 수정하면 [P-001](p001-context-and-intent.md)의 정확한 정본과 참조 원칙에 어긋날 수 있다.
- 현재 [기능 CSV 코드](../../../../barrel/core/spec_csv.py)·[서비스](../../../../barrel/core/service.py)는 프로젝트의 단일 `repo_path` 아래 `docs/spec/features.csv`를 사용한다. [아키텍처](../baseline/03-architecture-and-roadmap.md)의 `SpecRevision`·`ContextBundle`은 문서 revision과 참조를 다루지만 여러 저장소에 걸친 공통 문서의 기준 위치를 지정하지는 않는다.
- Q-013에서 폴더 이름·표현 형식은 구현자가 결정하도록 남겼다. 이번 질문은 이름을 다시 묻는 것이 아니라 **별도 Git 저장소를 하나 더 관리할지, 기존 코드 저장소에 공통 문서를 귀속할지**를 정한다.

## 조사와 추천

[Backstage TechDocs 공식 가이드](https://backstage.io/docs/features/techdocs/creating-and-publishing/)는 기본적으로 코드 가까이에 문서를 두는 방식을 설명하며, 별도의 문서 구성요소로 독립 문서를 관리하는 방식도 제시한다. 둘 다 가능한 구성 사례다. 이 자료가 여러 저장소 프로젝트에는 반드시 별도 문서 저장소를 쓰라고 권고한 것은 아니며, Backstage나 MkDocs 도입을 제안하는 것도 아니다.

질문 당시 **새 다중 저장소 프로젝트의 기본값으로 1안을 추천했고, 사용자가 1안을 선택했다.** 이는 Q-014의 로컬 폴더 구성과 P-001의 공통 의도 관리 요구를 함께 고려한 제안이다. 전체 기획의 기준을 특정 프론트엔드·백엔드에 종속시키지 않고, 새 모듈이 추가돼도 같은 기준을 참조할 수 있다. 반면 저장소 생성·접근·버전 연결을 하나 더 관리해야 한다. 2안은 저장소 수를 줄일 수 있는 대안으로 제시했지만 기본 정책으로 선택하지 않았다.

선택한 1안의 구성 예시는 다음과 같다. 독립 저장소를 함께 배치하는 구조는 확정했으며, 이름은 예시다.

```text
프로젝트/                 일반 로컬 폴더
  project-docs/           공통 기획·설계용 독립 Git 저장소
  frontend/               프론트엔드 독립 Git 저장소
  backend/                백엔드 독립 Git 저장소와 API 명세
```

공통 문서를 종류마다 다시 별도 저장소로 나누자는 제안은 아니다. 코드 저장소가 하나인 작은 프로젝트에 추가 저장소를 강제하는 정책으로 확장하지 않는다.

## 사용자에게 제시한 질문

**Q-015. 여러 저장소로 구성하는 새 프로젝트에서, 공통 기획·설계 문서는 어디에 둘까요?**

1. **공통 문서용 저장소 하나를 따로 두기 — 추천:** 프론트엔드·백엔드 저장소와 같은 상위 폴더에 `project-docs` 같은 독립 저장소를 둡니다. 전체 요구사항·기능명세·결정 기록·화면 흐름·저장소 간 관계를 여기서 관리합니다. 저장소가 하나 늘지만 공통 문서의 기준 위치가 명확합니다.
2. **대표 코드 저장소 안에 두기:** 백엔드 등 프로젝트의 대표 저장소 한 곳에 공통 문서를 모으고 다른 저장소가 참조합니다. 저장소 수는 적지만 전체 기획 문서가 특정 코드 저장소에 속하게 됩니다.

두 안 모두 서버 API 명세·구현 설명처럼 특정 저장소에 속하는 기술 문서는 해당 저장소에서 관리하고, 공통 문서에서 참조합니다. 기존 프로젝트의 문서 구조는 존중하며, 저장소 하나로 충분한 작은 프로젝트에는 문서용 저장소를 추가로 강제하지 않습니다.

## 사용자 답변 원문

```text
1
```

## 답변으로 확정된 내용

사용자는 **1안, 공통 문서용 저장소 하나를 따로 두기**를 선택했다. 당시 질문·선택지·공통 조건은 위에 보존한다.

1. 여러 독립 저장소로 구성하는 새 프로젝트는 공통 기획·설계용 Git 저장소를 하나 두는 것을 기본으로 한다. 프론트엔드·백엔드 등 관련 코드 저장소와 같은 로컬 상위 폴더 아래에 배치한다.
2. 전체 요구사항·기능명세·결정 기록·화면 흐름·저장소 간 관계는 공통 문서 저장소에서 관리한다. 특정 코드 저장소 하나를 공통 문서의 기본 보관 장소로 삼는 2안은 선택하지 않았다.
3. 서버 API 명세·구현 설명처럼 특정 저장소에 속하는 기술 문서는 해당 코드 저장소에서 관리하고 공통 문서에서 참조한다.
4. 기존 프로젝트의 문서 구조는 존중한다. 저장소 하나로 충분한 작은 프로젝트에 문서용 저장소를 추가로 강제하지 않는다.
5. `project-docs`는 예시 이름이다. 문서의 종류별로 여러 저장소를 만드는 정책이나 구체적인 도구·파일 형식을 확정한 답변은 아니다.

## 선택한 정책을 적용할 때의 경계

아래는 기존 결정과 연결한 설계 해석·검토 항목이다. 원문과 위의 선택 범위를 넘어 새 사용자 확정 사항으로 취급하지 않는다.

- 공통 문서와 저장소별 기술 문서는 각각의 책임 범위에 원본을 두고 서로 참조한다. 예를 들어 전체 주문 흐름에서 백엔드의 주문 API 명세를 참조하되 같은 API 정의를 두 곳에서 따로 수정하는 정본으로 만들지 않는다. 참조·생성 결과·검증용 사본은 원본 위치와 revision을 식별해야 한다.
- 요구·기능 ID와 관련 저장소·명세·구현·검증의 연결을 기록한다. 에이전트에게 한 프로젝트의 모든 문서를 한꺼번에 넣지 않고, [P-001](p001-context-and-intent.md)에 따라 해당 작업에 필요한 문서와 정확한 revision의 참조를 전달한다.
- 별도 문서 저장소를 쓰더라도 앱의 승인·위임·예산·실행 정본을 그 저장소로 옮기지 않는다. Git 커밋 여부와 승인 여부는 별개이며, 저장소를 복제한 것만으로 외부 권한이나 사용자 승인이 이전되지 않는다.
- 각 저장소의 commit을 한 번에 원자적으로 반영할 수 있다고 가정하지 않는다. 작업에서 사용한 공통 문서·개별 명세·구현의 버전을 연결하고, 관련 문서가 바뀌면 영향을 검토한 뒤 종속 작업을 진행한다. 사용자 입력이 필요한 충돌은 기존 D-020을 따른다.
- [Q-003](003-github-project-storage.md)의 새 프로젝트 자동 저장 위임과 [Q-013](013-project-specs-in-git.md)의 원격 저장 범위를 유지한다. 별도 문서 저장소도 허용한 소유자·공개 범위 안에서 관리한다. GitHub 미연결 작업을 막거나 기존 문서를 임의 업로드하는 선택으로 확대하지 않는다.
- 기존 프로젝트의 문서를 자동 이동·복제·삭제하지 않는다. 두 안 모두 기존 구조를 연결해서 사용할 수 있어야 한다. 사용자가 명시적으로 요청한 모노레포 및 저장소 하나로 충분한 프로젝트의 문서 배치는 그 구조를 존중한다.
- 1안의 상위 폴더는 관련 저장소를 모으는 일반 폴더다. 상위 폴더를 다시 Git으로 초기화하거나 submodule로 묶어야 한다는 요구가 아니다. 서비스별 초기 자동화 범위는 후속 [Q-017](017-git-hosting-support.md)의 GitHub 우선 지원 결정을 따른다.
- 문서용 저장소 추가에 별도 사람의 승인 단계를 매번 더하는 질문이 아니다. 프로젝트의 유효한 설정과 위임 범위 안에서는 앱이 관리하며, Q-011의 세 묶음 승인과 Q-001의 Git 실행 정책을 유지한다.
