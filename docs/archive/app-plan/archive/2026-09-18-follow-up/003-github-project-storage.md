# Q-003. 비개발자 신규 프로젝트의 GitHub 자동 저장

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


- 질문일·조사일: 2026-09-18
- 상태: **답변 원문 기록 완료 — 신규 프로젝트 자동 저장 위임 확정**
- 대상: GitHub를 연결한 비개발자가 앱에서 새로 만드는 프로젝트
- 선행 결정: [Q-001](001-git-delivery.md), [Q-002](002-git-github-onboarding.md)

## 기존 결정과 아직 남은 판단

- Q-001: 비개발자는 Git 허용 범위 질문 없이 에이전트가 작업 단위와 병합까지 관리한다.
- Q-002: GitHub 연결을 권장하되 건너뛰어도 로컬에서 개발·커밋·병합을 진행한다. 원격 저장소가 필요한 작업 진입 시 연결을 안내한다.
- 기존 [D-013 및 위임 정책](../baseline/02-product-decisions.md)은 프로젝트의 환경·대상·행동·비용 범위 안에서 자율 수행하도록 한다. GitHub 연결 후 새 프로젝트의 원격 저장소를 누가 소유하고 어떤 공개 범위로 만들지, 생성·업로드 위임을 언제 받을지는 정해져 있지 않다.

이번 질문은 새 프로젝트의 GitHub 자동 저장 기본값과 위임 시점을 정한다. GitHub 로그인만 했다는 사실을 모든 기존 로컬 프로젝트의 업로드 지시로 해석하지 않는다. 개발자의 프로젝트별 Git 허용 범위 선택은 Q-001을 따른다.

## 조사 근거

확인일: 2026-09-18. 기존 Q-002의 동일 주제 근거를 재사용하고 필요한 GitHub 저장소 생성 동작을 추가 확인했다.

- [GitHub Desktop의 저장소 게시 흐름](https://docs.github.com/en/desktop/overview/creating-your-first-repository-using-github-desktop): 로컬 저장소를 만든 뒤 별도 Publish repository 동작에서 GitHub에 게시한다. 이때 비공개 여부와 조직 대상을 선택할 수 있다. 로그인·로컬 작업·원격 게시를 구분하는 비교 사례다.
- [gh repo create](https://cli.github.com/manual/gh_repo_create): 비대화형 생성 시 저장소 이름과 공개 범위를 지정할 수 있다. 소유자 지정, 기존 로컬 저장소 연결, 로컬 커밋 push를 지원한다. 비공개 저장소 생성·업로드 자동화의 기술 근거이며, 이 제품이 사용자 허용 없이 실행해도 된다는 근거는 아니다.

## 추천 이유와 적용 범위

비개발자에게 Git·PR 세부 판단을 반복해서 요구하지 않으려면, GitHub 연결 과정에서 이해하기 쉬운 표현으로 자동 저장 범위를 한 번 정하고 재사용하는 방식이 적합하다는 판단이다. 개인 계정의 비공개 저장소를 기본안으로 제시하고, 조직 저장소나 공개 배포는 다른 목적의 선택으로 구분한다.

위 내용은 질문 당시 제시한 추천 이유다. 사용자는 아래 답변에서 1번을 선택했다. 제품 UI에서는 `git push`, `PR`, `remote` 같은 구현 용어를 필수 선택 문구로 사용하기보다 코드가 어디에 저장되는지 설명하는 방향으로 제안했다.

## 질문 원문

**Q-003. 비개발자가 GitHub를 연결한 뒤, 새 프로젝트의 온라인 코드 저장은 어떻게 처리할까요?**

1. **연결할 때 한 번 선택하고 자동 처리 — 추천:** “앞으로 만드는 새 프로젝트를 내 GitHub 비공개 저장소에 자동 저장” 여부를 받습니다. 켜면 이후 새 프로젝트마다 개인 계정에 비공개 저장소를 만들고 코드 업로드·병합까지 자동 관리합니다. 프로젝트별로 이 설정을 끌 수 있습니다.
2. **프로젝트마다 한 번 확인:** 새 프로젝트를 만들 때 “이 프로젝트를 GitHub에도 저장할까요?”를 묻습니다. 동의하면 개인 계정의 비공개 저장소를 만들고, 이후 업로드·병합은 자동 관리합니다.

두 안 모두 기존 저장소의 연결·소유자·공개 범위는 유지합니다. 조직 소유나 공개 저장소를 원하는 경우에는 해당 대상을 별도로 선택합니다.

## 답변으로 확정된 내용

사용자는 Q-003의 **1번, 연결할 때 한 번 선택하고 자동 처리**를 선택했다. 당시 선택지와 공통 조건은 위 질문 원문에 보존한다.

1. 비개발자가 GitHub를 연결할 때 “앞으로 만드는 새 프로젝트를 내 GitHub 비공개 저장소에 자동 저장” 여부를 한 번 선택한다.
2. 사용자가 이 설정을 켜면 이후 새 프로젝트마다 개인 계정에 비공개 저장소를 만들고 코드 업로드·병합까지 자동 관리한다.
3. 프로젝트별로 이 자동 저장 설정을 끌 수 있다.
4. 기존 저장소의 연결·소유자·공개 범위는 유지한다. 조직 소유나 공개 저장소를 원하는 경우에는 해당 대상을 별도로 선택한다.

GitHub 연결만으로 자동 저장 동의를 받은 것으로 처리하는 안이 아니다. 질문의 “여부를 받습니다. 켜면” 조건을 유지한다. 적용 대상은 비개발자가 앱에서 새로 만드는 프로젝트이며, 연결 전에 이미 있던 프로젝트를 일괄 업로드하는 정책은 이번 답변에 포함되지 않는다.

## 후속 세부사항과 검증 대상

아래는 후속 확정 내용, 미확정 사항, 구현 검증 대상을 구분한 기록이다. 후속 답변으로 정해진 항목은 해당 문서를 함께 확인한다.

- 연결 이전에 로컬에서 이미 만들던 프로젝트를 나중에 GitHub에 올리는 경우, 신규 프로젝트 자동 저장 동의를 기존 프로젝트 업로드 권한으로 확대하지 않는다. 실제 프로젝트의 요청·위임 범위를 확인하는 D-013의 적용 사례로 설계한다. 별도의 전역 자동 이전 정책을 확정한 것은 아니다.
- 조직 계정·사내 정책·쓰기 권한 부족, 원격 이름 충돌, 새 저장소 생성 성공 직후 응답 유실, 업로드 중 네트워크 단절의 처리. 기존 외부 효과 receipt·재조회 계약과 연결한다.
- 프로젝트 명세·설계 자료의 Git/원격 저장은 후속 [Q-013](013-project-specs-in-git.md)의 1안으로 확정했다. 정리된 프로젝트 문서를 코드와 함께 관리하고 GitHub 저장을 허용한 프로젝트에서 같이 업로드한다. 실제 제품 자산은 포함하며 대화 전체 원문·공통 기억·인증 정보·앱 내부 DB는 자동 저장 대상에서 제외한다. 모든 과거 이력의 신규 업로드·첨부 사본 전체 보관까지 확정한 것은 아니며 앱 전체 백업 기능으로 확장하지 않는다.
- GitHub 연결 해제·자동 저장 설정 변경 이후 적용 시점은 기존 정책 revision 계약과 정렬한다. 원격 저장소의 삭제·공개 전환이나 이미 업로드한 이력 삭제를 같은 동작으로 취급하지 않는다.
- 보호 브랜치·CI·필수 리뷰·병합 충돌로 자동 병합이 끝나지 않으면 실제 접근 권한과 필수 검증을 확인하고 기존 D-024/D-040의 미완료·대안·인계 계약을 적용한다. Q-001의 자동 병합 선택이 해당 조건을 대신하지 않는다. 이는 기존 결정의 적용이며 새로운 완료 면제 정책을 정하는 질문이 아니다.
