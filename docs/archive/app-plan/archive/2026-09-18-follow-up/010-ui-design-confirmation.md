# Q-010. 화면이 있는 프로젝트의 구현 전 디자인 확정

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


- 질문일·조사일: 2026-09-18
- 상태: **답변 저장 완료 — 1안 선택 및 와이어프레임·디자인 흐름 추가 지시**
- 대상: 개발 에이전트가 사용자의 요청으로 만드는 앱·웹 등 화면이 있는 프로젝트
- 범위: 새 화면 또는 큰 화면 변경의 구현 전 시안 확인 정책. 이 저장소 자체의 콘솔 디자인을 지금 선택하는 질문이 아니다.

## 기존 기획과 남은 판단

- [원래 흐름](../../00-original-flow.md)은 요구사항 인터뷰 → 기능명세 인터뷰 → 기술 조사·스택 확정 → 구현으로 이어진다. 화면의 모습·이동 흐름을 어떤 자료로 사용자와 확정할지는 별도로 명시하지 않았다.
- [REQ-023](../../requirements.csv), [FEAT-025/031](../../features.csv)은 기능·입출력·처리 규칙·검수기준과 승인 명세에 연결된 구현 계획을 요구한다. 이 기능명세 승인에 주요 화면 시안까지 포함할지는 남아 있다.
- [O-09](../baseline/02-product-decisions.md)는 레이아웃·접근성·오류 표현을 시제품에서 확인하도록 한다. 그러나 이것만으로 에이전트가 맡는 모든 사용자 프로젝트의 구현 전 디자인 확인 정책까지 정해졌다고 보기는 어렵다.
- [P-001](p001-context-and-intent.md)은 구현 담당자의 주관으로 요구를 채우지 않도록 세부 지시를 준비하라고 정했다. 디자인도 전달할 명세에 포함할 수 있지만, 사용자가 시안을 직접 승인해야 한다는 정책까지 해당 답변에서 확정되지는 않았다.
- 현재 [산출물 모델](../../../../barrel/core/models.py)의 `ARTIFACT_KINDS`에는 intake·purpose·requirements·feature_table·inventory·report가 있다. 주요 화면 시안과 기능명세 revision의 관계는 이 목록만으로 정의되지 않는다. 반드시 별도 산출물 종류를 추가해야 한다는 결론은 아니다.

예를 들어 ‘상품 목록에서 상품을 고르고 결제한다’는 기능이 같아도 화면 배치·정보량·스타일·이동 흐름은 달라질 수 있다. 기능 테스트 통과만으로 사용자가 기대한 화면과의 일치를 확정할 수 없으므로, 구현 전 확인을 기본 절차에 넣을지 정할 필요가 있다.

## 조사·비교 근거

- [v0의 공식 프로토타이핑 설명](https://v0.app/docs/prototyping)은 초기 화면·상호작용 검토로 가정을 확인하고, 기획·디자인 의도를 구현 단계에 전달하는 방식을 설명한다. 구현 전에 대표 화면과 흐름을 확인하자는 추천의 비교 근거다. 특정 도구나 모든 화면의 프로토타입 제작을 채택한 것은 아니다.
- [v0의 공식 스크린샷 입력 설명](https://v0.app/docs/screenshots)은 화면 자료를 바탕으로 UI를 만들 수 있으며, 동작·사용자 흐름·예외에 대한 명시적 설명을 함께 제공하도록 안내한다. 시안만으로 기능 명세를 대체하지 않고 화면과 동작 규칙을 함께 전달해야 한다는 근거다.

질문 당시에는 **주요 화면 시안을 기존 기능명세 승인에 포함하는 1안**을 추천했다. 사용자는 1안을 선택하면서 **기능명세서 이후 와이어프레임으로 화면 흐름을 먼저 설계하고, 그 뒤 API 작업과 디자인 구체화로 진행하는 단계**를 추가했다. 질문 당시의 단일 시안 표현만으로 이 후속 지시를 축소하지 않는다. 단계별 산출물과 기존 승인 시점의 구체적인 연결은 후속 [Q-011](011-wireframe-design-approval-flow.md)의 1안으로 확정했다.

## 사용자에게 제시한 질문

**Q-010. 에이전트가 화면이 있는 앱·웹을 만들 때, 구현 전에 디자인을 어떻게 확정할까요?**

1. **주요 화면 시안을 보고 기능명세와 함께 승인 — 추천:** 새 화면을 만들거나 화면 구성을 크게 바꿀 때, 주요 화면의 모습과 이동 흐름을 먼저 보여줍니다. 별도 승인 단계를 늘리지 않고 기존 기능명세 승인에 포함해 확정한 뒤 구현합니다.
2. **디자인은 에이전트에 위임:** 원하는 스타일·참고 자료를 받아 에이전트가 디자인을 정리하고 구현합니다. 구현 전 시안 확인은 필수로 두지 않으며, 실행 결과를 보고 수정을 요청할 수 있습니다.

두 안 모두 기존 프로젝트의 작은 수정은 별도 디자인 변경 요청이 없으면 기존 디자인을 따릅니다. 화면이 없는 프로젝트에는 시안을 요구하지 않습니다.

## 사용자 답변 원문

```text
1안 좋은 것 같아. 그런데 여기에 추가로 기능명세서 기반 와이어프레임 생성 단계까지 넣자.
요구사항명세서 -> 기능명세서 -> 와이어프레임 -> API 작업 및 디자인 구체화 -> ... 이렇게 가는거야. 더 현대적인 소프트웨어 공학 flow를 리서치해서 도입해도 좋아(빠르게 iteration 돌리기 좋아서 이 앱과 같은 AI workflow에 적합한 것으로).
화면이 있는 앱은 UI 를 디자인하기 전에 와이어프레임으로 플로우 디자인 정도는 하는게 중요하거든. 그래야 디자인을 갈아엎지 않고 와이어프레임 기반으로 UI 디자인에만 집중할 수 있으니까.
또, UI 를 만들 때 이미지가 들어가 있는거랑 이미지 없이 아이콘들로만 생성된 웹페이지랑 사용자가 느끼는 퀄리티가 달라. 모던 웹페이지들은(특히 랜딩페이지) 배경에 동영상이나 이미지 같은거 꼭 하나씩 넣잖아. 이미지 같은건 GPT 웹사이트를 통해 이미지 생성해서 다운로드 받아서 사용하고, 모던 UI 레퍼런스 조사를 리서치 단계에서 수행해도 좋으니, 이런식으로 작업해줘.
```

## 답변으로 확정된 내용

1. 사용자는 1안인 구현 전 주요 화면 확인 방향을 선택했다. 디자인을 에이전트에게 전부 위임해 사전 확인을 생략하는 2안을 선택한 것이 아니다.
2. 기능명세서를 바탕으로 **와이어프레임 생성 단계를 추가한다.** 사용자가 제시한 순서는 `요구사항명세서 -> 기능명세서 -> 와이어프레임 -> API 작업 및 디자인 구체화 -> ...`다.
3. 화면이 있는 앱은 상세 UI 디자인 전에 와이어프레임으로 화면 흐름을 설계한다. 흐름 때문에 상세 디자인을 다시 만드는 일을 줄이고, 이후 와이어프레임을 바탕으로 UI 디자인에 집중하려는 목적이다.
4. 빠르게 iteration을 돌리기 좋고 이 앱의 AI workflow에 적합한 현대적인 소프트웨어 공학 흐름을 조사해 도입하는 것을 허용했다. 특정 방법론·제품·승인 단계 수를 지정한 것은 아니다.
5. UI의 시각적 품질을 위해 이미지 등 시각 자료의 활용을 작업 흐름에 포함한다. 사용자는 특히 랜딩페이지의 배경 동영상·이미지를 예로 들었다.
6. 당시에는 이미지를 GPT 웹사이트를 통해 생성·다운로드하여 사용하도록 지시하고, 모던 UI 레퍼런스 조사를 허용했다. **후속 [Q-019](019-image-generation-fallback.md)에서 GPT에 한정할 필요가 없다고 정정했다.** Gemini nanobanana·grok·qwen 등 어떤 생성 서비스도 사용할 수 있으며, 핵심은 모던 웹디자인 레퍼런스를 많이 참고하고 이미지의 배경·본문 삽입 등 그 기법을 적용해 AI Slop을 피하는 것이다. GPT 우선이나 GPT 실패 후에만 다른 서비스를 허용하는 조건은 두지 않는다.
7. 당시 질문의 작은 수정에서 기존 디자인 유지, 화면 없는 프로젝트에 시안 비필수라는 공통 범위는 유지한다. 이번 추가 지시를 모든 유지보수 작업에 전체 화면 재설계를 강제하는 의미로 확대하지 않는다.

추가한 흐름·이미지 지시의 적용 경계와 후속 조사 사항은 [P-002](p002-wireframe-and-visual-workflow.md)에 연결한다. 사용자 원문은 이 문서가 보관한다. **후속 Q-011의 1안 선택으로 승인 단계 연결과 API 설계/실제 구현 구분을 확정했다.** 해당 답변 원문은 [Q-011](011-wireframe-design-approval-flow.md)에 보존한다.

## 기존 결정과 후속 지시를 정렬할 경계

아래는 기존 결정과의 연결 및 구현 검토 사항이다. 원문보다 넓은 정책을 확정한 것으로 취급하지 않는다.

- 시안의 목적은 주요 화면 모습과 흐름의 의도를 구체화하는 것이다. 모든 화면·픽셀·내부 작업마다 사용자 확인을 추가하지 않는다. 세부 제작 도구·표현 형식·화면 선정은 선택한 정책 안에서 정한다.
- 화면 자료는 동작·오류·빈 상태·권한·검수기준 등의 명세와 연결한다. 시안에 있는 요소만 보고 새로운 기능이나 권한을 임의로 추론하지 않는다.
- 기능명세 revision과 그 명세를 바탕으로 한 와이어프레임·디자인 자료의 관계를 식별할 수 있어야 한다. 승인 후 사용자 의도·범위를 바꾸는 변경은 기존 변경·재승인 정책과 연결한다.
- 와이어프레임·디자인 자료의 생성 순서와 사용자 승인 시점은 서로 다른 문제다. Q-010 당시에는 연결이 미정이었고, 후속 Q-011에서 요구사항 → 기능명세·와이어프레임 → 기술 스택·주요 화면 상세 디자인의 세 묶음 승인을 확정했다. 와이어프레임 단계는 생략하지 않는다.
- Q-010의 ‘API 작업’은 당시 답변만으로 범위를 단정하지 않았으며, 후속 Q-011의 공통 조건에서 API 입출력·권한·오류 규칙 설계를 먼저 하고 실제 코드는 필요한 승인 후 작은 기능 단위로 구현·검증하도록 확정했다. 승인 전 기술 실험은 기존 D-042 범위를 따른다.
- P-001에 따라 와이어프레임·디자인·동작 명세를 정리해 구현 담당자에게 전달한다. Q-006에 따라 공급자 내부 서브에이전트의 디자인 작업까지 별도 관리하는 기능을 추가하지 않는다.
- 두 안 모두 FEAT-033의 실제 검증과 D-024/FEAT-034의 필수 검수 통과 후 자동 완료를 유지한다. 별도 최종 사용자 승인 관문을 추가하지 않는다.
