## 검토에서 발견한 공백

[requirements.csv](../../requirements.csv)의 REQ-029/030과 [features.csv](../../features.csv)의 FEAT-031/033/034는 승인 명세에 연결된 구현·실제 테스트·증거·필수 기준 충족 후 자동 완료를 요구한다. [model-routing.csv](../../model-routing.csv)에는 조율·조언·구현·양사 조사·사전 평가 역할이 있지만, 구현 세션과 분리한 코드 리뷰를 항상 수행할지와 그 검토 역할은 명시되어 있지 않다.

현재 [verify.py](../../../../barrel/core/verify.py)는 오케스트레이터가 검증 명령을 실제로 실행하는 기반이다. 이것만으로 별도 AI 세션이 요구사항 누락·코드 논리·테스트의 적절성을 검토했다고 볼 수는 없다.

코드를 작성한 세션과 테스트를 구성한 세션이 같은 가정을 공유할 수 있으므로, 실행 결과뿐 아니라 승인 요구와 변경의 관계를 분리된 세션에서 검토할지 정할 필요가 있다는 설계 판단이다. 별도 세션이나 다른 모델 사용이 오류 발견을 보장한다는 주장은 아니다.

## 이미 정해져 있어 다시 묻지 않는 사항

자동 병합이 기존 저장소의 규칙에 막히는 경우는 기존 [위임·접근법·실패 계약](../baseline/04-resolved-details.md)과 [완료 조건](../baseline/03-architecture-and-roadmap.md)을 적용하는 것으로 해석한다. 아래는 새 사용자 답변이 아니라 기존 계약의 적용 정리다.

- 승인된 범위에서 수정 가능한 코드·테스트 문제는 원인을 검토하고 수정·재검증한다.
- 필수 리뷰·접근 권한 등 외부 조건이 충족되지 않으면 필요한 행동을 안내하며 해당 작업을 미완료로 유지한다. 독립 작업은 기존 의존성 규칙에 따라 계속할 수 있다.
- 자동 병합 선택만을 근거로 저장소의 보호 규칙을 해제하거나 기존 위임 범위를 확장하지 않는다.
- 실제 병합이 필요한 작업에서는 병합 예약·요청 수락과 실제 병합 완료를 구분한다.

## 공식 자료 조사

확인일: 2026-09-18. 자료는 비교·구현 근거이며 새 제품의 검증 결과가 아니다.

- [GitHub Copilot code review](https://docs.github.com/en/copilot/concepts/agents/code-review): 코드 리뷰를 별도 기능으로 제공하고 자동 리뷰와 새 push 재검토를 설정할 수 있다. 검토 결과와 실제 변경 버전을 연결하는 참고 사례다. 이 제품에 Copilot을 추가로 도입하거나 별도 구독을 요구하는 제안은 아니다.
- [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches): 저장소는 필수 리뷰·검사·서명 등 병합 조건을 설정할 수 있다. 앱 내부 검토 결과와 원격 저장소에서 요구하는 조건을 구분해야 한다.
- [gh pr merge](https://cli.github.com/manual/gh_pr_merge): 조건 충족 후 자동 병합하는 옵션과 대상 HEAD 일치 조건을 제공한다. 검토한 변경과 실제 병합 대상이 같은지 확인하고 실제 결과를 재조회하는 구현에 참고한다.

## 질문 원문

**Q-004. 구현을 마친 코드에 대해, 완료·병합 전에 별도 AI 세션의 코드 리뷰를 항상 수행할까요?**

1. **항상 수행 — 추천:** 구현한 세션과 다른 새 세션이 승인 명세·실제 변경·테스트 결과를 검토합니다. 확인된 결함을 수정하고 필요한 재검증을 마친 뒤 완료·병합합니다. 작은 코드 수정에도 적용하므로 검토 시간과 AI 사용량은 늘어납니다.
2. **위험도에 따라 수행:** 사전 평가에서 핵심 로직·인증·데이터 변경 등 영향이 큰 작업에는 별도 리뷰를 적용하고, 단순한 코드 수정은 기존 테스트·검수 절차로 완료합니다. 검토 비용은 줄지만 리뷰 필요성 판단에 의존합니다.

검토 단위·범위는 에이전트가 관리하며, 한 공급자만 연결되어 있어도 별도 세션으로 검토할 수 있게 합니다. 실제 테스트와 기존 필수 검수는 두 안 모두 유지합니다. 에이전트 내부의 품질 절차를 정하는 질문입니다.

## 답변으로 확정된 내용

사용자는 Q-004의 **2번, 위험도에 따라 수행**을 선택했다. 당시 선택지와 공통 조건은 위 질문 원문에 보존한다.

1. 사전 평가에서 핵심 로직·인증·데이터 변경 등 영향이 큰 작업에는 구현 세션과 분리한 별도 AI 코드 리뷰를 적용한다.
2. 단순한 코드 수정은 기존 테스트·검수 절차로 완료할 수 있다. 모든 코드 변경에 별도 리뷰를 필수로 두는 1번은 선택하지 않았다.
3. 검토 단위·범위는 에이전트가 관리한다.
4. 한 공급자만 연결되어 있어도 별도 세션으로 검토할 수 있게 한다.
5. 실제 테스트와 기존 필수 검수는 유지한다. 이 결정은 에이전트 내부의 품질 절차이며, 사용자 최종 승인 관문을 추가하는 결정이 아니다.

검토 역할의 기본 모델·강도, 위험도 판정의 세부 규칙, 지적의 판정·재검토 종료 기준은 이번 번호 답변으로 추가 확정되지 않았다.

## 후속 세부사항과 검증 대상

아래는 선택한 위험도 기반 리뷰와 기존 계획·실패 처리 정책 안에서 구현자가 정할 항목이다. 내부 리뷰 방식과 세부 수치를 모두 사용자 질문으로 바꾸지 않는다. 해결하려면 승인된 요구·범위가 달라지는 경우에 기존 변경 판단 절차를 적용한다.

- 검토 역할의 기본 모델·강도·대체 경로와 구현 세션에서 전달할 자료. 기존의 품질 우선 프리셋·단일 공급자 지원·추가 비용 정책과 연결한다.
- 검토 지적 중 반드시 해결해야 할 결함과 선택적 개선 제안의 구분, 구현자와 검토자의 판단이 다를 때의 판정·수정·재검토 종료 기준.
- 검토 중 코드·명세·기준 브랜치가 변경되면 어떤 근거를 무효화하고 다시 검토할지. 기존 입력 hash·revision·결과 통합 계약과 연결한다.
- 검토 세션 실패·사용량 소진·진전 없는 재검토에 기존 대체·예산·실패 처리 규칙을 적용할 수 있는지 확인한다. 필수 검토를 생략한 채 통과로 기록하지 않는다.
