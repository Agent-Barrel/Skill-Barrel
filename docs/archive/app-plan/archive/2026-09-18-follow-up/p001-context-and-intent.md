## 사용자 원문

아래는 Q-005 답변을 포함한 동일 메시지 전체다. 원문의 표현·띄어쓰기·조건을 보존한다.

```text
2안으로 해줘. 그리고 이거랑 별개로, 이 에이전트가 작동할 때 필요한 핵심 원칙을 줄게.
이 에이전트에서 오케스트레이션하는 에이전트들이 한번에 너무 큰 작업을 맡아서 context 압축해야하는 일이 발생하지 않도록 주의해줘. 이 시스템은 상용 에이전트 기반으로 돌아가지만, 작업 방식을 상용 에이전트에 의존해선 안돼. 정보들과 의도를 정확하게 정리하고(장황하지 않지만 문서 간의 참조와 내용을 확인하면 이번 작업(실제 구현이든 리서치이든, 작업 계획이든)에 필요한 모든 정보를 얻을 수 있도록 문서들을 구성), 그 내용을 에이전트에게 전달함으로서 지금 '필요한 작업'을 잘 분할해서 한 세션에서 필요한 작업이 의도한대로 잘 끝나되, context 가 over 될 정도로 부하가 큰 작업을 한세션에 맡기지 말라는거야. 작업을 분할하는거나 문서, 기획등 SOT 를 관리하는 에이전트는 높은 effort 와 고성능 모델로 계속 돌리면서 작업해도 돼.  특히 실 구현 작업에서는 구현 담당에이전트의 주관이 섞이지 않도록, 세부적인 내용들까지 다 정리해서 에이전트에게 전달해서 구현을 맡겨야 해.
정밀하거나 상용에이전트에게 실행시킬 작업 크기가 크다면(줘야할 프롬프트양이 너무 큰 경우) plan 모드를 사용해도 좋지만, 작업 계획을 반드시 검토하고 최초 의도와 부합하는지 확인한 뒤에 작업을 진행해줘. 의도확인 정도는 astra medium 정도로 해도 될 것 같아.
```

## 원문에서 확정된 원칙

아래는 원문을 적용 항목별로 연결한 정리이며 원문을 대체하지 않는다.

1. **세션에 과도하게 큰 작업을 맡기지 않는다.** 오케스트레이션하는 에이전트들이 한 번에 너무 큰 작업을 맡아 context 압축이 필요해지는 상황을 피하도록 작업을 분할한다. 한 세션에서 필요한 작업을 의도대로 마칠 수 있어야 한다.
2. **작업 방식의 주체는 이 시스템이다.** 상용 에이전트를 실행 기반으로 사용하더라도 작업 방식을 상용 에이전트에 의존하지 않는다.
3. **정보와 의도는 정확하고 간결한 정본 문서로 관리한다.** 문서의 내용과 문서 간 참조를 확인하면 해당 구현·리서치·계획 작업에 필요한 모든 정보를 얻을 수 있게 구성하고, 그 내용을 작업 에이전트에게 전달한다.
4. **작업 분할과 정본 관리는 고성능·높은 effort 에이전트가 맡을 수 있다.** 작업을 분할하거나 문서·기획 등 SOT를 관리하는 에이전트는 고성능 모델과 높은 effort로 계속 운영해도 된다.
5. **구현 담당자의 주관으로 요구를 채우지 않도록 세부 지시를 준비한다.** 실제 구현을 맡기기 전에 세부적인 내용까지 정리해 전달한다.
6. **정밀하거나 전달할 프롬프트가 큰 작업은 Plan 모드를 사용할 수 있다.** Plan 모드 사용 자체는 허용이며, 큰 작업을 한 세션에 과부하로 맡기라는 예외는 아니다.
7. **실행 전에 작업 계획을 검토하고 최초 의도와 부합하는지 확인한다.** Plan 모드를 사용했다는 사실만으로 의도 부합 확인을 마친 것으로 취급하지 않는다.
8. **의도 확인 역할에는 Astra medium 정도를 사용할 수 있다.** 사용자가 허용한 수준이며, 작업 분할·정본 관리 역할 전체를 medium으로 낮추는 결정이 아니다.

## 기존 결정과의 연결

아래는 다음 세션 정렬을 위한 적용 해석이다. 원문보다 넓은 결정을 추가한 것으로 취급하지 않는다.

**후속 명확화:** [Q-006 답변](006-native-subagent-boundary.md)에서 사용자는 상용 에이전트 내부의 서브에이전트까지 확인하지 않고 수행 방식을 자율로 두라고 정했다. 이 문서의 작업 분할·정본 전달·의도 확인은 앱이 직접 배정하는 작업을 중심으로 적용한다. 내부 서브에이전트마다 별도 문서·계획·맥락·사용량을 검토하는 요구로 확대하지 않으며, 과도한 세부 관리로 불필요한 토큰을 소비하지 않는다. 사용자 원문은 위와 Q-006에 각각 보존했다.

**추가 명확화:** [Q-016 답변](016-unexpected-context-compaction.md)에서 사용자는 예상 밖 압축의 별도 세션 관리 선택보다 작업 결과를 확인하면 제대로 수행했는지 판단할 수 있다고 답했다. 사전 분할·의도 전달·결과 검증에 집중하며, 압축 발생만으로 별도 정본 점검이나 의무적인 세션 교체를 추가하지 않는다. 실제 실행·검증 실패에는 기존 복구 정책을 적용한다.

- D-007, D-030/031 및 `ContextBundle`: 특정 공급자 세션의 자체 기억 대신 앱 정본을 사용한다는 기존 방향을 강화한다. 문서의 참조 관계·정확한 revision·생략 범위를 포함해 세션별 입력을 준비한다.
- D-022 및 `TaskContract`: 기존의 충분한 계획 요구를 작업 크기·지시의 구체성·실행 전 의도 확인까지 구체화한다. 계획을 작성하는 역할과 이를 최초 의도에 대조하는 역할을 구분할 필요가 있다.
- D-032: 문서·계획의 선행 변경과 필요한 승인 후 종속 구현을 시작한다. 작은 작업으로 나눴다는 이유만으로 의존성 있는 작업을 병렬화하지 않는다.
- D-034 및 RTE-011의 사전 평가는 요청·영향 범위를 판단한다. 이번 의도 확인은 작성된 작업 계획을 최초 의도에 대조하는 절차이므로, 같은 모델을 쓴다는 이유만으로 두 절차를 같다고 취급하지 않는다.
- [Q-004](004-independent-code-review.md)의 위험도별 코드 리뷰는 구현 후 품질 절차다. 이번 실행 전 계획·의도 확인과 구분한다. Q-004를 항상 코드 리뷰하는 정책으로 바꾼 답변은 아니다.
- 고성능 모델의 지속 운영 허용은 추가 비용·권한·예산을 무제한으로 확대하거나 정본을 한 장기 CLI 세션에만 맡기는 선택으로 해석하지 않는다.
- 이번 기록은 다음 세션의 기획 정렬을 위한 것이다. 기존 계획·CSV·코드 수정이나 실제 에이전트 실행·모델 변경을 수행한 것이 아니다.

## 현재 코드·기획과 대조해 확인한 정렬 대상

아래는 저장소를 읽어 확인한 차이와 적용 해석이다. 사용자에게 다시 선택받아야 하는 원칙이나 이번 세션의 코드 수정 내역이 아니다.

- [현재 유닛 실행기](../../../../barrel/core/unitloop.py)의 `_resolve_interactions`는 `AWAITING_PLAN_APPROVAL`이면 계획·최초 의도 대조 없이 `approve_plan()`을 호출한다. [Claude 배치 실행기](../../../../step2step/claude/runner.py)와 [Codex 제어 설명](../../../codex-control.md)에도 Plan 모드의 자동 승인 경로가 있다. **계획 승인 화면을 통과시켰다는 사실을 사용자 요구의 계획 검토·의도 확인으로 취급할 수 없다.** 다음 세션에는 내용 검토 결과를 실행 조건에 연결해야 한다. 이는 매번 사람의 승인을 추가한다는 뜻이 아니다.
- [현재 구현 프롬프트](../../../../barrel/prompts/developer_task.txt)는 기능 카드를 유일한 사양으로 표현한다. 누락 사항을 질문하라는 규칙은 있지만, 이번 원칙의 요구·의도·세부 설계·문서 참조를 모두 전달했는지는 별도다. [유닛 프롬프트 구성](../../../../barrel/core/unitloop.py)의 목표 문서·참조·검수 전달을 참조하되, 카드 한 장이나 전체 대화 이력만으로 필요한 정본 전달을 대체하지 않는다.
- [기존 O-07](../baseline/02-product-decisions.md)은 접근 범위를 강제할 수 없으면 직렬화하고 필요시 작업 단위를 크게 잡는다고 적혀 있다. 새 원칙 적용 시 **잠금 범위를 넓히는 것과 한 세션에 맡길 작업량을 늘리는 것을 구분**해야 한다. 저장소 전체를 잠가야 해도 실행 작업은 작은 단위로 순차 분할할 수 있다. O-07을 context 과부하를 허용하는 근거로 사용하지 않는다.
- [현재 Codex 이벤트 처리](../../../../step2step/codex/events.py)는 token usage를 보관하지만 `Turn.record()`의 일반 도구 내역에서 `contextCompaction`을 제외한다. [Claude 훅](../../../../step2step/claude/hooks.py)은 선택적 이벤트 파일이 있을 때 `PreCompact`를 기록한다. 이것만으로 사전 맥락 예산·재분할·압축 후 복구가 구현됐다고 볼 수 없다. 원시 이벤트와 정상화된 기록, 실제 중단 가능성을 각각 검증해야 한다.
- CLI의 내부 보조 에이전트 사용은 [Q-006](006-native-subagent-boundary.md)에서 자율로 확정했다. 앱이 내부 보조 에이전트까지 개별 확인·통제하는 기능을 이 원칙의 필수 구현으로 추가하지 않는다. 앱이 직접 배정하는 작업의 분할·의도 전달·결과 검증에 집중한다.

## 후속 설계·검증 항목과 사용자 판단의 구분

아래 항목 전부를 사용자에게 새로 선택받아야 하는 질문으로 취급하지 않는다. P-001·Q-006·Q-016과 기존 결정 안에서 구현자가 구체화·검증할 사항과 새로운 사용자 정책 판단을 구분한다. 추천이나 기술 추정을 사용자 확정으로 기록하지 않는다.

- 예상 밖 압축은 [Q-016](016-unexpected-context-compaction.md)에 따라 작업 결과 검증 중심으로 다룬다. 압축 전용 관리 정책을 미확정 질문으로 남겨 재질문하지 않는다. 실제 실행 실패 때의 정본 기록·재개·재검증은 기존 복구 계약 안에서 설계한다.
- 실행 전 의도 확인의 적용 범위를 작은 작업까지 어떻게 구체화할지, 새 작업 계획·계획 변경의 검토 시점과 결과 기록.
- 구현 중 전달받은 지시의 누락·모순·새 의존성을 발견한 경우 정본 관리자에게 되돌리는 기준. 사용자 새 판단이 필요한 경우와 기존 정본으로 해결할 경우의 구분.
- 사전 작업 분할에 필요한 입력 크기와 맥락 여유를 적절히 추정한다. 고정 토큰 수나 비율은 정하지 않았으며, 이를 위해 내부 세션이나 서브에이전트마다 별도 감시·AI 검토 계층을 만드는 것은 Q-006·Q-016의 요구가 아니다. 필요한 관측 정보·단위는 드라이버 구현에서 검증한다.
- SOT 관리자와 구현 담당자·계획 검토자 간의 쓰기 권한·문서 변경 요청·완료 산출물 채택 계약.
- 실제 기본 모델 식별자·강도·가용성과 대체 경로. “Astra medium 정도로 해도 된다”를 모든 환경에서 해당 모델/effort가 지원된다는 검증 결과로 취급하지 않는다.
