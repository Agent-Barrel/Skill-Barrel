## 기존 결정과 구분해야 하는 공백

- [Q-009](009-cancelled-work-artifacts.md)는 작업 취소 시 미반영 변경의 보관·폐기를 정했다. 프로젝트 등록과 대화·결정 이력 전체를 정리하는 동작까지 정한 답변은 아니다.
- [D-046](../baseline/04-resolved-details.md)은 개별 기억의 사용중지·영구삭제, D-062/D-063은 임시 자원의 정리를 다룬다. 프로젝트를 목록에서 보관하는 동작과 해당 프로젝트 앱 기록의 삭제를 같은 동작으로 구현할 근거는 없다.
- [Q-013](013-project-specs-in-git.md)·[Q-014](014-project-repository-scope.md)·[Q-015](015-shared-project-documentation.md) 이후 한 프로젝트에는 여러 코드 저장소와 공통 문서 저장소가 연결될 수 있다. 앱의 프로젝트 등록·이력, 로컬 코드·문서 원본, 원격 저장소·배포 자원을 구분해야 한다.
- [FEAT-003/042](../../features.csv)는 등록·조회·소통을 명세하지만 프로젝트 보관·등록 해제·프로젝트 단위 기록 삭제의 지원 범위를 정하지 않는다.
- 현재 코드 `50da927`의 [Project 모델](../../../../barrel/core/models.py)에는 보관·삭제 상태가 없고, [서비스](../../../../barrel/core/service.py)와 [웹 API](../../../../barrel/web/app.py)에서 프로젝트 생성·목록·조회는 확인했지만 프로젝트 보관·삭제 경로는 찾지 못했다. 현재 코드의 부재 자체를 새 기능 도입 승인으로 취급하지 않는다.

예를 들어 시험용 프로젝트를 기본 목록에서 치우려는 것과 그 프로젝트에 대한 대화·기억을 지우려는 것은 다른 의도다. 이 구분이 없으면 구현자가 목록 정리를 데이터 삭제로 해석하거나, 반대로 지우려는 데이터를 계속 보존할 수 있다.

## 공식 자료 조사와 추천

- [IntelliJ IDEA의 프로젝트 관리](https://www.jetbrains.com/help/idea/open-close-and-move-projects.html)는 프로젝트 닫기·다시 열기·최근 목록 관리 동작을 구분한다. 작업 화면의 정리와 프로젝트 파일을 다루는 동작을 구별하는 비교 사례다.
- [Linear의 보관·삭제 안내](https://linear.app/docs/delete-archive-issues)는 보관한 프로젝트를 다시 복원해 편집할 수 있다고 설명한다. 보관과 삭제된 항목의 처리를 별도로 다룬다. Linear의 자동 보관 시점이나 삭제 후 복원 기간을 이 앱의 정책으로 제안하는 것은 아니다.

질문 당시 **1안을 추천했고 사용자가 1안을 선택했다.** 기존 결정을 남겨 두고 나중에 유지보수할 수 있는 보관과, 사용자가 더 이상 남기고 싶지 않은 프로젝트 앱 기록의 삭제를 구분하는 방식이다. 2안은 초기 구현 범위를 줄이는 대안이었지만 선택하지 않았다.

## 사용자에게 제시한 질문

**Q-020. 더 이상 진행하지 않는 프로젝트를 정리하는 기능은 어디까지 제공할까요?**

1. **보관 + 앱 기록 영구 삭제 — 추천:** 보관하면 기본 목록에서 숨기고 이력을 유지해 나중에 다시 열 수 있습니다. 별도의 삭제 기능으로 해당 프로젝트의 앱 내 대화·명세 사본·프로젝트 기억도 지울 수 있게 합니다.
2. **초기는 보관만:** 목록에서 숨기고 나중에 다시 여는 기능만 제공합니다. 프로젝트 기록 전체를 지우는 기능은 이번 구현 범위에서 제외합니다.

두 안 모두 로컬 코드·Git에 저장한 문서·원격 저장소·배포 서비스는 유지합니다. 진행 중 작업과 미반영 변경은 기존 중단·보존 규칙에 따라 처리하며, 이미 정한 개별 기억 삭제 기능도 유지합니다.

## 답변으로 확정된 내용

사용자는 **1안, 보관 + 앱 기록 영구 삭제**를 선택했다. 당시 질문·선택지·공통 조건은 위에 보존한다.

1. 초기 구현 범위에 프로젝트 보관과 별도의 앱 기록 영구 삭제 기능을 모두 포함한다.
2. 보관하면 기본 프로젝트 목록에서 숨기되 이력을 유지하여 나중에 다시 열 수 있다. 보관만으로 기록을 삭제하지 않는다.
3. 별도의 삭제 기능으로 해당 프로젝트의 앱 내 대화·명세 사본·프로젝트 기억을 지울 수 있게 한다. 초기에는 보관만 제공하는 2안은 선택하지 않았다.
4. 로컬 코드·Git에 저장한 문서·원격 저장소·배포 서비스는 두 동작으로 삭제하지 않고 유지한다.
5. 진행 중 작업과 미반영 변경에는 기존 중단·보존 규칙을 적용한다. 이미 확정한 개별 기억 삭제 기능도 유지한다.

이 답변은 제품이 제공할 기능에 관한 결정이다. 현재 레포의 코드·문서·실제 프로젝트 기록을 삭제하라는 실행 요청이 아니다.

## 기존 결정과 연결한 적용 해석

아래는 기존 결정과 연결한 설계 해석·검토 항목이다. 질문의 선택 범위를 넘어 새로운 사용자 확정 사항으로 취급하지 않는다.

- 보관 상태와 작업 실행 상태를 구분하고, 오래된 Slack 답변·승인이나 앱 재시작만으로 관리가 다시 시작되지 않도록 기존 유효성 검사와 연결한다.
- 삭제 대상인 프로젝트 본문·명세 사본·프로젝트 기억의 파생 요약·색인은 기존 D-046의 삭제 전파 원칙과 연결한다. 공통 성공 경험은 후속 [Q-021](021-project-deletion-shared-experience.md)의 확정 답변에 따라 프로젝트 고유 정보를 제거하고 일반화된 개발 노하우만 유지한다. 고유 정보를 분리할 수 없는 경험은 삭제하며, 개별 공통 기억 직접 삭제는 기존 D-046을 유지한다.
- 프로젝트 기록을 지우더라도 이미 발생한 비용이 취소되거나 미확정 예산 예약이 풀렸다고 처리하지 않는다. 재정산·외부 효과 복구·중복 명령 거부에 필요한 최소 식별 기록과 삭제할 본문을 구분한다.
- 앱 밖의 Git 이력·Slack 메시지·공급자 기록·OS 백업까지 지웠다고 표시하지 않는다. 저장소·배포 자원 폐기는 별도로 범위를 지정하는 작업이다.
- 앱이 생성하거나 clone했더라도 사용자가 계속 이용하는 정식 프로젝트 저장소·코드·Git 문서는 위의 보존 대상이다. 앱이 만들었다는 이유만으로 임시 clone/worktree와 함께 정리하지 않는다. 임시 작업 사본은 기존 D-062/D-063의 소유권·소비자·결과 보존 조건으로 구분한다.
