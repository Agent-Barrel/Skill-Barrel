# Q-006. 작업용 CLI의 자체 보조 에이전트 생성 범위

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


- 질문일: 2026-09-18
- 상태: **답변 저장 완료 — 제시한 선택지 대신 내부 수행 방식의 자율성 확정**
- 선행 근거: [P-001](p001-context-and-intent.md)의 시스템 주도 작업 분할·정본 전달·context 과부하 예방
- 범위: 개발 에이전트 제품이 실행하는 상용 CLI 세션. 사용자가 따로 쓰는 개인 CLI 설정을 변경하는 질문이 아니다.

## 이 결정을 먼저 확인하는 이유

아래는 질문 당시 작성자의 검토 관점이다. **사용자는 내부 보조 에이전트까지 확인·관리할 필요가 없다고 답했다.** 따라서 아래의 내부 추적 필요성은 채택된 요구사항이 아니며, 실제 확정 범위는 답변 원문과 그 아래 정리를 따른다.

우리 시스템이 작은 작업을 나눠 맡겨도, 작업용 CLI가 내부에서 다시 보조 에이전트를 생성하면 별도의 작업·입력 맥락·모델 사용·산출물이 생긴다. 내부 작업의 범위와 전달 문서를 우리 시스템이 추적하지 않으면 사용자가 지정한 작업 분할·의도 보존 원칙을 전체 실행에 적용했다고 입증하기 어렵다. 이는 공식 기능을 이 제품에 적용할 때의 설계상 판단이다.

[기존 아키텍처](../baseline/03-architecture-and-roadmap.md)는 앱의 `TaskContract`, `ContextBundle`, 자원 잠금·예산·실행 슬롯을 정하지만, CLI 내부 보조 에이전트를 허용할지와 앱 작업 원장에 어떻게 포함할지는 정하지 않았다. 공급자의 보조 에이전트 기능이 있다는 사실만으로 그 안에서 작업·정본 관리를 맡기기로 확정하지 않는다.

## 조사 근거 — 사용자 결정과 구분

확인일: 2026-09-18. 아래는 공식 문서와 현재 저장소의 읽기 전용 조사이며, 실제 설치 버전에서 통제 실험을 수행한 결과가 아니다.

- Codex 공식 하위 에이전트 문서는 `agents.enabled`로 멀티 에이전트 도구를 켜고 끌 수 있고, 동시 하위 스레드 수와 기본 모델·effort 설정을 제공한다고 설명한다. 실제 앱이 사용할 CLI 버전의 지원·설정 우선순위는 별도 검증 대상이다. [OpenAI 공식 문서](https://developers.openai.com/es-419/docs/agent-configuration/subagents). 영어 원문 링크는 조회 시 404여서 공식 번역 페이지의 본문을 확인했다.
- Claude Code 공식 문서는 작업을 보조 에이전트에 자동 위임할 수 있고, 각 보조 에이전트가 별도 context를 사용한다고 설명한다. `permissions.deny`의 `Agent` 차단으로 위임을 막는 방법을 제시한다. 또한 보조 에이전트에도 자동 압축이 적용된다고 설명하므로, 내부 위임만으로 context 과부하 예방이 해결됐다고 간주하지 않는다. [Claude Code 하위 에이전트 문서](https://code.claude.com/docs/en/sub-agents).
- Claude CLI의 `--disallowedTools`는 도구 이름 전체를 지정하면 해당 도구를 사용 가능한 맥락에서 제거하는 수단으로 설명된다. 앱 관리 세션의 제어 후보이며 사용자 개인 설정의 일괄 변경을 뜻하지 않는다. [Claude CLI reference](https://code.claude.com/docs/en/cli-reference).
- 현재 [유닛 실행기](../../../../barrel/core/unitloop.py)는 앱이 관리하는 작업 단위·세션·검수 흐름을 갖지만, 이번에 확인한 코드에는 모든 CLI 내부 보조 에이전트의 작업 계약·정본 입력·맥락 크기를 앱이 배정하고 검토한다는 계약이 없다. [Claude 훅](../../../../step2step/claude/hooks.py)의 설명도 주 에이전트 `Stop`과 `SubagentStop`을 구분한다. 주 세션의 관측만으로 내부 작업까지 동일하게 관리된다고 가정하지 않는다.

## 사용자에게 제시한 질문

**Q-006. 우리 시스템이 일을 맡긴 Codex·Claude가, 내부에서 보조 에이전트를 추가로 만드는 것은 어디까지 허용할까요?**

1. **작업 배정은 우리 시스템에서만 — 추천:** 작업용 CLI의 자체 보조 에이전트 생성은 막습니다. 도움이 더 필요하면 우리 조율자에게 요청하고, 조율자가 작업을 나눠 필요한 문서·세부 지시를 준비한 뒤 별도 세션에 배정합니다. 우리 시스템 자체의 여러 에이전트 운영은 유지합니다.
2. **작은 읽기 전용 보조 작업만 내부 재위임 허용:** 우리 시스템이 사전에 정한 범위·맥락 크기·실행 한도 안에서 코드 탐색·자료 조회 같은 보조 작업은 CLI 내부 에이전트에 맡길 수 있습니다. 전달 문서·사용량·결과를 우리 시스템이 추적하며, 구현·정본 수정은 우리 시스템이 직접 배정한 에이전트만 수행합니다.

공통 조건: 작업 분할·정본·최초 의도 확인의 책임은 우리 시스템에 둔다. CLI 내부 작업을 허용하더라도 예산·동시 실행·권한·의존성 검사를 우회하지 않는다. 내부 보조 에이전트의 허용은 이번 문서 검토에서 실제 에이전트를 추가 실행하라는 지시가 아니다.

## 사용자 답변 원문

```text
에이전트 내부의 서브에이전트 확인까지는 굳이 안해도 될 것 같아. 작업을 잘 나눴고 의도를 상용에이전트에게 잘 전달했으면 걔들이 똑똑하기 때문에 시킨일을 알아서 잘 할거고, 그 방식은 자율로 둬도 될 것 같아. 결과물만 잘 나오면 된다고 생각해. 너무 마이크로 매니징하려고 하다가 불필요하게 토큰 소모량이 커지는건 원치 않아.
```

## 답변으로 확정된 내용

1. **상용 에이전트 내부의 서브에이전트까지 확인하지 않는다.** 우리 시스템이 내부 서브에이전트를 하나씩 배정·점검·검토하는 요구를 두지 않는다.
2. **맡긴 작업의 내부 수행 방식은 상용 에이전트에 자율로 둔다.** 우리 시스템이 작업을 잘 나누고 의도를 잘 전달한 것을 전제로 한다. 제시한 1안의 자체 생성 금지나 2안의 읽기 전용 재위임 제한을 선택한 답변이 아니다.
3. **우리 시스템은 작업 분할·정확한 의도 전달·결과물에 집중한다.** 내부 수행 절차를 세밀하게 관리하는 것보다 의도한 결과물이 제대로 나오는 것이 중요하다.
4. **과도한 세부 관리로 불필요한 토큰 소비를 늘리지 않는다.** 내부 서브에이전트의 입력·맥락·계획·실행을 모두 별도 AI 검토하는 절차를 추가하지 않는다. 새 수치 예산이나 모델별 토큰 상한을 정한 답변은 아니다.

## 이전 원칙·선택지와의 관계

- [P-001](p001-context-and-intent.md)의 작업 분할, 정확·간결한 SOT, 구체적인 구현 지시, 앱이 배정한 작업의 실행 전 계획·최초 의도 확인은 유지한다. 이를 공급자 내부의 모든 하위 계획·도구 호출까지 개별 검토하는 요구로 확대하지 않는다.
- “결과물만 잘 나오면 된다”는 결과 중심의 운영 원칙이다. [Q-004](004-independent-code-review.md)의 위험도별 코드 리뷰와 실제 테스트·필수 검수 조건을 폐기한 답변으로 해석하지 않는다.
- 기존 프로젝트 범위·권한·예산·외부 효과·작업 의존성은 앱이 맡기는 작업의 경계로 유지한다. 이 경계를 내부 서브에이전트별 계약·사용량 원장·개별 승인으로 세분화하는 요구는 채택하지 않는다.
- 질문 당시의 “내부 보조 에이전트를 모두 추적해야 한다”는 작성자 해석은 이번 답변으로 대체된다. 공식 문서에 차단·추적 수단이 있다는 사실은 해당 기능을 제품에서 구현해야 한다는 결정이 아니다.

## 채택하지 않은 제안과 후속 적용

- 내부 서브에이전트 생성 차단, 읽기 전용으로 제한하는 정책, 내부 작업마다 사전 계약·문서·모델·effort·맥락·사용량을 검사하는 체계는 이번 답변에서 채택하지 않았다. 이 문서의 조사 항목을 그대로 필수 구현 목록에 옮기지 않는다.
- 앱이 직접 배정하는 작업의 크기와 전달할 정본을 적절하게 준비하고, 돌아온 산출물을 기존 검수 기준과 최초 의도에 맞춰 확인한다. 내부 자율성을 이유로 큰 작업을 통째로 넘기는 것은 P-001과 맞지 않는다.
- 앱이 직접 관리하는 세션의 예상 밖 압축도 [Q-016](016-unexpected-context-compaction.md)에서 작업 결과 검증 중심으로 명확히 했다. 압축 감지에 따른 별도 점검·세션 교체 관문을 필수로 추가하거나 내부 서브에이전트 하나하나를 추적하지 않는다. 실제 실패는 기존 체크포인트·복구 계약을 적용한다.
- 후속 인터뷰에서도 사용자의 제품 정책 판단이 필요한 쟁점과 구현자가 자율로 해결할 내부 기술 세부사항을 구분한다. 불필요한 통제·검토 계층을 추가하는 방향으로 질문을 설계하지 않는다.
