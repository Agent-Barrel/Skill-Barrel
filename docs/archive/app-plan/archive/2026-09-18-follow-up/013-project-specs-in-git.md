# Q-013. 프로젝트 기획·설계 문서의 Git 관리와 원격 저장 범위

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


- 질문일·조사일: 2026-09-18
- 상태: **답변 저장 완료 — 1안 확정**
- 대상: 앱이 사용자 프로젝트를 위해 새로 만드는 요구사항·기능명세·결정 기록·와이어프레임·API 명세·디자인 자료
- 범위: 프로젝트 산출물을 코드와 함께 버전 관리하고 허용된 원격 저장소에 올릴지. 앱 전체 백업이나 중앙 Relay의 보관 범위를 바꾸는 질문이 아니다.

## 기존 기획과 남은 판단

- [Q-003](003-github-project-storage.md)은 GitHub 연결 때 새 프로젝트의 개인 비공개 저장소 자동 저장 여부를 한 번 선택하도록 했고, 자동 저장할 파일과 이력 범위를 후속 사항으로 남겼다.
- [P-001](p001-context-and-intent.md)은 필요한 정보·의도를 문서와 참조로 정확하게 전달하도록 한다. [Q-010](010-ui-design-confirmation.md)·[Q-011](011-wireframe-design-approval-flow.md)은 와이어프레임·API·상세 디자인 자료까지 그 흐름에 추가했다. 이 문서들이 코드 저장소에 함께 남을지는 별도다.
- [D-019](../baseline/decisions.md)·[REQ-026](../../requirements.csv)은 향후 프로젝트에도 요구·기능 CSV를 사용하도록 한다. [아키텍처의 저장·승인 계약](../baseline/03-architecture-and-roadmap.md)은 Mac 로컬 정본과 불변 승인 snapshot을 정하지만, 생성한 모든 프로젝트 설계 자료의 GitHub 업로드 범위를 확정하지는 않는다.
- 현재 [기능 CSV 코드](../../../../barrel/core/spec_csv.py)와 [서비스 프롬프트](../../../../barrel/core/service.py)는 프로젝트의 `docs/spec/features.csv`를 사용한다. 다만 이것만으로 새로 추가한 요구·결정·와이어프레임·API·디자인 자료 전체의 원격 저장 정책까지 구현됐다고 볼 수 없다.
- 현재 `Service._commit_develop_artifacts()`는 기능 CSV를 제외한 나머지에 `gitops.commit_all()`을 호출하며, [Git 작업 코드](../../../../barrel/core/gitops.py)의 해당 함수는 `git add -A`로 작업 트리 변경을 모은다. 기능 CSV는 별도 커밋 경로가 있다는 설명이지 모든 산출물의 게시 범위를 명시적으로 분류했다는 근거는 아니다.

예를 들어 사용자가 나중에 저장소를 다른 개발자에게 전달하면, 코드만 있어도 실행할 수는 있지만 왜 그 화면 흐름·API 규칙을 선택했는지는 따로 전달해야 할 수 있다. 반대로 앱에서 다룬 모든 대화·기억·실행 상태까지 프로젝트 저장소의 일부로 볼 필요는 없다. 프로젝트에 남길 정리된 자료의 범위를 정하려는 질문이다.

## 조사·비교 근거

- [Kiro 공식 가이드의 Specification as history](https://kiro.dev/docs/guides/learn-by-playing/05-using-specs-for-complex-work/)는 `.kiro/specs`의 명세 파일을 코드와 함께 커밋해 의도·설계를 향후 개발자와 에이전트가 참고할 수 있도록 권장한다. 코드와 프로젝트 명세를 함께 관리하는 직접적인 비교 사례다. Kiro 자체를 도입하거나 자연어로 단계 승인을 대신하는 정책까지 채택한 것은 아니다.
- [P-002](p002-wireframe-and-visual-workflow.md)에서 이미 확인한 [GitHub Spec Kit의 Spec of Specs](https://github.github.com/spec-kit/concepts/spec-of-specs.html)는 버전 관리하는 로드맵과 작은 명세의 상호 참조를 설명한다. 이 자료는 참조로 의도를 보존하는 방식의 근거로 재사용하며, 이 앱의 CSV 형식을 교체하는 이유로 사용하지 않는다.

질문 당시에는 **프로젝트의 기획·설계 자료를 코드와 함께 관리하는 1안**을 추천했고, 사용자가 1안을 선택했다. 특정 비교 제품이나 문서 도구의 전체 방식을 채택한 것은 아니다.

## 사용자에게 제시한 질문

**Q-013. 앱이 만드는 프로젝트 기획·설계 문서도 코드와 함께 Git으로 관리하고 GitHub에 저장할까요?**

1. **코드와 함께 관리 — 추천:** 요구사항·기능명세·결정 기록·와이어프레임·API 명세·디자인 자료를 프로젝트 문서로 남깁니다. 코드와 함께 버전을 관리하고, GitHub 저장을 허용한 프로젝트에서는 같이 업로드합니다. 다른 개발자나 에이전트가 저장소를 받아도 개발 의도를 확인할 수 있습니다.
2. **기획·설계는 앱 로컬에 보관:** 앱이 새로 만드는 기획·설계 자료는 Mac의 앱 관리 공간에 보관하고 GitHub 자동 저장에서 제외합니다. 코드와 실제 제품을 구성하는 파일은 프로젝트 저장소로 관리합니다.

두 안 모두 실제 제품에 쓰는 이미지·코드·실행에 필요한 파일은 프로젝트에 포함합니다. 대화 전체 원문·공통 기억·인증 정보·앱 내부 DB는 GitHub 자동 저장 대상에서 제외합니다. 기존 프로젝트의 문서와 저장 규칙은 존중합니다.

## 답변으로 확정된 내용

사용자는 **1안, 코드와 함께 관리**를 선택했다. 당시 질문·선택지·공통 조건은 위에 보존한다.

1. 앱이 만드는 요구사항·기능명세·결정 기록·와이어프레임·API 명세·디자인 자료를 프로젝트 문서로 남기고 코드와 함께 버전 관리한다.
2. GitHub 저장을 허용한 프로젝트에서는 이 기획·설계 자료도 코드와 함께 업로드한다. 다른 개발자나 에이전트가 저장소를 받아 개발 의도를 확인할 수 있도록 한다.
3. 실제 제품에 쓰는 이미지·코드·실행에 필요한 파일은 프로젝트에 포함한다.
4. 대화 전체 원문·공통 기억·인증 정보·앱 내부 DB는 GitHub 자동 저장 대상에서 제외한다.
5. 기존 프로젝트의 문서와 저장 규칙은 존중한다.

## 선택한 정책을 적용할 때의 경계

아래는 기존 결정과 연결하기 위한 구현 해석·검토 항목이다. 원문보다 넓은 정책을 확정한 것으로 취급하지 않는다.

**후속 확정:** [Q-014](014-project-repository-scope.md)에서 여러 독립 저장소를 한 프로젝트로 관리하는 범위를 확정했다. [Q-015](015-shared-project-documentation.md)에서는 새 다중 저장소 프로젝트의 공통 기획·설계를 별도 문서 저장소 하나에서 관리하고, 저장소별 기술 문서는 해당 코드 저장소에서 참조하도록 정했다. 기존 문서 구조와 작은 프로젝트를 존중하며, 이 문서의 Git 관리·원격 저장 범위는 유지한다.

- 1안은 해당 프로젝트의 의도·결정·설계·구현에 필요한 자료를 대상으로 한다. 공통 선호, 다른 프로젝트 정보, 전체 대화 로그나 CLI transcript를 문서 폴더에 통째로 넣는 결정이 아니다. 개발에 필요한 질문·답변에서 정리한 프로젝트 결정 기록과 전체 대화 원문을 구분한다.
- 문서를 코드와 함께 관리해도 앱의 실행·위임·예산·승인 정본은 기존 Mac 로컬 계약을 따른다. 저장소를 복제했다는 사실만으로 그 Mac에서의 로그인·외부 권한·승인 상태가 복원되지 않는다. 앱 전체 백업·복원 기능을 추가하지 않는다.
- 명세 초안 저장, 사용자 승인, Git 커밋, 원격 업로드, 실제 구현 완료를 서로 구분한다. 문서의 상태·revision·관련 입력이 드러나야 하며 파일이 Git에 있다는 이유만으로 유효한 승인이 있다고 판단하지 않는다.
- 1안의 자료와 코드에는 추적 가능한 참조를 두고, 직접 수정에 따른 충돌은 기존 D-020의 설명·사용자 판단 정책을 따른다. 앱의 snapshot과 작업본을 독립된 두 정본으로 운영하지 않는다.
- 프로젝트에 이미 있던 문서를 자동으로 삭제·이동하거나 이력을 지우지 않는다. 앱에서 생성하는 자료를 기존 프로젝트의 문서 구조와 연결한다.
- Q-001의 Git 실행 범위와 Q-003의 원격 자동 저장 위임을 유지한다. GitHub 연결을 건너뛴 프로젝트를 문서 저장 때문에 업로드하거나, 로그인만으로 기존 프로젝트를 일괄 업로드하지 않는다.
- 실행에 필요한 파일과 실제 비밀값을 구분한다. 설정 구조·예시와 자산은 프로젝트 산출물로 다루되 로그인 토큰·실제 비밀값·기기별 앱 상태를 자동 저장 범위에 포함하지 않는다. 단순 전체 스테이징을 게시 범위 결정의 대체로 삼지 않는다.
- 이미지 생성 서비스에서 생성해 실제 UI에 사용하는 이미지는 제품 자산이다. 공급자는 후속 [Q-019](019-image-generation-fallback.md)에 따라 GPT로 고정하지 않는다. 버려진 이미지 후보·브라우저 작업용 다운로드·일시적인 스크린샷까지 전부 영구 보관하는 뜻은 아니다. 필요한 원본·파생 파일·디자인 참조를 구분하고 기존 D-062/063의 정리 계약과 연결한다.
- 문서 폴더 이름, 자료의 표현 형식, 실제 이미지/디자인 파일의 저장 방법은 기존 프로젝트 구조와 기술 제약에 맞춰 구현자가 정한다. 이번 선택만으로 유료 외부 디자인 서비스 도입이나 Git 대용량 저장 과금까지 승인받은 것으로 취급하지 않는다.
