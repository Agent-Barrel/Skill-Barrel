# Q-009. 작업 취소 시 아직 반영하지 않은 변경분

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


- 질문일·조사일: 2026-09-18
- 상태: **답변 저장 완료 — 2안 확정**
- 대상: 사용자가 구현 작업을 명시적으로 취소한 경우, 해당 작업이 만든 미완료 코드·테스트 등 변경분
- 범위: 기본 브랜치에 병합하거나 원본 작업 폴더에 최종 적용하기 전의 작업 산출물. 사용자 원본·이전 변경이나 이미 적용한 결과 전체를 되돌리는 질문이 아니다.

## 기존 기획과 남은 판단

- [Q-007](007-restart-resumption.md)은 취소한 작업을 자동 재개하지 않는다고 정했다. 취소 시 미완료 변경분을 보관할지는 별도다.
- [D-062/063 및 디스크 정리 계약](../baseline/04-resolved-details.md)은 완료·취소·실패 때 불필요한 앱 소유 자원을 정리하되 필요한 결과를 먼저 보존하도록 한다. `clone·worktree`도 필요한 결과 보존과 프로세스 종료를 확인한 뒤 해제한다.
- [REQ-039 및 REQ-050](../../requirements.csv), [FEAT-044/045/058](../../features.csv)은 상태 보존·재개와 자원 정리를 연결한다. 그러나 **사용자가 취소한 작업의 미완료 변경분도 보관할 결과로 볼지**는 명시하지 않았다.
- [D-039](../baseline/04-resolved-details.md)의 기존 사용자 변경 보존, [D-031](../baseline/02-product-decisions.md)의 완료된 외부 동작은 소급 취소되지 않는다는 경계는 유지한다. 앱의 정리를 사용자 저장소 전체 초기화나 무조건 되돌리기로 구현할 근거는 없다.

예를 들어 로그인 기능을 구현하다 사용자가 취소하면, 실행을 멈추는 것과 작성 중이던 변경분을 지우는 것은 각각 처리해야 한다. 필요한 결과 보존과 불필요한 임시 공간 정리 중 어느 쪽에 해당하는지 사용자 정책을 정할 필요가 있다.

## 조사·비교 근거

- [Cursor Cloud Agents 공식 API 문서](https://prod.cursor.com/docs/cloud-agent/api/endpoints)는 실행 취소, 되돌릴 수 있는 아카이브, 영구삭제를 구분한다. 취소된 실행은 종료 상태이며 후속 작업은 새 실행으로 시작하는 구조다. 이는 실행 수명과 영구삭제를 나눠 설계하는 비교 사례다. Cursor의 취소·아카이브가 모든 미커밋 파일을 보존한다는 근거로 사용하지 않는다.
- [Git worktree 공식 문서](https://git-scm.com/docs/git-worktree)는 수정되거나 추적되지 않은 파일이 있는 작업 트리의 삭제에는 강제 옵션이 필요하다고 설명한다. 작업 공간 정리와 미완료 변경의 보존을 따로 확인할 필요가 있다는 기술 근거다. 강제 삭제 기능이 있다는 사실은 이 제품의 삭제 정책이 아니다.

질문 당시에는 미완료 변경분을 기본 보관하는 1안을 추천했다. **사용자는 추천 1안 대신 취소할 때 보관·폐기를 선택하는 2안을 골랐다.** 보관한 변경은 검수가 끝난 완성품으로 취급하지 않는다.

## 사용자에게 제시한 질문

**Q-009. 사용자가 작업을 취소하면, 그 작업이 만들었지만 아직 최종 반영하지 않은 변경분은 어떻게 처리할까요?**

1. **변경분을 보관하고 실행 종료 — 추천:** 미완료 변경분과 진행 상태를 남겨 나중에 확인·재사용할 수 있게 합니다. 자동으로 작업을 이어가거나 병합하지 않으며, 불필요한 빌드·임시 파일은 정리합니다. 사용자가 별도로 변경분을 폐기할 수 있습니다.
2. **취소할 때 보관·폐기를 선택:** 실행 중단은 바로 시작하고, 작성된 변경분을 간단히 보여준 뒤 ‘보관’ 또는 ‘폐기’를 선택받습니다. 선택 전까지는 변경분을 보존합니다.

두 안 모두 사용자가 원래 작성한 변경분은 보존합니다. 이미 반영된 코드·배포나 PC에 설치한 Git·npm 같은 도구를 작업 취소만으로 자동 되돌리거나 삭제하지 않습니다.

## 사용자 답변 원문

```text
2
```

## 답변으로 확정된 내용

사용자는 **2안, 취소할 때 보관·폐기를 선택**을 선택했다. 당시 선택지와 공통 조건은 위 질문에 보존한다.

1. 사용자가 작업을 취소하면 실행 중단을 바로 시작한다.
2. 해당 작업이 작성했지만 아직 최종 반영하지 않은 변경분을 간단히 보여주고, ‘보관’ 또는 ‘폐기’를 선택받는다.
3. 사용자의 선택 전까지 변경분을 보존한다.
4. 사용자가 원래 작성한 변경분은 보존한다.
5. 이미 반영된 코드·배포나 PC에 설치한 Git·npm 같은 도구를 작업 취소만으로 자동 되돌리거나 삭제하지 않는다.

## 구현 시 적용 경계

- 중단 요청과 실제 중단 완료를 구분한다. 실행 프로세스·외부 효과 확인은 기존 복구 계약을 따른다. 보관 여부의 답변을 기다리느라 취소 요청 이후에도 새 작업을 계속 배정하지 않는다.
- 보관한다면 실제 변경분과 재사용에 필요한 기준 revision·상태·필수 증거를 작업 산출물로 연결한다. 취소한 작업을 자동 재개하거나 미완료 결과를 검수 완료로 표시하지 않는다. 재사용 시 현재 요청·입력·승인에 맞는지 확인한다.
- 미완료 변경분의 보관은 해당 작업 산출물 관리다. D-055에서 제외한 앱 전체 백업·내보내기·복원 제품 기능을 추가하는 의미가 아니다. 전체 worktree·의존성·빌드 캐시를 통째로 무기한 보존할 필요는 없다.
- 앱의 해당 작업 변경과 사용자·다른 작업 변경을 구분할 수 있어야 한다. 구분이 불확실한 결과를 자동 삭제하지 않고 기존 D-039의 상태·변경 보존 계약에 따라 처리한다.
- 취소 전에 이미 병합·적용된 변경, 진행 중이던 외부 작업의 실제 결과, 다른 작업이 사용하는 결과는 별도로 확인한다. 되돌리기나 외부 자원 삭제가 필요하면 구체 범위의 작업으로 다룬다.
- [Q-008](008-git-tool-provisioning.md)에서 허용한 전역 도구 설치는 PC 환경 설정이다. 프로젝트 취소에 따른 앱 임시 파일 정리와 설치된 공유 도구의 제거를 같은 동작으로 취급하지 않는다.
- 보관 형식·정리 절차·UI 배치는 선택한 정책 안에서 구현자가 정한다. 개별 임시 파일이나 내부 에이전트 작업마다 별도 사용자 판단을 추가하지 않는다.
