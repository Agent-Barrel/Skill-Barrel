# Q-011. 와이어프레임·상세 디자인과 기존 승인 절차의 연결

> 보존 기록: 아래는 통합 전 원문/당시 판단이다. 현재 구현 기준은 [정본 안내](../../README.md)와 decisions.csv의 후속 관계를 따른다.


- 질문일·조사일: 2026-09-18
- 상태: **답변 저장 완료 — 1안 확정**
- 대상: 화면이 있는 새 프로젝트의 기본 흐름. 유지보수는 유효한 기존 승인·자료를 재사용하고 변경된 범위만 검토한다.

## 이번 질문이 필요한 이유

- [Q-010](010-ui-design-confirmation.md)에서 사용자는 구현 전 주요 화면을 확인하는 1안을 선택하면서 `기능명세서 → 와이어프레임 → API 작업 및 디자인 구체화` 단계를 추가했다.
- 기존 [단계 흐름](../baseline/03-architecture-and-roadmap.md)과 D-010/D-045는 요구사항·기능명세·기술 스택의 세 revision 승인을 요구한다. Q-010의 원래 1안도 별도 승인 단계를 늘리지 않는 방향이었다.
- 새 순서에서는 와이어프레임으로 흐름을 검토한 뒤 상세 디자인을 만들게 된다. 따라서 기존 승인에 어느 산출물을 함께 보여줄지 구체화해야 한다. 와이어프레임 생성 완료를 사용자 승인으로 간주하거나, 와이어프레임 승인만으로 상세 디자인 확인까지 생략하지 않는다.
- 이는 와이어프레임 추가나 주요 화면 확인의 필요성을 다시 묻는 질문이 아니다. 사용자가 답한 방향을 실제 승인 절차에 연결하는 질문이다.

## 조사에 따른 추천

[P-002의 조사·적용 제안](p002-wireframe-and-visual-workflow.md#조사-결과와-이-앱에-적용할-제안)에 근거와 출처를 기록했다. 명세→계획→작업의 일관성을 관리하는 [GitHub Spec Kit](https://github.github.com/spec-kit/reference/agentic-sdd.html), 구현 전 API 명세·모의 서버를 사용하는 [Stoplight의 설계 흐름](https://stoplight.io/openapi/design), 작은 단위의 빠른 피드백을 강조하는 [DORA](https://dora.dev/capabilities/working-in-small-batches/)를 비교했다.

질문 당시 **1안을 추천했고 사용자가 1안을 선택했다.** 기능명세 작성 후 와이어프레임까지 만들고 함께 승인받으며, 이후 기술 조사·API 설계·상세 디자인을 준비해 기술 스택과 주요 화면의 상세 시안을 함께 승인받는 방식이다. 내부 산출물 단계는 추가하되 기본 사용자 승인 시점은 세 번으로 유지한다.

‘API 작업’은 먼저 화면과 서버의 데이터·동작 규칙을 명세하고, 실제 제품 코드는 필요한 승인 이후 구현하는 구분을 두 안의 공통 조건으로 제시했다. 사용자의 1안 선택과 함께 적용한다. API 전체를 먼저 구현해야 UI를 만들 수 있는 순서로 고정하지 않는다. 세부 기술 규칙은 에이전트가 정리하되 사용자 요구·범위·예산·권한을 바꾸는 새 판단은 기존 정책대로 질문한다.

## 사용자에게 제시한 질문

**Q-011. 새 프로젝트에서 와이어프레임·상세 디자인 확인을 기존 승인 절차에 어떻게 넣을까요?**

1. **기존 세 번의 승인에 묶기 — 추천:** `요구사항` → `기능명세 + 와이어프레임` → `기술 스택 + 주요 화면의 상세 디자인` 순서로 승인받습니다. 와이어프레임으로 흐름을 먼저 확인하고 상세 디자인으로 넘어가되, 사용자 승인 시점은 세 번으로 유지합니다.
2. **산출물마다 별도로 승인받기:** `요구사항` → `기능명세` → `와이어프레임` → `기술 스택` → `주요 화면의 상세 디자인`을 각각 승인받습니다. 단계별 확인은 명확하지만 사용자 응답을 기다리는 시점이 늘어납니다.

두 안 모두 API가 필요한 프로젝트에서는 와이어프레임 이후 API의 입출력·권한·오류 규칙을 먼저 설계하고, 실제 코드는 필요한 승인 후 작은 기능 단위로 구현·검증합니다. 화면이나 API가 없는 프로젝트에 불필요한 단계를 강제하지 않습니다.

## 사용자 답변 원문

```text
1
```

## 답변으로 확정된 내용

사용자는 **1안, 기존 세 번의 승인에 묶기**를 선택했다. 당시 질문·선택지·공통 조건은 위에 보존한다.

1. 화면이 있는 새 프로젝트의 기본 사용자 승인 순서는 **요구사항 → 기능명세 + 와이어프레임 → 기술 스택 + 주요 화면의 상세 디자인**이다.
2. 기능명세를 바탕으로 와이어프레임을 만들고, 화면 흐름을 먼저 확인한 뒤 상세 디자인으로 진행한다.
3. 와이어프레임·상세 디자인 각각의 별도 승인 단계를 추가하는 2안은 채택하지 않았다. 기본 승인 시점은 세 번으로 유지한다.
4. API가 필요한 프로젝트에서는 와이어프레임 이후 API의 입출력·권한·오류 규칙을 먼저 설계한다. 실제 코드는 필요한 승인 후 작은 기능 단위로 구현·검증한다.
5. 화면이나 API가 없는 프로젝트에는 불필요한 단계를 강제하지 않는다.

## 구현 시 적용 경계

- 1안에서 기능명세는 와이어프레임의 입력으로 먼저 작성한다. 기능명세 최종 승인에 와이어프레임을 함께 포함하므로 와이어프레임의 선행 입력을 없애거나 단계 순서를 뒤집는 의미가 아니다.
- 1안의 마지막 묶음도 스택과 상세 디자인 각각의 내용·revision·참조가 드러나야 한다. 스택만 본 승인으로 나중에 바뀐 디자인까지 승인했다고 표시하지 않는다. API 명세의 세부 기술을 비개발자가 줄마다 승인하는 절차를 추가하지 않는다.
- 사용자에게 보여줄 기획 자료와 실제 제품 구현을 구분한다. 승인 전 기술 실험에는 기존 D-042가 적용된다.
- 새 자료에서 동작·범위 변경을 발견하면 관련 정본과 영향 범위를 갱신한다. 이전 승인·검수 증거를 변경된 자료에 조용히 재사용하지 않는다. 변경 없는 범위의 유효한 승인은 유지한다.
- 작은 기능 단위 작업은 에이전트가 관리한다. 각 작은 작업마다 별도 사람의 승인을 추가하거나 완성 결과에 최종 승인 관문을 추가하는 질문이 아니다.
- 기존 프로젝트의 경미한 UI 변경, UI가 없는 작업, API가 필요 없는 사이트는 필요한 산출물만 사용한다. 새 프로젝트의 전체 절차를 모든 유지보수 요청에 반복하지 않는다.
