## 사용자가 직접 확정·허용한 내용

- 기능명세서를 바탕으로 와이어프레임을 생성하는 단계를 추가한다.
- 사용자가 제시한 순서는 `요구사항명세서 -> 기능명세서 -> 와이어프레임 -> API 작업 및 디자인 구체화 -> ...`다.
- 와이어프레임으로 화면 흐름을 먼저 설계하고 그 결과를 바탕으로 상세 UI 디자인을 진행한다. 흐름 변경 때문에 상세 디자인을 갈아엎는 일을 줄이려는 의도다.
- 빠른 반복에 적합한 현대적인 소프트웨어 공학 흐름을 조사하고 이 앱의 AI workflow에 도입할 수 있다.
- 이미지 등 시각 자료를 활용한 UI 품질을 중시한다. 특히 랜딩페이지의 배경 동영상·이미지를 예로 들었다. Q-010 당시에는 GPT 웹사이트에서 생성·다운로드하도록 했으나, **Q-019에서 GPT에 한정하지 않고 Gemini nanobanana·grok·qwen 등 어떤 이미지 생성 서비스도 사용할 수 있다고 정정했다.** GPT 우선이나 실패 시에만 공급자 전환을 허용하는 조건을 두지 않는다.
- Q-019에서 핵심 의도를 재강조했다. **웹페이지에 AI Slop이 발생하지 않도록 모던 웹디자인 레퍼런스를 많이 참고하고, 이미지의 배경·본문 삽입 등 실제 적용된 기법을 프로젝트에 활용한다.** 특정 생성 서비스 도입 자체를 디자인 품질 목표로 삼지 않는다.

이 목록은 Q-010 원문을 정리하고 이미지·디자인 부분에 Q-019의 후속 지시를 반영한 것이다. **후속 [Q-011](011-wireframe-design-approval-flow.md)에서 사용자는 1안을 선택해 요구사항 → 기능명세·와이어프레임 → 기술 스택·주요 화면 상세 디자인의 세 묶음 승인을 확정했다.** API가 필요하면 와이어프레임 후 입출력·권한·오류 규칙을 먼저 설계하고, 실제 코드는 필요한 승인 후 작은 기능 단위로 구현·검증한다. 모든 화면에 특정 종류의 미디어를 의무화하는 규칙까지 추가한 답변은 아니다.

## 기존 결정과 연결할 원칙

- [P-001](p001-context-and-intent.md): 와이어프레임·디자인·API 관련 명세를 작업별로 필요한 범위와 참조로 전달한다. 전체 UI·API를 한 세션에 모두 구현하도록 작업 크기를 늘리지 않는다.
- [Q-006](006-native-subagent-boundary.md): 앱이 배정하는 작업의 입력과 결과를 관리한다. 상용 에이전트 내부의 모든 세부 작업·보조 에이전트를 검사하지 않는다.
- [D-010/D-045](../baseline/02-product-decisions.md), [FEAT-025/026/031](../../features.csv): 원래 단계 승인과 새 와이어프레임·디자인 자료의 관계를 명시해야 한다. 산출물을 생성했다는 사실을 사용자 승인으로 바꾸지 않는다.
- [D-032](../baseline/03-architecture-and-roadmap.md): API와 디자인을 병행할 수 있는지는 공통 입력·의존성·읽기/쓰기 범위를 확인한 후 판단한다. 사용자의 ‘API 작업 및 디자인 구체화’만으로 무조건 병렬 실행을 확정하지 않는다.
- [D-013/D-025](../baseline/02-product-decisions.md): 이미지 생성 서비스를 이용할 때 유효한 위임·로그인·화면 사용 범위를 적용한다. 기존에 허용한 범위를 불필요하게 반복 확인하지 않는다.
- [Q-010](010-ui-design-confirmation.md): 구현 전 주요 화면 확인 방향을 유지한다. 와이어프레임과 상세 시안을 한 종류로 취급해 사용자 추가 지시를 생략하지 않는다.

이 근거들을 조합한 추천은 **와이어프레임 선행 + API 명세 우선 + 작은 기능 단위의 구현·검증 반복**이다. 위 자료 중 하나가 이 앱의 전체 흐름을 이미 규정한다는 주장은 아니다.

### 산출물 흐름 제안

1. **요구사항명세서:** 대상 사용자·문제·구현 범위·성공 조건을 정한다. 유사 서비스와 UI 레퍼런스 조사는 필요한 질문을 하기 전에 수행하고, 이후 단계에서 새로 필요한 부분만 보완한다.
2. **기능명세서:** 행동·입출력·권한·예외·검수기준을 요구와 연결한다.
3. **와이어프레임:** 기능명세를 바탕으로 주요 화면의 정보 배치·이동 흐름·입력·분기·필요한 오류/빈 상태를 낮은 시각적 완성도로 확인한다. 이때 발견한 누락은 기능·요구 정본에 돌려보낸다. 상세 색상·이미지 제작을 앞세워 흐름 검토를 생략하지 않는다.
4. **기술 조사와 상세화:** 확인된 흐름을 바탕으로 필요한 기술·환경을 조사한다. API가 필요하면 화면과 서버 사이의 데이터·동작 규칙을 먼저 명세하고, UI는 와이어프레임과 레퍼런스를 바탕으로 색·타이포그래피·컴포넌트·반응형 배치·시각 자료를 구체화한다. 공통 입력이 안정적이고 읽기·쓰기 의존성이 없을 때 병행한다. Q-011에 따라 기능명세·와이어프레임 묶음을 먼저 승인받고, 이후 기술 스택·주요 화면 상세 디자인을 함께 승인받는다.
5. **작업 분할·계획·의도 확인:** 유효한 승인과 정본 revision을 기준으로 작은 구현 작업을 만든다. 각 작업은 관련 기능·화면/흐름·API·디자인 자료·검수조건을 참조한다. 한 세션에 전체 프로젝트를 넣지 않는다.
6. **작은 기능 단위 구현·실제 검증:** 예를 들어 ‘항목 생성 후 목록에 표시’ 한 경로의 UI·API·저장을 연결해 확인하고 다음 기능으로 진행한다. 한 기능도 크면 별도 세션으로 더 나누되, 통합 검증 결과로 해당 기능의 완료를 판단한다. 기반 작업이 선행해야 하면 의존성 순서를 지킨다.
7. **전체 승인 범위의 완료 판단:** 필수 검수·필요한 독립 리뷰·실행 환경 확인을 마친 뒤 기존 정책에 따라 자동 완료·Git 반영한다. 모의 API 통과나 화면 시안만으로 실제 통합 검증을 대체하지 않는다.

이 흐름은 현재 구현하기로 한 범위에 적용한다. 미래 기능 전부의 설계를 미리 끝내야 한다는 요구는 아니다. 기존 승인·디자인·API를 재사용할 수 있는 유지보수에서는 변경 영향이 있는 부분만 갱신한다. 작은 기능 단위 반복은 위임·변경 승인·실제 검증을 건너뛰는 예외가 아니다.

### UI 레퍼런스·이미지 작업의 연결 제안

- 리서치에서 프로젝트의 사용자·목적에 맞는 현대적인 웹디자인 사례를 폭넓게 확인한다. Q-019의 의도에 따라 참고할 이유와 실제 적용할 기법을 정리하고, 기능명세·와이어프레임의 흐름과 함께 상세 UI 방향을 정한다. 레퍼런스 수집에서 끝내지 않고 디자인·구현 지시와 실제 화면 검증에 연결한다. 조사 개수나 특정 스타일을 일률적으로 고정하지 않는다.
- 상세 디자인에서 이미지의 위치·목적·화면 비율·스타일을 정한다. **Q-019에 따라 GPT에 한정하지 않고 적합한 이미지 생성 서비스를 선택해 자산을 확보한다.** 배경·본문 이미지 등 레퍼런스의 기법을 프로젝트에 맞게 적용하고, 생성 지시와 확보한 파일을 해당 시안에 연결해 이후 구현 작업이 같은 자료를 사용하도록 한다. 공급자 나열을 전부 필수 연동해야 한다는 요구로 확대하지 않는다.
- [OpenAI 공식 이미지 생성 문서](https://learn.chatgpt.com/docs/image-generation)는 ChatGPT 웹 대화에서 이미지 생성·참고 이미지 활용을 지원하며, 웹의 사용 가능 여부·한도는 플랜과 워크스페이스 설정에 따름을 설명한다. 실제 문서 본문을 확인했다. CLI의 이미지 생성 기능이나 API 가격을 웹 구독의 지원·사용량으로 바꾸어 설명하지 않는다.
- 공식 문서에서 확인한 생성 지원과, 이 앱이 해당 사용자의 브라우저에서 생성 완료를 감지하고 원하는 파일을 다운로드하는 자동화의 성공은 구분한다. **브라우저 생성→다운로드→파일 확인→프로젝트 반영의 실제 왕복은 구현 단계 검증 대상**이며 이번 조사에서 실행해 검증한 것이 아니다. 현재 Codex의 구독 인증 코드만으로 웹 브라우저 로그인·이미지 기능이 준비됐다고 판정하지 않는다.
- 로그인·사용량 한도·화면 접근 등이 막히면 기존 인계·실패 처리·독립 작업 진행 정책과 연결한다. Q-019에서 허용한 공급자 선택의 자유를 적용하되 유료 API·신규 구독·소재 구매는 기존 비용·위임 범위로 판단한다. 필요한 최종 이미지를 확보하지 않은 결과를 확보 완료로 기록하지 않는다.
- 실제 화면에서 이미지 표시·잘림·모바일 배치·텍스트 가독성과 로딩 영향을 확인한다. 시안용 임시 자료와 최종 투입 자산을 구분한다. 동영상은 사용자가 든 시각 자료 예시이며, 이번 답변에서 동영상 생성 공급자나 모든 화면의 자동재생 정책까지 정한 것은 아니다.

## 후속 질문과 남은 확인

**[Q-011](011-wireframe-design-approval-flow.md)의 1안으로 확정:** 새 와이어프레임·상세 디자인을 기존 세 번의 승인에 묶는다. Q-010의 구현 전 주요 화면 확인을 유지하면서 새 단계의 구체적인 연결을 확정했다.

**[Q-019](019-image-generation-fallback.md)에서 정정·확정:** GPT를 고정하거나 우선할 필요 없이 다른 이미지 생성 서비스를 사용할 수 있다. 핵심은 모던 웹디자인 레퍼런스의 기법을 실제 화면에 적용해 AI Slop을 피하는 것이다. 공급자별 고정 우선순위나 실패 전용 전환 정책을 다시 질문할 필요는 없다.

아래는 구현 시 검증할 사항과 개별 프로젝트에서 정할 입력이다. 현재 인터뷰의 미답변 제품 정책과 구분하며, 추천안이나 기술 제약을 사용자 답변으로 승격하지 않는다.

- 와이어프레임의 구체 형식과 제작 도구, UI 자료의 표시·주석 방식, 이미지 생성 웹 자동화의 실제 지원은 기술 구현·검증으로 정한다. 아직 특정 도구나 브라우저 동작을 검증 완료로 표시하지 않는다.
- 영상 자산을 실제로 요구하는 프로젝트의 공급자·소재·비용·검수기준은 해당 프로젝트에서 구체화한다. 이미지 생성 지시를 영상 생성까지 자동 확대하지 않는다.
