## 검토에서 발견한 공백

[REQ-029/030](../../requirements.csv), [FEAT-031/033/034](../../features.csv), [완료·명세 변경 계약](../baseline/03-architecture-and-roadmap.md)은 승인된 필수 검수와 실제 검증을 충족해야 완료하도록 한다. [실패 처리 계약](../baseline/04-resolved-details.md)은 원인·대안부터 검토하고 승인 범위를 벗어나는 변경은 판단받도록 한다.

그러나 유지보수 대상이 처음부터 일부 테스트에 실패하던 경우, 이번 요청과 무관하고 필수 검수에도 해당하지 않는 실패를 근거와 함께 분리해 요청 범위를 완료할지, 매번 사용자 판단을 받을지는 명시되어 있지 않다. 예를 들어 화면 문구 수정 요청에 앞서 이미 실패하던 별도 통계 기능 테스트가 발견될 수 있다.

현재 [verify.py](../../../../barrel/core/verify.py)는 명령 종료 코드·출력·시간·오류를 수집하고, [gates.py](../../../../barrel/core/gates.py)는 게이트의 통과 여부를 판정한다. `must_fail_first`는 수정 전 실패해야 하는 회귀 검증의 기반이며, 요청과 무관한 기존 실패를 승인된 기준에서 분리하는 제품 정책과는 다르다.

## 공식 자료 조사

확인일: 2026-09-18. 아래는 판정 방식의 참고 자료이며 이 제품의 채택·검증 완료를 뜻하지 않는다.

- [GitLab Unit test reports](https://docs.gitlab.com/ci/testing/unit_test_reports/): source/target 브랜치의 결과를 비교해 새 실패·기존 실패·해결된 실패 등을 구분한다. 비교 대상 결과가 없으면 현재 실패만 표시한다. 보고서의 분류 자체가 CI job 상태를 바꾸지는 않는다. 변경 전후의 증거를 구분하는 참고 사례다.
- [SonarQube Cloud 품질 조건 설정](https://docs.sonarsource.com/sonarqube-cloud/standards/managing-quality-gates/managing-custom-quality-gates): 새 코드에 적용하는 조건과 전체 코드에 적용하는 조건을 구분할 수 있다. 검증 범위를 명시하는 참고 사례이며, 테스트 실패를 무시해도 된다는 근거는 아니다.

## 추천 이유

질문 당시에는, 요청과 무관한 기존 실패까지 자동으로 수정 범위에 넣으면 작은 유지보수 요청의 범위가 커질 수 있다는 이유로 근거를 갖춘 분리·완료 정책을 추천했다. **사용자는 이 추천 대신 2번, 발견할 때마다 사용자 판단을 선택했다.** 아래 질문의 1번을 현재 정책으로 적용하지 않는다.

기존 실패를 분리하는 판정은 파일이 다르다거나 같은 테스트 이름이 실패했다는 이유만으로 확정할 수 없다. 기준 코드·선택한 사용자 변경·실행 환경·실패 원인·이번 수정의 영향을 비교해야 한다는 구현상 판단이다.

## 질문 원문

**Q-005. 유지보수 대상에서 이번 요청과 무관한 기존 테스트 실패가 확인되면, 어떻게 처리할까요?**

1. **근거가 있으면 분리하고 요청 범위만 완료 — 추천:** 변경 전에도 실패했고 이번 수정과 무관하다는 근거가 있으며, 승인된 필수 검수에도 해당하지 않으면 기존 문제로 기록합니다. 이번 요청의 검증을 통과하면 완료하고, 남아 있는 문제를 결과에 함께 알립니다.
2. **발견할 때마다 사용자 판단:** 기존 실패의 원인·영향을 설명한 뒤, 이번 요청과 분리할지 수정 범위를 넓혀 함께 해결할지 사용자에게 묻습니다. 그 결정에 의존하는 완료 처리는 답변을 기다립니다.

두 안 모두 이번 변경으로 새로 생기거나 악화된 실패는 해결해야 합니다. 이미 정한 필수 검수와 원격 저장소의 병합 조건도 유지합니다. 기존 실패인지 입증할 수 없으면 임의로 제외하지 않습니다.

## 답변으로 확정된 내용

사용자는 Q-005의 **2번, 발견할 때마다 사용자 판단**을 선택했다. 당시 선택지와 공통 조건은 위 질문 원문에 보존한다.

1. 이번 요청과 무관한 기존 테스트 실패를 발견하면 원인·영향을 설명한다.
2. 이번 요청과 분리할지, 수정 범위를 넓혀 함께 해결할지 사용자에게 묻는다.
3. 그 결정에 의존하는 완료 처리는 답변을 기다린다.
4. 이번 변경으로 새로 생기거나 악화된 실패는 해결해야 한다. 기존 필수 검수와 원격 저장소의 병합 조건은 유지한다.
5. 기존 실패인지 입증할 수 없으면 임의로 제외하지 않는다.

추가 원칙의 확정 범위와 후속 확인 사항은 P-001을 함께 읽는다.

## 구현 시 구분할 증거와 상태

아래는 검증·설계 검토 대상이며 사용자 답변으로 확정한 구현 세부사항은 아니다.

- 기준 상태는 D-039에서 사용자가 선택한 작업 시작점·보존할 변경과 연결한다. dirty 저장소의 현재 입력을 단순히 HEAD와 같다고 가정하지 않는다.
- 변경 전후 코드·명세 revision, 테스트 목록/명령, 환경·의존성, 실패 원인과 출력, 영향 분석 근거를 연결한다. 실패 개수만 같은 경우는 동일 실패의 증거가 아니다.
- 테스트 미실행·환경 준비 실패·간헐적 실패·원인 미상은 비교로 입증된 기존 실패와 구분한다. 필요한 검증을 실행하지 못한 상태를 기존 실패라는 이유로 통과 처리하지 않는다.
- 실패 원시 결과와 제품의 요청 완료 판단은 별도로 기록한다. 실패한 전체 테스트 명령을 성공한 명령으로 고쳐 표시하거나, 성공을 만들기 위해 기존 필수 검수·테스트를 조용히 제거하지 않는다.
- 기준 상태를 나중에 재현해야 할 때도 사용자 원본을 되돌리거나 훼손하지 않고 별도 공간에서 가능한 범위를 검증한다. 외부 환경·추가 비용·권한은 기존 위임 범위에 따른다.
- 원격 병합에 해당 실패의 해결이 필수이면 그 조건이 남은 동안 실제 병합 완료로 표시하지 않는다. 요청의 완료 범위와 충돌하면 기존 변경 영향·승인 절차로 연결한다.
