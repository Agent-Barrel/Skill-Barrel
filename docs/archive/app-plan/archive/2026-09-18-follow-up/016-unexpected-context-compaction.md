# Q-016. 예상하지 못한 맥락 압축 이후의 작업 처리

- 질문일·조사일: 2026-09-18
- 상태: **답변 저장 완료 — 제시한 세션 관리 선택지 대신 작업 결과 검증으로 판단**

## 질문 당시의 검토 배경

이 절은 질문을 만든 당시의 관점이다. 압축 전용 처리 정책을 추가로 확정해야 한다는 판단은 사용자 답변에 따라 철회했다.

- [P-001](p001-context-and-intent.md)은 작업을 충분히 나누고, 필요한 의도·정보를 간결한 정본과 참조로 전달해 한 세션의 과부하·압축을 피하도록 한다. 처음부터 큰 작업을 넘기고 상용 에이전트의 압축에 맡기는 방식은 재검토하지 않는다.
- [Q-006](006-native-subagent-boundary.md)은 내부 서브에이전트까지 세세하게 확인하지 않고, 작업 분할·의도 전달·결과물에 집중하도록 했다. 이번 검토는 그 자율성을 유지한다.
- 작은 버그 수정으로 판단한 작업도 긴 오류 출력이나 예상 밖 의존성 조사 때문에 맥락이 커질 수 있다. 이때 압축이 발생했다는 사실만으로 해당 세션을 무조건 교체할지는 P-001 답변에서 확정하지 않았다.
- [기존 아키텍처](../baseline/03-architecture-and-roadmap.md)는 정본 입력·정책·실행 체크포인트와 새 세션을 통한 복구를 정한다. 세션 복구 불가·공급자 변경 등에 대한 계약만으로, 압축된 세션이 아직 동작할 때도 무조건 새 세션을 만들도록 결정한 것은 아니다.
- [Q-007](007-restart-resumption.md)은 앱·Mac 재시작 때 자동 재개할지의 정책이고, [Q-009](009-cancelled-work-artifacts.md)는 사용자가 작업을 취소했을 때 변경을 보관·폐기할지의 정책이다. 여기서의 내부 작업 인계를 사용자 취소나 앱 종료와 같게 처리하지 않는다.

## 공식 문서와 현재 코드 확인

아래는 공식 문서·코드의 읽기 전용 조사다. 실제 설치 버전에서 압축·차단·인계 실험을 수행한 결과는 아니다.

- [Claude Code의 맥락 설명](https://code.claude.com/docs/en/how-claude-code-works#the-context-window)은 한도에 가까워지면 오래된 도구 출력 정리와 대화 요약을 수행하고, 초기의 세부 지시가 누락될 수 있다고 설명한다. 따라서 압축 요약만을 정본의 대체로 신뢰하지 않는 설계가 필요하다는 것은 이 앱의 요구와 연결한 해석이다.
- [OpenAI 공식 app-server 문서](https://learn.chatgpt.com/docs/app-server)는 `contextCompaction` 항목의 시작·완료, `thread/tokenUsage/updated`, `turn/interrupt`를 설명한다. 압축·사용량·중단을 연결할 수 있는 관측 수단이며, 압축 전에 모든 작업을 반드시 멈출 수 있다거나 토큰 사용량이 곧 정확한 현재 맥락 점유량이라는 보장은 아니다.
- [Claude Code hooks 문서](https://code.claude.com/docs/en/hooks#precompact)는 `PreCompact`의 압축 차단과 `PostCompact`의 완료 후 관측을 설명한다. 차단 결과는 시점에 따라 다르며, 이미 context-limit 오류가 난 뒤의 복구 압축을 차단하면 현재 요청이 실패할 수 있다. `PostCompact`는 압축 결과를 바꿀 수 없다. 단순 차단만으로 정상적인 인계가 완성되는 것은 아니다.
- 현재 [Codex 이벤트 처리](../../../../step2step/codex/events.py)는 사용량을 보관하지만 `Turn.record()`의 일반 도구 기록에서는 `contextCompaction`을 제외한다. 이 사실은 원시 이벤트를 아예 수신하지 못한다는 뜻은 아니다. 상위 실행기가 의도한 복구 정책을 적용할 수 있는 전달·상태 연결은 별도로 확인해야 한다.
- 현재 [Claude 훅](../../../../step2step/claude/hooks.py)은 `events_file`이 지정된 경우 `PreCompact` 이벤트를 기록한다. [유닛 실행기](../../../../barrel/core/unitloop.py)는 작업별 세션과 실패 시 세션 교체를 갖지만, 이 기능만으로 정본 대조·압축 후 판단·남은 작업 재분할이 구현됐다고 볼 수 없다.
- 필요한 관측·중단·재개 기능은 기존 `DriverCapabilities` 및 V-02/V-03 실험에서 실제 CLI 버전별로 확인한다. 이번 질문으로 두 공급자의 기능·타이밍이 동일하다고 확정하지 않는다.

## 질문 당시의 추천 — 사용자 답변으로 채택하지 않음

**1안을 추천한다.** 정본으로 의도와 현재 상태를 확인할 수 있으면 거의 끝난 작은 작업을 굳이 새 세션으로 다시 넘길 필요가 줄어든다. 작업이 실제로 커졌거나 필요한 근거가 부족하면 남은 일만 분할해 인계하므로 P-001의 책임도 유지할 수 있다. 이 추천은 Q-006의 불필요한 토큰 소비를 줄이라는 지시를 함께 고려한 작성자의 판단이다.

2안은 압축 발생을 일관된 세션 교체 기준으로 삼아 동작이 단순하다. 대신 입력을 다시 읽고 진행 상태를 재구성하는 비용이 늘 수 있으며, 새 세션을 만들었다는 사실만으로 누락된 정보가 복구되는 것은 아니어서 정본 기반 인계는 여전히 필요하다.

두 안의 정상 경로는 사전 분할과 짧은 작업 세션이다. 압축을 반복하며 과도한 작업을 한 세션에 계속 맡기는 정상 운영 방식을 고르는 질문이 아니다.

## 사용자에게 제시한 질문

**Q-016. 작게 나눠 맡긴 작업에서 예상치 못한 맥락 압축이 발생하면 어떻게 처리할까요?**

1. **정본 확인 후 필요한 경우만 인계 — 추천:** 현재 지시·진행 기록·실제 변경을 확인해 의도대로 이어갈 수 있으면 같은 세션에서 마무리합니다. 필요한 정보가 부족하거나 남은 작업이 커졌다면, 완료한 부분을 보존하고 남은 일만 다시 나눠 새 세션에 넘깁니다.
2. **압축된 세션은 항상 교체:** 압축을 감지하면 중단 가능한 지점에서 정리하고, 남은 작업을 정본 기반의 새 세션으로 넘깁니다. 기준은 단순하지만 거의 끝난 작업도 재인계 비용이 발생합니다.

두 안 모두 처음부터 작은 작업으로 나눠 압축을 예방합니다. 대상은 앱이 직접 맡긴 작업 세션이며, 내부 서브에이전트까지 검사하지 않습니다. 기존 요구·권한·예산 안의 인계는 사용자에게 매번 확인하지 않고 자동 처리합니다.

## 사용자 답변 원문

```text
이런건 그냥 작업 결과를 확인하면 되는거잖아. 그럼 제대로 작업했는지 알 수 있을 것 같아.
```

## 답변으로 확정된 내용

1. **작업 결과를 확인해 제대로 수행했는지 판단한다.** 압축 여부에 따라 별도 처리 정책을 선택받는 방식보다 결과 검증에 집중한다.
2. 제시한 1안의 ‘압축 시 정본 대조 후 세션 유지 여부 판단’이나 2안의 ‘압축 시 항상 세션 교체’를 선택한 답변이 아니다. 둘 중 하나로 임의 분류하지 않는다.
3. [P-001](p001-context-and-intent.md)의 사전 작업 분할·정확한 의도와 세부 지시 전달, [Q-006](006-native-subagent-boundary.md)의 내부 수행 자율성과 불필요한 토큰 소비 방지 원칙을 유지한다.

## 기존 정책에 연결한 적용 해석

아래는 사용자 답변과 기존 결정을 함께 적용한 해석이다. 답변 원문을 대체하거나 새로운 제품 정책을 추가한 것으로 취급하지 않는다.

- 압축이 발생했다는 사실만으로 별도 AI 검토·정본 재주입·의무적인 세션 교체 관문을 추가하지 않는다. 압축 이벤트 감시나 차단 기능이 공식 도구에 존재한다는 조사 결과도 필수 제품 요구가 아니다.
- 작업 결과는 실제 산출물과 요청·명세·검수기준을 대조해 확인한다. 상용 에이전트가 ‘완료했다’고 답했다는 사실만으로 통과 처리하지 않는다. 기존 실제 테스트·필수 검수와 [Q-004](004-independent-code-review.md)의 위험도별 리뷰를 유지한다. 모든 작은 작업에 별도 리뷰를 추가하는 답변은 아니다.
- 결과 검증을 강조한 답변이 실행 전 계획·최초 의도 확인을 없애거나 처음부터 큰 작업을 통째로 맡기라는 뜻은 아니다.
- 실제 실행 실패·멈춤·검증 실패가 있으면 기존 복구·재시도·재계획 정책을 적용한다. 정상적인 실패 처리를 없애거나 세션 교체 자체를 금지하는 답변도 아니다. 그 구체 구현은 기존 권한·예산·정본 정책 안에서 결정한다.
- 이후 인터뷰는 사용자 목표·기능 범위·사용 경험·외부 영향 등 사용자의 판단이 필요한 사항에 집중한다. 내부 관리 세부사항을 모두 새로운 선택지로 만들어 반복 질문하지 않는다.

## 채택되지 않은 설계 제안의 취급

질문을 준비하며 압축 이벤트 감시·압축 후 정본 재확인·세션 교체·인계 항목을 검토했으나, 이를 새 필수 요구로 추가하지 않는다. 당시 질문·선택지와 연구 근거는 위에 보존했다. 구체적인 압축 전용 설계 메모는 현재 정책과 혼동하지 않도록 제거했으며, 일반 실패 복구·권한·예산·기존 산출물 보존은 해당 원래 결정을 따른다.
