## 이번 질의응답의 기록 원칙

이번 사용자 요청에 따라 기존 `docs/plan` 파일과 제품 코드는 수정하지 않는다. 이 폴더에 질문과 사용자 답변을 기록한다. 답변을 받을 때마다 다음 질문을 하기 전에 해당 답변 원문을 저장하고 저장 결과를 확인한다. 기존 문서의 원장·CSV 동시 갱신 절차는 이번 세션에 적용하지 않으며, 기존 계획과의 정렬은 다음 세션에서 수행한다.

사용자 답변의 맞춤법·표현·조건을 임의로 고치거나 생략하지 않는다. 질문의 추천안은 답변 전까지 미확정이다. 사용자가 선택지 번호로 답하면 그 답변 원문과 당시 선택지 문구를 함께 보존한다. 답변으로 확정된 범위와 작성자의 해석·추가 확인이 필요한 사항을 구분한다. 정정 답변이 오면 이전 원문을 남기고 대체 관계를 기록한다.

## 검토 근거

- [D-039 및 작업 시작 계약](../baseline/04-resolved-details.md): 시작 브랜치와 기존 미커밋 변경의 보존 방식은 프로젝트 선택 시 질문하도록 확정되어 있다.
- [D-013](../baseline/decisions.md): 외부 서비스 작업은 프로젝트별 위임 범위 안에서 자율 수행한다. Git 결과 전달의 기본 정책, 위임을 받는 시점, 로컬 커밋·push·PR·병합 사이의 구체 구분은 명시되어 있지 않다.
- [단계 흐름과 실행 스케줄러](../baseline/03-architecture-and-roadmap.md): 검증한 변경을 통합하고 필수 검수기준 충족 시 자동 완료하지만 Git 반영 범위의 기본 동작은 정의하지 않는다.
- 현재 [개발 결과 커밋 코드](../../../../barrel/core/service.py)의 `_commit_develop_artifacts`는 [gitops.py](../../../../barrel/core/gitops.py)의 `commit_all`을 호출한다. 이 함수는 `git add -A` 후 일부 제외 경로 외의 변경을 커밋한다. 이 방식을 새 기획에 그대로 이식하면 실행 중 생긴 사용자 변경까지 함께 커밋될 수 있으므로 변경 소유권을 구분해야 한다. 이 지적은 코드 수정이나 새 사용자 결정이 아니다.

## 질문 원문

**Q-001. 에이전트가 만든 변경을 Git에 자동 반영하는 기본 정책을 어떻게 할까요?**

시작 브랜치와 기존 변경 보존은 D-039로 정해졌지만, 작업 결과를 커밋·push·PR·병합 중 어디까지 자동 처리할지는 명시되어 있지 않습니다. 이 선택은 완료 조건과 Git 작업 권한에 영향을 줍니다.

1. **프로젝트별로 미리 정하기 — 추천:** 시작 설정에서 `파일 수정만 / 로컬 커밋까지 / push·PR까지 / 병합까지` 허용 범위와 대상을 정합니다. 이후 요청은 유효한 설정을 재사용하고, 범위를 바꿔야 할 때 질문합니다. 허용 범위 안에서는 반복 확인 없이 수행합니다.
2. **로컬 커밋을 공통 기본값으로:** 에이전트가 만든 변경은 자동 커밋합니다. push·PR·병합은 해당 요청에 명시적으로 포함되거나 별도 위임된 경우 수행합니다.
3. **파일 수정만 공통 기본값으로:** 수정·검증 결과를 남깁니다. 커밋부터는 해당 요청에 명시적으로 포함되거나 별도 위임된 경우 수행합니다.

원하는 번호 또는 다른 정책을 답해주세요. 기존 사용자 변경의 보존 방식은 D-039를 그대로 따릅니다.

## 사용자 답변 원문

```text
1번이 좋은 것 같아. 그런데 비개발자에게는 이 질문도 어려울 수 있으니까, 첫 온보딩 시 받은 유저 정보에 따라 비개발자이면 그냥 자동으로 머지까지 진행하는 걸로 해줘. 작업 단위는 너가 관리하고. 
처음에 말했듯이 타겟 고객은 개발자와 비개발자 모두야. 그리고 git 계정이 설정되어있지 않은 PC에서 이걸 설정하는 방법은 뭐가 좋을지도 고민해줘.(gh CLI 를 설치할지 아니면 git 설치 및 github 가입유도를 진행할지)
```

## 답변으로 확정된 내용

아래는 답변과 선택한 1번 문구를 연결한 정리이며, 위 원문을 대체하지 않는다.

1. Q-001의 **1번, 프로젝트별로 미리 정하기**를 선택했다. 프로젝트에서 허용 범위와 대상을 정하고, 이후 요청은 유효한 설정을 재사용하며 범위 변경이 필요할 때 질문한다. 허용 범위 안에서는 반복 확인 없이 수행한다.
2. 다만 **첫 온보딩에서 받은 사용자 정보상 비개발자이면, 이 Git 허용 범위 질문을 생략하고 자동으로 병합까지 진행**한다.
3. 작업 단위는 에이전트가 관리한다.
4. 제품의 대상 사용자는 **개발자와 비개발자 모두**다.
5. Git 관련 설정이 없는 PC의 온보딩 방안을 추가 조사한다. `gh CLI` 설치, Git 설치, GitHub 가입 안내 등을 검토해 달라는 요청이다. 특정 설치·인증 방식을 선택한 답변은 아니다.

**후속 보완:** [Q-018](018-nondeveloper-existing-project-start.md)에서 비개발자에게도 Git 지식과 기존 관리 정책이 있는지 먼저 질문하고, 잘 모르거나 정책이 없다고 하면 에이전트가 관리하도록 정했다. 위의 Git 허용 범위 메뉴 생략을 ‘비개발자에게는 기존 Git 정책을 전혀 확인하지 않는다’로 확대하지 않는다. 확인된 정책·시작점은 존중하며, 비개발자의 자동 병합 기본 방향 자체를 폐기한 답변은 아니다.

## 해석과 후속 확인이 필요한 사항

아래는 후속 답변으로 정해진 내용과 기존 결정 안에서 설계·검증할 항목을 구분한 것이다. 모든 항목을 새로운 사용자 선택 질문으로 취급하지 않는다.

- [Q-018](018-nondeveloper-existing-project-start.md)에서 비개발자도 Git 지식·기존 정책을 확인하는 조건을 확정했다. 구체적인 온보딩 표현·정보 재사용·설정 화면은 이 조건 안에서 설계하며, 비개발자 분류만으로 지식·정책 부재를 추정하지 않는다.
- GitHub 연결 없이 로컬 개발·커밋·병합까지 시작할 수 있는지는 [Q-002](002-git-github-onboarding.md)에서 확정했다. 연결 시 새 프로젝트 자동 저장을 선택하면 개인 비공개 저장소를 생성하고 업로드·병합까지 관리하는 범위는 [Q-003](003-github-project-storage.md)에서 확정했다. 연결 전에 이미 있던 프로젝트의 업로드는 새 프로젝트 자동 저장 동의에 포함된 것으로 추정하지 않고, 해당 프로젝트의 실제 요청·위임 범위를 확인한다. 이는 기존 범위를 적용하는 설계 해석이며 별도 전역 자동 업로드 정책을 추가한 것이 아니다.
- 기존 저장소의 병합 대상·접근 권한·보호 규칙·CI·충돌은 실제 작업에서 확인한다. 이번 답변만으로 기존 보호 규칙 우회나 운영 배포까지 허용한 것으로 확장하지 않는다. 필수 병합·검증이 남으면 기존 D-024의 완료 조건과 D-040의 원인·대안·인계 원칙을 적용한다. push가 배포를 유발하는 저장소도 실제 외부 효과를 D-013의 위임 범위로 판단한다.
- 기존 변경 보존·시작 브랜치 선택(D-039)의 비개발자 적용은 [Q-018](018-nondeveloper-existing-project-start.md)에서 확정했다. Git 지식·기존 정책을 먼저 확인하고, 잘 모르거나 정책이 없으면 기술적인 준비를 에이전트가 관리하며 필요한 사용자 의도만 쉬운 말로 묻는다.
- Git·gh 설치는 [Q-008](008-git-tool-provisioning.md), 작성자 정보·GitHub 사용자 로그인 후 자동 설정은 [Q-012](012-git-author-identity.md), 원격 서비스의 초기 지원 범위는 [Q-017](017-git-hosting-support.md)에서 정했다. 실제 계정·credential helper·설치 호환은 구현 검증으로 확인한다.
