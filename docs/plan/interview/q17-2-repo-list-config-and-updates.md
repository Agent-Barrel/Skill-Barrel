# Q17-2. 되살린 결정의 후속 지시: 레포 목록, 개인 설정 분리, 자동 업데이트

- 답변일: 2026-10-12
- 관련: [Q17](q17-restore-archived-decisions.md)의 후속, [구현 준비 점검](../readiness-2026-10-12.md)
- 기록 원칙: 사용자 답변은 받은 그대로 적는다. 내용이 다르면 답변 원문이 우선한다. 이 답에는 예외가 하나 있다(아래 원문 바로 뒤의 주).

## 직전에 AI가 보낸 내용 (요약)

사용자가 Q17의 13묶음이 각각 무엇인지 설명해 달라고 해서, 묶음마다 세 가지를 설명했다. 예전에 정한 것, 지금 설계의 상태, 되살리면 바뀌는 것이다. 이 답이 다룬 묶음은 다음과 같이 설명했다.
- **1번 (여러 저장소):** 기억·작업 트리·설정(`.barrel/`)은 공통 기획 레포에 두고, 실행 브랜치와 작업 공간은 레포마다 만든다.
- **5번 (개인 CLI 설정 분리, D-048):** 로그인은 Q12대로 모든 계정을 쓰고, 개인 지침·메모리·MCP·스킬·훅은 첫 설정 때 고른 것만 Barrel 세션에 넣는다.
- **8번 (CLI 버전 고정, D-049):** CLI 업데이트로 화면 읽기가 깨질 수 있으므로, 검증한 CLI 버전을 Barrel 전용 경로에 따로 두고 Barrel이 띄우는 세션은 그 버전으로 돌린다.

같은 답에서 작업 커밋을 요청받아, 그때까지의 작업을 `docs/readiness-2026-10-12` 브랜치에 커밋했다.

## 사용자 답변 (2026-10-12, 원문 그대로)

```text
1.에서 기획 레포에, 이 프로젝트가 어떤 레포들로 구성되어있는지 적어둬서 거기 있는 레포들을 클론받는 걸로 작업을 시작할 수 있도록 해줘.
5.는 이번 스킬에도 반영하는거 맞아? 이건 반영해줘야 해.
8.은 업데이트 막을 수 없으니까 원격의 스킬로 자동 업데이트 하는 기능이 있었으면 해.
깃허브 레포는 다른 organization 으로 이전할거야. [이전 이름] 이라는 이름 관련 내용은 이 레포에 더 이상 남아있지 않도록 해줘.
```

> **원문을 바꾼 곳 (AI):** 원문에는 이전 제품 이름이 그대로 쓰여 있었다. 이 답의 마지막 문장이 레포에서 그 이름을 지우라는 지시라서, 그 단어만 `[이전 이름]`으로 바꿔 적었다. 나머지는 받은 그대로다.

## 요약 (원문이 우선)

- **1번:** 기획 레포에 이 프로젝트를 이루는 레포의 목록을 적어 둔다. 작업은 그 목록의 레포들을 클론받는 것으로 시작할 수 있어야 한다.
- **5번:** 이번 스킬에도 반영한다. 반드시 반영해야 한다.
- **8번:** CLI 업데이트는 막을 수 없다. 그러니 원격의 스킬로 자동 업데이트하는 기능을 둔다.
- **같은 답의 별도 지시:**
  - GitHub 레포는 다른 organization으로 옮긴다.
  - 이전 이름과 관련된 내용은 이 레포에 더 이상 남기지 않는다.

## 이 답에 따른 정리 (AI 분석, 원문이 우선)

### 1번: 기획 레포의 레포 목록

- **파일:** 공통 기획 레포의 `.barrel/repos.json`에 목록을 둔다. 레포마다 다음을 적는다(이름과 형식은 AI가 정했다).
  - 이름, clone 주소, 상위 폴더 안의 폴더 이름, 역할(프론트엔드, 백엔드 등), 기본 브랜치
- **작업 시작:**
  - skill을 기획 레포나 그 상위 폴더에서 실행하면, Barrel이 목록을 읽어 상위 폴더에 없는 레포를 클론한다.
  - 이미 있는 레포는 그대로 쓰고 최신 내용을 받아 온다.
  - 그래서 팀원이나 새 PC는 기획 레포 하나만 받으면 작업을 시작할 수 있다.
- **새 컨셉:** Barrel이 기획 레포를 먼저 만든다. 기능별 코드 레포를 만들 때마다(Q-014) 목록에 더한다.
- **목록을 바꾸는 일:** 레포를 더하거나 빼는 것은 되돌리기 어려운 구조 결정이다([Q19](q19-new-technology-threshold.md)). 그래서 S5 의도 검토나 S6 스택 확정에서 확인받는다.
- **클론 권한:** 클론에는 사용자의 기존 git 인증을 쓴다. 인증이 없어 실패하면 사용자에게 로그인을 요청한다(원래 구상 10번).
- **레포가 하나인 프로젝트:** 목록에는 그 레포 하나만 있다.

### 5번: 개인 CLI 설정 분리

- Q17에서 되살렸고, 이번 답으로 반드시 반영할 항목이 됐다.
- **스킬 구조에서의 모습:**
  - Barrel이 띄우는 세션은 계정마다 Barrel이 관리하는 설정 폴더로 띄운다. 로그인만 사용자의 계정에서 가져온다.
  - 첫 설정 때 개인 지침, 메모리, MCP, 스킬, 훅의 목록을 보여 주고, 고른 것만 Barrel 설정에 넣는다.
  - 세션마다 실제로 불러온 설정과 버전을 기록한다(D-048).
- **spike에서 확인할 것:** 설정을 바꾼 폴더에서도 로그인을 그대로 쓸 수 있는가. Claude는 설정 폴더마다 키체인 항목이 따로 있고, Codex는 로그인 정보가 `auth.json`에 있다.
- 아직 `skill-plugin/`에는 반영하지 않았다. [구현 준비 점검](../readiness-2026-10-12.md)에 반드시 반영할 항목으로 적었다.

### 8번: 원격의 스킬로 자동 업데이트

- 예전 결정 D-049(검증된 CLI를 따로 둔다)를 대신한다.
- **만드는 것(AI가 정한다):**
  - 실행기는 원격 레포(플러그인 마켓플레이스)의 새 버전을 정기적으로 확인한다.
  - CLI 업데이트 뒤 화면 읽기 보정이 실패하면 바로 다시 확인한다.
  - 새 버전이 있으면 모든 계정 폴더의 플러그인과 실행기를 함께 올린다. 작업 중인 턴이 없는 안전한 지점에서 올리고, 세션은 파일에서 이어 간다(재개와 같은 경로).
- **동의:** 업데이트 때 동의를 받을지는 Q17에서 되살린 12번(D-058, "새 버전은 동의를 받아 올린다")과 겹친다. 그래서 [Q21](q21-auto-update-consent.md)에서 따로 물었다.

### 별도 지시: 이전 이름 지우기와 레포 이전

- **지우는 범위:** 레포의 파일에서 이전 이름을 지운다. 과거 커밋과 보존 브랜치까지 지울지는 아래에서 따로 물었다.
- **기록 원칙의 예외:** 답변 원문을 고치지 않는다는 원칙에 예외를 둔다. Q09 답변 원문과 이 답 원문에 든 이전 이름은 `[이전 이름]`으로 바꿨다. 사용자의 지시가 이 기록 원칙보다 우선한다.
- **GitHub 주소:** 레포를 다른 organization으로 옮기면 지금 주소가 바뀐다. 그래서 문서에 박아 둔 GitHub 주소는 빼고, 브랜치 이름으로만 가리킨다.

## 이름을 지우는 범위 (확인 질문과 답)

[Q21](q21-auto-update-consent.md)과 같은 메시지에서 물었다.

### 질문 (사용자에게 보낸 내용)

지금 브랜치의 파일 38개(78줄)는 바로 정리한다. 이전 이름은 다른 곳에도 남아 있다.
- **보존 브랜치(`archive/tauri-desktop-app`):** 528개 파일에 이름이 있고, 512개 경로에 이름이 들어 있다. 옛 Python 패키지 폴더와 Rust crate 이름 등이다.
- **과거 커밋:** 130개 커밋의 내용에 있고, 그중 9개는 커밋 메시지에도 있다.

과거 커밋까지 지우려면 git 기록을 다시 써야 해서 되돌리기 어렵다.

선택지:
- **A (추천) 과거 기록까지 모두 지운다.**
  - `git filter-repo`로 모든 브랜치의 커밋 내용, 경로, 메시지에서 이름을 바꾼다.
  - 모든 커밋 해시가 바뀐다. 문서에 적힌 해시는 새 해시로 고친다.
  - 다시 쓰기 전에 레포 전체를 레포 밖에 번들 파일로 백업한다.
  - 원격의 main과 보존 브랜치는 강제 push로 바꾼다. 다른 PC의 사본은 다시 받아야 한다.
- **B 두 브랜치의 지금 파일만 정리한다.** 보존 브랜치에 이름과 경로를 바꾸는 커밋을 더한다. 과거 커밋과 메시지에는 남고, 강제 push는 없다.
- **C 지금 브랜치의 파일만 정리한다.** 보존 브랜치와 과거 커밋에는 남는다.

추천 이유: "이 레포에 더 이상 남아있지 않도록"을 그대로 이루는 방법은 A뿐이다. 기록을 다시 쓰기에는 레포를 옮기기 전이 가장 좋다. 어느 쪽이든 정리한 내용은 커밋한다고 함께 알렸다.

질문 창에 보인 선택지 이름: `과거 기록까지 (추천)`, `두 브랜치의 지금 파일만`, `지금 브랜치 파일만`.

### 사용자 답변 (2026-10-12, 원문 그대로)

선택지를 골랐다.

```text
지금 브랜치 파일만
```

### 요약 (원문이 우선)

- 지금 브랜치의 파일에서만 이전 이름을 지운다.
- 보존 브랜치와 과거 커밋은 그대로 둔다. 그곳에는 이전 이름이 남는다.

### 이 답에 따른 정리 (AI 분석, 원문이 우선)

- **이 브랜치를 main에 합치면** main의 파일에도 이전 이름이 없어진다.
- **보관 문서의 코드 경로:** 보관 문서(`docs/archive/`)가 가리키던 옛 패키지 경로는 지금 패키지 이름(`barrel/`)으로 바꿔 적었다. 보존 브랜치의 실제 경로는 옛 이름 그대로라서 이 경로와 다르다. [docs/archive/README.md](../../archive/README.md)에 그렇게 적었다.
- **앞으로의 규칙:** 레포의 어떤 파일에도 이전 이름을 쓰지 않는다. [session-context.md](../session-context.md) §6에 적었다.

## 레포 이전 (2026-10-12)

이름 정리와 커밋을 알린 뒤, 사용자가 레포를 옮길 곳을 정했다.

### 사용자 지시 (2026-10-12, 원문 그대로)

```text
https://github.com/Agent-Barrel/Skill-Barrel 여기에 옮겨주면 돼. 지금 미커밋된 내용도 하나 있는 것 같은데, 이건 불필요하게 많은 CI나 test 가 생기지 않도록 주의해야할 점을 정리한 문서이니, 이것도 커밋까지한 뒤에 옮겨줘. 커밋 히스토리는 굳이 안가져가도 돼.
```

### 요약 (원문이 우선)

- 레포를 https://github.com/Agent-Barrel/Skill-Barrel 로 옮긴다.
- 커밋하지 않았던 문서도 커밋한 뒤 옮긴다. 불필요하게 많은 CI나 테스트가 생기지 않도록 주의할 점을 정리한 문서다([ci-test-redundancy.md](../ci-test-redundancy.md)).
- 커밋 기록은 가져가지 않아도 된다.

### 이 지시에 따른 정리 (AI 분석, 원문이 우선)

- **옮긴 방법:** 지금 브랜치의 파일을 기록 없는 커밋 하나로 만들어 새 레포의 `main`에 올렸다. 새 레포에는 그 커밋 하나만 있다.
- **새 레포에 없는 것:** 보존 브랜치(`archive/tauri-desktop-app`)와 과거 커밋.
  - 둘 다 이전 레포와 이 Mac의 로컬 저장소에만 있다.
  - 문서에 나오는 커밋 해시와 보존 브랜치는 이전 레포의 것이라고 [docs/plan/README.md](../README.md)와 [session-context.md](../session-context.md)에 적었다.
- **공개 레포:** 새 레포는 공개다. 이전 레포는 비공개였다.
  - 그래서 Q17 12번의 "비공개 레포를 마켓플레이스로 쓴다"는 "공개 레포 Agent-Barrel/Skill-Barrel을 마켓플레이스로 쓴다"로 바뀐다.
  - 누구나 설치할 수 있으므로, 사내·테스터용(D-051)이라는 대상을 레포 접근 권한으로 제한하지 못한다.
  - 올리기 전에 비밀값, 이메일 주소, 개인 경로, 회사 이름이 파일에 없는지 검사했다.
- **이 Mac의 로컬 저장소:**
  - `origin`을 새 레포로 바꾸고, 이전 레포는 `legacy`라는 원격으로 남겼다.
  - 이전 기록의 브랜치는 로컬에 그대로 둔다: `old-main`(이전 main), `archive/tauri-desktop-app`, `docs/readiness-2026-10-12`.
- **마켓플레이스 주소:** 아직 설치한 곳이 없으므로 처음부터 새 레포 주소를 쓴다([Q21](q21-auto-update-consent.md)).
