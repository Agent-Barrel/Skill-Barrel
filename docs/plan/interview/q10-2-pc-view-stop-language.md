## 질문 (사용자에게 보낸 내용)

Q10 답에서 새로 생긴 것 가운데 사용자가 정해야 할 것은 두 가지다. 작업 중지가 무엇을 어떻게 멈추는지, PC 화면을 무엇으로 만드는지. 나머지(Slack 언어 설정, 질문 형식, Slack 장애 처리 세부)는 답에서 바로 따라 나오므로 기본값으로 적었다.

### 지금 있는 코드

- **안전한 지점에서 멈추기:** unit loop는 중지 파일(`.unit-loop-stop`)을 작업 단위, 시도, 턴 사이에 확인한다(`barrel/core/unitloop.py:468`, `:536`, `:607`, `:676`). 진행 중인 턴은 끝날 때까지 기다린다.
- **즉시 끊기:** Claude 세션 `interrupt()`(`step2step/claude/session.py:511`, ESC), Codex 세션 `interrupt()`(`step2step/codex/session.py:441`, `turn/interrupt`). Codex `stop()`은 백그라운드 터미널까지 정리한다(`:575`).
- **강제 종료:** `stop(force=True)`로 프로세스를 끝낸다(`step2step/claude/session.py:186`).

### 다른 서비스 조사 요약 (작업 중지)

- **코딩 에이전트의 Stop은 "즉시 끊되 이어서 할 수 있게 둔다"가 기본이다.**
  - Claude Tag의 Stop은 즉시 멈추고 세션을 남긴다. 세션을 버리는 `!restart`는 따로 있다.
  - Claude Code의 Esc와 Codex의 interrupt도 작업을 남기고 같은 대화에서 이어 간다.
  - 세션을 끝내거나 지우는 일은 별도 동작이고, 확인 창은 주로 여기에 붙는다.
  - 예외는 GitHub Copilot이다. 멈추면 실행이 끝난다.
  - "지금 턴까지 마치고 멈추기"를 문서화한 에이전트 제품은 없었다.
  - ([How Claude Tag works](https://claude.com/docs/claude-tag/concepts/how-it-works), [Claude Code interactive mode](https://code.claude.com/docs/en/interactive-mode), [Codex App Server](https://learn.chatgpt.com/docs/app-server), [Copilot agent sessions](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents))
- **CI와 워크플로 도구는 단계를 나눈다.** 진행 중인 것을 마치게 두는 멈춤, 신호를 보내는 취소, 강제 종료의 세 단계다. 강제 단계는 점잖은 취소가 안 먹힐 때를 위해 생겼다. GitHub Actions의 force-cancel(2023), GitLab의 force cancel, Jenkins의 term/kill, Temporal의 terminate가 그 예다. ([GitHub force cancel](https://github.blog/changelog/2023-09-21-github-actions-force-cancel-workflows/), [Temporal](https://docs.temporal.io/encyclopedia/workflow/cancellation-and-termination), [Jenkins](https://www.jenkins.io/doc/book/using/aborting-a-build/))
- **멈췄는데 다시 살아나는 문제가 있다.** Anthropic은 멈춘 세션이 재생성되거나 Slack 확인 메시지로 다시 움직이는 문제를 2026-07-02와 2026-09-23에 고쳤다. Codex interrupt는 백그라운드 프로세스를 남길 수 있어 따로 정리해야 한다. ([CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md), [codex#42717](https://github.com/openai/codex/issues/42717))
- **Slack에서 멈추는 방법:**
  - Slack 자체의 Stop 버튼은 "에이전트 앱"으로 선언한 앱이 처리 중일 때만, 최대 1시간 동안 보인다. 그래서 이번 구조에는 맞지 않는다.
  - 일반 버튼에는 Slack 확인 창(빨간 확인 버튼)을 붙일 수 있다. Slack은 모든 동작에 확인을 붙이면 피로가 쌓인다고 경고한다.
  - 슬래시 명령은 스레드 안에서 쓸 수 없다.
  - ([Agent sessions](https://docs.slack.dev/ai/agent-sessions), [Confirmation dialog](https://docs.slack.dev/reference/block-kit/composition-objects/confirmation-dialog-object), [Slash commands](https://docs.slack.dev/interactivity/implementing-slash-commands))

### 조사 요약 (가벼운 PC 화면, 이 Mac에서 2026-10-07 측정)

| 방식 | 보이는 것 | 더 드는 메모리, 대기 중 CPU | 필요한 것 | 화면에서 중지 |
| --- | --- | --- | --- | --- |
| 실행기가 띄우는 웹 페이지 | 트리, 세션, 막힘, 질문 링크, 이벤트, 실시간 | 실행기에 +1.2~2.4 MiB, 1 ms 미만, 분당 4회 깨어남 | 없음(Python 표준 라이브러리), 페이지 약 6 KB | 된다 |
| 메뉴 막대 아이콘(Swift) | 개수, 트리는 하위 메뉴로만 | 별도 프로세스 7.6 MiB | 빌드와 서명, 또는 바이너리 배포 | 메뉴로 된다 |
| 메뉴 막대 아이콘(Python rumps) | 위와 같다 | 별도 프로세스 28.6 MiB | 의존성 약 27 MB | 메뉴로 된다 |
| 터미널 화면(curses / Textual) | 터미널 안의 트리 | curses 거의 0 / Textual 29.7 MiB, 분당 577회 깨어남 | 터미널 창을 계속 열어 둬야 한다 | 키로 된다 |
| 정적 HTML 파일(file://) | 트리, 새로고침 | 거의 0 | 없음 | 안 된다(서버가 없어 요청을 받을 곳이 없다) |

- 브라우저 탭 자체의 메모리는 재지 않았다.
- 지시를 받는 localhost 서버는 사용자가 연 웹페이지에서 공격받을 수 있다(CVE-2025-49596, CVE-2025-52882). 받는 동작이 "중지"뿐이고 아래 보안 조치를 하면, 위조 요청으로 할 수 있는 최악은 작업을 멈추는 것이다. 코드 실행으로 이어지지 않는다.

### 왜 지금 묻는지

Q10 답에서 PC 화면과 작업 중지를 더했다. 중지가 무엇을 어떻게 멈추는지에 따라 실행기의 중지 처리, Slack 버튼, PC 화면의 버튼이 정해진다. 화면 방식에 따라 플러그인에 넣을 것과 spike 항목이 정해진다.

### 10-d. 작업 중지는 무엇을, 어떻게 멈추는가

- **A (추천) 즉시 멈추고, 이어서 할 수 있게 둔다.**
  - 범위: 그 프로젝트의 실행 전체(오케스트레이터와 모든 작업 세션).
  - 순서:
    1. 새 세션을 띄우지 않는다.
    2. 도는 턴을 모두 끊는다(Claude ESC, Codex `turn/interrupt`와 백그라운드 터미널 정리).
    3. 세션을 닫는다. 15초 안에 멈추지 않는 세션은 프로세스를 끝낸다.
    4. 실행 상태에 "중지됨"과 끊긴 작업을 적고, Slack과 PC 화면에 알린다.
  - 파일 변경은 되돌리지 않는다. 재개하면 끊긴 말단 작업은 새 세션이 남은 변경 위에서 다시 맡는다.
  - 중지된 동안에는 질문 다시 알림과 3시간 스냅샷을 멈춘다. 그 사이 온 답은 기록해 두었다가 재개 때 반영한다.
  - 재개: Slack "중지됨" 메시지의 [재개] 버튼, 채널에 쓴 "재개", PC 화면의 [재개] 버튼. 새 오케스트레이터가 기억 단위와 실행 상태를 읽고 이어 간다.
  - 이유: 코딩 에이전트 제품들의 기본 동작과 같고, 지금 코드의 interrupt와 stop으로 바로 만든다.
- **B** 두 단계로 둔다. "중지"는 지금 턴까지 마치고 멈춘다(기존 중지 파일 방식). "즉시 중지"는 A처럼 끊는다. 재개는 A와 같다. CI 도구들의 방식이다. 턴이 길면 "중지"에 수십 분이 걸릴 수 있다.
- **C** 중지하면 실행을 끝낸다. 재개 버튼은 없고, 다시 하려면 skill을 다시 실행한다. 다시 실행하면 기억 단위와 실행 상태를 읽고 이어 간다.

범위는 프로젝트 실행 전체로 두었다. 작업 하나만 멈추는 기능은 넣지 않았다. 넣으려면 오케스트레이터가 그 작업을 다시 띄우지 않도록 막는 장치가 따로 필요하고, 화면과 Slack에 작업마다 버튼이 생긴다.

### 10-e. PC 화면을 무엇으로 만드는가

- **W (추천) 실행기가 띄우는 로컬 웹 페이지 하나.**
  - Python 표준 라이브러리 서버와 SSE로 실시간 갱신한다. 외부 패키지와 Node 빌드는 없다. 페이지는 약 6 KB(스타일 포함 약 15 KB)다.
  - 측정값: 실행기 메모리 +1.2~2.4 MiB, 대기 중 CPU 1 ms 미만, 분당 4회 깨어남.
  - 보여 주는 것: 대주제 > 중주제 > 말단 트리와 상태, 도는 세션(CLI, 모델), 막힌 작업과 이유, 답을 기다리는 질문(Slack 스레드 링크), 최근 이벤트, Slack 연결 상태.
  - 쓰기 동작: [중지]와 [재개]뿐이다(10-d가 C면 [중지]만).
  - 보안:
    - 127.0.0.1에만 연다.
    - 토큰을 확인하고, Host와 Origin을 확인하고, POST만 받는다.
    - 중지는 아무 인자도 받지 않는다.
    - 에이전트가 쓴 글자는 HTML로 해석되지 않게 처리한다.
  - 여는 법: 실행을 시작할 때 기본 브라우저로 열어 준다. 주소는 실행기가 다시 떠도 바뀌지 않아 즐겨찾기로 다시 열 수 있다. 주소에 토큰이 들어 있으므로 Slack에는 보내지 않는다.
  - 이유: 측정한 방식 가운데 가장 가볍고, 트리를 한눈에 보여 주면서 중지까지 되는 유일한 방식이다.
- **M** 메뉴 막대 아이콘. 개수와 중지 메뉴를 메뉴 막대에 둔다. 트리는 하위 메뉴로만 볼 수 있다. Swift로 만들면 7.6 MiB지만 빌드와 서명 부담이 있고, Python으로 만들면 28.6 MiB에 의존성이 약 27 MB다.
- **T** 터미널 화면. curses는 대기 중 자원을 거의 쓰지 않지만 터미널 창을 계속 열어 둬야 한다.

### 따로 정하지 않으면 이대로 한다고 제시한 기본값

1. **Slack에서 중지와 재개:**
   - 스냅샷 메시지에 [작업 중지] 버튼을 단다. 누르면 Slack 확인 창이 한 번 뜬다.
   - 채널에 "중지"라고만 쓰면 확인 없이 바로 멈춘다. "재개", "상태"도 같은 방식이다.
   - 중지되면 "중지됨" 메시지에 [재개] 버튼을 단다.
   - 중지와 재개는 등록한 사용자 본인만 할 수 있다.
2. **Slack 언어:**
   - 설정은 하나로 두고 모든 프로젝트에 쓴다. 기본은 한국어다.
   - 채널에 "언어 영어" 또는 "language korean"이라고 쓰면 바뀌고, 그다음 메시지부터 그 언어로 간다.
   - 영어일 때는 고정 문형의 영어 원문과 영어 정본(질문, 검토 문서, 최종 보고, 작업 이름)을 그대로 보낸다. Skill-Techblog를 거치지 않는다. 질문 머리말은 `[{프로젝트명}-Question]`이다.
   - 한국어로 다시 바꿀 때 한국어 표시 이름이 없는 작업은 그때 묶어서 만든다.
   - PC 화면도 같은 언어를 따른다.
3. **질문 형식과 다시 알림:**
   - 질문은 `[{프로젝트명}-질문]`으로 시작하고, 끝에 "이 스레드에 답해 주세요"를 넣는다. 프로젝트명은 실행을 시작할 때 정한 이름이고, 기본은 레포 폴더 이름이다.
   - 다시 알림은 그 질문 스레드에 답글로 달고 사용자를 멘션한다. 1, 2, 4, 8시간 뒤, 그 뒤로 8시간마다 보낸다. 시간은 질문이 실제로 Slack에 올라간 때부터 잰다.
   - "답이 꼭 필요한 질문"은 막힌 작업을 풀어야 하는 질문과 요청 전부로 본다. Q01과 Q06에 따라 Barrel은 AI가 판단할 수 없는 것만 묻기 때문이다.
4. **Slack이 끊겼을 때:**
   - 작업은 계속하고, 보내기만 기다린다.
   - 복구되면 스냅샷 하나와 쌓인 질문을 한꺼번에 보낸다. 끊긴 동안의 작업 내역은 보내지 않는다.
   - Q10 기본값 6번의 macOS 알림과 터미널 명령은 뺀다. 대신 PC 화면에 Slack 연결 상태와 아직 못 보낸 질문 수를 보여 준다.

## 닫은 화면을 다시 여는 방법 (AI 분석, 원문이 우선)

사용자가 방법을 강구하라고 맡겼으므로 AI가 정했다. 원칙은 두 가지다. PC 화면을 가볍게 두라는 Q10 답에 따라 상주 프로세스를 늘리지 않고, 토큰이 든 주소는 Slack으로 내보내지 않는다.

1. **주소를 고정한다.** 프로젝트마다 포트와 토큰을 한 번 정해, 본인만 읽을 수 있는 파일로 실행 상태 폴더에 둔다. 실행기가 다시 떠도 주소가 같으므로 브라우저 방문 기록이나 즐겨찾기로 다시 열 수 있다.
2. **Spotlight나 Dock에서 "Barrel"로 연다.**
   - skill이 처음 설정할 때 `~/Applications/Barrel.app`을 만든다. macOS 기본 도구 `osacompile`로 만드는 AppleScript 앱이다.
   - 이 앱을 실행하면 지금 도는 프로젝트의 화면 주소를 파일에서 읽어 기본 브라우저로 열고 바로 끝난다. 상주하지 않는다.
   - 도는 프로젝트가 여럿이면 목록에서 고르고, 하나도 없으면 그렇다고 알린다.
   - 앱 안에는 토큰을 넣지 않는다. 열 때마다 파일에서 읽는다.
   - ⌘Space에서 "Barrel"을 치거나, Dock에 끌어 두고 누르면 된다.
3. **Slack 채널에 "화면"이라고 쓴다.** 실행기가 이 Mac에서 그 프로젝트의 화면을 연다. 휴대폰에서 써도 PC에 열린다. 주소는 Slack으로 나가지 않는다.
4. **skill을 다시 부른다.** 이미 도는 프로젝트에서 skill을 부르면 오케스트레이터를 새로 띄우지 않고 화면을 연다.
