# Q19. 스택 확정을 받아야 하는 "새 기술"은 어디까지인가

- 질문일: 2026-10-12
- 관련: [Q13](q13-depth-by-impact.md), [skill-plugin/workflow.md](../skill-plugin/workflow.md#depth), [skill-plugin/interviews.md](../skill-plugin/interviews.md#stack), [원래 구상](../00-original-flow.md) 7·8번, [Q17](q17-restore-archived-decisions.md), [구현 준비 점검](../readiness-2026-10-12.md)
- 기록 원칙: 사용자 답변은 받은 그대로 적는다. 아래 "요약"은 찾아보기 편하도록 붙인 것이며, 내용이 다르면 답변 원문이 우선한다.

## 질문 (사용자에게 보낸 내용)

[Q18](q18-one-run-per-request.md)의 답을 받은 뒤 물었다.

### 왜 지금 묻는지

- **정해지지 않은 것:** Q13에서 "스택은 새 기술이 들어올 때만 확정받는다"고 정했지만, 무엇을 새 기술로 칠지는 정하지 않았다.
- **지금 문서의 임시 문구:** workflow.md 80줄은 AI가 임시로 "기존 결정에 없는 의존성, 서비스, 프레임워크, 도구 전부"로 적었다. 이대로면 날짜 처리 라이브러리 하나를 더할 때도 확정을 받아야 한다.
- **이 기준이 정하는 것:** S6에서 받는 질문 수와 Barrel이 혼자 고르는 범위가 정해진다.
- **비개발자:** [Q17](q17-restore-archived-decisions.md)에서 비개발자 지원을 되살렸으니 비개발자에게도 맞는 기준이어야 한다.

### 다른 팀과 도구 조사 요약

- **ADR(아키텍처 결정 기록) 관행:**
  - 되돌리기 비싼 결정만 기록하고 승인받는다. 언어, 프레임워크, 데이터 저장, 통신 방식, 인증, 배포 방식이 여기에 든다.
  - 구현 세부와 일상적인 의존성 갱신은 기록하지 않는다.
  - ([Bitwarden ADR 안내](https://contributing.bitwarden.com/architecture/adr/))
- **AGENTS.md 관행:**
  - "운영 의존성을 추가하기 전에 묻는다", "마이그레이션, 스키마 변경, 공개 API 변경, 새 외부 의존성은 사람이 판단한다" 같은 규칙을 자주 쓴다.
  - 공식 규격이 아니라 실무 글에서 나온 관행이다.
  - ([예시](https://flaviocopes.com/agents-md/))
- **GitHub dependency review action:** 패키지마다 사람에게 묻지 않는다. PR이 GPL처럼 금지한 라이선스나 취약점이 있는 의존성을 들여오면 자동으로 막는다. ([actions/dependency-review-action](https://github.com/actions/dependency-review-action))
- **패키지 환각:** LLM이 만든 코드에서 존재하지 않는 패키지 이름이 상용 모델 평균 5.2%, 공개 모델 평균 21.7% 나왔다. 그래서 묻지 않고 넣는 패키지도 실제로 있는지 확인해야 한다. ([arXiv 2406.10279](https://arxiv.org/abs/2406.10279))

> **질문 뒤 확인한 것 (AI, 2026-10-12):** AGENTS.md 관행으로 든 두 규칙 가운데 첫째만 출처를 확인했다.
> - **확인됨:** "운영 의존성을 추가하기 전에 묻는다"는 링크한 글을 포함해 세 실무 글에 있다([flaviocopes](https://flaviocopes.com/agents-md/), [how2shout](https://www.how2shout.com/ai/agents-md-file-guide.html), [Plannotator](https://docs.plannotator.ai/learn/ai-development/how-to-write-a-good-agents-md)).
> - **확인 안 됨:** "마이그레이션, 스키마 변경, 공개 API 변경, 새 외부 의존성은 사람이 판단한다"는 이 세 글에 없었다. 검색 요약에만 나왔고 출처를 찾지 못했다.
>
> 둘째 규칙을 빼도 조사 요약이 가리키는 방향은 같다. AGENTS.md 관행은 운영 의존성을 추가하기 전에 묻는 쪽이라 선택지 B에 가깝다. ADR 관행과 dependency review action은 A 쪽이다. 결정은 다시 묻지 않는다.

### 선택지

- **A (추천) 되돌리기 어려운 것만 확정받는다.**
  - 확정받는 것:
    - 언어와 런타임
    - 프레임워크
    - DB와 저장소
    - 외부 서비스와 API(인증, 결제, 호스팅 등)
    - 비용이 드는 것
    - 쓰는 방식을 제한하는 라이선스(GPL·AGPL 같은 카피레프트, PyQt 같은 상용)
    - PC에 설치하는 도구
  - Barrel이 고르는 것: 확정된 스택 안에서 쓰는 일반 라이브러리. 고른 이유를 결정 단위로 남기고, 최종 보고에 목록으로 적는다.
  - 확인만 하는 것: 새 패키지는 모두 실제로 있는지, 유지보수되는지, 라이선스와 취약점이 어떤지 확인한다. 묻지는 않는다.
  - 비개발자에게는 확정 질문을 쉬운 말과 추천안으로 낸다.
- **B 새 의존성은 모두 확정받는다.** 지금 문서의 문구다. 가장 꼼꼼하지만 질문이 많아지고, 비개발자는 답하기 어렵다.
- **C 비용, 라이선스, PC 설치만 확정받는다.** 프레임워크와 DB도 Barrel이 고르고 결과를 보고한다. 질문은 가장 적다. 대신 원래 구상 8번의 "기술 스택 확정(유저 인터뷰, 승인)"이 좁아진다.

추천 이유: 조사한 관행은 모두 되돌리기 비싼 선택만 사람이 정하고, 라이선스와 취약점은 기계로 걸러 낸다. A는 원래 구상 7번이 강조한 비용과 제약(PyQt 같은 유료 소스)을 확정 대상에 넣으면서도 라이브러리마다 질문하지 않는다.

질문 창에 보인 선택지 이름과 설명:
- `되돌리기 어려운 것만 (추천)`: 언어·프레임워크·DB·외부 서비스·비용·제한 라이선스·PC 설치 도구는 확정받고, 일반 라이브러리는 Barrel이 고른 뒤 이유와 목록을 남깁니다. 새 패키지는 모두 실재·라이선스·취약점을 확인합니다.
- `새 의존성은 모두`: 기존 결정에 없는 라이브러리·서비스·도구는 전부 확정받습니다. 가장 꼼꼼하지만 질문이 많아집니다.
- `비용·라이선스·PC 설치만`: 프레임워크와 DB도 Barrel이 고르고 결과를 보고합니다. 질문은 가장 적지만 스택 확정(원래 구상 8번)이 좁아집니다.

## 요약 (원문이 우선)

고른 선택지 A의 내용이 결정이다.
- **확정받는 것:** 되돌리기 어려운 선택만이다. 언어와 런타임, 프레임워크, DB와 저장소, 외부 서비스와 API(인증, 결제, 호스팅 등), 비용이 드는 것, 쓰는 방식을 제한하는 라이선스, PC에 설치하는 도구가 여기에 든다.
- **Barrel이 고르는 것:** 확정된 스택 안의 일반 라이브러리다. 이유를 결정 단위로 남기고, 최종 보고에 목록으로 적는다.
- **확인만 하는 것:** 새 패키지는 모두 실재, 유지보수, 라이선스, 취약점을 확인하고, 묻지 않는다.
- **비개발자:** 확정 질문을 쉬운 말과 추천안으로 낸다.

## 이 답에 따른 정리 (AI 분석, 원문이 우선)

- **고칠 곳:** [workflow.md](../skill-plugin/workflow.md#depth) 80줄의 "새 기술" 정의를 이 답으로 바꾼다. [interviews.md](../skill-plugin/interviews.md#stack)의 S6 스택 확정 내용도 함께 맞춘다.
- **이미 확정된 것으로 보는 것:** 온보딩에서 기록한 기존 스택과 의존성이다. 그 안에서 새로 쓰는 일반 라이브러리는 묻지 않는다.
- **분류가 바뀌는 라이브러리:** 일반 라이브러리라도 제한 라이선스나 비용이 따라오면 확정받는 쪽으로 옮긴다.
- **PC에 설치하는 도구:** 예전 결정 Q-008(도구는 승인을 받아 설치)과 같다. 작업 세션이 시스템 패키지를 직접 설치하지 못하게 막는 훅([plugin.md](../skill-plugin/plugin.md#hooks))은 그대로 둔다.
- **확인 방법(AI가 정한다):** 레지스트리를 조회해 실재와 최근 배포를 보고, 라이선스는 레지스트리 정보로 본다. 취약점은 OSV 같은 공개 취약점 DB로 본다.
- **고른 뒤에 바꿀 때:** Barrel이 고른 라이브러리가 맞지 않으면, 확정된 스택 안에서 바꾸고 이유를 남긴다(예전 결정 D-041).
- 아직 `skill-plugin/`에 반영하지 않았다.
