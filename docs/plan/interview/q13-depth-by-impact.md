# Q13. 작은 요청에도 인터뷰와 승인 단계를 모두 거치는가

- 질문일: 2026-10-08
- 관련: 2026-09-29 초안 OD-4, [Q01](q01-keep-working-scope.md), [Q06](q06-task-tree.md), [원래 구상](../00-original-flow.md) 2~8번
- 기록 원칙: 사용자 답변은 받은 그대로 적는다. 아래 "요약"은 찾아보기 편하도록 붙인 것이며, 내용이 다르면 답변 원문이 우선한다.

## 질문 (사용자에게 보낸 내용)

[Q15](q15-task-files-in-repo.md), [Q16](q16-engines-and-verification.md)과 같은 메시지에서 물었다.

### 왜 지금 묻는지

원래 흐름은 요구사항, 기능명세, 의도 요약과 트리 검토, 기술 조사, 스택 확정 순서다. "이 버그 고쳐줘" 같은 요청에도 이 단계를 전부 돌리면 질문과 승인이 많아진다. 이 답으로 workflow 문서의 단계 규칙이 정해진다.

### 다른 도구 조사 요약

- **깊이는 대개 사용자가 시작할 때 고른다.**
  - Kiro는 Feature, Bugfix, Quick Spec 가운데 하나를 고른다. Quick Spec은 단계 사이 승인 없이 질문만 먼저 받는다([문서](https://kiro.dev/docs/specs/quick-spec/)).
  - BMAD도 변경 크기에 따라 경로를 고르게 한다.
- **AI가 먼저 살펴보고 깊이를 정하는 사례도 나왔다.** BMAD Build(2026-09)는 "decides how much ceremony a change needs after investigating it"이고, 작은 변경에는 두 절짜리 명세만 쓴다. 다만 사용자가 내용을 확인하기 전에는 아무것도 쓰지 않는다([CHANGELOG](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md)).
- **흐름 하나를 모든 크기에 쓰면 작은 변경이 부풀어 오른다.**
  - Kiro가 작은 버그 하나를 사용자 스토리 4개와 수용 기준 16개로 만든 사례가 있다([Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).
  - Spec Kit은 버튼 하나를 고치는 데 파일 30개를 바꿨다([#1174](https://github.com/github/spec-kit/issues/1174)).
- **크기와 상관없이 남는 단계:** 거의 모든 도구가 코딩 전 확인은 한 번 남긴다. 단계를 늘리는 기준은 파일 수가 아니라 낯선 코드, 불분명한 방법, 되돌리기 어려운 동작, 핵심 경로다.
- **예전 계획의 기준:** 예전 계획에서 사용자가 정한 D-026과 D-034도 같은 입장이다. 검토 범위는 AI가 영향 근거로 판단하고, 파일 수로 정하지 않는다.

### 선택지

- **AI가 영향 범위로 깊이 결정 (추천)**
  - 오케스트레이터가 요청을 기억 단위와 코드에 비춰 국소, 확장, 전체로 나눈다.
  - 국소는 정본으로 답할 수 없는 것만 묻고, 짧은 작업 의도 요약 하나로 확인받는다.
  - 확장은 영향받는 부분만 인터뷰한다.
  - 전체(새 컨셉 포함)는 모든 단계를 거친다.
  - 스택은 새 기술이 들어올 때만 확정받는다.
  - 구현 전 작업 의도 검토(Q01)는 빼지 않고, 진행 중 위험이 드러나면 범위를 올린다.
- **항상 모든 단계** 요청 크기와 상관없이 요구사항, 기능명세, 의도·트리 검토, 기술 조사, 스택 확정을 모두 거친다. 일관되지만 작은 요청에도 질문과 승인이 많아진다.
- **시작할 때 사용자가 고름** skill을 실행할 때 '작게, 보통, 전체' 가운데 고른다(Kiro, BMAD 방식). 고른 깊이를 그대로 따른다.

## 사용자 답변 (2026-10-08, 원문 그대로)

선택지를 골랐다.

```text
AI가 영향 범위로 깊이 결정 (추천)
```

## 요약 (원문이 우선)

- 오케스트레이터가 요청을 기억 단위와 코드에 비춰 보고 영향 범위를 국소, 확장, 전체로 나눈 뒤 단계의 깊이를 정한다.
  - 국소: 정본으로 답할 수 없는 것만 묻고, 짧은 작업 의도 요약 하나로 확인받는다.
  - 확장: 영향받는 부분만 인터뷰한다.
  - 전체: 모든 단계를 거친다. 새 컨셉은 항상 전체다.
- 스택은 새 기술이 들어올 때만 확정받는다.
- 구현 전 작업 의도 검토(Q01)는 어떤 범위에서도 빼지 않는다.
- 진행 중 새 위험이 드러나면 범위를 올린다.

## 이 답에 따른 정리 (AI 분석, 원문이 우선)

- 영향 범위를 판단하는 근거는 예전 계획 D-026, D-034와 조사에서 나온 기준을 쓴다. 근거는 의도의 빈칸, 되돌리기 어려운 동작, 영향이 미치는 범위, 핵심 경로다. 파일 수로는 정하지 않는다.
- 판단 결과와 근거는 기억 단위로 남겨, 사용자가 작업 의도 요약을 검토할 때 함께 볼 수 있게 한다. AI가 정한 세부다.
