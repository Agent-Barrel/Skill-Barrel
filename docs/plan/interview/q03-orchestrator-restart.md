# Q03. 오케스트레이터는 언제, 어떻게 재시작하는가

- 질문일: 2026-10-06
- 관련: [어긋나는 점 3번](../README.md#conflicts)
- 기록 원칙: 사용자 답변은 받은 그대로 적는다. 아래 "선택지 대응"은 찾아보기 편하도록 붙인 요약이며, 내용이 다르면 답변 원문이 우선한다.

## 질문 전에 알린 것

Q02에서 새 세션을 띄우는 수단을 "step2step"이라고 적었다. 그런데 이번 조사에서 Claude Code 자체 백그라운드 세션(`claude --bg`, agent view, 연구 프리뷰)도 같은 역할을 할 수 있다는 것을 확인했다. 이 세션은 완전한 대화형 세션이고 구독으로 돌며, 터미널을 닫아도 이어진다. Q02의 역할 분담은 그대로 두고, 새 세션을 무엇으로 띄울지는 기술 조사 단계(원래 구상 7~8번)에서 따로 묻기로 했다.

## 질문 (사용자에게 보낸 내용)

### 왜 지금 묻는지

요청 원문에 "각 세션을 두뇌로 사용하고 문서를 통해 맥락을 파악하며 … 오케스트레이터도 필요한 경우 재시작"이 있다. 09-29 초안에서는 사용자가 연 CLI 세션이 끝까지 오케스트레이터였다. [Q02](q02-subagent-vs-session.md)에서 오래 걸리는 작업은 새 세션이 맡아 재시작 뒤에도 이어지게 했으므로, 오케스트레이터 자신을 언제, 누가 교체하는지가 정해져야 실행 구조를 그릴 수 있다.

### 다른 서비스 조사 요약

- **Anthropic 장기 실행 하네스:** 세션마다 새 맥락으로 시작해 진행 기록 파일, git 로그, 기능 목록부터 읽고 기능 하나를 맡는다. "compaction isn't sufficient"라고 적었다. ([글](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents))
- **Ralph 기법:** 루프를 돌 때마다 새 맥락으로 시작하고, 상태는 `fix_plan.md`, `specs/`, `AGENT.md`에 둔다. 메인 맥락은 "scheduler"로만 쓰고 일은 subagent에게 맡긴다. 약 15만 토큰을 넘으면 품질이 떨어졌다고 보고했다. ([글](https://ghuntley.com/ralph/))
- **Claude Code 자동 압축:** 맥락이 차면 대화 중간을 요약으로 바꾸며, 앞서 정한 제약이나 버린 방법 같은 세부가 사라진다. 실무자들은 인계 문서를 쓰고 작업이 끊기는 지점에서 새로 시작하라고 권한다. ([글](https://dev.to/jsmanifest/claude-code-session-compaction-in-2026-how-context-summarization-works-and-what-your-agent-forgets-am0))
- **Claude Code 백그라운드 세션과 세션 간 메시지:** 백그라운드 세션은 감독 프로세스가 돌려서, 띄운 쪽이 닫혀도 이어지고 사용자가 나중에 붙어서 답할 수 있다. 같은 PC의 세션끼리 텍스트 메시지를 주고받고, 상대가 한가해지면 알림을 받을 수 있다. ([agent view](https://code.claude.com/docs/en/agent-view), [세션 간 메시지](https://code.claude.com/docs/en/cross-session-messaging))
- **Codex `/goal`:** 목표 상태가 재시작 뒤에도 유지된다. ([문서](https://learn.chatgpt.com/use-cases/follow-goals))

공통점: 상태는 대화가 아니라 파일에 두고, 새 세션은 그 파일부터 읽고, 교체는 작업이 끊기는 지점에서 한다.

### 정할 것

재시작 시점, 새 오케스트레이터를 띄우는 주체, 사용자가 오케스트레이터와 대화하는 곳.

모든 선택지의 공통 원칙: 결정, 진행 상황, 대기 중인 질문은 생기는 즉시 문서에 적고, 오케스트레이터 대화에만 남는 정보가 없게 한다.

### 선택지

- **A (추천) 단계에 따라 나눈다.**
  - 인터뷰 단계(요구사항부터 기술 스택 확정까지): 사용자가 연 세션이 오케스트레이터다. 한 단계가 끝나거나 맥락이 일정량을 넘으면 인계 문서를 남기고, 새 세션이 문서만 읽고 이어 간다.
  - 구현 단계: 사용자 세션과 분리된 실행 드라이버가 오케스트레이터 세션을 띄운다. 오케스트레이터는 주제 하나를 처리하거나 맥락 한도에 이르면 끝나고, 드라이버가 문서 상태로 다음 오케스트레이터를 새로 띄운다. 사용자가 터미널을 닫아도 계속된다. 사람에게 물어야 할 질문은 사용자 세션이나 Slack으로 온다.
- **B** 사용자 세션 하나를 끝까지 오케스트레이터로 쓴다. 맥락이 한도에 가까워질 때만 인계 문서를 쓰고 새 세션으로 바꾼다. 구현도 이 세션이 지휘한다. 사용자 세션이 닫히면 지휘가 멈춘다.
- **C** 매 단계, 매 작업마다 새 오케스트레이터를 쓴다(Ralph 방식). 사용자 세션은 질의응답 창구만 맡는다. 대화가 이어져야 하는 인터뷰 단계에서는 매번 문서를 다시 읽는 비용이 든다.

교체를 사용자에게 어떻게 보이게 할지(새 세션을 열라고 안내할지, 자동으로 넘길지)는 구현 때 정해도 되는 세부로 두었다.

## 사용자 답변 (2026-10-06, 원문 그대로)

```text
지금 이 앱을 skill 로 만들려고 하는건데, A 방법이 실제 가능한 방법일지 고민해줘. 가능하다면 A 방법으로 해줘.
```

## 선택지 대응 (요약, 원문이 우선)

- 조건부 **A**. skill로 만들 때 A가 실제로 가능한지 검토하고, 가능하면 A로 한다.

## 가능성 검토 (AI 분석, 2026-10-06)

> **이후 변경:** 사용자가 아래의 "교체 때마다 `/clear` 입력" 조건을 받아들이지 않았다. 교체는 자동이어야 하고, 최초 세션은 부트로더로만 쓰는 방식을 검토하라고 했다. [Q03-2](q03-2-bootloader-session.md)를 본다.

이 절은 사용자 답변이 아니라 답변의 조건("가능한지 고민해줘")에 따라 AI가 확인한 내용이다. 결론: **A는 skill(플러그인)로 가능하다. A로 진행한다.** 아래 세 가지 조건이 붙는다.

### 인터뷰 단계: 가능. 교체할 때 사용자가 `/clear`를 한 번 입력한다.

- **맥락 사용량을 잴 수 있다.**
  - Claude Code와 Codex 모두 훅 입력에 `transcript_path`가 있다. 기록 파일에는 응답마다 토큰 사용량이 남는다.
  - Claude Code 기록의 `message.usage`로 이 세션을 계산하면 약 32만 토큰이다. Codex 기록에는 `token_count` 이벤트에 `last_token_usage`와 `model_context_window`(258,400)가 있다.
  - 플러그인 훅(`PostToolUse`, `UserPromptSubmit`)이 한도를 넘은 것을 감지하면 `additionalContext`로 "작업이 끊기는 지점에서 인계 문서를 쓰고 교체를 요청하라"고 넣을 수 있다.
  - 두 CLI 모두 `PreCompact` 훅이 있다. Claude Code는 이 훅으로 자동 압축을 막을 수 있다. ([Claude 훅](https://code.claude.com/docs/en/hooks), [Claude 상태줄 필드](https://code.claude.com/docs/en/statusline), [Codex 훅](https://learn.chatgpt.com/docs/hooks))
- **새 대화가 인계 문서를 읽고 바로 이어 갈 수 있다.**
  - 두 CLI 모두 `/clear`를 하면 `SessionStart` 훅이 source `clear`로 실행되고, `additionalContext`로 인계 문서 위치를 넣을 수 있다.
  - Codex에서 이 주입이 거부된다는 이슈 [#45999](https://github.com/openai/codex/issues/45999)는 2026-09-17에 설정 위치 오류로 밝혀져 닫혔다(`hookSpecificOutput` 아래에 둬야 한다).
- **한계가 두 가지 있다.**
  - skill이 자기 대화를 스스로 비울 방법은 없어서, 교체할 때마다 사용자가 `/clear`를 한 번 입력해야 한다.
  - Codex 훅은 처음에 `/hooks`에서 사용자가 한 번 신뢰해야 하고, 훅 내용이 바뀌면 다시 신뢰해야 한다.

### 구현 단계: 가능. 플러그인에 백그라운드 드라이버(Python)를 넣는다.

- **오케스트레이터와 작업 세션을 사용자 터미널 없이 띄우는 코드는 이미 있다.**
  - main의 unit loop와 `step2step`은 Claude 세션을 자체 PTY로 띄운다. 2026-07-31 야간 구축과 2026-08-12~13 Starfort 12유닛 실행에서 실측했다.
  - Codex는 app-server로 구동한다(2026-09-10 live 5/5).
  - 오케스트레이터가 주제 하나를 처리하면 닫고 다음 세션을 띄우는 일은 `SessionHandle`의 start/send/wait/stop으로 할 수 있다.
- **사용자 세션이 닫혀도 계속 돌 수 있다.** skill은 드라이버를 사용자 세션과 분리된 프로세스로 띄운다.
  - 2026-07-31 야간 구축 때 하네스의 백그라운드 작업이 강제 종료된 적이 있다. 그 뒤 분리(detached) 실행으로 바꿨고 재발하지 않았다. 이때 환경은 Windows였다(`archive/tauri-desktop-app` 브랜치의 `orchestration/reports/overnight-report.md`).
  - macOS에서 Claude Code 세션이 끝난 뒤에도 드라이버가 살아남는지는 아직 실측하지 않았다. 살아남지 못하면 launchd 사용자 에이전트로 띄운다.
- **질문을 전달할 수 있다.**
  - 막힌 작업의 질문은 파일로 남기고 그 작업만 멈춘다. unit loop에 blocked 처리가 있다.
  - 사용자가 CLI를 다시 열면 `SessionStart` 훅이 대기 중인 질문을 보여 준다.
  - Slack 같은 알림 경로는 어긋나는 점 9번에서 정한다.
- **skill만으로는 안 되는 부분이 있다.** 구현 단계 드라이버는 마크다운 지침이 아니라 Python 프로그램이다. 플러그인에 스크립트로 넣고 skill이 실행한다. 사용자 PC에 Python 3.12 이상이 필요하며, uv가 있으면 Python과 의존성을 자동으로 받을 수 있다.

### spike에서 확인할 것

1. macOS에서 드라이버를 띄운 Claude Code 세션이 끝난 뒤에도 드라이버가 계속 도는지 확인한다. 안 되면 launchd로 바꾼다.
2. `step2step` 화면 보정이 현재 버전(Claude Code 2.1.291, codex-cli 0.155.1)에서 유효한지 확인한다. 마지막 보정은 2.1.272에서 했다.
3. Codex에서 `/clear` 뒤 `SessionStart` 주입으로 인계가 이어지는지 확인한다.

Claude Code 자체 백그라운드 세션(`claude --bg`)으로 드라이버 일부를 대신할 수 있는지는 기술 조사 단계에서 따로 묻는다.
