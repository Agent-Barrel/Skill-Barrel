# Q22. Slack에서 받은 새 요청으로 새 실행을 시작하는가

- 질문일: 2026-10-12
- 관련: [Q18](q18-one-run-per-request.md), [Q03-3](q03-3-launcher-and-slack.md), [Q11](q11-launcher-topology.md), [skill-plugin/runs.md](../skill-plugin/runs.md#after)(AI 기본값 35번), [구현 준비 점검](../readiness-2026-10-12.md)
- 기록 원칙: 사용자 답변은 받은 그대로 적는다. 아래 "요약"은 찾아보기 편하도록 붙인 것이며, 내용이 다르면 답변 원문이 우선한다.

## 질문 (사용자에게 보낸 내용)

같은 날 오전 점검([Q17](q17-restore-archived-decisions.md)~[Q21](q21-auto-update-consent.md)) 뒤, 사용자가 같은 요청을 다시 했다. 설계와 인터뷰 기록으로 의도한 skill을 만들 수 있는지 확인하고, 남은 것을 하나씩 물어 달라는 요청이었다. 점검 결과를 먼저 알리고 이 질문을 했다.

### 먼저 알린 점검 결과

- **결론:** 의도한 skill을 만들 수 있다. Q01~Q21 답, 원래 구상 0~12번, 되살린 예전 결정이 모두 설계 안에 들어가 있고, 실행 바탕(`step2step`, unit loop)도 있다.
- **정본은 아직 예전 상태다.** `skill-plugin/`에는 Q17~Q21이 반영되지 않았고 [readiness-2026-10-12.md](../readiness-2026-10-12.md)에만 정리돼 있다. 구현 전에 정본을 고쳐야 한다. 사용자가 요청하면 고친다.
- **오전 점검은 "더 물을 것 없음"으로 끝났다.** 다시 대조해 보니 사용자가 판단해야 할 것이 2개 남아 있었다. 여기에 spike 준비용 사실 1묶음을 더해 하나씩 묻는다.
  1. Slack에서 받은 새 요청으로 새 실행을 시작하는가. Q18에서 생긴 빈틈이다.
  2. 재부팅이나 실행기 장애 뒤 Barrel이 저절로 다시 뜨는가. 예전 결정 Q-007은 "로그인할 때 자동 시작"을 정하지 않았다고 적었고, 지금 설계는 spike 결과에 맡겨 두었다.
  3. spike에 쓸 Slack 워크스페이스와 앱 설치 권한, 유지보수 과제용 레포, 여러 저장소 과제용 프로젝트
- **묻지 않고 AI가 채울 것** (이의가 있으면 말해 달라고 했다):
  - 예전 결정 가운데 계획 문서 어디에도 언급되지 않은 사용자 결정 3개를 스킬 구조에 맞춰 넣는다.
    - D-016: 일상 업무용 Mac에서 함께 돈다. 게이트와 작업 세션은 낮은 우선순위로 돌린다.
    - Q-002: GitHub 연결은 권하되 건너뛸 수 있다.
    - Q-020: 프로젝트 보관과 기록 삭제
  - Q17 5번(Barrel 전용 설정 폴더)에서 기존 로그인을 그대로 쓸 수 없다고 spike에서 나오면, 계정마다 Barrel 폴더에 한 번 더 로그인한다. 사용자가 "반드시 반영"하라고 했으므로 분리를 우선한다. spike 대안 목록에 없던 항목이다.
  - 와이어프레임과 상세 디자인을 만드는 형식과 도구는 예전 P-002에서 구현 때 정하기로 한 부분이라 AI가 정한다. Codex에는 구독 한도 안에서 쓰는 내장 이미지 생성(`$imagegen`)이 있어 유료 API 없이 시작할 수 있다.
  - AI 기본값 40개는 대부분 기존 답에서 바로 나오거나 기술 세부라 묻지 않는다. 사용자 판단이 걸린 1번(재시작)과 35번(실행 시작)만 질문에 넣었다.
- **참고:** 공개 레포에 LICENSE 파일이 없다. 구현과 무관해 질문에서 뺐다.

### 왜 지금 묻는지

- Q18에 따라 skill로 들어온 새 요청은 각각 새 실행이 된다. Slack 글은 진행 중인 실행에 주는 지시로만 받는다.
- 그래서 휴대폰으로 프로젝트 채널에 새 요청을 쓰면 갈 곳이 없다.
  - 진행 중인 실행이 있으면 그 실행의 지시로 들어간다.
  - 없으면 "Mac에서 skill을 실행하세요"라는 고정 답장만 간다(AI 기본값 35번).
- 이 답에 따라 실행기의 Slack 처리가 정해지고, 다음 질문(실행기를 늘 띄워 둘지)도 달라진다.
- 기존 코드에는 Slack 처리 부분이 없어 새로 만든다. 실행 시작은 skill과 같은 `barrel run start` 경로를 쓴다.

### 다른 서비스 조사 요약 (2026-10-12 확인)

- **Claude Code in Slack:**
  - 채널이나 스레드에서 @Claude를 부르면 코딩 요청인지 판단해 새 세션을 만든다.
  - 레포는 대화 내용을 보고 고르고, 잘못 고르면 "Change Repo" 버튼으로 바꾼다. 진행 상황은 그 스레드에 올린다.
  - ([문서](https://code.claude.com/docs/en/slack))
- **Codex(지금 이름은 @ChatGPT):** 채널에서 부르면 클라우드 작업을 시작한다. 같은 스레드의 후속 요청은 그 작업을 이어 간다. ([문서](https://learn.chatgpt.com/docs/third-party/slack))
- **Cursor:** `@Cursor [요청]`으로 에이전트를 시작한다. 이미 에이전트가 있는 스레드에서 새로 시작하려면 `@Cursor agent [요청]`을 쓴다. ([문서](https://cursor.com/docs/integrations/slack))
- **Devin:** 채널에서 @Devin을 부르면 세션을 시작하고 스레드로 답한다. ([문서](https://docs.devin.ai/integrations/slack))
- **공통점:** 채널의 새 글은 새 작업이 되고, 그 작업의 스레드 답글은 그 작업에 주는 지시가 된다.

### 선택지

- **A (추천) 기존 프로젝트의 새 요청은 Slack에서도 받는다.**
  - 프로젝트 채널에 명령어가 아닌 새 글을 쓰면 버튼으로 묻는다. [새 요청으로 시작]과 [진행 중인 실행 ○○에 지시] 가운데 고른다. 진행 중인 실행이 없으면 [새 요청으로 시작] 버튼만 나온다.
  - 실행이 하나만 돌 때도 채널에 바로 쓴 지시는 버튼을 한 번 눌러야 한다. 실행 스레드에 단 답글은 Q18대로 버튼 없이 그 실행의 지시가 된다.
  - Slack에서 시작한 실행도 skill로 시작한 실행과 똑같이 돌고, 시작 보고를 채널에 올린다.
  - 새 제품 컨셉은 Mac의 skill에서만 시작한다. 아직 폴더도 채널도 없기 때문이다.
- **B Slack은 진행 중인 실행에 주는 지시만 받는다 (지금 설계).** 새 요청은 Mac에서 skill로만 시작한다.
- **C 새 컨셉까지 Slack에서 받는다.** 봇 DM에 컨셉을 쓰면 미리 정해 둔 Mac 폴더에 새 프로젝트를 만들고 채널을 연다.

추천 이유:
- 조사한 서비스 모두 Slack의 새 글로 작업을 시작한다.
- Q18이 요청 하나를 실행 하나로 정했으니 같은 규칙이 Slack에도 맞는다.
- 중지, 재개, 상태 확인, 화면 열기는 이미 휴대폰에서 된다. 새 요청만 Mac에서 해야 할 이유가 적다.
- 버튼으로 한 번 확인받으므로 지시를 새 실행으로 잘못 여는 일이 없다.
- 새 컨셉은 폴더 위치와 프로젝트 이름을 Mac에서 정해야 해서 skill에 둔다.

함께 알린 것: A를 고르면 실행이 없을 때도 Slack 글을 받아야 하므로 실행기가 늘 떠 있어야 한다. 이것은 다음 질문에서 함께 정한다고 적었다.

질문 창에 보인 선택지 이름과 설명:
- `Slack에서도 받기 (추천)`: 기존 프로젝트의 새 요청은 채널에 써도 됩니다. 새 글은 [새 요청으로 시작] / [실행 ○○에 지시] 버튼으로 확인합니다. 새 컨셉은 Mac의 skill에서만 시작합니다.
- `지시만 받기 (지금 설계)`: Slack은 진행 중인 실행에 주는 지시만 받습니다. 새 요청은 Mac에서 skill로만 시작합니다.
- `새 컨셉까지 Slack`: 봇에게 DM으로 컨셉을 보내면 미리 정해 둔 Mac 폴더에 새 프로젝트를 만들고 채널을 엽니다.

## 사용자 답변 (2026-10-12, 원문 그대로)

선택지를 고르지 않고 직접 썼다.

```text
"Slack에서도 받기"도 좋은데, 이건 어쨌든 스킬을 실행해야 이 봇이 활성화되는거 아니야(봇이 로컬 클로드코드나 코덱스에 내용을 전달할 방법이 없어지는 것)? 주객이 전도된 것 같은데 실제 가능한건지 생각하고 말하는거야?
```

## 요약 (원문이 우선)

- 선택지를 고르지 않았다. "Slack에서도 받기"도 좋다고 했다.
- skill을 실행해야 봇이 활성화되는 것 아니냐고 물었다. 그렇지 않으면 봇이 로컬 Claude Code나 Codex에 내용을 전달할 방법이 없지 않으냐는 것이다.
- 주객이 전도된 것 같다며, 실제로 가능한지 생각하고 말한 것인지 물었다.

## AI가 답한 내용 (AI 분석, 원문이 우선)

가능하지만 조건이 하나 있다고 답했다. 그 조건을 먼저 묻지 않고 순서를 거꾸로 물었다는 점도 인정했다.

- **봇은 skill 세션이 아니라 실행기에 붙어 있다.**
  - 처음 한 번은 사용자 말대로다. skill의 첫 설정(S0)에서 봇(Slack 앱)과 실행기가 만들어진다.
  - 그 뒤로는 설계상(Q03-3, Q11) skill 세션이 실행기를 띄우고 끝난다. Mac에 따로 떠 있는 실행기 프로세스가 Slack 연결과 모든 세션 실행을 맡는다.
- **봇이 로컬 Claude Code에 내용을 넣는 것이 아니다. 실행기가 새 Claude Code·Codex 세션을 직접 띄운다.**
  - skill로 시작한 실행도 오케스트레이터는 실행기가 띄운다. skill은 `barrel run start`를 부를 뿐이다.
  - 이 부분은 지금 코드에도 있다. unit loop는 사용자 세션 없이 유닛마다 새 Claude 세션을 띄운다(`barrel/core/unitloop.py:433-442`에서 `step2step/claude/session.py:100-147`을 부른다). 2026-08 Starfort 12유닛 실행이 이렇게 돌았다.
- **조건: 메시지가 올 때 실행기가 떠 있어야 한다.**
  - 재부팅 뒤 아무도 실행기를 띄우지 않았다면 Slack 메시지를 받을 프로세스가 없다.
  - 메시지는 사라지지 않는다. 실행기가 다음에 뜰 때 채널 기록에서 읽어 처리한다([launcher.md](../skill-plugin/launcher.md#recovery)). 하지만 그때까지는 아무 일도 일어나지 않는다.
- **먼저 물었어야 할 것:** 지금 설계는 실행기를 언제까지 띄워 둘지 spike 결과에 맡겨 두었다(AI 기본값 1번). "Slack에서 새 요청"은 "실행기를 skill과 별개로 늘 띄워 두는가"에 달려 있다.
- **그래서:** 실행기를 얼마나 띄워 둘지를 먼저 묻고, Slack 새 요청은 그 선택지 안에 넣어 [Q22-2](q22-2-launcher-residency.md)로 다시 물었다.
