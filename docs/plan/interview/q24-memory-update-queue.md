# Q24. 작업이 끝날 때마다 기억을 갱신하고, 한 번에 한 세션만 고친다

- 지시일: 2026-10-12
- 관련: [Q07](q07-shared-memory.md), [Q14](q14-parallel-sessions.md), [Q15](q15-task-files-in-repo.md), [Q11](q11-launcher-topology.md), 예전 결정 D-032([결정 원장](../../archive/app-plan/decisions.csv)), [skill-plugin/memory.md](../skill-plugin/memory.md#rules), [skill-plugin/task-execution.md](../skill-plugin/task-execution.md#lanes), [구현 준비 점검](../readiness-2026-10-12.md)
- 기록 원칙: 사용자 지시는 받은 그대로 적는다. 아래 "요약"은 찾아보기 편하도록 붙인 것이며, 내용이 다르면 원문이 우선한다.

## 직전에 AI가 보낸 내용 (요약)

[Q23](q23-spike-inputs.md)의 답을 기록하고, 질문이 끝났다고 알렸다. 남은 일은 정본 개정과 spike이고, 사용자가 말하면 시작한다고 했다.

## 사용자 지시 (2026-10-12, 원문 그대로)

질문에 대한 답이 아니라 사용자가 먼저 꺼낸 지시다.

```text
하나 강조하고 싶은게 있어. Barrel 이 의도한대로 작동하려면 작업이 끝날 때마다 Barrel 이 Context 와 작업 이해에 사용하는 '기억'파일을 최신화하는게 무엇보다 중요해. 오케스트레이터가 실행한 세션이 종료될 때마다(더 좋은 '기억'파일 정리 시점이 있다면 추천해줘도 좋음), 기억 파일을 업데이트 하도록 명시해줘. 한번에 여러 세션에서 기억파일에 접근하진 못하도록(수정 시 충돌 위험이 있고, 덮어쓰기를 통한 유실의 위험도 있음), 편집락이나 접근 큐를 도입해서 한번에 여러 세션이 기억 수정을 하지 못하도록 해줘. 세션이 기억파일을 자기가 한 작업 기반으로 수정해야 완전 종료가 가능하지만, 한번에 모든 세션이 수정은 못하고 끝난 순서대로 기억 수정하고 종료하고 하는 식으로 작동하게 해주면 돼. 또, 작업 시작 시에도 어떤 작업이 진행할 에정인지도 '기억'에 적어둬서 과거 상태를 읽어 잘못 작업하는 일이 없도록 해줘. 이 문제에 대한 더 나은 방지법이 있으면 제시해줘도 좋아. 앞서 말했듯이, 병렬로 했을 때 작업의도에서 틀어지는 작업들이거나 서로 종속된 작업들이라면 병렬로 실행하지 않아도 좋아.
```

## 요약 (원문이 우선)

- Barrel이 의도대로 작동하려면, 작업이 끝날 때마다 Barrel이 맥락과 작업 이해에 쓰는 기억 파일을 최신으로 고치는 것이 무엇보다 중요하다.
- 오케스트레이터가 띄운 세션이 끝날 때마다 기억 파일을 갱신하도록 명시한다. 더 좋은 정리 시점이 있으면 추천해도 된다.
- 여러 세션이 한꺼번에 기억 파일을 고치지 못하게 편집 잠금이나 접근 대기열을 둔다. 동시에 고치면 충돌하고, 덮어쓰면 내용이 사라질 위험이 있다.
- 세션은 자기가 한 작업을 바탕으로 기억 파일을 고쳐야 완전히 끝날 수 있다. 다만 모든 세션이 한꺼번에 고치지는 못하고, 끝난 순서대로 기억을 고치고 종료한다.
- 작업을 시작할 때도 어떤 작업을 진행할 예정인지 기억에 적어 둔다. 과거 상태를 읽고 잘못 작업하는 일을 막기 위해서다.
- 이 문제를 더 잘 막는 방법이 있으면 제시해도 된다.
- 병렬로 돌렸을 때 작업 의도에서 틀어지는 작업이나 서로 종속된 작업은 병렬로 돌리지 않아도 된다.

## 지금 설계와 다른 점 (AI 분석, 원문이 우선)

- **기억을 쓰는 쪽:** 지금 설계에서는 오케스트레이터만 기억 단위를 쓴다. 작업 세션과 보조 세션은 `.barrel/`을 쓰지 않는다([memory.md](../skill-plugin/memory.md#rules), AI 기본값 8번·22번).
- **말단 작업이 한 일:** 결과 보고로 레포 밖 실행 상태에만 남는다([task-execution.md](../skill-plugin/task-execution.md#report)). 오케스트레이터는 작업 파일을 `done`으로 바꿀 뿐이다. 그래서 말단 작업이 실제로 만든 것과 알게 된 것이 기억 단위에 들어간다는 보장이 없다. 사용자가 짚은 빈틈이 실제로 있다.
- **병렬 규칙:** 파일(`write_set`, `read_set`)과 바깥 자원만 본다([task-execution.md](../skill-plugin/task-execution.md#lanes)). 기억 단위는 보지 않는다.
- **진행 중 표시:** 실행 상태(`run.json`)에만 있고, 세션에게 보여 주지 않는다.
- **잠금:** 기존 코드에는 프로세스 사이의 잠금이 없다. step2step 안의 스레드 잠금뿐이다(`step2step/codex/transport.py:20`, `:70`). 실행기는 PC에 하나이고(Q11) 모든 세션이 이미 실행기와 통신하므로, 대기열은 실행기 안에 하나 두면 된다.

## AI가 제안한 내용 (AI 분석, 원문이 우선)

### 지시를 그대로 명시하는 부분

- **기억 대기열:** 프로젝트마다 하나를 실행기 안에 둔다. `.barrel/`의 기억 단위와 작업 파일을 고치는 모든 쪽이 이 대기열을 거쳐 한 번에 하나씩 쓴다. 작업 세션, 보조 세션, 오케스트레이터, 답을 기록하는 실행기가 모두 여기에 든다.
- **끝난 순서대로:** 일을 마친 세션은 대기열에 줄을 선다. 차례가 오면 자기가 한 작업을 바탕으로 기억을 고치고, 그 뒤에야 종료된다.

### 추천 1. 갱신 시점: 코드를 합친 직후, 같은 차례 안에서

- **"세션이 끝날 때"를 더 구체적으로 정한다.** 한 차례 안에서 다음 순서로 한다. 세션은 마지막 단계를 마친 뒤에 종료된다.
  1. 그 작업의 코드를 실행 브랜치에 합친다. Q14대로 합친 결과로 게이트를 다시 돌린다.
  2. 세션이 최신 기억을 받아 본다. 기다리는 동안 다른 세션이 고친 단위도 알려 준다.
  3. 그 위에 자기 작업의 기억을 고친다.
  4. 실행기가 검사하고 커밋한다.
  5. 세션이 종료된다.
- **이유:** 합치기 전에 기억을 고치면, 합치기가 실패했을 때(충돌, 합친 뒤 게이트 실패) 기억이 실행 브랜치에 없는 코드를 설명하게 된다. 한 차례 안에서 하면 코드와 기억이 늘 함께 움직인다.
- **합치지 못하고 끝나는 세션**(질문으로 막힘, 포기)도 알게 된 것을 같은 대기열에서 남기고 끝난다. 예를 들어 실패한 방법과 그 이유를 남겨, 다음 시도가 같은 실패를 되풀이하지 않게 한다(예전 결정 D-040).

### 추천 2. 중주제가 끝날 때 한 번 더 정리

- 말단마다 고친 기억을 오케스트레이터가 중주제 끝에 한 번 훑어, 중복과 모순을 정리한다. 이 시점은 이미 인계와 회귀 검사를 하는 때다.
- 말단 갱신은 "최신"을, 중주제 정리는 "일관성"을 맡는다.

### 추천 3. 시작 기록

- **할 일 자체:** 중주제를 나눌 때 지금도 작업 파일(계약)로 레포에 커밋된다. 여기에 "이 작업이 바꿀 수 있는 기억 단위" 목록을 더한다.
- **진행 중 표시:** "지금 진행 중"이라는 표시는 실행 상태(레포 밖)에 둔다. 기억 색인과 함께 모든 세션에 보여 준다.
- **이유:**
  - 병렬 레인은 시작할 때의 커밋에 고정된다. 그 뒤에 레포에 커밋한 표시는 이미 돌고 있는 세션에 보이지 않는다. 실행 상태는 실행기를 통해 모든 세션이 바로 본다.
  - Q15도 진행 중 같은 순간 상태는 레포 밖에 두기로 했다.

### 추천 4. 병렬 규칙에 기억 단위를 더한다

- 한 작업이 바꿀 수 있는 기억 단위를 다른 작업이 읽거나 바꾸면, 두 작업을 함께 돌리지 않는다.
- 예전 결정 D-032의 "참조 문서 변경을 먼저 끝낸 뒤 이를 읽는 구현을 시작한다"를 기억 단위에 그대로 적용한 것이다. 사용자 말대로 서로 종속되거나 의도가 틀어질 수 있는 작업은 차례로 돌린다.
- 대기열은 쓰기 충돌을 막고, 이 규칙은 낡은 기억을 읽는 일을 처음부터 막는다.

### AI가 정하는 세부 (이의가 없으면 이대로)

- **작업 세션이 고칠 수 있는 범위:** 자기가 만든 것과 알게 된 것만 쓴다. 요구사항, 기능, 사용자의 결정, 답처럼 사용자가 원하는 것은 고치지 못한다. 그것이 바뀌어야 하면 오케스트레이터가 질문과 연쇄 변경으로 다룬다(Q01).
- **검사:** 실행기가 커밋 전에 형식, 링크, 고칠 수 있는 종류를 검사한다. 오케스트레이터는 다음 턴에 각 갱신을 계약과 대조한다.
- **사용자의 중지:** 기억 갱신을 기다리지 않는다(15초 안에 중지). 끊긴 작업은 재개한 뒤 끝날 때 갱신한다.
- **갱신 전에 세션이 죽으면:** 남은 변경과 결과 보고로 다음 세션이 갱신한다. 그 전에는 그 작업을 끝난 것으로 치지 않는다.
- **차례를 받은 세션이 멈추면:** 시간 제한 뒤 차례를 넘기고, 그 갱신은 다시 한다.

## 확인 질문과 답

### 질문 (사용자에게 보낸 내용)

위 제안을 알린 뒤 물었다. 추천 1~4와 AI가 정하는 세부를 함께 보냈다. 세부는 이의가 없으면 그대로 한다고 적었다.

질문 창에 보인 질문과 선택지:
- 질문: `기억 갱신을 어떻게 정본에 넣을까요?`
- `추천안대로 (추천)`: 말씀하신 규칙(대기열, 끝난 순서대로 갱신 후 종료, 시작 기록)에 추천 1~4를 더합니다: 합친 직후 갱신, 중주제 끝 정리, 진행 중 표시는 실행 상태에, 기억 단위가 겹치면 병렬 금지.
- `말씀하신 방식 그대로`: 세션이 끝날 때 대기열 순서대로 기억을 갱신하고, 시작 기록도 레포의 기억(.barrel/)에 커밋합니다. 추천 1~4는 넣지 않습니다.
