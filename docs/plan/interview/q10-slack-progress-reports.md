# Q10. Slack 진행 보고를 어떻게 보내는가

- 질문일: 2026-10-07
- 관련: [Q09](q09-slack-and-dashboard.md) 9-b의 변경, [Q08](q08-korean-docs.md), [Q01](q01-keep-working-scope.md), [원래 구상](../00-original-flow.md) 11·12번
- 기록 원칙: 사용자 답변은 받은 그대로 적는다. 아래 "요약"은 찾아보기 편하도록 붙인 것이며, 내용이 다르면 답변 원문이 우선한다.

## 사용자 요청 (2026-10-07, 원문 그대로)

이 질문의 출발점이 된 요청이다. Q09 9-b(로컬 웹 대시보드)와 그 구현 방식(미결)에 대한 후속 지시다.

```text
@docs/plan/session-context.md 를 보고, @docs/plan/00-original-flow.md 와 같이 작동하는 skill 을 만들려고 해.
@docs/plan/README.md 의 질문에 대한 내 인터뷰 내용은 @docs/plan/interview/ 에 있으니, 그걸 함께 참고하면돼.
이 스킬의 대시보드에 대해, 그냥 작업 현황을 사람에게 slack 으로 알려주는 형식으로 진행하는게 더 효과적일 것 같아서 그 방법으로 바꾸려 해. 기존 메시지를 편집하는게 아니라 작업 현황을 계속 보내주는거지. 이렇게 했을 때 문제점과 장점, 대시보드 방식의 문제점과 장점을 깊이 고민하고, 나한테 물어볼건 물어보면서 어떤식으로 구현할지 확정하자. 확정하면 확정된 내용을 @docs/plan/interview/ 에 신규 문서로 정리해주면 돼.
```

## 질문 (사용자에게 보낸 내용)

결론부터 알렸다. Slack 진행 보고로 바꾸는 방향은 조사 결과와 맞는다. 다만 그대로 옮기면 세 가지 문제가 생긴다. 질문이 보고에 묻히고, 지금 상태를 한눈에 볼 수 없고, 실행기가 죽어도 그냥 조용하다. 이 셋을 어떻게 막을지 정하면 구현 방식이 확정된다.

### 1. 무엇이 바뀌나

- **바뀌는 것:** Q09 9-b의 P(로컬 웹 대시보드)를 Slack 진행 보고로 바꾼다. 보고는 기존 메시지를 고치지 않고 새 메시지로 계속 보낸다.
- **그대로인 것:** 9-a의 X. 전용 봇, 프로젝트마다 채널 하나, 질문마다 스레드 하나, Socket Mode로 답 수신, 에이전트의 Slack 조회는 공식 Slack MCP.
- **Slack이 넘겨받을 일:** 대시보드가 맡기로 했던 작업 트리, 세션별 상태, 대기 질문, 최근 보고, 답과 지시 보내기.

### 2. 두 방식 비교

| | Slack 진행 보고 (새 메시지) | 로컬 웹 대시보드 |
| --- | --- | --- |
| 알아차리기 | 메시지가 사람에게 온다. 멘션하면 휴대폰까지 푸시 | 페이지를 열어야 보인다. 질문 알림은 결국 Slack이 따로 해야 한다 |
| 자리를 떠났을 때 | 휴대폰 Slack으로 보고 답한다 | 그 Mac에서만 된다. 휴대폰으로 보려면 Tailscale 같은 터널이 필요 |
| 지금 상태 한눈에 | 어렵다. 메시지는 "일어난 일"이라 스크롤하며 재구성해야 한다 | 쉽다. 트리, 막힌 작업, 대기 질문이 한 화면 |
| 지난 기록 | 시간순으로 남고 검색된다(무료 플랜은 90일) | 따로 만들지 않으면 현재 상태만 |
| 깊이 보기 | 링크로 넘긴다(메시지당 블록 50개, 섹션 3,000자) | 로그, diff, 기억 단위를 화면에서 바로 |
| 소음 | 많이 보내면 질문이 묻히고 채널을 음소거하게 된다 | 갱신이 잦아도 알림 피로가 없다 |
| 조용할 때 | 실행기가 죽어도 그냥 조용하다. "오래 걸리는 중"과 구분이 안 된다 | 페이지가 안 열리니 바로 안다 |
| 만드는 비용 | 봇은 Q09-a로 어차피 만든다. 보내는 코드만 더한다 | 웹 서버, 화면, 실시간 전송, 인증, Slack과의 질문함 동기화를 새로 만든다. Python 표준 라이브러리와 htmx로 가볍게 만들 수는 있다 |
| 보안 | 보고 내용이 Slack 서버로 나간다. 채널에 다른 사람이 있으면 지시를 넣을 수 있다 | 데이터가 Mac 밖으로 안 나간다. 대신 지시를 받는 localhost 서버는 사용자가 연 웹페이지에서 공격받을 수 있다(MCP Inspector CVE-2025-49596, Claude Code IDE 확장 CVE-2025-52882) |
| 속도 제한 | 채널당 초당 1건. 몰리면 메시지가 표시되지 않을 수 있다 | 없다 |

대시보드를 빼면 잃는 것은 세 가지다. 트리 전체를 한눈에 보는 것, 로그나 diff를 바로 여는 것, 데이터가 Mac 밖으로 나가지 않는 것. 앞의 둘은 상태 요약 메시지와 링크로 일부 메우고, 마지막은 보고에 넣는 내용을 줄여 대응한다(기본값 8번).

### 3. Slack 방식에서 막아야 할 것

1. **새 메시지라고 알림이 가지는 않는다.** Slack 기본 알림은 DM, 멘션, 키워드, 참여한 스레드의 답글뿐이다. 채널의 일반 메시지는 사용자가 채널 알림을 "모든 새 게시물"로 바꿔야 푸시된다. 봇은 이 설정을 바꿀 수 없다. 데스크톱 Slack을 쓰는 중이면 휴대폰 푸시는 기본으로 화면을 잠근 지 1분 뒤나 10분 동안 조작이 없을 때 간다. 그래서 실제 알림 정책은 "어느 메시지에 멘션하느냐"다. ([알림 가이드](https://slack.com/help/articles/360025446073-Guide-to-Slack-notifications), [알림 설정](https://slack.com/help/articles/201355156-Configure-your-Slack-notifications))
2. **보고가 많으면 질문이 묻힌다.**
   - Happy는 메시지마다 푸시했다가 "like a million notifications"라는 항의를 받고 완료, 권한, 질문 세 가지로 줄였다([happy#1259](https://github.com/slopus/happy/issues/1259)).
   - Omnara 사용자는 "80+ notifications"를 보고했다([omnara#145](https://github.com/omnara-ai/omnara/issues/145)).
   - CircleCI Slack orb는 "channel will become just noise"라는 이슈 뒤에 스레드를 넣었다([slack-orb#305](https://github.com/CircleCI-Public/slack-orb/issues/305)).
   - Google SRE 책의 원칙은 "Every page should be actionable"이다([SRE book 6장](https://sre.google/sre-book/monitoring-distributed-systems/)).
3. **지금 상태가 안 보인다.** 병렬 작업이 늘면 메시지 흐름에서 현재 상태를 읽기 어렵다. 세션 30개를 돌리다 "막힌 세션이 끝난 세션과 똑같아 보인다"는 보고가 있다([claude-code#94373](https://github.com/anthropics/claude-code/issues/94373)).
4. **조용함이 모호하다.** Factory(2026-09-29)와 Claude Tag(2026-09-11)가 실패했는데 스레드가 조용하던 문제를 고쳤고, Cursor에는 오래 걸린 작업의 완료 알림이 오지 않은 사례가 있다. 실행기가 죽으면 보고도 멈추므로 살아 있다는 신호가 따로 필요하다. ([Factory 릴리스 노트](https://docs.factory.com/changelog/release-notes), [Cursor 포럼](https://forum.cursor.com/t/no-slack-notification-background-agent/152122))
5. **한국어 문장 비용(Q08과 연결).** Q08 A안은 진행 보고도 영어로 쓴 뒤 Skill-Techblog로 한국어로 쓴다. 보고가 잦으면 보고마다 Claude 세션이 작성과 검토를 돌아 늦고 비싸다. Skill-Techblog는 Claude Code 전용이라 Codex 오케스트레이터는 직접 쓸 수 없다.
6. **재시작하면 스레드가 끊길 수 있다.** Argo CD는 어느 일이 어느 스레드인지를 메모리에만 둬서, 재시작하면 새 스레드를 연다. 고치는 PR은 아직 열려 있다([notifications-engine#461](https://github.com/argoproj/notifications-engine/pull/461)).

편집하지 않고 새 메시지로 보내는 선택은 조사 결과와 맞는다. Anthropic의 Claude Tag는 진행 체크리스트를 한 메시지에서 고쳐 왔다. 문서에 "Slack does not send notifications when a message is edited, so the thread can look frozen"이라고 적었고, 2026-09-16부터 막힘을 알림이 가는 새 답글로 바꿨다. 반대로 스레드에 다시 올리던 진행 메시지는 팔로워에게 알림을 보내서 2026-10-01에 멈췄다. 새 메시지로 가되 소음을 막는 장치가 필요하다는 뜻이다. ([How Claude Tag works](https://claude.com/docs/claude-tag/concepts/how-it-works.md), [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md))

### 4. 다른 서비스는 어떻게 하나

- **코딩 에이전트:** 진행 보고는 줄이고 질문, 승인, 결과만 새로 보낸다.
  - Cursor는 2026-08-31 주에 군더더기 답글과 턴 완료 푸시를 없애고 질문과 승인 푸시만 남겼다([릴리스 노트](https://cursor.com/docs/release-notes/cloud-agents)).
  - Devin은 질문을 스레드에 답 버튼과 함께 올리고, 답 없이 넘어가면 "skipped"로 표시한다. 블로그(홍보 글) 제목은 "Silence is your default"다. ([문서](https://docs.devin.ai/integrations/slack), [블로그](https://devin.ai/blog/devins-slack-etiquette))
  - GitHub Copilot, Factory, Devin은 큰 작업을 작업 전용 채널로 옮겨 원래 대화를 시끄럽게 만들지 않는다.
- **운영 도구:** 일 하나에 부모 메시지 하나를 두고 세부는 그 스레드에 단다. incident.io, PagerDuty, GitHub Slack 앱은 부모 메시지를 고쳐 최신 상태로 둔다. Rootly는 새 메시지 모드를 "Noisier but harder to miss"라고 설명한다. ([Rootly](https://docs.rootly.com/integrations/slack/smart-defaults), [GitHub in Slack](https://docs.github.com/en/integrations/how-tos/slack/use-github-in-slack))
- **Slack 가이드:** 응답은 스레드로 하고, "Five issue updates should be one message, not five". 대시보드는 앱 홈 탭에 두라고 안내한다. ([Agent design](https://docs.slack.dev/concepts/agent-design), [Choosing the right surface](https://docs.slack.dev/concepts/choosing-the-right-surface))
- **대시보드 쪽:** 에이전트 세션 관리 도구 14개 중 11개가 자기 창 밖으로 알림을 보낸다. Omnara는 에이전트가 몇 시간 뒤에야 막힌 채 발견되는 문제("stuck hours later") 때문에 만들어졌다. 화면만으로는 부족하고 푸시가 필요하다는 것이 공통 교훈이다. ([Omnara README](https://github.com/omnara-ai/omnara/blob/9ddd1b14c05e55a8d384c2e98dd835cd86a61e44/README.md))
- **쓰지 않을 것:** Slack이 2026년에 추가한 에이전트용 진행 표시(스트리밍, 작업 카드, agent sessions)는 모두 한 메시지를 계속 갱신하는 방식이라 이번 방향과 맞지 않는다. 일부는 유료 플랜이 필요하다.

### 왜 지금 묻는지

대시보드를 빼면 Q09-b가 맡던 "지금 상태 보기"와 "지시 보내기"를 Slack이 맡아야 한다. 위 1~4번을 막는 방식에 따라 실행기의 이벤트 기록 구조, 봇 권한, skill-plugin 초안 개정 내용, spike 항목이 달라진다.

### 10-a. 무엇을 채널 본문에, 무엇을 스레드에 보내는가

- **A (추천) 큰 일은 채널 본문에, 세부는 스레드에 보낸다.**
  - 채널 본문(새 메시지): 단계 전환, 대주제와 중주제의 시작과 완료, 질문, 사람만 할 수 있는 일 요청, 재시도 끝에 포기한 작업, 사용 한도로 전체가 멈춤과 재개, 전체 완료.
  - 스레드:
    - 말단 작업의 시작, 계획 승인, 완료, 재시도는 그 작업이 속한 중주제 시작 메시지의 스레드에 단다.
    - 인터뷰 단계의 세부(조사 시작과 끝 등)는 그 단계 시작 메시지의 스레드에 단다.
  - 이유: 채널이 요약 기록처럼 읽힌다. 운영 도구와 Slack 가이드가 쓰는 구조다.
  - 분량(추정, 말단 작업 80개·중주제 14개·질문 30개 기준): 채널 본문 약 100건, 스레드 답글 약 250건.
- **B** 모든 이벤트를 채널 본문에 보낸다. 스레드를 열지 않아도 다 보이지만, 같은 규모에서 채널 본문이 약 340건이 된다.
- **C** 채널을 둘로 나눈다. 질문·요청 채널과 진행 보고 채널을 따로 둔다. 가장 깔끔하지만 Q09-a의 "프로젝트마다 채널 하나"가 바뀐다.

참고: 스레드에 한 번 답글을 달면 그 스레드를 팔로우하게 되어, 이후 그 스레드의 답글마다 알림이 온다. A에서 보고 스레드에 글을 남기면 그 중주제의 세부 보고도 알림으로 오므로, 필요하면 그 스레드의 팔로우를 끄면 된다.

### 10-b. 메시지를 고치지 않고 "지금 상태"를 어떻게 보는가

- **X (추천) 상태 요약(스냅샷)을 새 메시지로 보낸다.**
  - 보내는 때:
    - 사용자가 채널에 "상태"라고 쓰거나 봇을 멘션할 때
    - 단계가 바뀌거나 대주제가 끝날 때
    - 작업 중인데 채널 본문이 3시간 동안 조용할 때(살아 있다는 신호를 겸한다)
  - 내용: 대주제와 중주제 트리와 각 상태, 지금 도는 세션(CLI, 모델), 막힌 작업과 이유, 답을 기다리는 질문(스레드 링크).
- **Y** 스냅샷 없이 채널 본문 메시지마다 붙는 진행 한 줄(기본값 2번)로만 본다.
- **Z** Slack 앱 홈 탭에 현재 상태 화면을 두고 계속 갱신한다. 메시지가 아니라 앱 화면이라 알림이 없고, Socket Mode와 휴대폰에서 동작한다. 진행 보고는 그대로 새 메시지로 보낸다.

### 10-c. 보고 문장은 누가 쓰는가 (Q08과 연결)

Q08 질문의 A안에는 "진행 보고는 영어로 쓴 뒤 … 한국어로 번역해서 보낸다"가 있고, 답변 원문은 "한국어로 써야하는 글은 영어원분 기반으로 Skill-Techblog 스킬을 사용해서 쓰면 돼"다.

- **K (추천) 진행 보고는 실행기의 한국어 고정 문형에 값만 채워 보낸다.**
  - 고정 문형은 개발할 때 영어 원문으로 쓰고, Skill-Techblog로 한 번 한국어로 만든다.
  - 작업 이름은 작업을 나눌 때 한국어 표시 이름을 함께 만든다. 대주제와 중주제는 구현 전 검토 문서를 만들 때, 소주제는 그 중주제를 나눌 때 묶어서 만든다.
  - 매번 내용이 달라지는 글(질문, 검토 문서, 최종 보고)은 지금처럼 Skill-Techblog로 쓰고, 진행 보고에는 그 글로 가는 링크만 단다.
  - 이유: 보고 하나마다 모델을 부르지 않아 바로 나가고, 두 CLI에서 똑같이 동작한다.
- **L** Q08을 글자 그대로 따른다. 보고마다 영어로 쓰고 Skill-Techblog로 한국어 글을 쓴다. 보고마다 Claude 세션이 작성과 검토를 돌아 늦어지고, Codex 오케스트레이터는 Claude 세션을 따로 띄워야 한다.
- **M** K와 같되 작업 이름은 영어 그대로 쓴다. 한국어 표시 이름을 만드는 단계가 없어진다.

### 따로 정하지 않으면 이대로 한다고 제시한 기본값

1. **멘션:** 사람이 해야 할 일(질문, 검토 요청, 로그인이나 자격증명처럼 사람만 할 수 있는 일, 전체 완료)에만 멘션한다. 보고마다 푸시를 받고 싶으면 채널 알림을 "모든 새 게시물"로 바꾸면 된다.
2. **진행 한 줄:** 채널 본문 메시지 끝에 "말단 34/80 완료 · 진행 3 · 막힘 1 · 답 대기 1" 같은 한 줄을 붙여, 마지막 메시지가 곧 현재 상태가 되게 한다. 휴대폰 알림은 메시지의 `text`만 보여 주므로 `text`에 요약을 넣는다.
3. **상태가 바뀔 때만 보낸다:** 재시도 중인 오류는 결과가 나올 때까지 보내지 않는다. 1분 안에 몰린 스레드 세부 이벤트는 한 메시지로 묶는다. 채널당 초당 1건을 넘기지 않는다.
4. **살아 있음과 다시 알림:** 작업 중인데 채널 본문이 3시간 동안 조용하면 "진행 중" 메시지를 보낸다(10-b가 X면 스냅샷). 실행기가 다시 뜨면 재시작했다고 알린다. 답이 없는 질문은 새로 올리지 않고, 4시간 뒤 한 번, 그 뒤로 하루 한 번 원래 질문 스레드 링크와 함께 다시 멘션한다.
5. **보내는 경로:** 봇으로 보내는 것은 실행기뿐이다. 오케스트레이터와 작업 세션은 실행기 명령으로 이벤트를 남긴다. 지금 있는 `Notifier`(`barrel/core/unitloop.py:326`), `RunState`(`:370`), 세션 감시 이벤트(`step2step/claude/watchdog.py:17`)를 레포 밖 실행 상태 폴더의 이벤트 기록 하나로 모은다. 어느 일이 어느 스레드인지도 거기 저장해, 실행기가 재시작해도 같은 스레드에 이어 쓴다.
6. **Slack이 안 될 때:** 지금 `Notifier`처럼 macOS 알림 센터로 알린다. 연결이 돌아오면 밀린 이벤트를 하나씩 보내지 않고 요약을 한 번만 보낸다. Omnara는 재개 때 밀린 알림을 한꺼번에 쏟아냈다. 같은 상태 요약을 터미널에서 출력하는 명령을 둔다.
7. **지시:** 질문 스레드의 답글은 그 질문의 답으로 받는다. 그 밖의 채널 글과 보고 스레드의 답글은 오케스트레이터에 지시로 넣는다. 지시가 처음 정한 내용을 바꾸면 Q01대로 연쇄 변경까지 함께 묻는다.
8. **권한과 내용:** 채널은 비공개로 만든다. 답과 지시는 등록한 사용자 본인 계정에서 온 것만 받는다(예전 계획의 D-043과 같은 원칙). 자격증명, 토큰, 키는 보내기 전에 가린다. 긴 내용은 레포 문서 경로나 커밋·PR 링크로 대신한다.
9. **정본:** Slack 메시지는 정본이 아니다. 정본은 레포의 기억 단위와 실행 상태(Q07)라서 무료 플랜의 90일 제한에 걸려도 잃는 것이 없다.

## 이 답에 따른 정리 (AI 분석, 원문이 우선)

- **Q09-b와의 관계:** 로컬 웹 대시보드(P)가 맡기로 했던 일 가운데 질문에 답하기, 지시 보내기, Slack과 같은 질문함은 Slack이 맡는다. PC에는 작업 현황을 보고 작업을 중지하는 가벼운 화면이 남는다.
- **기본값 처리:**
  - 기본값 1, 2, 3, 5, 7, 8, 9번: 사용자가 따로 이의를 말하지 않았다. 이 문장은 AI의 기록이다.
  - 기본값 4번: 다시 알림 주기는 사용자가 정한 주기(1, 2, 4, 8시간 뒤, 그 뒤로 8시간마다)로 바뀐다. 3시간 동안 조용할 때 보내는 스냅샷과 재시작 알림에는 이의가 없었다.
  - 기본값 6번: 사용자가 정한 방식으로 바뀐다. AI가 제시한 macOS 알림 센터 알림과 터미널 상태 명령은 이 답에 없으므로 빠지는 것으로 읽었다. 터미널 명령이 하던 일은 PC 화면이 맡는다. [Q10-2](q10-2-pc-view-stop-language.md)에서 확인한다.
- **해석이 필요한 점(Q10-2에서 확인한다):**
  - "반드시 답변이 필요한 질문": Q01과 Q06에 따라 Barrel이 사람에게 묻는 질문은 AI가 판단할 수 없는 것뿐이다. 그래서 막힌 작업을 풀어야 하는 질문과 요청은 모두 여기에 해당한다고 읽었다.
  - 다시 알림의 시계는 질문이 실제로 Slack에 올라간 때부터 잰다. Slack이 끊긴 동안 쌓인 질문은 복구 후 올라간 때부터 잰다.
  - Slack이 끊겨도 작업은 계속한다. 기다리는 것은 보내기뿐이다. 보내지 못한 질문에 걸린 작업은 Q01대로 그 작업만 멈춘다.
  - 영어로 설정하면 질문 머리말은 `[{프로젝트명}-Question]`으로 한다. 영어 설정에서는 영어 정본을 그대로 보내므로 Skill-Techblog를 거치지 않는다.
- **새로 정할 것:** 작업 중지의 범위와 방식, PC 화면을 만드는 방법, 언어 설정을 바꾸는 곳. [Q10-2](q10-2-pc-view-stop-language.md)에서 묻는다.
