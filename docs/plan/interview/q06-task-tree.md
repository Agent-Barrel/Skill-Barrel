# Q06. 작업 트리를 언제, 어디까지 미리 나누는가

- 질문일: 2026-10-06
- 관련: [어긋나는 점 6번](../README.md#conflicts), [insight.md](../insight.md)
- 기록 원칙: 사용자 답변은 받은 그대로 적는다. 아래 "선택지 대응"은 찾아보기 편하도록 붙인 요약이며, 내용이 다르면 답변 원문이 우선한다.

## 질문 (사용자에게 보낸 내용)

### 왜 지금 묻는지

insight.md에서 이미 정한 것: 작업을 대주제 → 중주제 → 소주제 트리로 나누고, 대주제부터 재귀적으로 실행한다. 깊이는 프로젝트에 맞춰 조절한다. 처음엔 굵은 줄기만 파악한 채로 들어가고, 각 작업의 계획을 세우면서 세부 맥락을 파악한다. 그래서 "트리냐 목록이냐"는 묻지 않았다. 남은 것은 트리를 언제, 어디까지 미리 나누는지와 말단 작업의 크기 기준이다. 이 답에 따라 [Q01](q01-keep-working-scope.md)의 "구현 전 작업 의도 검토"에서 무엇을 보여 줄지가 정해진다.

### 다른 도구 조사 요약

- **Kiro:** 명세 단계에서 작업 목록을 한 번에 만든다. 깊이는 상위 작업과 하위 작업, 두 단계까지만 둔다. 작업마다 관련 요구사항 번호를 달고, 서로 의존하지 않는 작업은 묶어 동시에 실행한다. ([문서](https://kiro.dev/docs/specs/))
- **Taskmaster:** PRD에서 `tasks.json`을 먼저 만들고, 작업마다 복잡도를 1~10점으로 매겨 복잡한 작업만 하위 작업으로 더 나눈다(`expand`). ([정리](https://tryhamster.com/research/taskmaster))
- **BMAD:** PRD를 에픽 단위로 나눠 두고, 스토리(실제 구현 단위) 파일은 그 차례가 왔을 때 만든다. 스토리 파일 하나에 그 작업에 필요한 맥락이 다 들어 있고, 개발은 스토리마다 새 대화에서 한다. 스토리당 맥락은 약 8천 토큰이다. ([정리](https://www.keech.dev/blog/bmad-method-rewriting-epic-story-breakdown))
- **Spec Kit:** 작업을 처음에 전부 나눈다. 한 사례에서 기능 하나에 명세 2,577줄을 쓰고 리뷰에 3.5시간이 걸렸다. 반복 방식은 8분이었다. ([Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html))

### 정할 것과 선택지

말단 작업의 크기 기준은 다음 네 가지를 모두 만족하는 크기로 제시했다(09-29 초안 기준, 다르게 생각하면 말해 달라고 했다).

1. 새 세션 하나가 맥락 압축 없이 끝낼 수 있다.
2. 결과가 하나다.
3. 쓸 파일 범위를 미리 적을 수 있다.
4. 검증 방법이 정해져 있다.

트리를 미리 나누는 깊이:

- **A (추천)** 검토 때는 중주제까지만 보여 주고, 소주제는 그 노드 차례에 나눈다.
  - 기능명세가 끝나면 대주제와 중주제까지 나눠, 작업 의도 요약과 함께 검토받는다(Q01).
  - 소주제(말단 작업)는 그 중주제 차례가 왔을 때 관련 맥락을 따라 읽으며 나눈다. 맥락 사이의 충돌은 그 노드의 작업을 시작하기 전에 정리한다.
  - 나누다가 처음 방향과 달라져야 하는 점이 나오면 Slack으로 묻는다(Q01).
- **B** 검토 때는 대주제만 보여 주고, 나머지는 모두 그때그때 나눈다.
- **C** 처음에 말단 작업까지 모두 나눠 검토받고 시작한다(Kiro, Spec Kit, Taskmaster 방식).

## 사용자 답변 (2026-10-06, 원문 그대로)

```text
A안이 좋은 것 같아. 그런데 처음 방향과 달라져야하는 사항에 대해서도 기획의도, 요구사항명세, 기능명세를 검토했을 때에 작업 방향성을 유추할 수 없거나, 새로운 의사결정이 필요해서 실제 사용자 판단이 필요한 경우에 사용자에게 질문하게 해줘.
```

## 선택지 대응 (요약, 원문이 우선)

- **A.** 검토 때는 대주제와 중주제까지 보여 주고, 소주제는 그 노드 차례에 나눈다.
- 처음 방향과 달라져야 하는 사항이 생겨도 바로 묻지 않는다. 먼저 기획 의도, 요구사항 명세, 기능 명세를 검토한다. 그래도 작업 방향을 유추할 수 없거나, 새로운 의사결정이 필요해서 실제 사용자 판단이 필요할 때만 사용자에게 묻는다.
- 말단 작업 크기 기준(위 1~4번)에 대해 사용자는 따로 이의를 말하지 않았다. 이 문장은 AI의 기록이다.
