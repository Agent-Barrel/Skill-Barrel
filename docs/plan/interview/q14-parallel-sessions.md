# Q14. 구현 세션을 동시에 여러 개 돌리는가

- 질문일: 2026-10-07
- 관련: 2026-09-29 초안 OD-8, [Q01](q01-keep-working-scope.md), [Q12](q12-model-config-and-cli-fallback.md)
- 기록 원칙: 사용자 답변은 받은 그대로 적는다. 아래 "요약"은 찾아보기 편하도록 붙인 것이며, 내용이 다르면 답변 원문이 우선한다.
- 번호: 조사가 먼저 끝나서 [Q13](q13-depth-by-impact.md)보다 먼저 물었다. 번호는 사용자에게 보인 그대로 둔다.

## 질문 (사용자에게 보낸 내용)

### 왜 지금 묻는지

- Q01에서 막힌 작업만 멈추고 나머지는 계속하기로 했다.
- Q12에서 이 PC의 CLI와 계정(Claude 2개, Codex 1개)을 모두 쓰기로 했다.
- 지금 unit loop는 한 작업 폴더에서 한 번에 하나만 돌린다(`barrel/core/unitloop.py:532`).
- 동시에 몇 개를 돌리는지, 서로 어떻게 떼어 놓는지, 결과를 어떻게 합치는지에 따라 실행기의 작업 실행 구조가 달라진다.

### 다른 도구 조사 요약

- **떼어 놓는 방법:** 보통 작업마다 git worktree를 따로 둔다.
  - [Cursor 2.0](https://cursor.com/changelog/2-0)(2025-10, 최대 8개), Codex 앱, Conductor, [Kiro Crew](https://kiro.dev/docs/crew/features/task-runner/)(2026-09, 동시 3개)가 이 방식이다.
  - [Kiro IDE](https://kiro.dev/blog/faster-smarter-specs/)(2026-05)와 [Claude agent teams](https://code.claude.com/docs/en/agent-teams)는 한 폴더에서 돌린다. 대신 같은 파일을 건드리는 작업은 동시에 돌리지 않는다.
- **동시 개수:** 작게 둔다. Kiro Crew는 3개, Claude agent teams는 3~5명을 권한다.
- **문제:**
  - 결과를 합칠 때 충돌이 난다. 에이전트가 만든 PR의 28~42%가 충돌했다([1](https://arxiv.org/abs/2604.03551), [2](https://arxiv.org/abs/2607.04697)).
  - 여러 에이전트가 같은 버그를 고치다 서로의 결과를 덮어쓰기도 한다. Anthropic의 [C 컴파일러 실험](https://www.anthropic.com/engineering/building-c-compiler)에서 16개를 병렬로 돌렸을 때 이런 일이 있었다.
  - 사용량은 세션 수에 비례해 빨리 준다("ten agents … roughly ten times as fast", [agent view](https://code.claude.com/docs/en/agent-view)).
  - 세션을 한꺼번에 띄우면 서버가 요청을 제한한 사례도 있다([비공식](https://github.com/anthropics/claude-code/issues/53922)).
- **완화책:** 동시에 바뀐 내용을 에이전트에게 알려 주면, 합친 뒤 깨진 경우의 82%가 회복됐다([STALE](https://arxiv.org/abs/2609.25396), 2026-09).

### 선택지

- **worktree로 병렬, 기본 2개 (추천)**
  - 서로 의존하지 않고 쓰는 파일이 겹치지 않는 말단 작업만 동시에 돌린다.
  - 작업마다 git worktree를 따로 쓴다. 동시 개수만큼 만들어 두고 다시 써서 의존성 설치를 줄인다.
  - 게이트를 통과하면 실행 브랜치에 합친 뒤, 합친 결과로 게이트를 다시 돌린다.
  - 충돌하면 함께 바뀐 내용을 알려 주고 그 작업을 새 기준에서 다시 맡긴다.
  - 동시 개수는 `.barrel/config.json`에서 정하고 기본은 2다. 세션은 계정에 나눠 띄운다.
- **구현은 한 번에 하나**
  - 구현 세션은 하나씩만 돌린다. 막힌 작업은 건너뛰고 다음 작업을 한다.
  - 조사, 조언, 검토 세션은 구현과 동시에 돌 수 있다.
  - 합치는 단계가 없어 가장 단순하지만 느리다.
- **한 폴더에서 병렬**
  - 첫 선택지처럼 동시에 돌리되 worktree 없이 한 폴더에서 돌린다(Kiro IDE 방식).
  - 준비 비용은 없지만, 한 작업의 게이트가 다른 작업이 고치는 중인 코드를 보게 된다.

추천 이유:
- 계정마다 구현 세션 하나씩 나눠 돌리면, 한 계정의 사용량은 세션 하나를 돌릴 때와 같다.
- worktree로 떼어 놓으면 한 작업의 게이트가 다른 작업의 절반만 고친 코드를 보지 않는다.

## 사용자 답변 (2026-10-07, 원문 그대로)

선택지를 골랐다.

```text
worktree로 병렬, 기본 2개 (추천)
```

## 요약 (원문이 우선)

- 서로 의존하지 않고 쓰는 파일이 겹치지 않는 말단 작업은 동시에 돌린다.
- 동시에 도는 작업마다 git worktree를 따로 쓰고, worktree는 다시 쓴다.
- 게이트를 통과한 결과는 실행 브랜치에 합치고, 합친 결과로 게이트를 다시 돌린다. 충돌하면 함께 바뀐 내용을 알려 주고 새 기준에서 다시 맡긴다.
- 동시 개수는 `.barrel/config.json`에서 정하고, 기본은 2다. 세션은 계정에 나눠 띄운다.

## 이 답에 따른 정리 (AI 분석, 원문이 우선)

- 예전 계획의 D-032(읽기와 쓰기 범위가 겹치지 않을 때만 병렬로 돌리고, 독립인지 모르면 차례로 돌린다)와 같은 방향이다.
- 사용자의 체크아웃은 건드리지 않는다. 실행 브랜치와 worktree는 레포 밖 실행 상태 폴더에 둔다. AI가 정한 세부이며 [task-execution.md](../skill-plugin/task-execution.md)에 적었다.
- 조사, 조언, 검토, 한국어 작성 세션은 제품 코드를 쓰지 않으므로 이 동시 개수에 넣지 않는다. AI가 정한 세부다.
