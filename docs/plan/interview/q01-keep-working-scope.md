# Q01. "끊임없이 작동"은 어디까지인가

- 질문일: 2026-10-06
- 관련: [어긋나는 점 1번](../README.md#conflicts)
- 기록 원칙: 사용자 답변은 받은 그대로 적는다. 아래 "선택지 대응"은 찾아보기 편하도록 붙인 요약이며, 내용이 다르면 답변 원문이 우선한다.

## 질문 (사용자에게 보낸 내용)

### 왜 지금 묻는지

두 원문이 서로 다르게 읽힐 수 있다.

- 09-29: "에이전트가 작업이 끝나기 전까지 계속 돌아가게하는게 아니라, '확정이 필요한 것들을 실제 작업하기 전에 유저에게 전부 도출…'"
- 10-06: "의도와 정확히 align 된 결과물을 만들기까지 끊임없이 작동"

09-29는 확정 없이 무작정 돌리는 것을 거부한 것이고, 10-06은 확정된 의도에 맞을 때까지 멈추지 않는 것을 요구한 것으로 읽힌다. 다만 이 해석이 맞는지 확인이 필요하다. 이 답에 따라 실행 구조와 멈춤 규칙이 정해진다.

### 다른 서비스 조사 요약

- **Claude Code `/goal`** (v2.1.139, 2026-05): 매 턴 끝에 일하는 모델과 다른 모델이 완료 조건을 판정한다. 판정 모델은 대화만 보고 파일을 직접 읽지 않는다. 조건 충족, "불가능" 판정, 사람이 고쳐야 하는 오류(인증, 크레딧, 모델 없음), 진전 없는 턴 반복에서 멈춘다. 사용 한도는 리셋 후 자동 재개한다. ([문서](https://code.claude.com/docs/en/goal))
- **Codex `/goal`** (0.128.0, 2026-04-30): 목표가 재시작 뒤에도 유지되고, 완료, 막힘, 교체까지 계속한다. 시작 전에 "검증 가능한 종료 조건"을 쓰라고 안내한다. ([문서](https://learn.chatgpt.com/use-cases/follow-goals))
- **Kiro**: 요구사항, 설계, 작업 분할 단계는 사용자가 승인한다. 구현은 Autopilot(승인 없이)과 Supervised(편집마다 승인) 중에서 고른다. ([문서](https://kiro.dev/docs/ide/chat/autopilot/))
- **Claude 공식 ralph-loop 플러그인**: Stop 훅으로 종료를 막고, 완료 문구가 나오거나 최대 반복 수에 이를 때까지 반복한다. ([저장소](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop))
- **Devin**: 질문이 생기면 세션 상태가 `blocked`가 되고 답을 기다린다.

공통점: 검증 가능한 종료 조건, 일한 쪽과 다른 판정자, 사람이 풀어야 하는 막힘에서의 멈춤.

### 정할 것과 선택지

**1-a. 확정을 마친 뒤 실행 중 언제 멈추고 묻는가**

- **A (추천)** 막힌 작업만 멈추고, 그 작업과 무관한 작업은 계속한다. 멈춤 조건은 세 가지다.
  - 확정 문서로 답할 수 없는 새 결정
  - 사용자만 할 수 있는 일(로그인, 자격증명, 결제, 권한 승인)
  - 사용 한도(리셋 후 자동 재개)

  테스트 실패, 빌드 오류, 환경 문제는 스스로 재시도하고 계획을 다시 세운다.
- **B** 질문이 하나라도 생기면 전체 실행을 멈추고 답을 기다린다(09-29 초안 OD-9의 `halt`).
- **C** 멈추지 않는다. 새 결정도 오케스트레이터가 확정 문서와 조사로 판단해 기록하고 진행하며, 사용자에게 사후 보고한다.

**1-b. 마지막 "의도와 맞다" 판정을 누가 하는가**

- **X** 판정 코드와 작업하지 않은 새 세션의 의도 대조만으로 완료하고, 사용자에게 결과를 보고한다.
- **Y (추천)** X를 통과한 뒤 사용자 검수까지 받아야 완료한다. 검수에서 "의도와 다르다"면 확정 단계로 돌아가 다시 반복한다. 중간 작업은 X로, 최종 결과물만 사용자가 본다.

## 사용자 답변 (2026-10-06, 원문 그대로)

```text
확정 없이 무작정 돌리는 방식을 피하라는거야. @docs/plan/00-original-flow.md 을 보면 내가 요구사항 도출을 먼저 진행하라고 했고, 이건 다음과 같은 의도야 : 작동하는 초기에 진행할 방향성과 목적, 구현 의도를 사람에게 명확히 도출하고, 작업 간에 이 초기 방향성과 부득이하게 달라져야하는 점들에 대해 임의로 판단하지 않고 사람의 판단에 맡김.  
기존 코딩 에이전트들은 사람과 완전히 align 되어있지 않아서 완성물이 제작자의 의도대로 작동하지 않는 경우가 많았는데, 이런 문제를 개발은 사람이 매번 지시하면서 붙어있지 않아도 끊임없이 진행되게 하려는게 목표인거야. 이를 위해 초기에 방향성과 의도를 명확하게 해서 그 내용을 참고하면 AI 스스로 질문에 대한 답을 얻을 수 있게 하는거지.
그래서 결과적으로, 막힌 작업만 멈추고, 그 작업과 무관한 작업은 계속하라는 것이고, 마지막에 "의도와 맞다"는 판정은 초기에 뽑은 요구사항 명세서와 기능명세서 기반으로 AI 가 판단해서 진행하는거야. 그래서 결국 요구사항 도출과 기능명세서 단계에서, 이 프로젝트 진행을 위해 사람이 어떤 의도를 가지고 있는지 확인해야할 정보들을 전부 추출해서 가지고 있는게 중요해. 사람의 초기 기획 기반으로 시작해서 여러 질문(인터뷰)을 통해 요구사항을 도출하고 요구사항을 통해 기능명세서 및 스펙을 정하는(여기서도 인터뷰) 과정을 통해 문서화하다보면 작업의 의도와 목적이 충분히 명확하게 문서화될거라는 거지.
이 작업들이 완료되면 AI 가 판단한 작업의도를 정리해서 검토 받고, 실제 구현 작업에 들어가면 더 정확할 것 같아.
그래서 그거 기반으로 AI 가 판단 가능한 것들은 진행하고 판단이 불가능한 것들에 대해서만 사람에게 물어보는 방식으로 작동했으면 해.
나중에 사람이 처음에 정한 내용을 바꾸려고 할 때는 그 변경에 따라 기존과 충돌되어서 연쇄 변경이 필요해지는 것들에 대해서도 함께 정하도록하고(맥락을 함께 줘서 사람이 자기가 정해야하는 내용을 명확히 이해할 수 있도록 해야함)
```

## 선택지 대응 (요약, 원문이 우선)

- 1-a: **A**. 막힌 작업만 멈추고, 무관한 작업은 계속한다.
- 1-b: X도 Y도 그대로는 아니다. 최종 판정은 초기에 만든 요구사항 명세서와 기능명세서를 근거로 AI가 한다. 대신 구현에 들어가기 전에 AI가 정리한 작업 의도를 사용자가 검토한다.
- 질문에 없던 내용:
  - 초기 방향과 부득이하게 달라져야 하는 점은 AI가 임의로 판단하지 않고 사람에게 맡긴다.
  - AI가 판단할 수 있는 것은 진행하고, 판단할 수 없는 것만 묻는다.
  - 사람이 처음 정한 내용을 바꿀 때는 그 변경과 충돌해 연쇄 변경이 필요한 것도 함께 정하게 한다. 이때 사람이 무엇을 정해야 하는지 이해할 수 있도록 맥락을 같이 준다.
